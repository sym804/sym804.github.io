테스트 자동화 기본

테스트 자동화는 도구로 테스트를 실행하고 결과를 판정하는 활동이다. 이점과 한계, 테스트 피라미드, 테스트 용이성, 자동화 아키텍처(gTAA)와 프레임워크 계층, 케이스 자동화 방식 7가지, 도입 절차와 파이프라인 배치, 작성 원칙을 ISTQB CTAL-TAE 기준으로 설명한다.

기본기난이도 기초최종 업데이트 2026-11-24

테스트 자동화는 소프트웨어 도구로 테스트 활동을 수행하거나 지원하는 것이다. 개념의 기준은 ISTQB CTFL v4.0.1과 테스트 자동화 엔지니어링 실라버스(CTAL-TAE v2.0, 2024)이고, 자동화 대상 선정부터 도입 절차, 파이프라인 배치, 작성 원칙까지 실무 기준을 함께 둔다.

정의와 범위

섹션 제목: “정의와 범위”

CTAL-TAE v2.0은 테스트 자동화를 다음 활동 중 하나 이상으로 정의한다. 테스트 실행과 보고를 포함한다.

  • 목적에 맞게 만든 도구로 테스트 스위트를 제어하고 실행을 준비함
  • 테스트를 자동으로 실행함
  • 실제 결과와 기대 결과를 비교함

자동화 대상은 UI가 있는 시스템에 한정되지 않는다. UI 없는 시스템(API, 배치), 모바일 앱, 네트워크 프로토콜과 연결도 대상이다. 실행 외의 테스트 활동도 도구로 지원할 수 있다. CTFL 6장은 테스트 관리, 정적 테스트, 테스트 설계·구현(TC, 데이터, 절차 생성), 실행과 커버리지 측정, 비기능 테스트, DevOps 파이프라인 도구를 모두 테스트 도구로 본다. 『소프트웨어 테스트 자동화 구축과 6가지 핵심 활동』도 자동화를 “테스트 수명주기 전체에 소프트웨어 기술을 적용해 효율과 효과를 높이는 것”으로 넓게 정의한다.

용어 뜻
SUT(System Under Test) 테스트 대상 시스템
TAS(Test Automation Solution) 특정 SUT를 위해 구현한 자동화 솔루션 전체. 도구, 프레임워크, 테스트웨어를 포함함
TAA(Test Automation Architecture) TAS의 기술 설계. 도구와 라이브러리 선택, 연결 요구(방화벽, DB, URL, 대역, 메시지 큐), 테스트·결함 관리 도구 연동, 버전 관리를 정함
TAF(Test Automation Framework) TAS의 기반. 테스트 하네스(테스트 러너), 테스트 라이브러리, 스크립트, 스위트로 구성됨
TAE(Test Automation Engineer) 자동화를 설계, 구현, 유지보수하는 역할

이점, 단점, 한계

섹션 제목: “이점, 단점, 한계”

이점(CTAL-TAE 1.1, CTFL 6.2)

  • 빌드마다 수동보다 많은 테스트를 실행함
  • 수동으로 불가능한 테스트를 실행함. 예: 실시간 응답 측정, 원격·병렬 실행
  • 수동보다 복잡한 테스트를 실행하고, 더 빨리 실행함
  • 사람의 실수가 줄고 회차 사이 실행 방식이 일관됨
  • 품질에 대한 피드백이 빨라 결함을 일찍 찾음
  • 커버리지처럼 사람이 측정하기 어려운 값을 객관적으로 측정함
  • 반복 작업이 줄어 테스터가 더 깊은 테스트를 설계할 시간을 얻음

단점과 위험

  • 비용: 자동화 엔지니어 채용, 하드웨어, 교육, 초기 구축 투자
  • 시간: 자동화 솔루션을 개발하고 유지보수하는 시간
  • 목표: 명확한 자동화 목표가 없을 때의 성과 판단 불가
  • 경직성: SUT 변경에 쉽게 깨지는 테스트
  • 자동화 코드 자체가 만드는 결함
  • 도구에 대한 비현실적 기대, 도입·유지 비용의 과소 추정
  • 수동이 더 적합한 테스트에 대한 도구 사용
  • 도구에 대한 지나친 의존과 그로 인한 비판적 사고 생략
  • 도구 공급사의 사업 중단이나 지원 부족, 오픈소스 프로젝트의 유지보수 중단
  • 개발 플랫폼과 호환되지 않거나 규제 요구를 충족하지 못하는 도구 선택

한계

  • 모든 수동 테스트를 자동화할 수는 없음
  • 자동화 테스트는 프로그래밍된 것만 확인함. 작성하지 않은 단언은 검사되지 않음
  • 기계가 해석할 수 있는 결과만 확인하므로 일부 품질 특성(사용성, 문구의 자연스러움)은 자동화로 확인하기 어려움
  • 자동화된 테스트 오라클로 판정할 수 있는 결과만 확인함

자동화를 처음 도입하면 테스트 노력이 오히려 늘어난다. 새 도구와 방식의 학습 비용이 생기고, 수동 테스트도 계속 수행해야 하며, 자동화 자체가 작은 개발 프로젝트이기 때문이다. 투자 회수는 같은 테스트를 여러 빌드와 여러 환경에서 반복 실행하면서 이루어진다. 한 번만 실행하는 테스트는 자동화할 가치가 없는 경우가 많다.

손익분기점은 실행 횟수로 판단한다. 수동 테스트의 회당 비용 m과 자동화의 회당 실행·유지보수 비용 a가 일정하다고 단순화하면, 구축 비용이 I일 때 손익분기 실행 횟수는 I / (m - a)이고 a가 m보다 작을 때만 존재한다. 그림처럼 회당 비용이 회차마다 달라지면 회차별 비용 차이(수동 비용 - 자동화 비용)를 누적한 값이 구축 비용 I에 도달하는 회차가 손익분기점이다. 빌드마다, 여러 환경에서 반복 실행하면 이 횟수에 더 빨리 도달하고, 화면이 자주 바뀌어 스크립트 수정이 잦으면 a가 커져 필요한 횟수가 늘어난다. 그림의 수동 선이 점점 가팔라지는 것은 제품 기능이 늘어 회귀 범위가 커지면 수동 회당 비용 m도 함께 커지기 때문이다. m이 커질수록 손익분기점에 더 일찍 도달한다. 자동화 대상은 이 기준으로 고른다(자동화 대상 선정).

테스트 피라미드와 테스트 사분면

섹션 제목: “테스트 피라미드와 테스트 사분면”

테스트 피라미드는 테스트마다 세분성이 다르다는 것을 보여 주는 모델이다. 아래층일수록 작고 격리되고 빨라서 많이 두고, 위층일수록 넓은 기능을 확인하지만 느리고 다른 요소에 의존해서 적게 둔다.

층 예 개수 실행 속도 실패 시 원인 특정
E2E(UI) 로그인부터 결제까지 화면 흐름 적음 느림 어려움
통합(서비스, API) 주문 API가 결제 모듈과 DB를 거쳐 응답 보통 보통 보통
단위(컴포넌트) 할인 계산 함수, 입력 검증 함수 많음 빠름 쉬움

원래 모델(Cohn 2009)은 단위, 서비스, UI 세 층이고 층의 수와 이름은 팀마다 다르다. 피라미드를 거꾸로 세운 모양(E2E가 가장 많고 단위가 적음)이 되면 스위트가 느려지고 Flaky 테스트가 늘어난다.

테스트 사분면은 비즈니스·기술 관점과 팀 지원·제품 비평 축으로 테스트를 나눈다. Q1(컴포넌트·컴포넌트 통합 테스트)과 Q4(스모크, 성능 등 비기능 테스트)는 주로 자동화하고, Q3(탐색적, 사용성, 사용자 인수 테스트)는 주로 수동으로 수행하며, Q2(기능, 스토리, API 테스트)는 둘 다 사용한다. 자세한 내용은 ISTQB CTFL 실라버스 핵심 정리에 있다.

자동화 대상 선정

섹션 제목: “자동화 대상 선정”

자동화하기 좋은 테스트

  • 매 릴리즈 반복하는 회귀 테스트, 배포 직후 스모크 테스트
  • 결과가 명확해 코드로 판정할 수 있는 테스트(계산 결과, 응답 계약, 권한 차단)
  • 사람이 하면 실수하기 쉬운 대량 조합, 대량 데이터 대조
  • 리스크가 높아 매번 확인해야 하는 경로(권한 게이트, 결제, 데이터 격리)
  • 수동으로는 필요한 규모, 정밀도, 반복성을 확보하기 어려운 테스트(대규모 부하, 정확한 동시 요청, 장시간 실행)

자동화를 미루는 테스트

  • 화면과 명세가 자주 변경되는 신규 기능. 명세가 안정된 뒤 자동화함
  • 판정에 사람의 판단이 필요한 테스트(사용성, 문구의 자연스러움). 시각 회귀로 일부만 보조함
  • 한 번만 수행하는 테스트. 자동화 작성 비용이 수동 수행 비용보다 큰 경우가 많음. 대량 데이터 대조처럼 한 번이라도 자동화가 유리한 경우는 예외로 판단함
  • 물리적 확인이 필요한 테스트(인쇄물, 실제 기기의 버튼 조작). 일부 단계만 자동화함

선정할 때는 TC마다 실행 빈도, 수동 수행 시간, 예상 유지 비용, 리스크를 적어 우선순위를 정한다. 중복되는 TC는 정리하고, 하나의 자동화 테스트가 여러 항목을 확인하되 테스트끼리 중복되지 않게 한다. 자동화율(전체 TC 중 자동화한 비율) 자체를 목표로 두지 않는다.

테스트 용이성

섹션 제목: “테스트 용이성”

SUT가 테스트를 지원하는 정도를 테스트 용이성(Testability)이라고 한다. 비기능 요구사항이므로 기능과 함께 설계하고 구현해야 하며, 자동화 엔지니어가 개선할 부분을 아키텍트와 개발자에게 제안한다.

  • 관측성(Observability): 테스트가 실제 결과를 확인할 수 있는 인터페이스. 로그, 상태 조회 API, 화면 요소의 접근성 이름
  • 제어성(Controllability): 테스트가 SUT를 조작할 수 있는 인터페이스. UI 요소, 함수 호출, 통신 인터페이스, 설정 전환
  • 아키텍처 투명성: 구성 요소와 인터페이스가 문서화되어 모든 레벨에서 관측과 제어가 가능한 상태

개발 측에서 지원할 수 있는 것

  • 화면 요소에 고유하고 안정된 식별자를 부여함(접근성 이름, data-testid). 식별자를 변경할 때 자동화 영향을 함께 검토함
  • 환경 변수나 배포 변수로 테스트에 필요한 설정을 전환함(외부 결제를 테스트 모드로, 메일 발송을 수집함으로)
  • 로그에 함수 이름, 호스트와 프로세스 ID, 밀리초 단위 시각, 처리 중인 데이터의 식별자를 기록함. 테스트 실패를 로그로 추적해 증상뿐 아니라 원인 위치까지 결함 보고에 넣을 수 있음

프레임워크 계층

섹션 제목: “프레임워크 계층”

TAF는 목적이 같은 클래스를 계층으로 묶는다. 계층이 많으면 설계가 복잡해지므로 적게 유지한다.

  • 테스트 스크립트 계층: TC와 스위트 정의. 비즈니스 로직 계층만 호출하고 코어 라이브러리를 직접 호출하지 않음
  • 비즈니스 로직 계층: SUT에 의존하는 라이브러리. 업무 단계, 사용자 흐름, API 호출을 구현하고 SUT에 맞춘 설정을 둠
  • 코어 라이브러리 계층: SUT와 무관한 라이브러리. 같은 기술 스택의 다른 프로젝트에서도 재사용함
계층 Playwright 프로젝트에서의 예
테스트 스크립트 tests/order.spec.ts: “쿠폰을 적용해 결제한다” 시나리오
비즈니스 로직 pages/CartPage.ts, flows/checkout.ts, fixtures/auth.ts: 장바구니 조작, 결제 흐름, 이 서비스의 인증 토큰 발급과 주문 테스트 데이터 생성
코어 라이브러리 lib/http.ts, lib/logger.ts, lib/unique.ts: 범용 HTTP 요청, 로그, 고유값 생성

코어 라이브러리를 공유하면 여러 프로젝트가 각자의 TAF를 빠르게 만들 수 있다.

테스트 케이스 자동화 방식

섹션 제목: “테스트 케이스 자동화 방식”
방식 특징 장점 단점
캡처·재생(Capture/Playback) 수동 조작을 기록해 스크립트를 생성함. 코드를 노출하지 않으면 노코드, 노출하면 로우코드 처음 시작이 쉬움 유지·확장이 어려움. 기록한 SUT 버전에 강하게 의존하고, 기록 시 SUT가 필요하며, TC마다 따로 기록해야 함
선형 스크립팅 별도 라이브러리 없이 절차를 그대로 코드로 씀. 기록한 스크립트를 수정해 사용하기도 함 시작이 쉽고 캡처·재생보다 수정이 쉬움 유지·확장이 어려움. 작은 범위, 변경이 드문 SUT에만 적합함
구조화 스크립팅 재사용 가능한 단계, 사용자 흐름을 라이브러리로 만듦 유지, 확장, 이식이 쉬움. 비즈니스 로직과 스크립트를 분리함 프로그래밍 역량과 초기 프레임워크 투자가 필요함
TDD 개발자가 실패하는 테스트를 먼저 쓰고(Red) 통과시킨 뒤(Green) 리팩터링함 코드 품질과 테스트 용이성 향상, 상위 레벨로 결함이 덜 전파됨 익숙해지는 데 시간이 걸리고, 잘못 적용하면 거짓 신뢰를 줌
데이터 주도(DDT) 구조화 스크립트에 데이터 파일(CSV, 엑셀, DB 덤프)을 공급해 같은 스크립트를 여러 데이터로 실행함 데이터 추가로 TC를 쉽게 늘리고, 분석가가 데이터 파일로 테스트를 정의함 테스트 데이터 관리가 필요함
키워드 주도(KDT) 사용자 관점의 키워드와 데이터로 테스트 단계를 표처럼 작성함. 대개 DDT 위에 구축함 업무 분석가도 자동화 TC 작성에 참여함. 수동 테스트 문서로도 사용함 키워드 구현과 유지가 복잡하고 작은 시스템에는 부담이 큼
BDD Given/When/Then 자연어로 인수 기준을 쓰고 도구가 실행함 개발자, 사업 담당자, 테스터의 소통 개선. 명세 커버리지 확보 부정·경계 TC는 따로 정의해야 함. 사업 담당자 참여 없이 문장 형식만 쓰는 경우가 많음. 단계 문장이 복잡하면 디버깅 비용이 커짐

설계 원칙과 패턴

섹션 제목: “설계 원칙과 패턴”

자동화도 소프트웨어 개발이므로 같은 설계 원칙을 따른다.

  • 객체 지향 원칙: 캡슐화, 추상화, 상속, 다형성
  • SOLID: 단일 책임, 개방·폐쇄, 리스코프 치환, 인터페이스 분리, 의존성 역전
  • CTAL-TAE가 자동화 엔지니어에게 가장 중요하다고 꼽는 패턴은 퍼사드, 싱글턴, 페이지 객체 모델 셋임
  • 퍼사드(Facade): 구현 세부를 숨기고 테스트 작성에 필요한 것만 노출함
  • 싱글턴(Singleton): SUT와 통신하는 드라이버를 하나만 두도록 보장함
  • 페이지 객체 모델(POM): 화면마다 클래스를 두고 로케이터와 조작을 모음. 화면 구조가 바뀌면 페이지 클래스 한 곳만 수정함
  • 플로 모델(Flow Model): 페이지 객체 모델의 확장. 페이지 객체 위에 사용자 동작을 모은 퍼사드를 하나 더 둠. 여러 스크립트가 같은 업무 단계를 재사용함

하네스, 픽스처, 대역, 오라클

섹션 제목: “하네스, 픽스처, 대역, 오라클”
  • 테스트 하네스(Test Harness): 테스트를 실행하는 데 필요한 스텁, 드라이버, 러너의 묶음
  • 테스트 픽스처(Test Fixture): 테스트 실행에 필요한 환경과 데이터. 사전·사후 조건을 정하고, 테스트를 반복 가능하고 서로 독립적으로 만듦. Playwright의 test.extend, pytest의 fixture가 해당함
  • 대역(Test Double): 외부 서비스나 모듈을 대신하는 구현. 스텁(정해진 응답 반환), 모의 객체(호출을 기록하고 검증), 가짜 객체(간단한 실제 구현) 등이 있음. 대역으로 실패 상황(타임아웃, 5xx)을 만들어 오류 처리 분기를 테스트함
  • 테스트 오라클(Test Oracle): 결과가 맞는지 판정하는 근거. 결과 판정까지 자동화하려면 코드로 판정할 수 있는 오라클(계산식, 이전 버전 결과, 명세의 고정값)이 필요함

유지보수성

섹션 제목: “유지보수성”

코딩 표준과 팀의 합의가 자동화 솔루션의 유지보수성을 크게 좌우한다. CTAL-TAE는 클린 코드 원칙을 기준으로 제시한다.

  • 클래스, 메서드, 변수에 의미 있는 이름을 공통 규칙으로 붙임. 예: loginButton, resetPasswordButton
  • 프로젝트 구조를 논리적이고 공통되게 유지함
  • 하드코딩을 피함. 바뀔 수 있는 값은 데이터 파일로, 바뀌지 않는 값은 상수로 둠
  • 메서드의 입력 파라미터를 적게, 메서드를 짧고 단순하게 유지함
  • 로그를 남기고, 필요한 곳에 설계 패턴을 적용함
  • 테스트 용이성을 우선함

도입 절차: 파일럿과 도구 선택

섹션 제목: “도입 절차: 파일럿과 도구 선택”

파일럿

섹션 제목: “파일럿”

시범 적용은 짧게 진행하지만 이후 방향을 크게 좌우하므로 검증 범위를 먼저 정한다.

  • 기술 평가: 사용할 프로그래밍 언어, 도구(상용·오픈소스), 대상 테스트 레벨, 대상 TC, TC 개발 방식. 여러 방식의 프로토타입을 만들어 장단점을 비교함
  • 비기술 평가: 팀의 지식과 경험, 팀 구조, 라이선스와 조직 규칙, 계획한 테스트 유형과 레벨
  • 일정을 정하고 진행 상황을 주기적으로 확인해 리스크를 조기에 찾음
  • 파일럿 중에 CI/CD에 통합해 봄. SUT, 자동화 솔루션, 조직의 도구 연동 문제가 일찍 드러남
  • 파일럿이 끝나면 자동화 엔지니어와 테스트 관리자가 성공 여부를 평가하고 결정함

배포 리스크

  • 환경: 방화벽 개방, CPU·메모리 사용량, 네트워크 연결과 안정성. 모바일 실기기는 전원, 배터리, 네트워크, SUT 접근을 갖춰야 함
  • 패키징: 자동화 코드도 SUT처럼 버전 관리하고 저장소로 공유함
  • 로그: Fatal, Error, Warn, Info, Debug, Trace 수준을 구분해 남김
  • 테스트 구조: 하네스와 픽스처로 사전·사후 조건과 스위트 구성을 정함
  • 업데이트: 테스트 에이전트의 자동 업데이트, 기기의 버전 변경으로 결과가 달라짐. 버전 고정과 기기 구성 계획으로 완화함

도구 선택

섹션 제목: “도구 선택”

먼저 SUT를 분석해 요구를 정한다. 자동화할 테스트 활동(관리, 설계, 생성, 실행), 지원할 레벨과 유형, 사용할 사람의 역할과 역량, SUT 종류(웹, 모바일, API), 테스트 데이터의 가용성, 외부 시스템처럼 직접 도달할 수 없는 대상을 대역으로 처리할 방법을 확인한다. 모든 요구를 만족하는 도구 하나는 없을 수 있다는 점을 이해관계자와 공유한다.

팀에 프로그래밍 경험이 적으면 로우코드·노코드 도구가 선택지가 되고, 프로그래밍 역량이 있으면 SUT와 같은 언어의 도구를 선택해 개발자와 함께 디버깅하고 서로 교차 학습하기 쉽다.

평가는 도구를 열, 요구를 행으로 둔 비교표로 정리한다. 가중치 방식의 예는 다음과 같다.

  1. 해결하려는 문제를 정함
  2. 도구 요구와 기준을 좁힘
  3. 기준을 만족하는 후보 목록을 만듦. 요구 충족, 사용 기간, 사용자 기반, 과거 경험으로 후보를 줄임
  4. 기준마다 중요도 가중치(1~5)를 정함
  5. 후보마다 기준별 점수(1~5)를 매김
  6. 가중치 x 점수의 합으로 비교함
기준 가중치 도구 A 점수 도구 B 점수
대상 브라우저와 모바일 지원 5 5 3
팀의 언어(TypeScript)와 일치 4 5 2
CI 통합과 병렬 실행 4 4 4
라이선스 비용 3 5 2
합계 25+20+16+15 = 76 15+8+16+6 = 45

위 수치는 계산 방법을 보여 주는 예시다.

파이프라인 배치

섹션 제목: “파이프라인 배치”

자동화 테스트는 사람 없이 실행되므로 파이프라인에 넣기 좋다. CTAL-TAE가 제시하는 배치는 다음과 같다.

  • 자동화 프로젝트의 구성 테스트: 자동화 코드를 빌드할 때 스크립트가 참조하는 파일 경로와 파일 존재를 확인함
  • 컴포넌트 테스트: 빌드 단계에서 실행하며 품질 게이트 역할을 함
  • 컴포넌트 통합 테스트: 하위 컴포넌트 대상이면 CI에서 컴포넌트 테스트와 함께 실행함
  • 시스템 테스트: 지속적 배포 파이프라인의 마지막 품질 게이트 역할을 함
  • 시스템 통합 테스트: 따로 개발한 구성 요소가 함께 동작하는지 확인하며 지속적 전달 파이프라인의 품질 게이트 역할을 함

시스템 레벨 이상의 테스트를 배포 단계 안에서 실행하면 결과에 따라 배포를 실패 처리하고 롤백할 수 있지만, 재실행하려면 다시 배포해야 한다. 배포 성공 뒤 별도 파이프라인에서 실행하면 스위트를 유연하게 바꿀 수 있지만 품질 게이트 역할을 하지 못해 롤백을 수동으로 판단해야 한다. 이때는 간단한 배포 확인 스크립트를 배포 단계에 함께 둔다. 회귀 스위트를 매일 밤 실행하는 것처럼 주기적 실행에도 파이프라인을 사용한다.

레벨과 방식별 TC 예시

섹션 제목: “레벨과 방식별 TC 예시”

같은 “쿠폰 적용” 기능을 레벨과 방식별로 나눠 자동화한 예다.

구분 자동화 TC 예시
단위 최소 주문 금액 30,000원(예시 값) 쿠폰의 할인 계산 함수에 29,999원, 30,000원을 입력해 할인액 0원, 3,000원을 반환하는지 단언함
API 다른 사용자의 쿠폰 id로 적용 요청을 전송해 403이 반환되고, 이후 조회한 장바구니 금액과 쿠폰 상태가 요청 전과 같은지 단언함
API 같은 쿠폰으로 주문 두 건을 동시에 결제 요청해 1건만 성공하고 쿠폰 사용 기록이 1건인지 단언함
E2E 로그인 후 장바구니에서 쿠폰을 선택하고 결제까지 진행해 주문 완료 화면의 결제 금액이 할인 반영 금액과 같은지 단언함
시각 회귀 쿠폰 선택 영역을 라이트·다크 테마에서 캡처해 베이스라인과 비교함. 할인 금액처럼 화면에 표시되는 값은 DOM 단언으로 따로 확인함(시각 회귀 테스트)

자동화 테스트 작성 원칙

섹션 제목: “자동화 테스트 작성 원칙”
  • 독립: 테스트마다 필요한 데이터를 직접 생성하고 끝나면 정리함. 다른 테스트의 실행 결과나 순서에 의존하지 않음
  • 로케이터: 화면 구조보다 사용자가 보는 역할과 이름으로 요소를 찾음(Playwright getByRole, getByLabel)
  • 대기: 고정 시간 대기 대신 기다릴 조건(URL, 응답, 요소 상태)을 명시함
  • 단언: 기능이 동작하지 않았을 때 실패하도록 작성함. “요소가 있다”보다 “저장한 값이 목록에 표시된다”를 확인함
  • 비밀값: 계정, 토큰, API 키는 코드에 넣지 않고 CI 비밀값과 환경 변수로 주입함
  • 검출력 확인: 새 테스트는 막으려던 결함을 일부러 주입해 실패하는지 확인함(변이 주입으로 테스트 검출력 확인)

실행 환경과 CI

섹션 제목: “실행 환경과 CI”
  • 실행 순서: 의존성 설치, 단위 테스트, 빌드, 브라우저 설치, E2E. 빌드 산출물을 서빙하는 E2E는 빌드 뒤에 실행함(E2E 테스트 전 빌드)
  • 버전 고정: 테스트 도구와 브라우저 버전, CI 러너 OS 버전을 고정함. 버전이 변경되면 렌더링이 달라져 시각 회귀 비교가 모두 실패할 수 있음
  • 환경 분리: 테스트는 개발·운영 DB와 분리된 데이터를 사용함. 운영 환경 대상 자동화는 조회만 수행함
  • 자동화 계정: 사람 계정을 공유하지 않고 권한이 제한된 전용 API 키나 테스트 계정을 사용함
  • 결과 확인: 푸시 뒤 CI의 대상 커밋과 결론을 확인함(작업 트리와 커밋 상태 구분)

적용 예: 쇼핑몰 회귀 자동화 첫 단계

섹션 제목: “적용 예: 쇼핑몰 회귀 자동화 첫 단계”

수동 회귀 TC 300건이 있는 쇼핑몰에서 처음 자동화 범위를 정하는 예다.

  • 파일럿: 결제 흐름 하나를 두 방식(선형 스크립트, 페이지 객체 기반 구조화 스크립트)으로 작성해 CI에 넣고, 2주 동안 실행 시간, 실패 원인, 수정에 든 시간을 비교함
  • 1단계(스모크): 로그인, 상품 검색, 장바구니 담기, 결제(테스트 모드) 4개 흐름을 E2E로 작성해 배포마다 실행함
  • 2단계(API): 쿠폰 금액 계산, 재고 차감, 주문 상태 전이, 다른 사용자 주문 접근 차단을 API 테스트로 작성함. 화면 E2E보다 빠르고 실패 위치가 분명함
  • 3단계(회귀 확대): 수동 회귀 TC 중 실행 빈도가 높고 판정이 명확한 TC부터 옮김. 자동화한 TC는 TCMS에 자동화 여부를 표시하고, 이번 회차의 대상 빌드에서 자동화 결과가 기록된 TC만 수동 수행에서 제외함. 격리 중이거나 실행되지 않은 TC는 수동 범위에 남김
  • 제외: 신규 이벤트 페이지(매달 변경), 배너 문구 검수(사람 판단)

테스트 계획, 실패 분류, 보고에 적용

섹션 제목: “테스트 계획, 실패 분류, 보고에 적용”
  • 계획: 이번 회차에서 자동화로 확인하는 범위와 수동으로 확인하는 범위를 나눠 적음. 자동화가 확인하지 않는 영역이 계획서에 드러나야 함
  • 실패 분류: 자동화 실패는 바로 결함으로 등록하지 않고 원인(테스트, 제품, 환경 등)부터 분류함(E2E 실패 분류). 재시도로 통과한 테스트는 Flaky 테스트 관리 기준으로 관리함
  • 보고: 통과율 하나 대신 자동화 범위, 실패 분류 결과, 격리 중인 테스트, 수동으로 남은 범위를 함께 보고함. 자동화가 막아야 했는데 운영에서 발견된 결함도 함께 집계해 자동화가 실제로 결함을 찾고 있는지 확인함

현장 노트

  • 타입 검사 명령(tsc --noEmit)이 CI에서 항상 통과했는데, 루트 설정이 하위 프로젝트 참조만 두고 있어 실제 검사 대상이 0개였음. 프로덕션 빌드를 깨는 타입 오류가 이 구멍으로 CI를 통과함. 검사 명령을 tsc -b --force로 변경함
  • 타입 검사, 단위 테스트, 빌드가 모두 통과한 상태에서 비로그인 공개 페이지가 전부 로그인 화면으로 이동되는 결함이 있었음. 401 응답 처리가 로그인 화면 외 모든 경로를 로그인으로 보냈기 때문이고, 공개 경로 허용 목록을 두어 수정함. 브라우저로 직접 열어 보고서야 드러난 결함임
  • 로컬에서 E2E를 실행할 때 설정의 기존 서버 재사용 옵션 때문에 개발 서버가 그대로 사용되어 테스트 계정 로그인이 모두 실패하고 로그인 횟수 제한으로 5분간 잠김. 증상이 “테스트마다 10초 타임아웃”이라 처음에는 코드 문제로 오인함
  • 자동화용으로 만든 사람 계정이 관리자 권한으로 남아 보안 점검에서 높은 위험 등급(High)으로 지적됨. 계정을 사용 중지하고 자동화는 권한이 제한된 API 키로 전환함
  • 테스트 도구 버전 범위를 ^로 두어 새 버전이 설치되자 브라우저 버전이 변경되어 시각 회귀 비교가 모두 실패함. 정확한 버전으로 고정함

규칙

  • 자동화 테스트도 결함을 주입해 실패하는지 확인한 뒤에 결과를 신뢰함
  • 자동화 실패는 분류를 거친 뒤 결함으로 등록함. 재시도 통과를 PASS와 같은 결과로 집계하지 않음
  • 테스트 도구, 브라우저, CI 러너 OS 버전을 고정함
  • 자동화 코드도 SUT와 같은 수준으로 리뷰하고 버전 관리함

흔한 실수

섹션 제목: “흔한 실수”
  • 녹화 기능으로 만든 스크립트를 그대로 쌓아 화면이 바뀔 때마다 모든 스크립트를 다시 녹화함
  • 수동 TC를 절차 그대로 E2E로 옮겨 느리고 깨지기 쉬운 스위트를 만듦
  • 자동화율을 목표로 두고 판정이 어려운 테스트까지 자동화해 실패 분석 시간이 늘어남
  • 도입 직후 테스트 노력이 줄어들 것으로 기대하고 일정을 잡음
  • 프레임워크를 정교하게 만드는 데 집중하다 결함을 찾는다는 본래 목적을 놓침
  • 테스트끼리 데이터를 공유해 실행 순서가 변경되면 실패함
  • 실패한 테스트를 재시도와 대기 시간 증가로 덮음
  • CI가 통과하면 검사가 실제로 수행되었다고 가정함. 검사 대상이 0개여도 통과로 나올 수 있음

기초와 용어ISTQB CTFL 실라버스 핵심 정리ISTQB Certified Tester Foundation Level 실라버스 v4.0.1의 6개 장(테스팅 기초, 개발 수명주기와 테스팅, 정적 테스트, 테스트 분석과 설계, 테스트 활동 관리, 테스트 도구) 핵심 개념. 개념마다 실무에 적용한 위키 문서를 연결한다.기초와 용어테스트 레벨과 테스트 유형테스트 레벨은 시스템을 어느 통합 단계에서 검증하는지를, 테스트 유형은 어떤 품질 특성을 검증하는지를 나타내는 분류다. 두 분류는 서로 독립이며, 테스트마다 레벨을 하나 정하고 테스트 유형은 하나 이상 적용할 수 있다.자동화E2E 실패 분류Playwright 실패를 산출물 근거로 원인별로 분류하는 방법. 원인 분류 체계를 고르는 기준, 결과 상태 확인, 산출물 확인, 재현 순서, 결과 기록 기준을 다룬다. 분류는 수정보다 먼저 수행한다.자동화Flaky 테스트 관리코드와 환경이 같은데도 실행마다 결과가 달라지는 테스트(Flaky 테스트)의 원인을 분류하고 탐지, 격리, 수정하는 절차다.자동화책 정리: 소프트웨어 테스트 자동화 구축과 6가지 핵심 활동엘프리드 더스틴 외 『소프트웨어 테스트 자동화 구축과 6가지 핵심 활동』(원서 Implementing Automated Software Testing, 2009)의 자동화 정의, 6가지 핵심 활동, 자동화가 실패하는 이유와 신화 10가지, 개발 측 고려 사항, 도구 선택 방법과 현재 실무에 적용하는 방법.
