책 정리: 소프트웨어 테스트 자동화 구축과 6가지 핵심 활동

엘프리드 더스틴 외 『소프트웨어 테스트 자동화 구축과 6가지 핵심 활동』(원서 Implementing Automated Software Testing, 2009)의 자동화 정의, 6가지 핵심 활동, 자동화가 실패하는 이유와 신화 10가지, 개발 측 고려 사항, 도구 선택 방법과 현재 실무에 적용하는 방법.

기본기난이도 중급최종 업데이트 2026-11-24

자동화를 도구 도입이 아니라 요구사항부터 인력까지 이어지는 프로그램으로 다루는 책이다. 미 국방부 사업을 주로 수행한 저자 회사(IDT)의 경험을 바탕으로, 자동화가 왜 실패하는지와 성공하려면 무엇을 해야 하는지를 다룬다. 저자들의 이전 책 『Automated Software Testing』(1999)이 제시한 자동화 테스트 수명주기 방법론(ATLM)을 가볍게 다듬은 프로세스가 바탕이다.

근거는 출판사가 공개한 서문과 4장 전문, 목차다. 4장은 절 단위로 자세히 다루고, 나머지 장은 서문의 장 소개와 목차의 절 제목 수준이다. 4장 외 장의 세부 내용은 원문 확인이 필요하다.

책의 출발점

섹션 제목: “책의 출발점”

자동화의 정의

섹션 제목: “자동화의 정의”

책은 자동화 소프트웨어 테스트(AST)를 “테스트 수명주기(STL) 전체에 소프트웨어 기술을 적용하고 구현해 수명주기의 효율과 효과를 높이는 것”으로 정의한다. 테스트 실행 자동화만이 아니라 요구사항 추적, 테스트 데이터 생성, 결과 분석, 결함 추적, 보고까지 포함하는 넓은 정의다.

설문 결과

섹션 제목: “설문 결과”

저자 회사가 2007년에 1년 동안 수행한 설문(전 세계 테스트 전문가 약 700명 응답)의 결과다.

  • 응답자의 약 70%가 자동화가 효과가 크다고 보면서도, 왜 자동화하는지와 자기 프로젝트에 어떻게 적용할지는 확신하지 못함
  • 응답자의 절반은 자동화를 구현할 경험, 시간, 예산이 부족하다고 답함
  • 72%가 자동화가 유용하고 경영진도 동의한다고 답했지만, 대부분 구현하지 않았거나 일부만 성공함
  • 자동화가 실패한 이유: 시간 부족 37%, 전문성 부족 20%, 예산 부족 17%, 도구 비호환 11%, 기타(복합) 15%

책은 자동화가 덜 쓰이는 가장 큰 이유를 경험 부족으로 보고, 필요한 역량을 갖춘 사람을 배치하는 것을 핵심 활동의 하나로 둔다.

4장. 자동화가 실패하는 이유와 피해야 할 함정

섹션 제목: “4장. 자동화가 실패하는 이유와 피해야 할 함정”

책은 자동화가 실패하는 이유로 다섯 가지를 든다. 연구개발이 테스트에 관심을 두지 않음, 자동화에 대한 신화와 오해, 자동화 프로세스 부재, 개발 단계에서 자동화를 고려하지 않음, 자동화 표준 부재. 여기에 비즈니스 케이스 부재가 더해진다.

연구개발의 테스트 경시

섹션 제목: “연구개발의 테스트 경시”

신기술 보도와 연구는 개발(R&D)만 다루고 그 기술을 어떻게 테스트할지(R&D&T)는 다루지 않는다. 책이 짚는 흐름은 다음과 같다.

  • 소프트웨어와 테스트가 사업을 이끄는 쪽으로 바뀌고 있음. 품질이 낮거나 늦으면 경쟁 제품은 클릭 몇 번 거리에 있음
  • 인지 품질과 실제 품질은 다름. 자주 발생하고 핵심 기능에 영향을 주는 결함 10개는 결함 밀도가 낮아도 품질이 나쁘게 인식되고, 거의 발생하지 않고 영향이 없는 결함 100개는 결함 밀도가 높아도 품질이 좋게 인식됨. 가장 자주 쓰는 기능의 사용성과 신뢰성에 테스트를 집중하는 사용 기반 테스트를 권함
  • 일정이 늦으면 테스트가 비난받지만 실제 원인은 다른 곳에 있는 경우가 많음. 단위 테스트 부족, 빌드·릴리즈 자동화 부재, 개발팀의 통합·시스템 테스트 부족 같은 개발 관행과 테스트 추정을 반영하지 않은 비현실적 일정을 원인으로 듦
  • 개발자는 시스템 테스트를 하지 않음. 단위 테스트와 TDD를 하는 개발자도 통합·시스템 테스트는 부족하고, 개발 프로세스가 아무리 좋아도 통합·시스템 테스트는 계속 필요함

자동화의 신화와 현실

섹션 제목: “자동화의 신화와 현실”
신화 현실
도구가 테스트 계획을 자동으로 만들어 줌 계획을 작성하고 테스트를 설계·실행·분석까지 해 주는 도구는 없음. 자동화는 수동 테스트를 보강하는 것이고, 전략 수립과 테스트 기법에 필요한 분석적 사고를 대신하지 않음
도구 하나로 모든 테스트를 지원함 모든 운영체제와 언어를 지원하는 도구는 없음. 여러 OS와 언어를 쓰는 조직이 실시간 임베디드 테스트 전체를 도구 하나로 자동화하려 한 예를 듦
도입하면 테스트 노력이 바로 줄어듦 도입 초기에는 노력이 오히려 늘어남. 학습 곡선이 있고, 수동 테스트도 계속해야 하며, 자동화 자체가 작은 개발 프로젝트임
도입하면 일정이 바로 줄어듦 수정된 테스트 프로세스를 만들고 팀이 익혀야 함. 프로세스가 자리 잡은 뒤에 생산성과 일정 효과가 나타남
도구는 쓰기 쉬움 녹화로 만든 스크립트는 견고하고 재사용 가능하게 만들려면 프로그래밍으로 수정해야 함. 교육과 학습 기간을 계획해야 함
모든 테스트를 자동화할 수 있음 도구가 인식하지 못하는 제3자 컨트롤이 있고, 인쇄물 확인처럼 물리적 확인이 필요한 테스트가 있음. 한 번만 실행하는 테스트는 자동화할 가치가 없는 경우가 많음
자동화하면 100% 테스트할 수 있음 6~8자 대문자·숫자 비밀번호(숫자 1개 이상)의 경우의 수만 약 2조 6,844억 개이고, 분당 1건씩 하루 480건을 만들면 원서는 155년이 걸린다고 썼지만, 실제로 계산하면 약 1,532만 년임(원서의 계산 오류). 동등 분할 같은 기법으로 데이터를 줄여야 함
녹화·재생이 곧 자동화임 녹화는 입력값을 하드코딩하고 재사용할 수 없는 스크립트를 만듦. 데이터 파일 읽기, 조건문, 반복문, 변수와 함수를 넣어 소프트웨어 개발 방식으로 만들어야 함
자동화는 수동 테스터의 일임 자동화 테스터에게는 소프트웨어 개발 역량이 필요함. 개발 배경 없는 수동 테스터가 자동화 프로그램을 성공시키기는 어려움
시스템 테스트만 자동화하면 됨 단위 테스트를 자동화하고 통합 테스트와 빌드를 자동화하면 시스템 테스트에서 발견되는 결함이 줄고 기간이 짧아짐. 결함은 일찍 찾을수록 수정 비용이 낮음

같은 절에서 책은 테스트의 목적이 결함을 찾는 것임을 강조한다. 정교한 프레임워크로 수만 건을 빠르게 실행해도, 잡아야 할 결함이 운영으로 새면 그 자동화는 실패로 평가된다. 그래서 자동화가 찾아야 할 결함을 실제로 찾는지 지표로 확인하라고 한다. 또 자동화 비용은 테스트가 야간 빌드, 여러 테스트 단계, 여러 설치 구성에서 수십·수백 번 실행될 때 분산되어 회수된다고 설명한다.

개발 단계의 자동화 고려 부족

섹션 제목: “개발 단계의 자동화 고려 부족”

개발자가 자동화를 고려해 코드를 작성하면 자동화가 성공할 가능성이 높아진다.

  • 테스트 용이성 확보: 가장 흔한 방법은 로그. 로그 항목에 클래스·메서드(함수) 이름, 호스트 이름과 프로세스 ID, 밀리초 단위 시각, 현재 처리와 오류를 설명하는 메시지를 넣음. 주요 도메인 객체의 ID나 키를 함께 남기면 테스트 절차가 시스템을 거치는 경로를 DB 데이터와 맞춰 추적할 수 있음
  • 로그로 얻는 것: 장애 시 책임 컴포넌트 식별, 계산 오류에 관여한 컴포넌트와 엔티티 식별. 테스터가 증상뿐 아니라 원인 위치를 결함 보고에 담을 수 있음
  • 객체 이름 규칙: 자동화 도구는 객체 이름으로 요소를 찾으므로 모든 객체에 고유한 이름을 붙이고, 자동화를 고려하지 않고 이름을 바꾸지 않음
  • 표준 준수: 개방형 아키텍처 표준, 코딩 표준, 표준 문서 양식, 표준 방식의 TC 문서화(모델에서 TC 자동 생성이 가능해짐)
  • 코드 재사용(라이브러리 개념): 재사용하는 컴포넌트에는 그 컴포넌트의 자동화 테스트도 함께 적용함
  • 원격 화면 기반 녹화 도구를 쓸 때 대상 시스템의 글꼴 다듬기, 색 깊이, 해상도 같은 표시 설정을 바꾸지 않음

도구 선택

섹션 제목: “도구 선택”

“어떤 도구가 최고인가”에 대한 답은 대개 “상황에 따라 다르다”이다. 해결할 문제를 이해한 뒤에 도구를 평가하고, 상용, 오픈소스, 자체 개발 중에서 선택한다. 책은 이 절의 제목을 “숲과 나무”로 붙였다.

  • 상용 도구: 기능 로드맵, 지원 조직, 안정성이 장점이고 공급사 종속, 다른 제품과의 연동 부족, 라이선스 비용이 단점임
  • 오픈소스: 라이선스 비용 없음, 지원(편차는 있음), 플랫폼 이식성, 수정 가능, 가벼움, 특정 공급사에 묶이지 않음

평가 절차

  1. 해결하려는 문제를 정함
  2. 도구 요구와 기준을 좁힘
  3. 기준을 만족하는 도구 목록을 만듦
  4. 기준마다 중요도 가중치(1~5)를 정함
  5. 후보마다 점수(1~5)를 매김
  6. 가중치와 점수를 곱해 비교함

후보를 줄이는 기준은 상위 요구 충족, 사용 기간(오래 살아남은 도구인가), 사용자 기반(오픈소스라면 활발한 개발 커뮤니티), 과거 경험이다. 평가할 품질 속성으로 설치 용이성, 깨끗한 제거, 지원 조직의 대응, 문서의 완전성, 설정 가능성, 분석을 원하는 대상에 맞게 조정하는 능력, 다른 도구와의 연동, 도구 분석과 사람 분석의 균형, 확장성, 새 기술을 따라가는 능력(기술 지연)을 든다.

공급사 간 자동화 표준 부재

섹션 제목: “공급사 간 자동화 표준 부재”

표준이 있으면 자동화가 쉬워지고, 테스트 패턴을 재사용하고, 도구를 바꾸거나 함께 쓸 수 있다. 책은 표준화가 필요한 영역으로 스크립트 언어, 녹화 기능, 테스트 데이터 생성 방식, 스크립트 모듈화, 도구와 테스트 하네스 사이의 API, 결과 출력과 보고 형식, 요구사항·형상·결함 관리 도구와의 연동을 든다.

비즈니스 케이스 부재

섹션 제목: “비즈니스 케이스 부재”

비즈니스 케이스를 만들고 승인받아 모든 이해관계자가 동의하면, 모두가 자동화의 성공에 책임을 느끼고 성공 가능성이 높아진다. 작성 방법은 3장에 있다.

6가지 핵심 활동

섹션 제목: “6가지 핵심 활동”

2부는 비즈니스 케이스로 경영진을 설득하고 함정을 이해한 뒤 “어떻게 자동화할지”를 다룬다. 아래 장 설명은 서문, 절 구성은 목차 기준이다.

1. 요구사항 이해(5장)

섹션 제목: “1. 요구사항 이해(5장)”

자동화 전략을 세우기 전에 요구사항을 이해해야 한다. 해결하려는 문제를 정하는 방법과 요구사항이 없을 때 정보를 모으는 방법을 다룬다.

  • 절 구성: 자동화 지원 요구사항 이해, 요구사항을 보완하는 추가 정보, 정보가 없을 때, 요구사항 추적성 매트릭스(RTM) 작성 시작
  • 실무 연결: 자동화 대상 TC와 근거 요구사항의 연결표. TC 작성 원칙

2. 자동화 전략 수립(6장)

섹션 제목: “2. 자동화 전략 수립(6장)”

테스트 환경, 자동화 스크립트와 관련 산출물의 형상 관리를 포함한 자동화 접근법을 단계별로 다룬다. 무엇을 자동화할지 정할 때 고려할 점과 상용, 오픈소스, 자체 개발 중 올바른 도구를 고르는 일의 중요성도 다룬다.

  • 절 구성: 자동화 전략 문서, 범위와 자동화 목표, 접근법, 자동화 프레임워크(ASTF), 자동화 환경과 구성, RTM 자동화, 결함 추적 자동화
  • 실무 연결: 자동화 대상 선정, 피라미드 배분, 도구 선택. 테스트 자동화 기본

3. 자동화 프레임워크 테스트(7장)

섹션 제목: “3. 자동화 프레임워크 테스트(7장)”

테스트 기법을 이해하고 TC를 문서화하는 일의 중요성을 다룬다. 자동화 담당자는 문서화가 여전히 중요하다는 점을 자주 잊는다. TC 문서는 자동화의 설계도이고, TC를 요구사항으로 추적할 수 있어야 하며, 입력과 기대 결과를 담아야 한다.

  • 절 구성: 프레임워크가 요구사항을 충족하고 기능이 기대대로 동작하는지 검증, 설계·개발·TC를 포함한 모든 산출물의 동료 리뷰, 요구사항과 커버리지 검증, 고객 리뷰
  • 실무 연결: 자동화 코드 리뷰, 결함을 주입해 테스트의 검출력 확인. 변이 주입으로 테스트 검출력 확인

4. 진척 현황 추적과 조정(8장)

섹션 제목: “4. 진척 현황 추적과 조정(8장)”

자동화 프로그램을 시작할 때 정한 목표(3장의 비즈니스 케이스)를 추적하는 일을 다룬다. 동료 리뷰, 인스펙션, 자동화·테스트 지표로 목표 대비 진척을 측정한다.

  • 절 구성: 프로그램 추적과 결함 예방, 자동화 지표, 근본 원인 분석
  • 실무 연결: 실패 분류, Flaky 비율, 운영 유출 결함 집계. E2E 실패 분류, Flaky 테스트 관리

5. 자동화 프로세스 구현(9장)

섹션 제목: “5. 자동화 프로세스 구현(9장)”

스크립트 몇 개는 프로세스 없이도 만들 수 있지만, 큰 자동화 프로그램에는 가볍고 조정 가능한 프로세스가 필요하다.

  • 절 구성: 단계와 마일스톤, 1단계 요구사항 수집과 자동화 필요 분석, 2단계 TC 설계와 개발, 3단계 프레임워크와 스크립트 개발, 4단계 자동화 실행과 결과 보고, 5단계 프로그램 검토와 평가, 가상 품질 게이트, 프로세스 측정
  • 실무 연결: CI 단계 순서와 통과 기준. E2E 테스트 전 빌드, 작업 트리와 커밋 상태 구분

6. 적합한 인력 배치(10장)

섹션 제목: “6. 적합한 인력 배치(10장)”

자동화에 필요한 역량을 다룬다. 테스트 기법 지식과 분석 역량도 중요하지만, 자동화에는 요구사항 분석, 설계, 개발, 테스트 같은 개발팀 수준의 소프트웨어 개발 역량이 필요하다. 역량 구성은 9장의 프로세스 단계와 대응한다.

  • 절 구성: 프로그램 관리, 시스템 엔지니어링, 소프트웨어 개발, 형상 관리, 품질 보증, 도메인 전문가
  • 실무 연결: 테스트 설계, 자동화 코드, 결과 판정의 역할 분담. 1인 QA라면 판정 기준을 문서로 남겨 다른 사람이 이어받을 수 있게 함

지금 읽을 때 걸러 볼 부분

섹션 제목: “지금 읽을 때 걸러 볼 부분”

책은 2009년, 국방 분야 경험을 바탕으로 쓰였다. 원칙은 지금도 그대로 통하지만 일부 사례와 기술은 시대와 분야가 다르다.

  • 지금도 그대로 통하는 것: 자동화는 수동 테스트의 보강이라는 관점, 도입 초기 노력 증가, 자동화에 개발 역량이 필요하다는 점, 테스트 용이성과 객체 이름 규칙, 녹화 스크립트의 한계, 가중치 기반 도구 평가, 결함을 찾는지로 자동화를 평가하는 관점
  • 지금 맥락에 맞게 바꿔 읽을 것: 녹화·재생 도구는 Playwright 코드 생성기 같은 도구로 바뀌었지만 생성한 코드를 그대로 쌓으면 같은 문제가 생김. 객체 이름 규칙은 접근성 이름과 data-testid 규칙으로 이어짐. OMG IDL, 개방형 아키텍처 표준 같은 사례는 국방 시스템 맥락임
  • 다른 자료로 보완할 것: 지금의 CI/CD 파이프라인 구성, 테스트 피라미드 적용, Flaky 테스트 관리 절차는 이 책이 다루지 않으므로 ISTQB CTAL-TAE v2.0(2024)과 위키의 자동화 문서로 보완함

규칙

  • 설문 수치와 비밀번호 경우의 수 예는 책의 내용을 인용한 것임

관련 문서

자동화테스트 자동화 기본테스트 자동화는 도구로 테스트를 실행하고 결과를 판정하는 활동이다. 이점과 한계, 테스트 피라미드, 테스트 용이성, 자동화 아키텍처(gTAA)와 프레임워크 계층, 케이스 자동화 방식 7가지, 도입 절차와 파이프라인 배치, 작성 원칙을 ISTQB CTAL-TAE 기준으로 설명한다.기초와 용어ISTQB CTFL 실라버스 핵심 정리ISTQB Certified Tester Foundation Level 실라버스 v4.0.1의 6개 장(테스팅 기초, 개발 수명주기와 테스팅, 정적 테스트, 테스트 분석과 설계, 테스트 활동 관리, 테스트 도구) 핵심 개념. 개념마다 실무에 적용한 위키 문서를 연결한다.프로세스회귀 테스트 범위 선정변경 뒤 기존 기능이 의도하지 않게 실패하는지 확인하기 위해, 회귀 스위트에서 이번 회차에 수행할 TC를 선택하는 절차다(Regression Test Selection).
