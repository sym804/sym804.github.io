E2E 실패 분류

Playwright 실패를 산출물 근거로 원인별로 분류하는 방법. 원인 분류 체계를 고르는 기준, 결과 상태 확인, 산출물 확인, 재현 순서, 결과 기록 기준을 다룬다. 분류는 수정보다 먼저 수행한다.

분류 체계 선택

섹션 제목: “분류 체계 선택”

Playwright는 재시도를 켰을 때 결과를 passed(첫 실행에서 통과), flaky(첫 실행에서 실패하고 재시도에서 통과), failed(모든 재시도에서 실패)로 나눈다. 이 값은 결과의 분류이고, 무엇을 고쳐야 하는지 알려 주는 원인 분류는 팀이 정한다.

  • 3분류(테스트, 제품, 환경): 분류가 단순해 판정이 빠름. 제품 결함을 누가 고칠지는 따로 정해야 함
  • 제품을 담당별로 나눈 분류(테스트, 프론트엔드, 백엔드, 환경 등): 담당 조직과 분류가 대응하면 배정에 바로 활용할 수 있음. 화면 증상만으로 프론트엔드와 백엔드를 구분할 수 없는 실패는 판정 보류로 둠
  • Flaky를 독립 분류로 두는 방식: 격리 대상을 고르고 Flaky 비율을 집계하기 쉬움. 대신 원인이 기록되지 않아 수정 담당이 정해지지 않음
  • Flaky를 원인 분류에 더한 표시로 두는 방식: 원인 추적이 이어짐. 대신 Flaky 집계는 표시를 따로 세야 함. 관리 절차는 Flaky 테스트 관리에 있음

선택 기준은 분류 결과를 원인 분석과 담당 배정 중 어디에 주로 사용하는가다. 담당 배정이 목적이면 조직 단위의 분류를 사용하거나, 원인 분류와 별도로 담당 필드를 둔다. 어느 체계든 근거가 없는 실패는 분류하지 않고 판정 보류로 남기고, 분류마다 근거(오류 문구, 확인한 산출물)를 함께 기록한다.

결과 상태 확인

섹션 제목: “결과 상태 확인”

판정의 출발점은 터미널 출력이 아니라 JSON 리포터 결과다. JSON 리포터는 테스트마다 아래 상태 중 하나를 기록한다.

  • expected: 기대대로 끝남. 통과한 테스트와, test.fail로 표시한 테스트가 실제로 실패한 경우가 여기에 해당함
  • unexpected: 기대와 다르게 끝남. 분류의 주 대상
  • flaky: 재시도에서 결과가 바뀜
  • skipped: 실행하지 않음. test.skip 같은 의도된 건너뛰기와, 직렬 실행(test.describe.serial)에서 앞 테스트가 실패해 실행되지 않은 경우를 구분함

test.fail은 실패가 예상되는 테스트에 붙이는 표시다. Playwright는 이 테스트가 실제로 실패하는지 확인하고, 통과하면 실패로 보고한다. 그래서 알려진 결함이 고쳐지면 실행 결과에서 바로 드러난다. 이 경우 표시를 지우기 전에 결함이 실제로 해결되었는지 수동으로 확인한다.

산출물 확인

섹션 제목: “산출물 확인”

테스트 제목만 보고 원인을 추측하지 않는다. 실패마다 아래 산출물을 직접 연다.

  • 오류 문구: 기대값과 실제값, 실패한 로케이터
  • 스크린샷과 영상: screenshot: 'only-on-failure', video: 'retain-on-failure' 설정으로 실패한 테스트만 남김
  • 트레이스: trace: 'on-first-retry'로 첫 재시도의 트레이스를 남기고 Trace Viewer로 열면 동작 순서, 각 단계의 DOM 스냅샷, 네트워크 요청, 콘솔 로그를 확인할 수 있음

오류 문구가 같은 실패끼리 먼저 묶고, 묶음마다 원인을 확인한다. 같은 문구라도 원인이 다르면 묶음을 나눈다. test.fail로 표시한 테스트도 오류 문구를 확인한다. 결함 증상에서 실패했는지, 화면이 바뀌어 셀렉터 단계에서 먼저 실패했는지에 따라 의미가 다르기 때문이다.

원인을 좁히는 순서

섹션 제목: “원인을 좁히는 순서”
  1. 실행 대상 확인: webServer가 빌드 산출물을 서빙하는 명령(vite preview 등)이면 소스를 고친 뒤 다시 빌드하지 않았을 때 이전 번들로 실행됨(E2E는 빌드 뒤에 실행). 산출물과 소스의 수정 시각을 비교함
  2. 환경 확인: 로그인 단계 실패, 테스트 데이터 누락이나 오염, 앞선 테스트가 남긴 자원, 외부 서비스 장애처럼 제품 코드와 무관한 원인을 먼저 배제함
  3. 서버 응답 확인: 트레이스의 네트워크 탭에서 4xx, 5xx 응답이나 응답 형식 변경을 확인함. 화면에 표시된 오류 메시지가 서버 응답에서 온 것인지도 확인함
  4. 화면 동작 확인: 스크린샷과 DOM 스냅샷에서 사용자가 보는 동작이 기대 결과와 다른지 확인함
  5. 테스트 코드 확인: 화면은 정상인데 셀렉터, 문구, 대기 조건, 진입 경로가 어긋났는지 확인함

재현은 대상만 좁혀서 실행한다. npx playwright test <파일> -g "<제목>"으로 범위를 줄이고, 간헐적 실패는 --repeat-each로 반복 실행해 빈도를 확인한다.

시각 비교 실패는 플랫폼부터 확인한다. Playwright 문서에 따르면 브라우저 렌더링은 OS, 버전, 설정, 하드웨어, 헤드리스 여부에 따라 달라질 수 있어, 베이스라인을 생성한 환경과 같은 환경에서 비교해야 한다. 스냅샷 파일 이름에 브라우저와 플랫폼이 붙는 것도 이 때문이다.

자주 보는 원인

섹션 제목: “자주 보는 원인”
  • 대기 조건: waitForLoadState('networkidle')은 Playwright 문서가 테스트에 사용하지 말라고 안내하는 방식임. 클라이언트 라우팅 이동은 waitForURL로, 화면 상태는 웹 단언(expect(locator).toBeVisible() 등)으로 기다림
  • 이전 상태의 잔존: 이전 작업의 알림 문구가 화면에 남아 있으면 새 작업이 실패해도 단언이 통과할 수 있음. 단언 대상을 이번 작업에서만 나타나는 문구나 요소로 정함
  • 여러 요소에 일치하는 로케이터: Playwright 로케이터는 엄격 모드라 둘 이상에 일치하면 조작이 실패함. 역할과 이름, 상위 영역으로 범위를 좁힘
  • 숨긴 입력 요소: 디자인을 위해 시각적으로 숨긴 체크박스나 라디오는 보이지 않는 요소라 조작 조건을 만족하지 않음. 사용자가 실제로 클릭하는 label이나 대체 요소를 조작함
  • 요소 부재 판단: “버튼이 없다”는 판단은 전체 화면 캡처와 버튼 전체 목록(아이콘 버튼 포함)을 확인한 뒤에 내림. 텍스트만 추출하면 이름 없는 아이콘 버튼을 놓침

결과 기록

섹션 제목: “결과 기록”

결과 값 체계는 도구마다 다르다. 예를 들어 TestRail의 기본 상태는 Untested, Passed, Failed, Retest, Blocked 다섯 가지다(TestRail, TC 관리 도구 운영 기준). 어떤 체계를 쓰든 아래를 구분해 기록하면 집계가 왜곡되지 않는다.

  • 의도적으로 건너뛴 테스트(특정 환경에서만 수행하는 테스트 등)는 실패로 세지 않음
  • 앞 단계 실패나 환경 장애로 판정할 수 없는 테스트는 실패와 따로 차단으로 집계하고, 차단 원인을 함께 기록함
  • 미수행 상태는 회차 진행 중의 임시 상태로 두고, 회차를 마칠 때 수행하지 않은 사유를 기록함

규칙

  • 단언을 완화해 통과시키지 않음
  • 근거 없는 timeout 상향, 고정 대기, force: true는 해결책으로 제시하지 않음. 무엇을 기다려야 하는지(URL, 응답, 요소 상태)를 기재함
  • 제품 결함으로 실패하는 테스트를 통과하도록 수정하지 않음. 결함이 등록되면 test.fail로 표시하고 결함 번호를 남김
  • 운영 환경에서는 응답을 가로채거나 바꿔 재현하지 않음. 운영 오류 로그와 모니터링이 오염됨

현장 노트

  • 재시도로 통과한 테스트를 테스트 코드 문제로 단정하지 않음. Flaky 후보로 따로 기록하고 원인을 확인함
  • 첫 렌더링이 느린 화면의 시간 초과는 같은 화면의 평소 소요 시간과 비교한 뒤 결함 여부를 판단함
