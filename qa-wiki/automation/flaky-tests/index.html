Flaky 테스트 관리

코드와 환경이 같은데도 실행마다 결과가 달라지는 테스트(Flaky 테스트)의 원인을 분류하고 탐지, 격리, 수정하는 절차다.

기본기난이도 중급최종 업데이트 2026-11-24

플래키, 불안정한 테스트

Flaky 테스트(Flake라고도 함)가 늘어나면 테스트 실패가 제품 결함 때문인지 구분하기 어려워진다. 실패하면 우선 다시 실행하는 관행이 생기고, 실제 결함으로 인한 실패도 재실행으로 넘어가게 된다. 개별 실패의 분류는 E2E 실패 분류를 따르고, 반복되는 불안정은 아래 절차로 관리한다.

원인 유형

섹션 제목: “원인 유형”
  • 비동기 대기: 렌더링, 라우팅, 응답 완료 신호를 기다리지 않고 고정 시간 대기나 즉시 단언에 의존함. 실행 환경이 느려지면 실패함
  • 상태 공유: 앞 테스트가 남긴 DB 행, 브라우저 저장소, 쿠키, 로그인 세션. 실행 순서를 변경하거나 단독 실행하면 결과가 달라짐
  • 자원 경합: 병렬 워커가 같은 계정, 같은 데이터, 같은 포트를 사용함
  • 시간·난수: 현재 시각, 시간대, 자정·월말 경계, 시드 없는 난수, 정렬 기준 없는 조회 결과의 순서
  • 외부 의존: 외부 API, 네트워크, 서드파티 스크립트, 테스트 환경 자체의 불안정

탐지

섹션 제목: “탐지”
  • Playwright는 retries를 설정하면 첫 실행에서 실패하고 재시도에서 통과한 테스트를 flaky로 분류함. 재시도는 기본값으로 꺼져 있음
  • 회차 안의 재시도 통과(flaky)와 회차 간 뒤집힘(코드 변경 없이 이전 회차 PASS, 이번 회차 FAIL)을 구분해 기록함
  • 판정 결과는 테스트별 이력으로 누적함. 같은 테스트가 반복해서 불안정한지가 수정 순서의 근거임
  • 의심 테스트는 반복 실행으로 재현함. --repeat-each로 같은 테스트를 여러 번 실행하고, 단독 실행과 전체 실행, 워커 수 1과 기본값의 결과를 비교함
  • 실패 증거(트레이스, 스크린샷, 서버 로그)를 보존함. Playwright trace: 'on-first-retry'는 첫 재시도에서 트레이스를 기록함

격리와 수정 기한

섹션 제목: “격리와 수정 기한”
  • 원인이 테스트 코드나 실행 환경으로 확인된 테스트는 격리 표시 후 필수 게이트에서 제외할 수 있음. 격리 중에도 실행과 결과 기록은 계속함
  • 우선순위 매우 높음 TC는 격리해도 회귀 범위에서 제외하지 않음. 수정 전까지 같은 항목을 수동으로 확인하고 결과를 기록함
  • 격리할 때 수정 이슈를 등록하고 기한을 정함. 기한이 지나면 수정, 재작성, 삭제 중 하나를 결정함
  • 격리 목록은 주기적으로 검토함. 이슈는 닫혔는데 격리 표시가 남은 테스트가 없는지 확인함
  • 수정 방법
    • 기다릴 대상을 명시함(URL, 응답, 요소 상태)
    • 테스트마다 데이터를 생성하고 정리함
    • 계정과 데이터를 워커별로 분리함
    • 현재 시각과 난수 시드를 고정하거나 주입함
    • 외부 의존은 테스트 대역(Test Double)으로 대체하고, 실제 연동은 별도 테스트로 분리함

제품 결함 은폐 주의

섹션 제목: “제품 결함 은폐 주의”

간헐적 실패의 원인이 제품에 있을 수 있다. 동시성 결함, 경합 조건, 자원 누수, 캐시 무효화 누락은 실제 사용자에게도 간헐적으로 발생한다. 테스트 코드의 문제로 확인하기 전에 격리하면 제품 결함을 놓치게 된다.

  • 재시도 통과는 Flaky 후보로만 기록함. 원인 확인 전에는 테스트 결함으로 확정하지 않음
  • 원인이 제품(화면이나 서버)으로 확인되면 격리하지 않고 결함으로 등록함. 재현 빈도는 간헐로 기록하고 실패 회차의 증거를 첨부함(이슈 양식)

규칙

  • 재시도는 flaky 분류를 기록하는 용도로 사용함. 재시도 통과를 PASS와 같은 결과로 집계하지 않음
  • 단언(assertion)을 완화해 통과시키지 않음

재현 실행과 판정 기준 예시

섹션 제목: “재현 실행과 판정 기준 예시”
확인 대상 실행과 판정 기준
재시도 없는 실패율 --retries=0 --repeat-each=20(예시 값)으로 대상 테스트를 실행해 실패 횟수를 기록함. 0/20이면 “단독 실행에서 재현 안 됨”으로 기록하고 다음 항목을 확인함
상태 공유 대상 테스트를 단독으로 20회, 같은 파일 전체로 20회 실행해 단독 실행은 모두 통과하고 파일 전체 실행에서만 실패하면 앞 테스트가 남긴 상태를 원인 후보로 기록함
자원 경합 전체 스위트를 --workers=1과 기본 워커 수로 각각 10회 실행해 병렬 실행에서만 실패하면 공유 계정, 데이터, 포트를 원인 후보로 기록함
시간 의존 page.clock으로 시각을 자정 직전(23:59:59), 월말로 고정하고 컨텍스트의 timezoneId를 변경한 상태로 실행해 특정 시각이나 시간대에서만 실패하는지 확인함
제품 원인 실패 회차의 서버 로그에서 같은 시각의 4xx·5xx 응답, 잠금 대기, 예외를 찾아 테스트 코드와 무관한 서버 오류가 있으면 제품 원인 후보로 분류함
수정 완료 수정 전 실패율 p를 측정한 뒤 연속 통과 횟수 n을 (1-p)^n이 0.05 이하가 되도록 정함. 예: p가 20%면 14회, 10%면 29회 연속 통과를 완료 기준으로 둠. 횟수는 수행 전에 정하고 수정 전과 같은 조건에서 실행한 결과를 모두 기록함. 이 계산은 매 실행이 서로 독립이고 실패 확률이 일정하다는 전제이므로, 실행 사이에 상태나 캐시를 공유하면 이 계산만으로 완료를 판정하지 않음. 원하는 결과가 나올 때까지 반복하면 이 계산이 성립하지 않음

간헐 실패는 적은 횟수의 연속 통과만으로 수정 여부를 판단할 수 없다. 실패율 20%인 테스트가 수정 없이 5회 연속 통과할 확률은 약 33%다. 수정 완료 기준의 반복 횟수는 수정 전에 측정한 실패율로 정한다.

적용 예: 장바구니 수량 변경 테스트

섹션 제목: “적용 예: 장바구니 수량 변경 테스트”

가상의 상황: “장바구니에서 수량을 2로 변경하면 합계 금액이 갱신된다”를 확인하는 E2E 테스트가 최근 CI 10회 중 2회 실패했고, 2회 모두 재시도에서 통과해 flaky로 분류됨.

  1. 기록: 테스트별 이력에 회차, 커밋, 결과(flaky), 실패한 단언(합계 금액 기대 20,000원, 실제 0원), 트레이스 링크를 남김
  2. 재현: 단독 20회 실패 0회, 파일 전체를 --workers=1로 20회 실행해 실패 0회, 전체 스위트를 기본 워커 수로 20회 실행해 실패 4회. 병렬 실행에서만 실패하므로 자원 경합을 원인 후보로 둠
  3. 증거 확인: 실패 회차 트레이스에서 장바구니 조회 응답의 항목이 0개. 같은 시각의 서버 로그에 다른 워커의 테스트가 같은 테스트 계정으로 장바구니 비우기를 요청한 기록이 있음
  4. 분류: 테스트 데이터 설계 문제이므로 테스트 원인으로 분류함. 서버 로그에 장바구니 API의 5xx나 잠금 오류가 있었다면 제품 원인 후보로 결함을 등록함
  5. 수정: 워커마다 별도 계정(testInfo.parallelIndex 기준)을 사용하고, 테스트 시작 시 장바구니 데이터를 직접 생성함
  6. 판정: 수정 전 실패율 20%(20회 중 4회) 기준으로 전체 스위트를 기본 워커 수로 14회 이상 연속 통과하면 수정 완료로 기록하고 격리를 해제함

테스트 계획, 결함 분류, 보고에 적용

섹션 제목: “테스트 계획, 결함 분류, 보고에 적용”

테스트 계획

  • CI의 재시도 횟수, flaky 결과의 집계 방식, 격리 기준과 수정 기한을 테스트 계획서나 자동화 전략 문서에 기록함
  • 필수 게이트에 포함할 테스트와, 격리 중 수동으로 확인할 항목을 정함
  • 반복 실행과 재현에 필요한 CI 시간을 별도로 계획함. Flaky 재현은 같은 테스트를 수십 회 실행함

결함 분류

  • 테스트 자체의 불안정은 제품 결함과 별도 이슈로 등록하고, 원인 유형(비동기 대기, 상태 공유, 자원 경합, 시간·난수, 외부 의존)을 라벨로 남김
  • 원인이 제품(화면이나 서버)이면 제품 결함으로 등록하고, 재현 빈도를 “간헐(20회 중 4회)“처럼 시도 횟수와 함께 기록함

보고

  • 회차 결과를 PASS, FAIL, flaky(재시도 통과), 격리 중으로 나눠 기록함. 재시도 통과를 PASS에 합산하지 않음
  • 격리 중인 테스트 목록, 격리 기한, 해당 기능의 수동 확인 결과를 함께 보고함
  • 테스트별 불안정 횟수 상위 목록을 주기적으로 보고해 수정 순서를 정함

현장 노트

  • 전체 E2E를 실행할 때마다 서로 다른 3건이 Flaky로 실패함. 개별 측정에서 가장 오래 걸린 테스트가 26.7초로 테스트 timeout 30초의 89%를 사용하고 있었음. 약 14분 동안 직렬로 실행하는 중에 머신 부하가 높아지면 한도를 넘는 것으로 판단하고, timeout을 60초로 변경하며 측정 근거를 설정 주석에 남김. 성능 회귀는 별도 API 테스트의 2초 경고로 확인함
  • 같은 스위트에서 지수 이름 텍스트로 찾는 로케이터(getByText(...).first())가 상단 시장 요약 막대와 지수 카드 두 요소에 일치함. 렌더링 순서에 따라 상단 막대가 선택되면 클릭해도 모달이 열리지 않아 간헐적으로 실패함. 카드에 data-testid를 추가하자 해당 테스트의 실행 시간이 20초대에서 7.5초로 줄었음
  • 같은 스위트에 고정 대기(waitForTimeout)가 127개 있었음. 전면 교체 대신 Flaky로 확인된 파일부터 조건 대기(행 수 증가, 결과 영역 표시)로 변경함
  • 요청 단위 DB 세션의 정리가 응답 전송 뒤에 실행되는 웹 프레임워크 버전에서, 잠금을 보유한 채 커밋 없이 성공을 반환하는 라우트의 다음 요청이 409를 받음. CI에서만 간헐적으로 실패했고 로컬에서는 101건이 모두 통과함. 라우트 함수를 직접 호출해 반환 시점의 잠금 보유 여부를 확인하는 테스트로 매번 재현되게 만들었고, 제품 코드를 수정함
  • 산출물을 갱신한 뒤 같은 API 요청을 반복하면 8회 중 1회꼴로 이전 값이 반환됨. 서버 워커마다 캐시를 따로 두어 한 워커만 갱신 전 값을 보유하고 있었음. 워커가 여럿인 서버에서 값을 확인할 때는 응답에 워커 식별자를 기록해 모든 워커의 응답을 확인함. 8회 중 1회꼴인 현상은 5회 반복으로 한 번도 보지 못할 확률이 약 51%임
  • xfail(strict=False)로 표시한 골든값 테스트는 결과와 무관하게 스위트를 실패시키지 않음. 골든값 7.31이 매일 갱신되는 데이터에 고정되어 있어 실제 값은 약 5.05로 달라진 상태였음. 새 값으로 다시 고정하면 다음 날 같은 상태가 반복되므로, 고정 데이터 스냅샷을 사용하거나 값 대신 성질(부호, 범위)을 단언하는 방안을 결정 대기로 기록함

흔한 실수

섹션 제목: “흔한 실수”
  • 재시도 횟수를 늘려 실패를 덮음. 파이프라인은 통과로 표시되지만 실패 원인과 빈도가 기록되지 않음
  • 측정 근거 없이 고정 대기(waitForTimeout)나 timeout 값을 늘림. 더 느린 환경에서는 다시 실패하고 전체 실행 시간만 늘어남
  • 격리 후 방치함. 해당 기능의 자동 회귀 검증이 수행되지 않는 상태가 계속됨
  • 실패한 테스트를 단독으로 다시 실행해 통과하면 원인 없이 닫음. 상태 공유가 원인이면 단독 실행에서는 재현되지 않음

섹션 제목: “출처”

관련 문서

자동화E2E 실패 분류Playwright 실패를 산출물 근거로 원인별로 분류하는 방법. 원인 분류 체계를 고르는 기준, 결과 상태 확인, 산출물 확인, 재현 순서, 결과 기록 기준을 다룬다. 분류는 수정보다 먼저 수행한다.자동화E2E 테스트 전 빌드빌드 산출물을 대상으로 E2E 테스트를 실행하는 구성에서는 소스를 수정해도 다시 빌드하지 않으면 이전 번들로 테스트가 실행된다.
