동등 분할

시스템이 똑같이 처리할 것으로 기대되는 입력을 한 묶음(동등 클래스)으로 보고, 묶음마다 대표값 하나만 테스트하는 기법이다(Equivalence Partitioning).

기본기난이도 기초최종 업데이트 2026-11-24

EP, Equivalence Partitioning, 동등 클래스, 동치 분할

가능한 입력을 모두 테스트할 수는 없다. 처리가 같은 입력을 한 묶음으로 정하면 테스트 수를 묶음 수로 줄일 수 있다.

클래스 분할

섹션 제목: “클래스 분할”
  • 유효 클래스와 무효 클래스를 모두 정의함. 무효 클래스를 제외하면 오류 처리 검증이 모두 누락됨
  • 분할 기준은 입력값의 형태가 아니라 시스템의 처리. 명세상 같은 처리와 결과를 기대하는 값은 한 클래스
  • 무효 클래스는 TC 하나에 하나씩만 포함함. 둘을 함께 포함하면 어느 값 때문에 거부되었는지 구분할 수 없음

예: 필수 입력인 나이(0~120 정수)

클래스 대표값 기대 결과
유효: 0~120 35 허용
무효: 음수 -1 거부
무효: 120 초과 200 거부
무효: 숫자이지만 정수 아님 3.5 거부
무효: 숫자 아님 “abc” 거부
무효: 비어 있음 빈값 필수 오류

경계값 분석과 함께 사용한다. 동등 분할로 입력을 묶고, 경계값 분석으로 묶음 사이의 경계값을 선택한다.

출력 클래스

섹션 제목: “출력 클래스”

결과도 클래스로 나눈다. 결과 화면이 성공, 부분 성공, 실패, 빈 결과 네 가지라면 각 결과가 표시되는 입력을 하나씩 선택한다.

TC 예시

섹션 제목: “TC 예시”
클래스 TC 예시
유효 클래스 대표값 나이에 35를 입력해 저장하면 저장 완료 문구가 표시되고 상세 화면에 35가 표시되는지 확인함
무효: 숫자이지만 정수 아님 나이에 3.5를 입력해 저장하면 명세의 정수 입력 오류 문구가 표시되고, 저장 값이 변경되지 않는지 확인함
무효: 비어 있음 나이를 비운 채 저장하면 필수 입력 오류가 표시되고 저장되지 않는지 확인함
서버 측 무효 클래스 화면 검증을 거치지 않고 나이 "abc"를 API로 전송해 400과 오류 필드가 반환되고 저장되지 않는지 확인함
출력 클래스: 빈 결과 결과가 0건인 조건으로 검색해 오류 문구가 아니라 빈 결과 안내 문구가 표시되는지 확인함
출력 클래스: 값 없음 판정 기록이 하나도 없는 대상의 합격률이 0%가 아니라 명세에 정한 “값 없음” 표기로 표시되는지 확인함

적용 예: 휴대폰 번호 입력

섹션 제목: “적용 예: 휴대폰 번호 입력”

요구사항이 “가입 화면에서 휴대폰 번호를 입력받아 인증 문자를 보낸다.” 한 줄인 경우, 처리 기준으로 클래스를 나누려면 먼저 아래 항목을 기획과 확인해야 한다.

  • 하이픈과 공백을 허용하는지, 허용하면 제거한 값으로 저장하는지
  • 국가 번호(+82) 형식을 받는지
  • 010 외 식별번호를 받는지
  • 이미 가입된 번호이거나 발송 횟수를 초과했을 때 어떤 안내를 표시하는지

“하이픈·공백은 제거해 저장, 국가 번호 미지원, 010으로 시작하는 11자리만 허용”으로 확정했다고 가정하면 클래스는 다음과 같다.

클래스 대표값 기대 결과
유효: 숫자 11자리 01012345678 인증 문자 발송
유효: 하이픈·공백 포함(정규화 경로) 010-1234-5678 인증 문자 발송, 01012345678로 저장
무효: 자릿수 부족 0101234567 형식 오류
무효: 자릿수 초과 010123456789 형식 오류
무효: 010 외 식별번호 01112345678 형식 오류
무효: 국가 번호 형식 +821012345678 형식 오류
무효: 숫자 외 문자 010-12ab-5678 형식 오류
무효: 비어 있음 빈값 필수 오류

출력 클래스는 인증 문자 발송, 형식 오류, 이미 가입된 번호 안내, 발송 횟수 초과 안내 네 가지다. 마지막 두 가지는 입력 형식이 유효해도 데이터 상태로 결과가 달라지므로 사전 조건(가입된 번호, 발송 이력)을 갖춘 TC를 따로 작성한다.

하이픈 포함 값은 정규화를 거치므로 숫자 11자리와 다른 클래스로 둔다. 같은 클래스로 묶으면 정규화 경로를 확인하는 TC가 빠진다. 정규화 경로의 TC 예: 010-1234-5678로 가입한 뒤 01012345678로 다시 가입을 시도해 “이미 가입된 번호” 안내가 표시되는지 확인한다. 중복 검사가 정규화 전 값으로 수행되면 같은 번호로 계정이 두 개 생성될 수 있다.

자릿수 10, 11, 12는 경계값 분석으로 선택한 값이다. 대표값 하나로 끝나는 클래스와 경계값이 필요한 클래스를 구분해 TC 수를 정한다.

테스트 계획, 결함 분류, 보고에 적용

섹션 제목: “테스트 계획, 결함 분류, 보고에 적용”

테스트 계획

  • 입력 항목마다 클래스 표(클래스, 근거가 된 명세 문장, 대표값, 기대 결과)를 TC 설계 산출물로 남김. 근거 문장이 있어야 리뷰에서 빠진 클래스를 확인할 수 있음
  • 처리 기준을 명세로 확정할 수 없는 입력은 확인 항목으로 분리함
  • 동등 분할 커버리지(수행한 클래스 수 / 식별한 클래스 수, ISTQB CTFL v4.0.1)를 목표로 정함. 무효 클래스는 TC 하나에 하나씩 수행하는 것을 전제로 계산함

결함 분류

  • 결함이 대표값에서 재현되면 같은 클래스의 다른 값에서도 재현되는지 확인해 함께 기록함
  • 같은 클래스의 다른 값에서 재현되지 않으면 클래스 분할과 구현이 다른 것임. 명세상 같은 클래스가 맞으면 구현 결함으로 기록하고 그 값을 보강 TC로 추가함. 명세상 다른 처리가 맞으면 클래스 표를 수정하고 새 클래스의 TC를 추가함
  • 원인 유형에 “클래스 누락”(명세에는 있으나 설계에서 빠진 클래스)과 “클래스 병합 오류”(처리가 다른 값을 한 클래스로 묶음)를 두면 설계 단계의 결함을 따로 집계할 수 있음

보고

  • 입력 클래스와 출력 클래스를 나눠 수행 범위를 기록함. 예: “휴대폰 번호 입력 클래스 8개, 출력 클래스 4개 중 11개 수행, 발송 횟수 초과 1개는 테스트 환경의 발송 제한 미설정으로 미수행”

현장 노트

  • 이슈 로그의 상태 값은 완료, 진행중, 미해결 세 가지. 트래커와의 대조는 완료 여부만 비교하므로 필요한 구분은 “완료인지 아닌지” 두 가지뿐
  • 로그와 트래커의 상태를 비교하는 대조 도구가 진행중 문자열만 미완료로 판정해 미해결을 사용하는 프로젝트의 행이 모두 불일치로 검출됨. 처리 기준으로 클래스를 나누었다면 진행중과 미해결은 한 클래스
  • 계좌별 잔고를 합산해 추이를 표시하는 화면에서 빈칸을 0으로 합산하자, 일부 계좌만 기록한 달이 합계 급감으로 표시됨. 미기록과 잔고 0은 처리가 다른 클래스. 숫자로 입력된 칸만 합산하고 전 계좌 기록 여부를 함께 반환하도록 수정했고, 일부만 기록한 달은 그래프의 속 빈 점과 경고 문구로 구분해 표시함
  • 숫자 입력에서 숫자, 소수점, 부호 외 문자를 제거([^0-9.-])하는 처리가 1e5를 15로 변환함. 지수 표기가 입력 클래스에 없었던 것으로 판단함. AI 교차 검증에서는 발견되지 않았고 직접 재현으로 발견함. 콤마와 공백만 제거하고 Number.isFinite로 판정해, 실패하면 저장하지 않도록 수정함
  • TC 관리 도구의 프로젝트 목록에서 판정 기록이 없는 프로젝트의 합격률을 값 없음(null, 화면 -)으로 표시하도록 변경함. 판정 없음과 합격률 0%를 다른 출력 클래스로 구분함

거래량 0과 거래량 값 없음을 구분하지 않아 잘못된 값이 적재된 사례는 금융 데이터 검증의 함정에 있다.

흔한 실수

섹션 제목: “흔한 실수”
  • 입력값의 형태(한 자리 숫자, 두 자리 숫자)로 클래스를 나눔. 처리가 같으면 한 클래스
  • 빈 문자열, 0, 명시적 null, 필드 누락을 한 클래스로 묶음. 네 경우는 처리와 의미가 다른 경우가 많아 명세로 확인함
  • 정규화나 변환을 거치는 입력을 원래 형식과 같은 클래스로 묶어 변환 경로를 확인하지 않음
  • 화면 검증으로 무효 클래스를 확인하고 서버 판정은 확인하지 않음

출처

섹션 제목: “출처”

  • ISO 표준 원문은 유료이며 링크는 ISO 공식 안내 페이지임

관련 문서

테스트 설계경계값 분석처리 결과가 달라지는 경계와 그 바로 안팎의 값을 선택해 테스트하는 기법이다(Boundary Value Analysis).테스트 설계결정 테이블 테스트여러 조건의 조합에 따라 동작이 달라지는 규칙을 표로 정리하고, 표의 열마다 테스트 케이스를 도출하는 기법이다(Decision Table Testing). 명세의 누락과 모순을 설계 단계에서 찾는 데도 사용한다.테스트 설계상태 전이 테스트대상이 가질 수 있는 상태와 상태를 변경하는 사건을 정리한 뒤, 허용된 전이와 차단되어야 하는 전이를 모두 테스트하는 기법이다(State Transition Testing).
