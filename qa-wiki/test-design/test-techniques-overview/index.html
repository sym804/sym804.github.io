테스트 기법 분류: 블랙박스, 화이트박스, 경험 기반, 협업 기반

테스트 기법은 블랙박스(명세 기반), 화이트박스(구조 기반), 경험 기반, 협업 기반으로 나뉜다. 분류마다 정의, 근거, 커버리지, 강점과 한계를 설명하고 구문·분기 커버리지 계산 예를 든다.

기본기난이도 기초최종 업데이트 2026-11-24

테스트 기법은 무엇을 테스트할지(테스트 분석)와 어떻게 테스트할지(테스트 설계)를 정하는 체계적인 방법이다. 기법을 사용하면 적은 수의 TC로 필요한 범위를 확인할 수 있고, 테스트 조건, 커버리지 항목, 테스트 데이터를 근거 있게 정할 수 있다. ISTQB CTFL v4.0.1은 기법을 블랙박스, 화이트박스, 경험 기반 셋으로 나누고, 결함 검출보다 결함 예방에 초점을 둔 협업 기반 접근법을 따로 다룬다.

구분 설계 근거 TC 작성 시점 커버리지 측정 대표 기법
블랙박스(명세 기반) 명세된 동작. 내부 구조는 참조하지 않음 명세가 있으면 구현 전에도 가능 명세에서 도출한 항목(분할, 경계, 규칙, 전이) 동등 분할, 경계값 분석, 결정 테이블, 상태 전이
화이트박스(구조 기반) 내부 구조와 처리(코드, 아키텍처, 워크플로, 데이터 흐름) 설계나 구현이 있어야 가능 코드 구조 항목(구문, 분기) 구문 테스트, 분기 테스트
경험 기반 테스터의 지식과 경험 언제든 가능. 다른 기법의 보완 정형화된 측정이 어려움 오류 추측, 탐색적 테스트, 체크리스트 기반 테스트
협업 기반 사용자 스토리와 인수 기준에 대한 팀의 합의 구현 전(테스트 우선) 인수 기준 충족 여부 협업 스토리 작성, 인수 기준, ATDD

블랙박스 테스트(명세 기반)

섹션 제목: “블랙박스 테스트(명세 기반)”

블랙박스 기법은 테스트 대상의 내부 구조를 참조하지 않고 명세된 동작을 분석해 TC를 도출한다. 근거는 요구사항, 기획서, 사용자 스토리, API 명세, 사용자 매뉴얼처럼 “무엇을 해야 하는지”를 적은 문서다. TC가 구현 방식과 독립적이라서, 구현이 바뀌어도 요구 동작이 같으면 TC를 그대로 사용할 수 있다. 블랙박스 테스트의 주된 목적은 시스템의 동작이 명세와 일치하는지 확인하는 것이다.

기법 커버리지 항목 이런 명세에 사용
동등 분할 동등 분할(유효·무효 클래스) 같은 방식으로 처리되는 값의 묶음이 있는 입력, 출력, 설정
경계값 분석 경계값(2값 방식) 또는 경계값과 양쪽 이웃(3값 방식) 순서가 있는 범위(금액, 길이, 날짜, 개수)
결정 테이블 테스트 실현 가능한 조건 조합의 열 조건 조합에 따라 결과가 달라지는 업무 규칙
상태 전이 테스트 상태, 유효 전이, 전체 전이(무효 전이 포함) 이전 이력에 따라 같은 입력에도 반응이 달라지는 기능

강점

  • 사용자 관점의 동작을 직접 확인함. 명세의 누락과 모순도 함께 드러남
  • 코드를 보지 않아도 설계할 수 있어 구현 전에 TC를 준비할 수 있음
  • 구현 방식이 변경되어도 TC를 유지할 수 있음

한계

  • 명세에 없는 동작(구현에만 있는 분기, 숨은 기능)은 TC로 도출되지 않음
  • 실제로 코드의 어느 부분이 실행되었는지 측정하지 못함. 블랙박스 테스트만으로는 코드 커버리지를 알 수 없음

화이트박스 테스트(구조 기반)

섹션 제목: “화이트박스 테스트(구조 기반)”

화이트박스 기법은 테스트 대상의 내부 구조와 처리를 분석해 TC를 도출한다. 구조는 코드에 한정되지 않고 아키텍처, 워크플로, 데이터 흐름도 포함한다. TC가 설계 방식에 의존하므로 설계나 구현이 있어야 작성할 수 있다. 화이트박스 테스트의 주된 목적은 내부 구조를 받아들일 수 있는 수준까지 테스트로 수행(커버)하는 것이다.

CTFL v4.0.1은 코드 기반 기법 중 가장 많이 쓰이는 구문 테스트와 분기 테스트를 다룬다. 안전 필수 분야에서는 이보다 엄격한 기법(조건 커버리지, MC/DC 등)을 사용한다.

구문 테스트와 구문 커버리지

섹션 제목: “구문 테스트와 구문 커버리지”
  • 커버리지 항목: 실행 가능한 구문(Statement)
  • 계산: 테스트로 실행한 구문 수 / 실행 가능한 구문 수 x 100
  • 100% 달성 의미: 모든 구문이 적어도 한 번 실행됨. 결함이 있는 구문도 실행되므로 장애로 드러날 기회가 생김
  • 한계: 실행만으로 모든 결함이 드러나지는 않음. 분모가 0일 때만 실패하는 나눗셈처럼 데이터에 의존하는 결함은 남을 수 있고, 판단 로직의 모든 결과(분기)를 확인하지 않음

분기 테스트와 분기 커버리지

섹션 제목: “분기 테스트와 분기 커버리지”
  • 분기(Branch): 제어 흐름 그래프에서 두 노드 사이의 제어 이동. 조건 없는 이동(직선 코드)과 조건에 따른 이동(if의 참·거짓, switch의 각 case, 반복문의 계속·종료)이 있음
  • 계산: 테스트로 수행한 분기 수 / 전체 분기 수 x 100
  • 포함 관계: 분기 커버리지 100%는 구문 커버리지 100%를 포함함. 반대는 성립하지 않음
  • 한계: 특정 경로(분기의 특정 조합)를 거쳐야만 드러나는 결함은 분기 커버리지 100%로도 놓칠 수 있음

계산 예

섹션 제목: “계산 예”

요구사항: “VIP 쿠폰은 10% 할인한다. 쿠폰이 없으면 할인하지 않는다.”

TC 입력 실행한 구문 수행한 판단 결과 실제 결과
TC1 amount 10,000, coupon “VIP” 1, 2, 3, 4 참 9,000(정상)
TC2 amount 10,000, coupon 없음 1, 2, 4 거짓 NaN(결함 검출)
  • TC1만 수행하면 구문 커버리지는 4/4로 100%임. 조건 분기(판단의 참, 거짓) 기준으로는 2개 중 1개만 수행해 분기 커버리지가 50%이고, 이 상태에서는 결함이 드러나지 않음. 조건 없는 분기까지 세는 제어 흐름 그래프 기준(1→2, 2→3, 3→4, 2→4의 4개)으로는 3/4, 75%임
  • TC1과 TC2를 함께 수행하면 조건 분기 2/2, 전체 분기 4/4로 분기 커버리지 100%임
  • 분기 커버리지를 채우려고 거짓 분기를 수행하는 TC2를 추가하면 초기값 누락 결함이 장애(NaN)로 드러남
  • 요구사항이 “30,000원 이상 주문에서만 쿠폰 적용”이었는데 그 조건이 코드에 아예 없다면, 화이트박스 기법으로는 그 누락을 찾지 못함. 없는 코드는 커버리지 항목이 되지 않기 때문이고, 명세에서 도출한 블랙박스 TC(29,999원 주문에 VIP 쿠폰)로 찾음

화이트박스 테스트의 가치

섹션 제목: “화이트박스 테스트의 가치”
  • 명세가 모호하거나 오래되었거나 불완전해도 구현 전체를 기준으로 테스트할 수 있음
  • 실행하지 않는 정적 테스트에도 사용함. 실행 준비가 안 된 코드, 의사 코드, 제어 흐름으로 표현할 수 있는 상위 로직을 리뷰할 때 사용함
  • 커버리지를 객관적으로 측정해, 실행되지 않은 코드를 찾고 추가할 TC의 근거로 사용함

실무에서 QA가 화이트박스 관점을 사용하는 방법

  • 커버리지 리포트에서 실행되지 않은 분기를 찾아, 그 분기를 실행시키는 입력을 명세에서 확인하고 TC를 추가함
  • 변경된 코드의 분기(새로 추가된 if, 예외 처리)를 읽고 그 분기에 도달하는 TC가 있는지 확인함
  • 오류 처리 분기(외부 API 타임아웃, DB 저장 실패)는 대역(Test Double)으로 실패를 만들어 수행함

그레이박스 테스트

섹션 제목: “그레이박스 테스트”

내부 구조 일부(DB 스키마, 로그, API 구조)를 알고 외부에서 테스트하는 방식을 실무에서 그레이박스라고 부른다. 예를 들어 화면에서 주문을 생성한 뒤 DB의 주문 상태와 로그의 처리 순서를 함께 확인한다. ISTQB CTFL v4.0.1의 분류에는 없는 용어이고, 블랙박스 TC를 설계하면서 판정과 원인 분석에 내부 정보를 사용하는 방식으로 이해하면 된다.

경험 기반 테스트

섹션 제목: “경험 기반 테스트”

경험 기반 기법은 테스터의 지식과 경험으로 TC를 설계한다. 효과는 테스터의 역량에 크게 좌우되며, 블랙박스와 화이트박스 기법이 놓친 결함을 찾을 수 있어 두 기법을 보완한다.

오류 추측

섹션 제목: “오류 추측”

다음 지식을 바탕으로 오류, 결함, 장애가 발생할 곳을 예상해 TC를 설계한다.

  • 애플리케이션이 과거에 동작한 방식
  • 개발자가 자주 하는 실수와 그 실수가 만드는 결함 유형
  • 비슷한 다른 애플리케이션에서 발생한 장애 유형
결함 범주 예상할 결함 예 TC 예
입력 올바른 입력 거부, 파라미터 누락 이름에 공백만 입력, 이모지 포함 입력
출력 형식 오류, 잘못된 결과 금액 천 단위 구분 기호, 날짜 시간대 표시
로직 빠진 경우, 잘못된 연산자 >= 대신 >로 구현한 경계
계산 잘못된 피연산자, 잘못된 계산 반올림 위치, 0 나누기
인터페이스 파라미터 불일치, 호환되지 않는 타입 숫자 문자열 “007”을 숫자로 변환해 앞의 0이 사라짐
데이터 잘못된 초기화, 잘못된 타입 빈값과 0을 같게 처리, null과 필드 누락 혼동

결함 공격(Fault Attack)은 오류 추측을 체계화한 방법이다. 발생 가능한 오류, 결함, 장애 목록을 작성하거나 확보하고, 목록의 항목마다 그 결함을 드러내는 테스트를 설계한다. 목록은 경험, 결함·장애 데이터, 소프트웨어가 실패하는 이유에 대한 일반 지식으로 만든다.

탐색적 테스트

섹션 제목: “탐색적 테스트”

테스트 대상을 학습하면서 설계, 실행, 평가를 동시에 진행한다. 명세가 부족하거나 일정이 촉박할 때 유용하고, 정형 기법을 보완한다. 세션 기반으로 운영할 때는 차터, 타임박스, 디브리핑을 사용한다. 자세한 절차는 탐색적 테스트와 세션 기반 테스트 관리에 있다.

체크리스트 기반 테스트

섹션 제목: “체크리스트 기반 테스트”

체크리스트의 테스트 조건을 수행하도록 테스트를 설계하고 실행한다. 체크리스트는 경험, 사용자에게 중요한 것에 대한 지식, 소프트웨어가 실패하는 이유에 대한 이해로 만든다.

  • 항목은 하나씩 따로, 직접 확인할 수 있게 질문 형태로 씀. 예: “필수 입력란을 비우고 저장하면 해당 입력란 옆에 오류 문구가 표시되는가?”
  • 넣지 않을 항목: 자동으로 확인할 수 있는 항목, 진입·종료 기준에 더 맞는 항목, 지나치게 일반적인 항목
  • 개발자가 같은 실수를 피하게 되면 일부 항목은 효과가 떨어지고, 심각한 결함이 새로 발견되면 항목을 추가해야 함. 결함 분석 결과로 정기적으로 갱신하되 목록이 너무 길어지지 않게 관리함
  • 상세 TC가 없을 때 일관성을 주지만, 항목이 추상적이면 수행자마다 실제 테스트가 달라짐(커버리지는 넓어질 수 있으나 반복성이 떨어짐)

협업 기반 접근법

섹션 제목: “협업 기반 접근법”

앞의 세 기법이 결함 검출을 목적으로 한다면, 이 접근법들은 협업과 소통으로 결함이 만들어지지 않게 하는 데 초점을 둔다.

협업 사용자 스토리 작성

섹션 제목: “협업 사용자 스토리 작성”

사용자 스토리는 사용자나 구매자에게 가치 있는 기능을 나타내며 세 요소(3C)로 구성된다.

  • 카드(Card): 스토리를 적은 매체(카드, 전자 보드 항목)
  • 대화(Conversation): 소프트웨어를 어떻게 사용할지에 대한 설명. 문서나 구두
  • 확인(Confirmation): 인수 기준

일반적인 형식은 “[역할]로서, [목표]를 원한다. 그래서 [가치]를 얻을 수 있다” 뒤에 인수 기준을 붙인다. 좋은 스토리는 INVEST(독립적, 협상 가능, 가치 있음, 추정 가능, 작음, 테스트 가능) 조건을 만족한다. 이해관계자가 스토리를 어떻게 테스트할지 모르면 스토리가 불명확하거나 가치가 드러나지 않은 것일 수 있다.

인수 기준

섹션 제목: “인수 기준”

사용자 스토리 구현이 이해관계자에게 인수되려면 충족해야 하는 조건이다. 테스트가 수행해야 할 테스트 조건으로 볼 수 있다. 스토리의 범위를 정하고, 합의를 이루고, 긍정·부정 시나리오를 기술하고, 인수 테스트와 추정의 근거가 된다.

  • 시나리오형: Given/When/Then 형식. 예: “Given 장바구니 금액이 29,000원일 때, When 30,000원 이상 쿠폰을 적용하면, Then 적용이 거부되고 최소 금액 안내가 표시된다”
  • 규칙형: 검증 항목 목록이나 입력과 출력의 대응표

인수 테스트 주도 개발(ATDD)

섹션 제목: “인수 테스트 주도 개발(ATDD)”

스토리를 구현하기 전에 고객, 개발자, 테스터가 함께 TC를 만드는 테스트 우선 방식이다.

  1. 명세 워크숍에서 스토리와 인수 기준을 분석하고 불완전한 부분, 모호한 부분, 결함을 해결함
  2. 인수 기준을 근거로 TC를 작성함. TC는 소프트웨어가 어떻게 동작하는지 보여 주는 예시 역할을 함
  3. 긍정 TC부터 작성하고, 이어서 부정 TC, 마지막으로 비기능 특성(성능, 사용성) TC를 작성함
  4. 자동화 프레임워크가 지원하는 형식으로 작성하면 개발자가 기능을 구현하면서 TC를 자동화할 수 있고, 인수 테스트가 실행 가능한 요구사항이 됨

TC는 스토리의 특성을 모두 다루되 스토리 범위를 벗어나지 않으며, 두 TC가 같은 특성을 중복해서 다루지 않게 작성한다.

적용 예: 배송비 계산 기능

섹션 제목: “적용 예: 배송비 계산 기능”

요구사항: “주문 금액 30,000원 이상이면 배송비 무료, 미만이면 3,000원. 제주·도서 지역은 3,000원을 추가한다. 회원 등급이 골드이면 금액과 무관하게 기본 배송비가 무료다.”

  • 블랙박스
    • 동등 분할: 주문 금액(30,000원 미만, 이상), 지역(일반, 제주·도서), 등급(골드, 그 외)
    • 경계값: 29,999원, 30,000원
    • 결정 테이블: 금액 x 지역 x 등급 조합 8열. 골드 회원의 제주 주문은 기본 배송비 0원과 추가 배송비 3,000원으로 기대 결과를 정함. 이 조합에 “배송비 무료” 안내를 그대로 표시하면 사용자가 추가 배송비를 예상하지 못하므로 안내 문구는 기획 확인 항목으로 둠
  • 화이트박스
    • 구현을 읽어 지역 판정이 우편번호 범위 비교로 되어 있음을 확인하고, 범위 끝 우편번호를 수행하는 TC를 추가함
    • 커버리지 리포트에서 “주소 없음” 예외 분기가 실행되지 않음을 확인하고, 주소 없는 주문 요청 TC를 추가함
  • 경험 기반
    • 오류 추측: 쿠폰 할인 후 금액이 30,000원 미만이 될 때 배송비 기준 금액이 할인 전인지 후인지, 부분 취소 후 남은 금액이 기준 미만이 될 때 배송비를 재계산하는지 확인함
    • 체크리스트: 금액 표시 형식, 배송비 안내 문구 위치
  • 협업 기반
    • 기획 리뷰에서 “주문 금액”이 할인 전 금액인지 할인 후 금액인지 인수 기준에 명시하도록 합의함

테스트 계획, 결함 분류, 보고에 적용

섹션 제목: “테스트 계획, 결함 분류, 보고에 적용”
  • 계획: 기능별로 사용할 기법과 목표 커버리지를 적음. 예: “결제 금액 계산은 결정 테이블 열 100%와 금액 경계 2값 방식 100%, 계산 모듈의 분기 커버리지 90% 이상”
  • 결함 분류: 결함을 찾은 기법을 기록함. 화이트박스나 경험 기반으로만 찾은 결함이 많으면 명세가 부족하다는 신호이고, 해당 명세 보강을 요청함
  • 보고: 기법별 커버리지를 따로 보고함. 블랙박스 커버리지(명세 항목)와 코드 커버리지는 다른 축이라 하나의 수치로 합치지 않음

현장 노트

  • “상장 폐지 종목의 종가 0 때문에 로그 계산이 -inf가 된다”는 지적은 코드만 읽고 결함을 예상한 오류 추측이었음. 실제 데이터를 조회하니 종가가 0 이하인 행은 0행이라 당시에는 장애로 이어지지 않았음. 그래도 같은 입력이 들어올 수 있는 구조라 가드를 추가함. 오류 추측은 데이터로 확인한 뒤 수용 여부를 정함
  • 마스킹 같은 업계 용어를 우리말로 직역한 조어가 문서 검사 체크리스트를 모두 통과해 사람이 지적한 뒤에야 발견됨. 이후 그 유형을 사전으로 만들어 검사 항목에 추가함. 새로 발견된 결함 유형으로 체크리스트를 갱신한 사례임
  • 같은 파일 객체를 다시 사용할 때만 드러나는 결함이 화면 E2E에서는 검출되지 않고 단위 테스트에서만 검출된 사례가 있음. 구현 구조(객체 재사용)를 알아야 설계할 수 있는 TC였음(테스트 레벨과 테스트 유형의 현장 노트)

규칙

  • 블랙박스 기법으로 명세를 커버하고, 화이트박스 커버리지로 실행되지 않은 코드를 찾고, 경험 기반 기법으로 둘의 빈틈을 채움
  • 코드 커버리지 100%를 테스트 완료로 해석하지 않음. 구현되지 않은 요구사항은 코드 커버리지에 나타나지 않음
  • 체크리스트는 결함 분석 결과로 갱신함

흔한 실수

섹션 제목: “흔한 실수”
  • 블랙박스를 “코드를 모르는 사람이 하는 테스트”, 화이트박스를 “개발자가 하는 테스트”로 이해함. 구분 기준은 수행자가 아니라 TC 설계의 근거임
  • 구문 커버리지 100%를 분기까지 확인한 것으로 보고함
  • 경험 기반 테스트를 기록 없이 수행해 무엇을 확인했는지 남지 않음
  • 인수 기준을 개발 완료 후에 작성해 협업 기반 접근의 예방 효과를 잃음

기초와 용어테스팅의 7원칙테스팅의 일반 원칙 7가지(ISTQB CTFL v4.0.1 1.3)는 테스트로 보장할 수 있는 것과 없는 것을 정한다. 원칙마다 뜻과 근거, 테스트 계획·설계·보고에 반영하는 방법을 사례와 함께 설명한다.기초와 용어테스트 레벨과 테스트 유형테스트 레벨은 시스템을 어느 통합 단계에서 검증하는지를, 테스트 유형은 어떤 품질 특성을 검증하는지를 나타내는 분류다. 두 분류는 서로 독립이며, 테스트마다 레벨을 하나 정하고 테스트 유형은 하나 이상 적용할 수 있다.테스트 설계동등 분할시스템이 똑같이 처리할 것으로 기대되는 입력을 한 묶음(동등 클래스)으로 보고, 묶음마다 대표값 하나만 테스트하는 기법이다(Equivalence Partitioning).테스트 설계탐색적 테스트와 세션 기반 테스트 관리테스트 대상을 학습하면서 테스트 설계, 실행, 결과 평가를 동시에 진행하는 경험 기반 기법이다(Exploratory Testing). ISTQB, Kaner, Bach·Bolton의 정의 차이, 테스트 아이디어(HTSM)와 판정 기준(FEW HICCUPPS) 휴리스틱, 세션 기반 테스트 관리의 차터, 세션 기록, TBS 지표를 다룬다.
