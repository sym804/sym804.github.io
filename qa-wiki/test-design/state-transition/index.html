상태 전이 테스트

대상이 가질 수 있는 상태와 상태를 변경하는 사건을 정리한 뒤, 허용된 전이와 차단되어야 하는 전이를 모두 테스트하는 기법이다(State Transition Testing).

기본기난이도 중급최종 업데이트 2026-11-24

상태 전이도, State Transition

같은 입력이라도 대상의 현재 상태에 따라 결과가 달라지는 기능에 적용한다. 주문, 결제, 계정, 결재, 테스트 수행 같은 흐름이 대상이다.

절차

섹션 제목: “절차”
  1. 상태를 나열함. 예: 작성 중, 진행 중, 완료, 삭제됨
  2. 상태를 변경하는 사건을 나열함. 예: 시작, 완료 처리, 다시 열기, 삭제
  3. 상태와 사건의 표를 작성함. 칸마다 다음 상태 또는 “허용 안 됨”을 기록함
  4. 허용된 전이마다 TC 하나, 허용 안 됨 칸마다 TC 하나를 작성함
현재 상태 \ 사건 시작 완료 처리 다시 열기 삭제
작성 중 진행 중 허용 안 됨 허용 안 됨 삭제됨
진행 중 허용 안 됨 완료 허용 안 됨 삭제됨
완료 허용 안 됨 허용 안 됨 진행 중 삭제됨
삭제됨 허용 안 됨 허용 안 됨 허용 안 됨 허용 안 됨

놓치기 쉬운 것

섹션 제목: “놓치기 쉬운 것”
  • 허용 안 됨 칸: 버튼 숨김만으로는 차단으로 판정하지 않음. 같은 요청을 API로 전송해도 차단되는지 확인함
  • 되돌리기: 되돌린 뒤의 상태와 데이터
  • 삭제 후 참조: 삭제한 대상을 가리키던 목록, 통계, 링크의 표시 방식
  • 열린 화면에 남은 이전 상태: 다른 탭에서 완료 처리한 대상을 이 탭에서 수정할 때의 동작
  • 상태에서 파생된 값: 상태 변경 뒤 진행률, 합격률 같은 집계를 다시 계산하는 기준
  • 같은 사건의 동시 요청: 1회용 코드 사용, 승인, 완료 처리처럼 한 번만 일어나야 하는 전이에 같은 요청이 동시에 들어올 때의 결과

TC 예시

섹션 제목: “TC 예시”

위 표의 전이에서 도출한 TC다.

전이 TC 예시
작성 중 + 시작 작성 중인 수행에서 시작을 클릭하면 상태가 진행 중으로 표시되고 결과 입력이 가능해지는지 확인함
완료 + 다시 열기 완료된 수행을 다시 열면 상태가 진행 중으로 변경되고, 입력된 결과는 유지되며, 목록의 진행률이 다시 계산되는지 확인함
허용 안 됨: 작성 중 + 완료 처리 작성 중인 수행에 완료 처리 버튼이 표시되지 않는지 확인하고, 같은 요청을 API로 전송해 명세의 오류 코드(예: 409)가 반환되며 상태가 작성 중으로 유지되는지 확인함
허용 안 됨: 삭제됨 + 다시 열기 삭제된 수행의 id로 다시 열기 API를 호출해 404가 반환되고 목록과 통계에 다시 표시되지 않는지 확인함
이전 상태가 남은 화면 탭 A에서 완료 처리한 뒤 진행 중으로 표시된 탭 B에서 결과를 저장하면, 명세에 정한 대로 저장이 거부되고 최신 상태 안내가 표시되는지 확인함
동시 사건 같은 수행에 완료 처리 요청 두 건을 동시에 보내 상태 변경과 이력 기록이 1건만 발생하는지 확인함. 두 번째 요청의 응답(오류 또는 같은 결과를 반환하는 멱등 처리)은 명세에 따라 판정함

적용 예: 로그인 실패 잠금이 있는 계정

섹션 제목: “적용 예: 로그인 실패 잠금이 있는 계정”

요구사항이 “로그인을 5회 연속 실패하면 계정을 30분간 잠근다. 관리자는 잠금을 해제할 수 있다.” 두 줄인 경우(횟수와 시간은 예), 먼저 상태와 사건을 정리한다.

  • 상태: 활성(연속 실패 0~3회), 활성(연속 실패 4회), 잠금
  • 사건: 올바른 비밀번호로 로그인, 틀린 비밀번호로 로그인, 잠금 후 30분 경과, 관리자 잠금 해제

연속 실패 횟수는 동등 분할로 0~3회를 한 상태로 묶고, 다음 실패에서 잠금으로 넘어가는 4회를 별도 상태로 둔다.

현재 상태 \ 사건 올바른 비밀번호 틀린 비밀번호 30분 경과 관리자 해제
활성(실패 0~3회) 로그인, 실패 0회 실패 횟수 + 1(3회에서 실패하면 실패 4회 상태) 해당 없음 확인 항목
활성(실패 4회) 로그인, 실패 0회 잠금 해당 없음 확인 항목
잠금 허용 안 됨(로그인 거부) 확인 항목 활성, 실패 0회 활성, 실패 0회

표를 채우면 명세로 답할 수 없는 칸이 드러난다. 기획과 확인할 항목은 다음과 같다.

  • 잠금 중 틀린 비밀번호로 시도하면 잠금 시간이 연장되는지
  • 잠금 중 로그인 거부 문구가 계정 존재 여부를 드러내지 않는지(보안 테스트의 기본 관점)
  • 잠금 상태가 아닌 계정에 관리자 해제를 실행하면 실패 횟수가 초기화되는지
  • 비밀번호 재설정이 잠금 해제 사건에 해당하는지
  • 잠금 시점에 이미 로그인된 다른 기기의 세션을 유지하는지

확인 항목을 확정한 뒤 도출되는 TC는 다음과 같다.

  • 유효 전이: 실패 3회 뒤 올바른 비밀번호로 로그인하면 성공하고 실패 횟수가 0으로 초기화됨. 이후 4회 실패해도 잠기지 않음
  • 유효 전이: 실패 4회 상태에서 1회 더 실패하면 잠금 안내가 표시되고, 이후 올바른 비밀번호로도 로그인되지 않음
  • 유효 전이: 잠금 후 관리자가 해제하면 즉시 로그인됨
  • 허용 안 됨: 잠금 상태에서 화면을 거치지 않고 로그인 API로 올바른 비밀번호를 전송해도 토큰이 발급되지 않음
  • 경계: 잠금 후 29분 59초에는 로그인이 거부되고 30분 1초에는 성공함(경계값 분석, 시각을 조작할 수 있는 환경에서 수행)

“실패 0~3회”와 “실패 4회”를 한 상태로 두면 5번째 실패에서 잠기는지, 4번째에서 잠기는지를 확인하는 TC가 빠진다. 상태를 나누는 기준은 다음 사건에 대한 반응이 달라지는 지점이다.

테스트 계획, 결함 분류, 보고에 적용

섹션 제목: “테스트 계획, 결함 분류, 보고에 적용”

테스트 계획

  • 커버리지 기준을 정해 계획서에 기록함. ISTQB CTFL v4.0.1은 모든 상태 커버리지, 유효 전이 커버리지(0-switch), 모든 전이 커버리지(허용 안 됨 포함)를 구분함
  • 매 릴리즈 회귀 범위에는 허용 안 됨 칸 중 권한, 결제, 데이터 손실과 관련된 칸을 포함함
  • 상태 표와 확인 항목 목록을 명세 리뷰 산출물로 남김. 구현 전에 기획과 개발이 같은 표를 확인하게 됨

결함 분류

  • 결함에 현재 상태, 사건, 기대한 다음 상태, 실제 다음 상태를 함께 기록함
  • 재현 절차의 사전 조건에 그 상태를 만드는 방법을 기록함. 예: “틀린 비밀번호로 4회 로그인한 계정”
  • 원인 유형을 잘못된 다음 상태, 허용 안 됨 칸의 미차단, 파생 값 미갱신, 동시 요청으로 나눠 라벨로 남기면 어느 칸에서 결함이 반복되는지 집계할 수 있음

보고

  • 전이 커버리지를 유효 전이와 허용 안 됨 칸으로 나눠 보고함. 예: “유효 전이 9개 중 9개, 허용 안 됨 칸 11개 중 8개 수행. 3개는 API가 제공되지 않아 화면 차단만 확인”

현장 노트

  • TC 관리 도구의 메인 화면이 프로젝트별 수치를 “가장 최근에 생성한 수행(테스트 회차)” 하나로 계산함. 새 수행을 생성하기만 해도 그 프로젝트의 진행률이 0%, 합격률이 빈값으로 변경됨
  • 상태 전이 표에 “새 수행 생성” 사건을 추가하고 그 뒤의 파생 값을 기대 결과로 기록했다면 설계 단계에서 발견할 수 있었던 결함
  • 조치: 진행 중 수행과 최근 완료 수행을 구분해 표시하도록 수정함
  • 관리자가 비밀번호를 초기화한 “임시 비밀번호” 상태에서 비밀번호 강제 변경을 화면에서만 처리하고 서버는 확인하지 않음. 임시 비밀번호로 로그인한 뒤 GET /api/projects를 보내면 200이 반환됨. 이 상태에서 허용하는 경로를 내 정보 조회, 비밀번호 변경, 로그아웃 셋으로 정하고 나머지는 403을 반환하도록 수정함
  • 계정 찾기·비밀번호 재설정용 1회용 코드로 동시에 8건을 요청하자 4건이 성공함. 코드를 읽고 사용 처리하는 사이에 행 잠금이 없었음. 코드 행을 SELECT ... FOR UPDATE로 읽도록 수정하고, 동시 요청 중 1건만 성공하고 7건은 401인지 단언하는 테스트를 추가함. 데이터베이스를 PostgreSQL로 전환하는 과정에서 동시 요청 테스트로 재현됨

흔한 실수

섹션 제목: “흔한 실수”
  • 허용된 전이만 TC로 작성하고 허용 안 됨 칸은 작성하지 않음
  • 화면에서 버튼이 숨겨진 것으로 허용 안 됨 칸을 통과 처리함
  • 상태를 화면의 상태 표시 문구 기준으로만 나눔. 실패 횟수, 임시 비밀번호 여부처럼 화면에 표시되지 않지만 다음 반응을 달라지게 하는 값도 상태에 포함함
  • 상태 변경 뒤 목록, 통계, 진행률 같은 파생 값을 기대 결과에 포함하지 않음
  • 단일 요청으로만 확인하고 같은 사건의 동시 요청은 확인하지 않음
