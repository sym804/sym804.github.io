탐색적 테스트와 세션 기반 테스트 관리

테스트 대상을 학습하면서 테스트 설계, 실행, 결과 평가를 동시에 진행하는 경험 기반 기법이다(Exploratory Testing). ISTQB, Kaner, Bach·Bolton의 정의 차이, 테스트 아이디어(HTSM)와 판정 기준(FEW HICCUPPS) 휴리스틱, 세션 기반 테스트 관리의 차터, 세션 기록, TBS 지표를 다룬다.

기본기난이도 중급최종 업데이트 2026-11-24

스크립트 테스트는 미리 작성한 절차를 따르고, 탐색적 테스트는 직전 결과를 보고 다음 조작을 정한다. 세션 기반 테스트 관리(Session-Based Test Management)는 이 탐색에 목표, 시간 한도, 기록을 추가해 무엇을 확인했고 무엇이 남았는지 보고할 수 있게 한다. 탐색에서 발견한 주요 경로는 스크립트 TC로 옮겨 반복 확인한다.

정의

섹션 제목: “정의”

출처마다 탐색적 테스트를 기법, 접근법, 스타일, 테스팅 자체로 다르게 분류한다.

출처 정의 강조점
ISTQB CTFL v4.0.1 4.4.2 테스터가 테스트 대상을 학습하면서 테스트를 동시에 설계, 실행, 평가함 경험 기반 테스트 기법(4.4)의 하나로 분류함. 명세가 부족하거나 시간 압박이 클 때, 다른 형식적 기법을 보완할 때 유용함. 세션 기반 테스트는 구조화 방법의 하나로 소개함
ISTQB 용어집(ISO/IEC/IEEE 29119-1 기반) 테스터의 지식, 테스트 항목 탐색, 이전 테스트 결과를 바탕으로 테스트를 동적으로 설계하고 실행하는 테스트 접근법 접근법(test approach)으로 분류함. 관련 용어로 테스트 차터(test charter)를 연결함
Cem Kaner, 2008 튜토리얼 개별 테스터의 자유와 책임을 강조하는 테스트 스타일. 테스트 관련 학습, 설계, 실행, 결과 해석을 프로젝트 전체에서 병행하는 상호 보완 활동으로 다루어 테스터가 자기 작업의 가치를 계속 최적화하게 함 테스터 개인의 판단과 책임, 프로젝트 전 기간에 걸친 학습
James Bach·Michael Bolton, Exploratory Testing 3.0 2006년 무렵 “학습, 테스트 설계, 테스트 실행의 동시 수행”으로 정리함. 현재 Rapid Software Testing 방법론에서는 모든 테스팅을 탐색적이라고 보고, 테스팅을 “탐색과 실험으로 제품을 학습하며 평가하는 과정”으로 정의함 탐색과 스크립트를 가르는 기준은 주체성(agency). 스크립트는 문서에 한정하지 않고 테스터의 선택 밖에서 테스트를 통제하는 모든 요소를 가리킴
  • 공통점: 학습, 설계, 실행, 결과 해석을 차례로 나눈 단계로 보지 않고 함께 진행하는 활동으로 봄
  • 용어의 기원: Cem Kaner가 만든 용어임. Kaner는 2008년 4월 튜토리얼 초록에서 실리콘밸리에서 흔했던 숙련된 작업 방식을 가리키려고 24년 전에 이 말을 만들었다고 밝힘. Bach·Bolton은 Kaner의 첫 글이 용어를 정의하지는 않았지만 테스트를 수행하면서 설계한다는 점을 처음 직접 다뤘다고 적음
  • 실무 문서에서는 어느 정의를 따르는지 밝혀 둠. 이 문서의 세션 구성과 보고 방식은 ISTQB 정의와 세션 기반 테스트 관리를 기준으로 함

적용하는 경우

섹션 제목: “적용하는 경우”
  • 명세가 불완전하거나 일정이 짧아 스크립트 TC를 충분히 작성하기 어려운 경우
  • 스크립트 TC로 표현하기 어려운 복합 흐름, 사용성, 예외 흐름을 확인하는 경우
  • 스크립트 TC가 통과한 뒤 결함이 몰린 영역이나 새 기능을 추가로 확인하는 경우

세션 구성

섹션 제목: “세션 구성”
  • 차터(Charter): 세션의 목표. 대상 영역, 사용할 자원과 데이터, 탐색할 리스크나 질문을 한두 문장으로 작성함
    • 예: “주문 취소 화면을 대상으로, 결제 수단별 테스트 계정을 사용해, 부분 취소 뒤 금액 표시 오류를 탐색”
  • 타임박스(Time-box): 팀이 정한 고정 시간. 표준이 정한 길이는 없으며 중단 없이 집중할 수 있는 시간으로 설정함
  • 세션 기록(Session Sheet): 세션 중에 바로 작성함
    • 수행한 경로와 사용한 데이터
    • 발견한 결함과 그 시점의 재현 절차, 증거
    • 명세 확인이 필요한 질문
    • 차터 밖에서 발견한 다음 세션 후보
    • 시간 배분: 테스트 설계와 실행, 결함 조사, 환경 준비에 사용한 시간

결함 원인 추적이 길어지면 확인한 내용까지 기록하고 차터로 복귀한다. 원인 분석은 이슈로 등록하고, 차터 밖에서 발견한 영역은 새 차터로 등록한다.

차터의 탐색 대상을 정할 때 사용하는 관점은 다음과 같다.

  • 진입 경로: 링크 이동, 주소 직접 입력(북마크, 공유 링크), 뒤로 가기, 새로 고침, 새 탭
  • 중단과 반복: 저장 중 네트워크 끊김, 탭 닫기, 버튼 연속 클릭, 같은 요청 재전송
  • 데이터 변형: 빈값, 앞뒤 공백, 대소문자, 최대 길이, 이미 존재하는 값
  • 맥락 변경: 역할, 표시 언어, 테마, 화면 폭, 두 탭에서 동시 수정
  • 스크립트 TC가 통과한 영역의 바로 옆 기능과 화면 사이 이동

테스트 아이디어: Heuristic Test Strategy Model

섹션 제목: “테스트 아이디어: Heuristic Test Strategy Model”

James Bach의 Heuristic Test Strategy Model(HTSM, v6.3, 2024-11-05)은 테스트를 설계하고 고를 때 확인할 항목을 안내어(guideword) 목록으로 정리한 모델이다. 프로젝트 환경(Project Environment), 제품 요소(Product Factors), 품질 기준 범주(Quality Criteria Categories), 일반 테스트 기법(General Test Techniques, 9개 계열)으로 구성되고, 조직과 맥락에 맞게 수정해 사용하도록 권한다. 차터의 대상 영역은 제품 요소에서, 탐색할 리스크는 품질 기준 범주에서 정할 수 있다.

제품 요소는 7개 범주이며 앞 글자를 따면 SFDIPOT이다.

범주 HTSM의 설명 QA 질문 예(회원 가입)
Structure 제품을 구성하는 물리적 요소 전부. 코드, 하드웨어, 서비스, 실행 파일 외 파일, 약관이나 웹 페이지 같은 부속물 가입 확인 메일 템플릿과 약관 페이지가 이번 배포에 포함됐는가
Function 제품이 하는 모든 것. 비즈니스 규칙, 계산, 보안 관련 기능, 상태 전이, 오류 처리, 기능 간 상호작용 가입 요청이 실패하면 어떤 메시지를 표시하고 어느 화면으로 복구되는가
Data 제품이 처리하고 만드는 모든 데이터. 입출력, 기본값, 영속 데이터, 개수, 크기, 잘못된 값, 생성부터 삭제까지의 생명주기 탈퇴한 계정의 이메일로 다시 가입하면 어떻게 처리되는가
Interfaces 제품에 접근하거나 제품이 표현되는 모든 통로. UI, 시스템 인터페이스, API/SDK, 가져오기와 내보내기 화면을 거치지 않고 API로 가입 요청을 보내도 같은 입력 검증이 적용되는가
Platform 제품이 의존하는, 프로젝트 밖의 모든 것. 외부 하드웨어와 소프트웨어, 내장 컴포넌트, 자원 사용량 지원 대상 브라우저와 OS 조합에서 같은 결과가 나오는가
Operations 사람들이 제품으로 겪을 수 있는 모든 경험. 사용자 유형, 사용 환경, 일반·드문·극단·부적절한 사용 같은 이메일로 짧은 간격의 가입 시도를 반복하면 어떻게 처리되는가
Time 제품과 시간의 모든 관계. 시간 데이터, 입출력 시점, 빠르거나 느린 입력, 동시성 인증 메일 링크를 만료 시간 뒤에 열면 어떻게 처리되는가

품질 기준 범주는 사람들이 제품의 가치를 판단하는 차원이며 제품 리스크의 범주로도 볼 수 있다. Capability, Reliability, Usability, Charisma, Security, Scalability, Compatibility, Performance, Installability, Development 10개이고, HTSM은 범주마다 이 프로젝트에서 중요한지 정한 뒤 제품이 그 면에서 잘 동작하는지 어떻게 알아볼지 생각하도록 안내한다.

판정 기준: 오라클 휴리스틱

섹션 제목: “판정 기준: 오라클 휴리스틱”

ISTQB 용어집은 테스트 오라클(test oracle)을 기대 결과를 정하는 근거로 정의한다. 명세가 없거나 불완전한 영역에서는 Michael Bolton이 정리한 일관성 휴리스틱을 판정 근거로 사용할 수 있다. 원래 목록은 James Bach가 만들었고 Bolton이 Better Software 잡지 기고 “Testing Without a Map”에서 HICCUPPS로 소개했다. 2012년 글 “FEW HICCUPPS”는 그 뒤에 추가한 Standards, Familiarity, Explainability, World를 포함한 목록을 공개했다.

기준 기대하는 일관성 회원 가입 예
Familiarity 알려진 문제 패턴과 일치하지 않음. 목록에서 유일한 불일치 휴리스틱 연속 클릭 중복 생성처럼 자주 보던 결함이 나타나지 않음
Explainability 동작을 자신과 다른 사람에게 설명할 수 있음 같은 입력이 통과할 때와 거부될 때의 차이를 설명할 수 있음
World 세상에 대해 알거나 관찰할 수 있는 사실과 일치 존재하지 않는 날짜를 생년월일로 받지 않음
History 이전 버전과 일치 지난 릴리즈에서 허용하던 이메일 형식을 그대로 허용함
Image 조직이 내세우려는 이미지, 브랜드, 평판과 일치 오류 메시지에 내부 예외 문구를 표시하지 않음
Claims 중요한 사람이 문서나 대화로 말한 내용과 일치 요구사항의 “가입 직후 로그인 상태가 된다”
Comparable Products 같은 제품군, 경쟁 제품, 같은 데이터를 처리하는 제품, 대체 알고리즘과 일치 같은 회사의 다른 서비스와 비밀번호 규칙 안내가 같음
User Desires 합리적인 사용자가 원할 만한 것과 일치. 2014-12-05에 User Expectations에서 이름을 바꿈 입력 오류 뒤에도 이미 입력한 값이 유지됨
Product 같은 제품 안의 비슷한 요소와 일치 가입 화면의 이메일 검증이 로그인 화면과 같음
Purpose 사람들이 제품을 사용하는 명시적, 암묵적 용도와 일치 가입을 마친 사용자가 바로 서비스를 이용할 수 있음
Statutes and Standards 관련 법령, 규정, 표준과 일치 개인정보 수집 동의 절차, 접근성 표준
  • 명세에 없는 동작을 결함으로 보고할 때 근거로 삼은 기준을 이슈의 기대 결과에 적음. 예: “로그인 화면처럼 이메일 앞뒤 공백을 제거함(Product)”. Bolton은 관찰이 왜 문제를 가리키는지 의사결정자가 이해할 수 있을 때 보고의 신뢰도가 높아진다고 설명함
  • Claims는 프로젝트 안에서, Statutes and Standards는 프로젝트 밖에서 나옴. 프로젝트가 따르기로 정하지 않은 표준과 어긋나는 동작은 책임자가 표준을 따를지 정하기 전까지 이슈(issue)로 다룸. 이 문서의 흐름에서는 확인 항목으로 기록함
  • 한계: Bolton은 오라클 원칙이 모든 휴리스틱처럼 틀릴 수 있고 맥락에 따라 달라진다고 적음. 기준과 어긋난다고 문제가 확정되지 않으며, 없는 문제를 보거나 있는 문제를 놓칠 수도 있음. Kaner도 오라클을 불완전하고 틀릴 수 있는 휴리스틱으로 설명함
  • 목록은 완전하지 않음. Bolton은 문제인지 아닌지를 여러 오라클 원칙과 가치 판단을 함께 적용해 사람이 결정한다고 적음. 이 문서의 흐름에서는 기획 확인으로 결함을 확정함

디브리핑과 TC 편입

섹션 제목: “디브리핑과 TC 편입”

세션 직후 수행자와 검토자가 세션 기록을 함께 검토한다(Debriefing).

  • 차터 달성 여부, 확인하지 못한 영역과 남은 리스크
  • 발견한 결함은 이슈 양식으로 등록함. 발견 블록은 세션 기록의 재현 절차와 증거로 작성함
  • 명세 질문은 확인 항목으로 기록함
  • 반복 확인이 필요한 경로는 TC 작성 원칙에 맞춰 스크립트 TC로 작성하고 회귀 스위트에 편입함
  • 다음 세션의 차터를 결정함

규칙

  • 세션마다 차터와 세션 기록을 남김. 기록이 없는 수행은 탐색적 테스트 결과로 보고하지 않음
  • 결함을 발견하면 그 시점의 데이터와 조작 순서를 바로 기록함. 세션이 끝난 뒤에 기억으로 작성하지 않음

세션 지표

섹션 제목: “세션 지표”

Jonathan Bach의 “Session-Based Test Management”(STQE 잡지 2000년 11/12월호)는 James Bach와 함께 만든 세션 기반 테스트 관리를 설명한다. 원문은 세션을 중단 없이 진행하고, 제3자가 검토할 수 있고, 차터가 있는 테스트 작업 단위(uninterrupted block of reviewable, chartered test effort)로 정의한다. 원문 팀의 세션은 90분 안팎이었고 45분에 가까우면 short, 2시간에 가까우면 long으로 기록했다.

  • TBS 지표: 세션 시간을 세 작업으로 나눈 비율. 테스터가 추정해 세션 기록에 적음
    • Test design and execution: 제품을 훑어보며 문제를 찾는 시간
    • Bug investigation and reporting: 문제로 보이는 동작을 만난 뒤 조사하고 보고하는 시간
    • Session setup: 앞의 두 작업을 가능하게 하는 나머지 시간. 장비 설정, 자료 찾기, 매뉴얼 읽기, 세션 기록 작성을 포함함
  • 동시에 진행한 작업: 테스트를 중단시킨 시간만 셈. 테스트 50%, 결함 조사 50%는 결함이 없었다면 두 배를 테스트할 수 있었다는 뜻으로 읽음
  • 차터 대비 기회(on charter / on opportunity): 차터에 맞지 않는 테스트를 opportunity testing이라 하고 그 비율을 함께 적음. 중요해 보이는 차터 밖 문제를 만나면 차터에서 벗어나도 됨. 세션 대부분이 opportunity였다면 테스트 관리자가 차터를 실제 수행 내용에 맞게 고치고 원래 차터는 새 세션에서 다시 사용함
  • Bugs와 Issues: Bugs는 제품 품질에 관한 우려, Issues는 테스트 프로세스나 프로젝트에 관한 질문과 문제로 구분함
  • 비세션 작업: 세션만 수행하면 하루 5.333 세션이 가능하다고 가정하고, 근무 인원 기준 최대 세션 수에서 실제 세션 수를 빼서 추정함
  • 디브리핑 안건 PROOF: Past(세션 중 일어난 일), Results(달성한 것), Obstacles(테스트를 방해한 것), Outlook(남은 일), Feelings(테스터의 느낌)

이 문서의 세션 기록 항목 중 시간 배분이 TBS에 해당하고, 명세 질문이 Issues에 해당한다. 원문의 Session setup에는 세션 기록 작성 시간도 포함된다. 원문은 테스트 관리자의 혼동이나 편향, 보고 규칙에 대한 오해로 지표가 왜곡될 수 있다고 적고, 디브리핑을 생략해 본 결과 세션 기록의 질이 떨어지고 지표가 의미를 잃었다고 보고한다.

적용 예: 회원 가입

섹션 제목: “적용 예: 회원 가입”

요구사항이 “이메일과 비밀번호로 가입하고, 가입 직후 로그인 상태가 된다.“인 경우 세션을 다음과 같이 진행한다. 세션 시간과 기록 내용은 예시다.

차터

  • 차터 1: 회원 가입 화면을 대상으로, 주소 직접 입력·뒤로 가기·새로 고침으로 진입 경로를 변경해 가며, 화면 접근과 입력값 유지 오류를 탐색
  • 차터 2: 가입 요청을 대상으로, 브라우저 개발자 도구의 네트워크 속도 제한과 [가입] 연속 클릭을 사용해, 중복 계정 생성과 오류 뒤 화면 상태를 탐색
  • 차터 3: 이메일 입력을 대상으로, 대소문자·앞뒤 공백·이미 가입한 주소를 사용해, 같은 사람이 계정 두 개를 만드는 경로를 탐색
  • 차터 4: 가입 직후 로그인 상태를 대상으로, 새 탭과 새로 고침을 사용해, 세션 유지 오류를 탐색

차터 2의 세션 기록(타임박스 예: 60분)

  • 수행 경로: 속도 제한 없음, 느린 3G 조건에서 각각 가입. 느린 조건에서 [가입]을 두 번 연속 클릭
  • 결함: 느린 조건에서 [가입]을 연속 클릭하면 같은 이메일로 계정이 2건 생성됨. 회원 목록 캡처와 요청 2건의 시각을 증거로 남김
  • 질문: 이메일의 대소문자를 구분하는지 명세에 없음(차터 3의 사전 확인 항목)
  • 다음 세션 후보: 비밀번호 재설정 요청의 연속 클릭
  • 시간 배분: 테스트 설계와 실행 40분, 결함 조사 15분, 환경 준비 5분

디브리핑 결과

  • 중복 계정 결함을 이슈로 등록함. 재현 절차는 세션 기록의 조작 순서를 그대로 사용함
  • 대소문자 구분은 기획 확인 전까지 TC로 작성하지 않고 확인 항목으로 기록함
  • 연속 클릭 중복 생성 경로를 스크립트 TC로 작성해 회귀 스위트에 편입함
  • 차터 3은 명세 확인 뒤 수행하기로 하고, 비밀번호 재설정 차터를 추가함

TC 예시

섹션 제목: “TC 예시”
항목 TC 예시
차터 “회원 가입 화면을 대상으로, 주소 직접 입력·뒤로 가기·새로 고침으로 진입 경로를 변경해 가며, 화면 접근과 입력값 유지 오류를 탐색”(타임박스 예: 60분)
세션 기록의 결함 항목 1. 네트워크 속도를 느린 3G로 제한함 2. 회원 가입 화면에서 새 이메일과 비밀번호를 입력함 3. [가입]을 두 번 연속 클릭함. 실제 결과: 같은 이메일의 계정 2건이 회원 목록에 표시됨
편입한 스크립트 TC: 중복 요청 네트워크를 느린 3G로 제한한 상태에서 [가입]을 두 번 연속 클릭해, 가입 요청이 1건만 전송되고 DB에 해당 이메일 계정이 1건만 생성되는지 확인함. 서버의 중복 요청 차단은 API 동시 전송 TC로 따로 확인함
편입한 스크립트 TC: 진입 경로 비로그인 상태에서 새 탭 주소창에 회원 가입 화면 주소를 입력해, 로그인 화면으로 이동되지 않고 회원 가입 화면이 표시되는지 확인함
편입한 스크립트 TC: 세션 유지 가입을 완료한 직후 새로 고침해 로그인 화면으로 이동되지 않고 로그인한 사용자의 계정 메뉴가 표시되는지 확인함

테스트 계획, 결함 분류, 보고에 적용

섹션 제목: “테스트 계획, 결함 분류, 보고에 적용”

테스트 계획

  • 차터 목록, 차터별 타임박스, 세션 수, 수행자를 계획서에 기록함. 차터는 리스크 기반 테스트의 우선순위가 높은 영역부터 배정함
  • 스크립트 TC와 탐색적 테스트에 배분한 시간을 함께 기록함. 예: 회귀 스위트 1일, 신규 기능 탐색 세션 6회
  • 완료 기준에 “계획한 차터 전부 수행, 세션마다 디브리핑 완료”를 포함함

결함 분류

  • 이슈의 발견 경로에 탐색적 테스트와 차터 식별자를 기록함. 나중에 어떤 차터가 결함을 많이 발견했는지 집계할 수 있음
  • 세션에서 한 번만 관측한 결함은 재현 빈도를 “1회만 관측”으로 기록하고, 세션 중에 남긴 로그와 캡처를 증거로 첨부함(이슈 양식)
  • 명세 질문에서 나온 항목은 결함과 구분해 확인 항목으로 관리함. 기획 답변으로 결함이 확정되면 그때 이슈로 등록함

보고

  • 세션 수, 차터별 달성 여부, 발견한 결함 수, 질문 수, 편입한 스크립트 TC 수, 확인하지 못한 영역을 함께 보고함. “탐색적 테스트 3시간 수행”만 적지 않음
  • 시간 배분에서 환경 준비나 결함 조사 비율이 높으면 그 사유(환경 장애, 결함 밀집)를 함께 기록함. 차터를 달성하지 못한 원인을 구분하는 근거가 됨

현장 노트

  • TC 관리 도구에서 비로그인으로 열 수 있는 공개 페이지(회원 가입 등)를 주소로 직접 열면 로그인 화면으로 이동됨. 로그인 화면의 링크로 이동하면 화면 내부 라우팅이라 문제가 나타나지 않음. 원인은 401 응답을 받으면 로그인 화면 외의 모든 경로를 로그인 화면으로 이동시키는 처리였고, 공개 경로 목록에 있는 주소는 이동 대상에서 제외하도록 수정함. 타입 검사, 단위 테스트, 빌드가 모두 통과한 상태였고 브라우저에서 주소를 직접 열었을 때만 확인됨
  • 화면 요소 이름을 확인하지 않고 확인용 자동화 스크립트를 작성해 두 번 실패함. Export 이름으로 찾은 버튼은 30초 시간 초과로 실패했고(실제 이름 “다운로드”), 첫 번째 select로 잡은 요소는 헤더의 프로젝트 선택 상자였음. 브라우저 자동화 CLI의 접근성 트리 스냅샷으로 요소의 역할과 이름을 확인한 뒤 조작하도록 변경함. 반복 실행할 회귀 TC는 Playwright 테스트로 작성함

애드혹 테스트와의 차이

섹션 제목: “애드혹 테스트와의 차이”

SBTM 원문은 탐색적 테스트를 애드혹 프로세스라고 적고, Bach·Bolton은 Exploratory Testing 3.0에서 애드혹을 사전적 의미(“이 목적을 위해”)로 보아 탐색적 테스트와 애드혹 테스트를 더 이상 구분하지 않는다. 아래 표는 차터와 기록의 유무로 세션 기반 탐색과 기록 없는 수행을 구분한 것이다.

항목 탐색적 테스트(세션 기반) 애드혹 테스트(Ad hoc Testing)
목표 차터로 사전에 정함 정하지 않음

프로세스TC 작성 원칙처음 보는 사람이 따라 할 수 있고 수행 직후 통과와 실패를 판정할 수 있는 테스트 케이스의 작성 기준. TC 형식(단계형, BDD 시나리오, 체크리스트, 탐색적 테스트 차터)의 선택 기준, 구성 요소별 작성법, 리뷰 점검 항목을 다룬다.프로세스이슈 양식버그 이슈의 대표 양식(ISTQB 결함 보고서 항목, Bugzilla 요약·설명, GitHub 이슈 폼)과 선택 기준. 운영 예로 발견 블록과 종결 블록을 나눈 버그 양식과 작업(개선) 양식을 둔다.프로세스회귀 테스트 범위 선정변경 뒤 기존 기능이 의도하지 않게 실패하는지 확인하기 위해, 회귀 스위트에서 이번 회차에 수행할 TC를 선택하는 절차다(Regression Test Selection).
