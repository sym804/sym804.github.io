조합 테스트(페어와이즈)

파라미터가 여러 개일 때 모든 조합을 수행하지 않고, 임의의 두 파라미터 값 쌍이 모두 한 번 이상 포함되도록 테스트 집합을 구성하는 기법이다(Pairwise Testing). 두 파라미터를 넘는 상호작용까지 보장하는 기법은 t-way 조합 테스트라고 한다.

기본기난이도 중급최종 업데이트 2026-11-24

파라미터 4개에 값이 3개씩이면 전수 조합은 81개다. 모든 두 파라미터 값 쌍을 한 번 이상 포함하는 집합(2-way 커버링 배열)은 9행으로 구성할 수 있다. 파라미터와 값이 늘수록 두 수의 차이는 더 커진다.

절차

섹션 제목: “절차”
  1. 파라미터 도출: 결과에 영향을 줄 수 있는 독립 변수. 입력 항목, 설정, 실행 환경(OS, 브라우저, 표시 언어, 테마, 역할)
  2. 값 도출: 파라미터마다 동등 분할로 대표값을 선택함. 경계값이 필요하면 값으로 추가함
  3. 제약 조건 정의: 동시에 성립할 수 없는 값 쌍. 예: 특정 OS에서만 제공되는 브라우저
  4. 커버링 배열 생성: 조합 생성 도구에 파라미터, 값, 제약 조건을 입력해 생성함
  5. 보강: 리스크가 높은 조합과 셋 이상의 파라미터가 함께 관여하는 조합을 별도 행으로 추가함
  6. 행마다 기대 결과를 작성함

예: 화면 환경 조합

섹션 제목: “예: 화면 환경 조합”

파라미터 셋(브라우저, 테마, 표시 언어)이 값을 두 개씩 가지면 전수 조합은 8행이다. 아래 4행으로 세 파라미터 사이의 모든 값 쌍이 한 번씩 포함된다.

행 브라우저 테마 표시 언어
1 Chrome 라이트 한국어
2 Chrome 다크 영어
3 Firefox 라이트 영어
4 Firefox 다크 한국어
  • 브라우저와 테마, 브라우저와 언어, 테마와 언어 쌍이 각각 4가지씩 모두 포함됨
  • 세 값 조합 8가지 중 4가지(예: Chrome, 다크, 한국어)는 포함되지 않음. 세 값이 함께 있을 때만 발생하는 결함이 의심되면 보강 행으로 추가함

적용 예: 주문 결제 화면

섹션 제목: “적용 예: 주문 결제 화면”

요구사항이 “결제 수단은 카드, 계좌이체, 간편결제를 지원하고 쿠폰과 적립금을 함께 사용할 수 있다. PC와 모바일 웹에서 제공하며, 모바일 웹은 계좌이체를 제공하지 않는다.“인 경우 파라미터와 값은 다음과 같다.

  • 결제 수단: 카드, 계좌이체, 간편결제
  • 쿠폰: 없음, 정액(예: 4,000원), 정률(예: 10%)
  • 적립금: 미사용, 일부 사용(예: 3,000원)
  • 기기: PC, 모바일 웹
  • 제약 조건: 계좌이체와 모바일 웹은 함께 성립하지 않음

전수 조합 36개 중 제약 조건을 만족하는 조합은 30개이고, 값 쌍은 36개다. 제약 조건을 적용한 2-way 커버링 배열은 9행이다. 상품 금액이 50,000원이고 명세의 할인 순서가 “쿠폰 적용 뒤 적립금 차감”일 때 행마다 기대 결제 금액은 다음과 같다.

행 결제 수단 쿠폰 적립금 기기 기대 결제 금액
1 카드 없음 미사용 PC 50,000원
2 카드 정액 미사용 PC 46,000원
3 카드 정률 일부 모바일 웹 42,000원
4 계좌이체 없음 미사용 PC 50,000원
5 계좌이체 정액 일부 PC 43,000원
6 계좌이체 정률 미사용 PC 45,000원
7 간편결제 없음 일부 모바일 웹 47,000원
8 간편결제 정액 미사용 모바일 웹 46,000원
9 간편결제 정률 미사용 PC 45,000원
  • 쿠폰 종류마다 결제 금액이 달라지도록 금액을 정함. 정액 쿠폰을 5,000원으로 정하면 정률 10%와 같은 45,000원이 되어, 두 쿠폰의 할인 방식이 뒤바뀌어 적용되는 결함이 행 2, 6에서 드러나지 않음
  • 할인 순서를 반대로 구현하면 행 3의 결제 금액이 42,300원((50,000 - 3,000) x 0.9)이 되어 검출됨. 정액 쿠폰 행(행 5)은 순서와 무관하게 43,000원이라 검출되지 않음
  • 제약 조건은 커버링 배열에서 제외하는 것과 별도로 TC로 작성함. 모바일 웹에서 계좌이체가 표시되지 않고 API로 직접 요청해도 거부되는지 확인함
  • 만료 쿠폰, 보유액을 넘는 적립금 같은 무효 값은 아래 「무효 값과 마스킹」 기준에 따라 별도 TC로 작성함
  • 결제 취소 뒤 쿠폰과 적립금의 복원은 값의 조합이 아니라 수행 순서에 따라 결과가 달라지므로 상태 전이 테스트로 확인함

무효 값과 마스킹

섹션 제목: “무효 값과 마스킹”

입력을 거부하는 무효 값을 유효 조합 행에 섞으면, 그 행은 무효 값 때문에 앞 단계에서 거부된다. 같은 행에 담긴 나머지 값 쌍은 실제로 실행되지 않은 채 커버된 것으로 집계된다. 이를 마스킹(Masking)이라고 한다.

  • 무효 값은 별도 TC로 작성함. TC 하나에 무효 값 하나, 나머지 파라미터는 유효 값
  • 행이 BLOCK되거나 확인 지점 전에 실패하면 그 행에 담긴 값 쌍은 미검증으로 처리함. 결함 수정 뒤 그 행을 다시 수행함

규칙

  • 무효 값은 커버링 배열에 포함하지 않음
  • 생성된 행을 임의로 삭제하지 않음. 실행할 수 없는 행이 나오면 제약 조건을 추가하고 다시 생성함

TC 예시

섹션 제목: “TC 예시”
항목 TC 예시
커버링 배열 행 행 3 조건(카드, 정률 쿠폰 10%, 적립금 3,000원, 모바일 웹)으로 50,000원 상품을 결제해 결제 금액과 카드 승인 금액이 42,000원이고, 주문 상세에 쿠폰 할인 5,000원과 적립금 사용 3,000원이 표시되는지 확인함
제약 조건 모바일 웹 결제 화면의 결제 수단 목록에 계좌이체가 없고, 모바일 웹 세션에서 결제 API에 계좌이체를 지정해 요청하면 거부되고 주문이 생성되지 않는지 확인함
무효 값(TC 하나에 무효 값 하나) 카드, 적립금 미사용, PC 조건에서 만료된 쿠폰을 선택해 적용이 거부되고 안내 문구(예: “사용 기간이 지난 쿠폰입니다.”)가 표시되며 결제 금액이 50,000원으로 유지되는지 확인함
값으로 추가한 경계값 보유 적립금이 N(예: 3,000원)일 때 N-1, N을 입력하면 입력한 금액만큼 차감되고, N+1을 입력하면 거부되어 결제 금액이 변경되지 않는지 확인함
보강 행(t=3) 세 값이 함께 있을 때만 계산 경로가 달라지는 것으로 의심되는 조합(예: 간편결제, 정률 쿠폰, 적립금 일부)을 별도 행으로 수행해 결제 금액과 간편결제 승인 금액이 모두 42,000원인지 확인함
환경 값 적용 다크 테마 행을 수행하기 전에 테마 설정 메뉴에 다크가 선택되어 있고 화면 배경이 어두운 색으로 표시되는지 확인함. 적용되지 않았으면 그 행을 BLOCK으로 기록함

환경 값 적용 확인

섹션 제목: “환경 값 적용 확인”

행의 파라미터가 테마, 모션 감소, 표시 언어, JavaScript 사용 여부 같은 실행 환경이면 테스트 도구에 지정한 값이 실제 화면에 적용되지 않을 수 있다. 적용되지 않은 행은 다른 값으로 수행된 것이라 통과해도 그 행의 값 쌍을 확인한 근거가 되지 않는다.

  • 행을 수행하기 전에 환경 값이 적용되었는지 확인하는 절차를 둠. 자동화 테스트는 테스트 시작 시 적용 여부를 단언함
  • 앱이 운영체제나 브라우저 설정이 아니라 자체 저장 값(예: 로컬 스토리지)으로 테마나 언어를 정하면 브라우저 옵션만으로는 값이 변경되지 않음. 제품이 값을 읽는 위치를 먼저 확인함
  • 적용되지 않은 행은 PASS가 아니라 BLOCK으로 기록하고, 그 행의 값 쌍을 미검증으로 처리함
  • 운영체제가 파라미터이고 시각 회귀 베이스라인을 사용하면 베이스라인도 운영체제별로 관리함(시각 회귀 테스트)

현장 노트

  • 모션 감소 회귀 테스트에 Playwright test.use({ reducedMotion: "reduce" })를 지정했으나 해당 설정에서는 적용되지 않아 matchMedia 결과가 계속 no-preference였음. 테스트는 일반 모션 경로를 검사하며 통과함. page.emulateMedia()로 명시 적용하고, 테스트 시작 시 matchMedia 결과를 단언하도록 수정함
  • 테마를 localStorage의 값으로 정하는 앱에서 Playwright의 색 구성표 옵션으로는 다크 테마가 적용되지 않음. 페이지 로드 전에 실행되는 초기화 스크립트로 저장 값을 넣어 다크 테마를 적용함
  • 파일 상단에 test.use({ javaScriptEnabled: false })를 지정한 테스트 파일에서 browser.newContext()로 연 새 컨텍스트에도 그 옵션이 합쳐져 JavaScript가 꺼진 상태로 열림. 하이드레이션이 일어나지 않아 화면이 골격(스켈레톤) 상태로 남았고 테스트가 실패함. 같은 코드를 별도 파일로 옮기면 통과했음. 새 컨텍스트를 열 때 javaScriptEnabled를 명시하도록 수정함

테스트 계획, 결함 분류, 보고에 적용

섹션 제목: “테스트 계획, 결함 분류, 보고에 적용”

테스트 계획

  • 파라미터, 값, 값을 선택한 근거(동등 분할 클래스), 제약 조건, 상호작용 강도(t), 생성 도구와 버전, 생성된 행을 계획서에 기록함. 생성 도구가 무작위 시드를 사용하면 시드도 기록해 같은 행을 다시 생성할 수 있게 함
  • 전수 조합 수, 제약 조건 적용 후 조합 수, 생성 행 수를 함께 기록함. 예: 36개, 30개, 9행
  • 제외한 값과 그 근거를 기록함. 예: “태블릿은 모바일 웹과 같은 레이아웃을 사용해 같은 클래스로 묶음”
  • 보강 행은 추가 근거(리스크, 과거 결함)와 함께 커버링 배열 행과 구분해 기록함

결함 분류

  • 행이 실패하면 그 행의 값 쌍 중 PASS로 판정된 다른 행에도 포함된 쌍을 조사 우선순위에서 뒤로 미룸. 세 값 이상의 상호작용이나 간헐 실패가 있으면 같은 쌍을 포함한 행도 통과할 수 있어 확정 제외가 아님. 예: 행 3이 실패하고 행 7이 통과하면 (적립금 일부, 모바일 웹) 쌍이 뒤로 밀려 우선 조사할 후보가 6쌍에서 5쌍으로 줄어듦
  • 남은 후보 쌍 중 하나만 유지한 추가 행을 수행해 원인 조합을 좁힘. 예: (정률 쿠폰, 적립금 일부)만 유지한 행(간편결제, 정률, 일부, PC)도 실패하면 쿠폰과 적립금의 조합이 원인 후보로 남음
  • 이슈의 사전 조건과 재현 절차에는 좁힌 값 조합과 나머지 파라미터의 값을 기록하고, 결함에 관여한 파라미터 수를 함께 기록함
  • 관여한 파라미터가 셋 이상이면 t=2 배열로는 검출이 보장되지 않는 결함임. 다음 회차에 해당 파라미터의 t를 높이거나 보강 행을 추가함

보고

  • 쌍 커버리지는 생성한 행이 아니라 실제로 판정까지 수행한 행(PASS, FAIL)을 기준으로 집계함. BLOCK이나 조기 실패로 확인 지점에 도달하지 못한 행의 쌍은 미검증으로 기록함. 예: “값 쌍 36개 중 32개 확인. 행 5가 결제 대행사 테스트 환경 장애로 BLOCK되어 4쌍 미검증”
  • 상호작용 강도, 보강 행 수, 제외한 값을 함께 적어 “조합 테스트 완료”가 어느 범위를 뜻하는지 보고서에 남김

적용 범위와 한계

섹션 제목: “적용 범위와 한계”
  • 2-way 커버링 배열이 보장하는 것은 선택한 값 사이의 모든 쌍이 한 번 이상 포함된다는 조합 커버리지임. 결함 검출 자체는 보장하지 않음. 대표값 선택, 기대 결과가 부적절하면 결함을 놓침
  • 셋 이상의 파라미터가 함께 관여하는 결함은 상호작용 강도(t)를 높여 확인함. t를 높이면 행 수가 늘어남
  • 수행 순서나 이전 상태에 따라 결과가 달라지면 조합만으로는 부족함. 상태 전이 테스트와 함께 사용함
  • 조건 조합마다 동작이 명세로 정해진 업무 규칙은 결정 테이블 테스트로 모든 규칙을 확인함

흔한 실수

섹션 제목: “흔한 실수”
  • 도구 없이 조합 몇 개를 선택해 수행하고 페어와이즈로 기록함. 모든 쌍이 포함되었는지 확인할 근거가 없음
  • 제약 조건을 정의하지 않고 생성하면 실행할 수 없는 행이 발생하고, 그 행을 삭제하면서 다른 쌍까지 누락됨
  • 값을 동등 분할 없이 모두 나열해 행 수가 불필요하게 늘어남
  • 행마다 기대 결과를 작성하지 않고 “정상 표시”로 일괄 기록함

출처

섹션 제목: “출처”
  • NIST SP 800-142 Practical Combinatorial Testing, 2010
  • ISO/IEC/IEEE 29119-4:2021 테스트 기법
  • ISO 표준 원문은 유료이며 링크는 ISO 공식 안내 페이지임

관련 문서

테스트 설계동등 분할시스템이 똑같이 처리할 것으로 기대되는 입력을 한 묶음(동등 클래스)으로 보고, 묶음마다 대표값 하나만 테스트하는 기법이다(Equivalence Partitioning).테스트 설계결정 테이블 테스트여러 조건의 조합에 따라 동작이 달라지는 규칙을 표로 정리하고, 표의 열마다 테스트 케이스를 도출하는 기법이다(Decision Table Testing). 명세의 누락과 모순을 설계 단계에서 찾는 데도 사용한다.테스트 설계리스크 기반 테스트실패했을 때의 피해와 실패할 가능성을 기준으로 무엇을 먼저, 얼마나 깊게 테스트할지 정하는 방식이다(Risk-Based Testing).
