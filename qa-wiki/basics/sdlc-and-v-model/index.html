개발 수명주기와 V-모델

소프트웨어 개발 수명주기(SDLC) 모델의 분류와 모델 선택이 테스트에 주는 영향, V-모델의 개발 단계와 테스트 레벨 대응, 독일 연방 정부의 V-Modell XT, 의료기기·자동차 분야 공개 문서에서 확인되는 범위를 정리한다.

기본기난이도 기초최종 업데이트 2026-11-24

SDLC, V모델, V-model, 개발 생명주기

소프트웨어 개발 수명주기(SDLC, Software Development Lifecycle)는 소프트웨어 개발의 각 단계에서 수행하는 활동과, 그 활동들이 논리적·시간적으로 맺는 관계를 말한다(ISTQB 용어집). SDLC 모델은 이 과정을 추상화한 상위 수준의 표현이며, 개발 단계와 활동 유형의 관계를 정의한다(ISTQB CTFL v4.0.1 2.1). 선택한 모델에 따라 테스트를 언제, 얼마나 문서화해, 어떤 기법으로 수행할지가 달라진다. 테스트 레벨 각각의 정의와 TC 예시는 테스트 레벨과 테스트 유형에 있고, 이 문서는 수명주기 모델과 테스트 활동의 관계를 다룬다.

정의

섹션 제목: “정의”
용어 ISTQB 용어집 다른 출처
SDLC 개발의 각 단계에서 수행하는 활동과, 활동 사이의 논리적·시간적 관계. 동의어 lifecycle model SWEBOK v4.0a 10장: 표준이 정한 활동을 선택한 수명주기 모델(SLCM)에 대응시켜 만든 프로젝트별 활동 순서(ISO/IEC/IEEE 24765 인용)
순차형 개발 모델 시스템 전체를 서로 겹치지 않고 이어지는 여러 단계로 선형 개발하는 모델 SWEBOK이 인용한 24765의 폭포수 모델: 개념, 요구사항, 설계, 구현, 테스트, 설치·점검 단계를 차례로 수행하고, 단계가 겹칠 수는 있지만 반복은 거의 없음
반복형 개발 모델 반복되는 주기를 거듭하며 개발하는 모델 SWEBOK(PMBOK 인용): 범위는 초기에 정하고 시간·비용 추정은 이해가 깊어질 때마다 수정함
점진형 개발 모델 일련의 증분(Increment)으로 개발하는 모델 SWEBOK(PMBOK 인용): 정해진 기간 안에 반복마다 기능을 추가하고, 마지막 반복 뒤에 완성으로 간주함. 예측형일 수도 있음
V-모델 비즈니스 요구사항 명세부터 인도까지의 주요 개발 단계와, 인수 테스트부터 컴포넌트 테스트까지의 테스트 레벨을 일대일로 대응시킨 순차형 SDLC 모델 SWEBOK: 폭포수 모델의 변형·확장 중 하나이며, 이름과 세부가 다른 변형이 많음

출처마다 다른 점

  • 순차형의 단계 겹침: 용어집은 “겹침 없음”, 24765의 폭포수 정의는 “겹칠 수 있음”으로 씀. 반복이 거의 없다는 점은 같음
  • 애자일의 위치: CTFL 2.1은 모델 분류를 순차형, 반복형, 점진형 셋으로 두고, 애자일은 ATDD, BDD, DDD, XP, FDD, Kanban, Lean IT, Scrum, TDD와 함께 “더 상세한 개발 방법과 애자일 실천”으로 분류함. SWEBOK 10장은 애자일 모델을 잘 알려진 수명주기 모델의 예로 들면서도, 애자일 자체를 하나의 방법으로 보는 것은 오해라고 씀
  • 예측형(Predictive) 분류: SWEBOK은 폭포수 모델을 예측형 수명주기의 예로 들고, 예측형을 범위·시간·비용을 초기에 정하며 요구사항 집합이 크게 바뀌지 않는다고 가정하는 수명주기로 정의함

SDLC 모델 분류

섹션 제목: “SDLC 모델 분류”
분류 예(CTFL 2.1) 특징 동적 테스트 시점
순차형 폭포수, V-모델 앞 단계가 끝나야 다음 단계를 시작함. 폭포수는 문서 중심(SWEBOK) 실행 가능한 코드가 후반에 나오므로 늦게 시작함
반복형 나선형, 프로토타이핑 주기를 반복함. 나선형은 리스크 주도(SWEBOK) 반복마다
점진형 통합 프로세스(UP) 증분마다 기능을 추가함. UP는 반복형이면서 점진형인 프레임워크(SWEBOK) 증분마다
애자일 방법·실천 Scrum, XP, Kanban 프로젝트 전체에서 변경이 일어난다고 가정함 반복마다. 회귀 테스트를 쉽게 하도록 광범위한 테스트 자동화를 선호함

모델 선택이 테스트에 주는 영향

섹션 제목: “모델 선택이 테스트에 주는 영향”

CTFL 2.1.1은 테스트를 SDLC에 맞춰야 성공한다고 보고, 모델 선택이 다음 다섯 가지를 바꾼다고 정리한다.

  • 테스트 활동의 범위와 시점(테스트 레벨, 테스트 유형)
  • 테스트 문서의 상세 수준
  • 테스트 기법과 테스트 접근법
  • 테스트 자동화의 범위
  • 테스터의 역할과 책임
관점 순차형 반복형·점진형 애자일
테스터의 초기 참여 요구사항 리뷰, 테스트 분석, 테스트 설계 반복마다 정적 테스트와 동적 테스트 반복마다 정적 테스트와 동적 테스트
동적 테스트 후반에 시작 반복마다 모든 테스트 레벨에서 수행 가능 반복마다 수행
회귀 테스트 2.1.1에 언급 없음 잦은 인도로 빠른 피드백과 광범위한 회귀 테스트가 필요함 회귀를 쉽게 하려고 자동화를 넓게 적용함
문서 2.1.1에 언급 없음. 폭포수는 문서 중심(SWEBOK) 2.1.1에 언급 없음 가벼운 작업 산출물 문서
수동 테스트 2.1.1에 언급 없음 2.1.1에 언급 없음 사전 분석·설계가 적게 드는 경험 기반 기법 위주

모델과 무관한 좋은 테스트 관행

섹션 제목: “모델과 무관한 좋은 테스트 관행”

CTFL 2.1.2는 어떤 모델에도 적용되는 관행 네 가지를 각각의 목적과 함께 제시한다.

관행 목적
모든 개발 활동에 대응하는 테스트 활동을 둠 모든 개발 활동을 품질 관리 대상으로 둠
테스트 레벨마다 목적을 다르게 정함 중복 없이 충분한 범위를 테스트함
각 테스트 레벨의 분석과 설계를 대응하는 개발 단계에서 시작함 조기 테스팅 원칙을 따름
작업 산출물 초안이 나오는 즉시 리뷰에 참여함 결함을 일찍 발견해 시프트 레프트를 지원함

테스트 주도 방식

섹션 제목: “테스트 주도 방식”

CTFL 2.1.3은 TDD, ATDD, BDD를 테스트로 개발을 이끄는 비슷한 방식으로 묶는다. 세 방식 모두 코드 작성 전에 테스트를 정의하므로 조기 테스팅과 시프트 레프트를 따르고, 반복형 개발 모델을 지원하며, 작성한 테스트는 자동화 테스트로 남아 이후 변경과 리팩터링에서 코드 품질을 확인하는 데 사용된다.

방식 핵심 실라버스 인용 문헌
TDD(테스트 주도 개발) 상세한 설계 대신 TC로 코딩을 이끎. 테스트 작성, 테스트를 통과하는 코드 작성, 테스트와 코드 리팩터링 순서 Beck 2003
ATDD(인수 테스트 주도 개발) 시스템 설계 과정에서 인수 기준으로부터 테스트를 도출하고, 해당 부분을 개발하기 전에 작성함 Gärtner 2011
BDD(행위 주도 개발) 원하는 동작을 이해관계자가 읽을 수 있는 자연어(주로 Given/When/Then)로 TC에 표현하고, 실행 가능한 테스트로 변환함 Chelimsky 2010

DevOps와 테스트

섹션 제목: “DevOps와 테스트”

DevOps는 개발(테스트 포함)과 운영이 공동 목표를 위해 함께 일하도록 하는 조직 접근법이다. 팀 자율성, 빠른 피드백, 통합된 도구 체인, CI(지속적 통합)와 CD(지속적 인도) 같은 기술 실천을 장려하고, 조직 문화의 변화를 요구한다(CTFL 2.1.4).

테스트 관점의 이점

  • 코드 품질과 기존 코드 영향에 대한 빠른 피드백
  • CI가 컴포넌트 테스트와 정적 분석을 함께 제출하도록 유도해 시프트 레프트를 촉진함
  • 자동화된 프로세스로 안정적인 테스트 환경 확보
  • 성능 효율성, 신뢰성 같은 비기능 특성의 가시성 향상
  • 파이프라인 자동화로 반복 수동 테스트 감소
  • 자동화 회귀 테스트의 규모로 회귀 리스크 최소화

리스크와 과제

  • 인도 파이프라인을 정의하고 구축해야 함
  • CI/CD 도구를 도입하고 유지해야 함
  • 테스트 자동화에 추가 자원이 들고 구축과 유지가 어려울 수 있음

자동화 비중이 높아도 사용자 관점의 수동 테스트는 여전히 필요하다.

시프트 레프트

섹션 제목: “시프트 레프트”

용어집은 시프트 레프트(Shift Left)를 “SDLC에서 테스트와 품질 보증 활동을 가능한 한 일찍 수행하는 테스트 접근법”으로 정의한다. CTFL 2.1.5는 이를 조기 테스팅 원칙의 다른 이름으로 설명하며, 뒤 단계의 테스트를 소홀히 해도 된다는 뜻은 아니라고 덧붙인다. 실천 방법은 다음과 같다.

  • 테스터 관점에서 명세를 리뷰함. 모호함, 불완전함, 불일치 같은 잠재 결함을 찾음
  • 코드 작성 전에 TC를 작성하고, 구현 중 테스트 하네스에서 코드를 실행함
  • CI와 CD로 빠른 피드백을 받고, 코드 저장소에 제출할 때 자동화 컴포넌트 테스트를 함께 실행함
  • 동적 테스트 전이나 자동화 프로세스 안에서 소스 코드 정적 분석을 수행함
  • 가능하면 컴포넌트 테스트 레벨부터 비기능 테스트를 수행함

시프트 레프트는 초기에 교육, 노력, 비용을 더 들이고 뒤 단계의 노력과 비용을 줄이는 방식이라 이해관계자의 동의가 필요하다. SWEBOK 5장(6.1.2)은 애자일, DevOps, TDD를 시프트 레프트 흐름에 속하는 수명주기로 들고, 2000년대 초의 통합 프로세스(UP)를 그 선행 모델로 본다.

회고

섹션 제목: “회고”

회고는 프로젝트나 반복의 끝, 릴리즈 마일스톤, 또는 필요할 때 연다. 시점과 진행 방식은 따르는 SDLC 모델에 따라 정한다. 테스터뿐 아니라 개발자, 아키텍트, 제품 책임자, 비즈니스 분석가가 참여해 잘된 점과 유지할 점, 개선할 점, 개선을 반영하고 성공을 유지하는 방법을 논의한다. 결과는 기록해 보통 테스트 완료 보고서에 포함하고, 권고한 개선 항목은 후속 조치를 확인한다(CTFL 2.1.6).

테스트 측면의 이점

  • 프로세스 개선 제안 반영으로 테스트 효과성과 효율성 향상
  • 테스트 프로세스 공동 리뷰로 테스트웨어 품질 향상
  • 문제 제기와 개선 제안 기회로 팀 결속과 학습
  • 요구사항의 범위와 품질 문제 해결로 테스트 베이시스 품질 향상
  • 협업 방식의 정기 점검으로 개발과 테스트의 협력 향상

V-모델의 구조

섹션 제목: “V-모델의 구조”

V-모델은 왼쪽 가지에서 요구사항을 점점 상세한 설계로 분해하고, 오른쪽 가지에서 구현한 부분을 통합하며 테스트한다. V-Modell XT 2.4도 왼쪽 가지에서 단계별로 분해하며 명세하고, 수평 단계마다 시스템 요소가 명세에 맞는지 확인하는 구조로 설명한다(아래 「V-Modell XT」 절). 아래 그림과 표는 단계를 다섯으로 나눈 대응이다.

왼쪽 개발 단계 산출물(대응 테스트의 테스트 베이시스) 오른쪽 테스트 레벨
요구사항 정의 비즈니스·사용자 요구사항, 인수 기준 인수 테스트
시스템 설계 시스템 요구사항 명세, 기능·비기능 명세 시스템 테스트
아키텍처 설계 아키텍처, 컴포넌트 사이와 외부 시스템과의 인터페이스 명세 통합 테스트(컴포넌트 통합, 시스템 통합)
상세 설계(모듈 설계) 모듈 명세, 상세 설계 컴포넌트 테스트
구현 소스 코드 V의 꼭짓점. 코드 리뷰와 정적 분석 대상
  • 단계 이름과 개수는 출처마다 다름. 용어집은 양 끝(비즈니스 요구사항 명세와 인수 테스트, 그리고 컴포넌트 테스트)만 정하고, SWEBOK은 이름과 세부가 다른 변형이 많다고 씀
  • 가운데 단계의 대응도 출처마다 다름. FDA 지침은 시스템 테스트 계획과 인수 테스트 계획을 요구사항 단계에, 모듈 테스트 계획과 통합 테스트 계획을 설계 단계에 둠(아래 표). V-Modell XT는 수준을 넷으로 나눔(V-Modell XT 절)
  • CTFL v4.0.1의 테스트 레벨은 다섯임. 위 표는 컴포넌트 통합과 시스템 통합을 아키텍처 설계 단계에 함께 대응시킴

산출물이 테스트 베이시스가 됨

섹션 제목: “산출물이 테스트 베이시스가 됨”

테스트 베이시스(Test Basis)는 테스트 분석과 테스트 설계의 근거가 되는 지식이다(용어집). V-모델에서는 왼쪽 단계의 산출물이 같은 높이에 있는 테스트 레벨의 테스트 베이시스가 된다. V-Modell XT 2.4는 테스트 명세(Prüfspezifikation)를 왼쪽 가지에서 요구사항, 명세, 아키텍처로부터 도출하고, 테스트 기록(Prüfprotokoll)을 오른쪽 가지에서 실제 테스트 대상별로 남긴다고 정한다. FDA 지침(5.2.3, 5.2.4)도 설계 명세와 요구사항 사이, TC와 설계 명세·소스 코드 사이의 추적성 분석을 전형적인 작업으로 든다.

테스트 설계는 왼쪽에서 시작함

섹션 제목: “테스트 설계는 왼쪽에서 시작함”

동적 테스트 실행은 오른쪽 가지에서 일어나지만, 각 레벨의 테스트 분석과 설계는 대응하는 왼쪽 단계에서 시작한다(CTFL 2.1.2). FDA 지침은 같은 순서를 작업 목록으로 적는다.

수명주기 활동(FDA 5.2) 테스트 관련 전형적 작업
요구사항(5.2.2) 시스템 테스트 계획 작성, 인수 테스트 계획 작성, 모호성 리뷰
설계(5.2.3) 모듈 테스트 계획 작성, 통합 테스트 계획 작성, 모듈·통합·시스템·인수 테스트 설계
구현(5.2.4) 모듈·통합·시스템·인수 테스트 절차와 TC 작성
개발자 테스트(5.2.5) 테스트 계획과 TC는 개발 과정에서 가능한 한 일찍 작성함

순차형 모델에서는 한 테스트 레벨의 종료 기준을 다음 레벨의 진입 기준에 포함하는 경우가 많다. 반복형 모델에서는 이 연결이 적용되지 않을 수 있고, 테스트 레벨이 시간상 겹칠 수 있다(CTFL 2.2).

V-Modell XT

섹션 제목: “V-Modell XT”

V-Modell XT는 시스템 개발 프로젝트를 계획하고 수행하기 위한 독일의 프로세스 모델(Vorgehensmodell)이다. 공개 문서로 확인한 사항은 다음과 같다.

항목 V-Modell XT V-Modell XT Bund
대상 발주자, 수주자, 자체 개발 프로젝트 연방 행정기관의 발주자 측 프로젝트와 자체 소프트웨어 개발. 하드웨어 개발은 제외
발행 WEIT e.V.(V-Modell XT 발전 협회) 연방 정보기술 책임자의 위임을 받아 연방 IT 센터(ITZBund)가 발행
최신 판 2.4(2024-05-24 발표) 2.4(2024-05-24 발표)
라이선스 Apache License 2.0. 문서는 독일어 Apache License 2.0. 문서는 독일어
  • WEIT e.V.는 V-Modell XT를 V-Modell 97의 후속 모델로 소개함
  • 산출물(Produkt) 중심 모델임. 산출물마다 책임 역할을 하나씩 두고, 결정 지점(Entscheidungspunkt)마다 정해진 산출물로 진행 여부를 판단함. 결정 지점은 품질 게이트(Quality Gate)에 해당함

  • 개발 주기를 여러 번 거치는 반복 진행을 전제로 함
  • V-Modell XT 2.4 문서는 V자형 진행을 Barry Boehm이 1970년대 말에 처음 기술했다고 설명함

원칙 내용
명세와 분해 왼쪽 가지에서 전체 시스템을 모듈 수준까지 단계별로 분해하며 상세하게 명세함

V-Modell XT Bund 2.4는 Scrum 기반의 소프트웨어 개발 절차(B.2.2.6)를 포함하고, 결정 지점에 스프린트 시작과 스프린트 종료를 둔다. 애자일 방법을 적용하면 반복 대신 스프린트 단위로 수주자를 관리하고 “반복 계획 완료” 결정 지점은 사용하지 않는다(B.1.3.3).

한계와 선택 기준

섹션 제목: “한계와 선택 기준”

V-모델은 순차형이므로 순차형의 전제를 그대로 가진다.

  • 요구사항 변경: SWEBOK의 예측형 수명주기는 요구사항 집합이 크게 바뀌지 않는다고 가정함. 왼쪽 산출물이 테스트 베이시스이므로 요구사항이 바뀌면 그 산출물에서 도출한 테스트 설계도 함께 바뀜
  • 동적 테스트 시점: 실행 가능한 코드가 후반에 나와 동적 테스트를 일찍 수행하기 어려움(CTFL 2.1.1)
  • 반복이 거의 없는 고전 형태의 한계를 V-Modell XT는 V를 여러 번 거치는 반복과 증분으로 보완함
판단 기준 순차형(V-모델) 반복형·점진형 애자일
요구사항 초기에 확정하고 크게 바뀌지 않는다고 가정함 반복형은 범위를 대체로 초기에 정하고 추정을 갱신함. 점진형은 기능을 차례로 추가하며 예측형으로도 운영할 수 있음 프로젝트 전체에서 변경을 가정함
인도 마지막에 한 번 인도하는 형태가 많음(SWEBOK) 반복·증분마다 동작하는 결과물 짧은 주기의 작은 증분
동적 테스트 후반에 시작함 반복·증분마다 반복마다
회귀 테스트 2.1.1에 언급 없음 잦은 인도로 광범위하게 필요함 넓은 자동화로 수행함

SWEBOK 10장은 폭포수와 애자일의 우열 논쟁을 역사적 맥락에서 이해해야 하며 근거가 되는 실증 측정이 부족했다고 쓰고, 프로젝트마다 특성과 이해관계자 요구에 맞춰 수명주기를 조정(Adaptation)하라고 권한다(2.5, 2.8). 위 표는 모델 하나를 고르는 기준표로 쓰기보다, 프로젝트가 어떤 전제 위에 있는지 확인하는 용도로 사용한다.

규제 분야 문서에서 확인되는 범위

섹션 제목: “규제 분야 문서에서 확인되는 범위”

규제 분야에서 V-모델이 쓰인다는 주장은 공개 1차 자료로 다음 범위까지만 확인된다.

  • 의료기기(FDA): General Principles of Software Validation(2002-01-11 최종 지침)은 특정 수명주기 모델을 권고하지 않는다고 명시함(4.4, 5.1). 요구하는 것은 제품과 조직에 맞는 모델을 정해 탄생부터 폐기까지 적용하는 것(5.1), 테스트 계획과 TC를 가능한 한 일찍 작성하는 것(5.2.5), 변경 뒤 영향 분석과 회귀 테스트를 수행하는 것(4.7), 확인(Validation) 활동의 범위를 소프트웨어 복잡도와 안전 리스크에 맞추는 것(4.8)임. 2026-11 기준 이 지침의 6절은 2025-09-24 발행된 Computer Software Assurance 지침으로 대체되었고 나머지 절은 유효함
  • 자동차(ISTQB CT-AuT v2.1, 2025-04-30): MiL 테스트 환경을 V-모델 왼쪽의 기술 시스템 설계 검증에, SiL을 오른쪽의 컴포넌트·통합 테스트에, HiL을 시스템 테스트에 배치함(3.2.4.3). ASPICE는 이해관계자 요구사항부터 소프트웨어 단위까지의 수직 추적성과, 개발 산출물과 테스트 명세·결과 사이의 수평 추적성을 모두 양방향으로 요구함(2.1.2.6)

같은 실라버스는 CTFL의 테스트 레벨을 ISO 26262:2018, ASPICE 4.0의 테스트 레벨과 다음과 같이 대응시킨다(2.4.2). ISO 26262와 ASPICE의 “시스템”은 하드웨어와 소프트웨어를 포함하고, CTFL의 “시스템”은 소프트웨어만 가리킨다는 차이가 있다.

자주 혼동하는 점

섹션 제목: “자주 혼동하는 점”
  • V-모델을 “개발이 끝난 뒤 테스트하는 모델”로 봄. 동적 테스트 실행은 늦지만 테스트 분석과 설계는 대응하는 왼쪽 단계에서 시작함
  • 테스트 레벨을 V-모델에만 있는 개념으로 봄. SWEBOK 5장(2.1)은 단위, 통합, 시스템, 인수의 네 단계가 특정 개발 프로세스를 전제하지 않는다고 씀. 반복형과 점진형에서도 반복마다 모든 테스트 레벨에서 정적·동적 테스트를 수행할 수 있음(CTFL 2.1.1)
  • V-Modell XT를 고전 V-모델과 같은 것으로 봄. V-Modell XT는 반복 진행을 전제로 하고, 테일러링과 결정 지점을 두며, Scrum 절차를 포함함
  • 애자일을 문서를 쓰지 않는 방식으로 봄. SWEBOK 10장은 애자일 선언이 문서가 필요 없다고 말하지 않으며, 문서를 만들지 않아 폭포수보다 빠르다는 생각을 오해로 듦
  • 규제 분야라면 V-모델이 필수라고 봄. FDA 지침은 특정 모델을 권고하지 않음

QA에서 적용

섹션 제목: “QA에서 적용”
  • 테스트 계획서에 프로젝트의 수명주기 모델을 적고, CTFL 2.1.1의 다섯 항목(범위와 시점, 문서 수준, 기법, 자동화 범위, 테스터 역할)을 그 모델에 맞춰 정함
  • 요구사항 초안이 나오면 리뷰에 참여해 인수 테스트 조건을 먼저 작성하고, 설계 문서가 나올 때마다 대응하는 레벨의 테스트 설계를 시작함. TC로 옮기지 못하는 문장은 명세의 모호함으로 기록함(TC 작성 원칙, 테스팅의 7원칙)
  • 요구사항, 설계, TC, 실행 결과를 서로 연결해 둠. 변경 요청이 오면 연결된 TC를 영향 범위로 사용함(회귀 테스트 범위 선정, 형상관리 기본)
  • 순차형 프로젝트에서는 레벨마다 진입·종료 기준을 정하고, 앞 레벨의 종료 기준을 다음 레벨의 진입 기준에 포함함(ISTQB CTFL 실라버스 핵심 정리)
  • 반복형·애자일 프로젝트에서는 반복마다 모든 레벨의 테스트를 계획하고, 회귀 테스트를 CI 파이프라인에서 자동 실행함(테스트 자동화 기본, GitHub Actions)
  • 오른쪽 각 레벨의 결과를 왼쪽 산출물 대비 검증과 사용자 목적 대비 확인으로 나눠 보고함(검증과 확인)
  • 회고 결과와 개선 항목을 테스트 완료 보고서에 기록하고 다음 반복에서 후속 조치를 확인함

관련 문서

기초와 용어ISTQB CTFL 실라버스 핵심 정리ISTQB Certified Tester Foundation Level 실라버스 v4.0.1의 6개 장(테스팅 기초, 개발 수명주기와 테스팅, 정적 테스트, 테스트 분석과 설계, 테스트 활동 관리, 테스트 도구) 핵심 개념. 개념마다 실무에 적용한 위키 문서를 연결한다.기초와 용어테스트 레벨과 테스트 유형테스트 레벨은 시스템을 어느 통합 단계에서 검증하는지를, 테스트 유형은 어떤 품질 특성을 검증하는지를 나타내는 분류다. 두 분류는 서로 독립이며, 테스트마다 레벨을 하나 정하고 테스트 유형은 하나 이상 적용할 수 있다.기초와 용어검증과 확인(V&V)검증(Verification)은 산출물이 명세를 충족하는지, 확인(Validation)은 제품이 사용자의 필요와 의도된 사용에 맞는지를 판정하는 활동이다. ISTQB, SWEBOK, FDA, NASA의 정의를 비교하고 정적·동적 V&V, 수명주기 단계별 활동, 독립 V&V(IV&V)를 정리한다.프로세스회귀 테스트 범위 선정변경 뒤 기존 기능이 의도하지 않게 실패하는지 확인하기 위해, 회귀 스위트에서 이번 회차에 수행할 TC를 선택하는 절차다(Regression Test Selection).
