용어 사전

이 위키에서 사용하는 QA 용어의 영문 표기와 뜻. 혼동하기 쉬운 용어 쌍과 팀에서 용어를 맞추는 방법을 함께 둔다.

기본기난이도 기초최종 업데이트 2026-11-24

이 위키에서 실제로 사용하는 용어만 수록한다. 정의는 ISTQB 용어와 각 표준을 기준으로 하되, 위키 안에서 좁혀 쓰는 뜻이 있으면 그 뜻을 함께 적는다. 용어마다 자세히 다루는 문서를 연결했다.

결함과 이슈

섹션 제목: “결함과 이슈”
용어 뜻
오류
Error, Mistake		 결함을 만든 사람의 실수. 요구사항 오해, 코드 작성 실수 등
결함
Defect, Bug		 요구사항이나 명세와 다르게 만들어진 작업 산출물의 문제. 코드뿐 아니라 문서와 설정에도 있음
장애
Failure		 결함이 실행되어 시스템이 기대와 다르게 동작한 현상. 이 위키에서는 테스트 환경이 동작하지 않는 상태(환경 장애)에도 사용함
심각도
Severity		 결함이 사용자와 제품에 미치는 영향의 크기
등급: Blocker, Critical, Major, Minor, Trivial(심각도 기준)
우선순위
Priority		 결함의 수정 시점과 TC의 수행 순서를 정하는 기준
심각도와 별개의 축(TC 작성 원칙)
재현 빈도
Reproducibility		 결함이 재현되는 정도
항상, 간헐, 1회만 관측, 미확인 중 하나(이슈 양식)
결함 생명주기
Defect Lifecycle		 결함이 등록부터 종결까지 거치는 상태와 전이 규칙(결함 생명주기)
보류
Deferred		 이번 릴리즈에서 수정하지 않기로 합의한 상태. 종결이 아니라 미해결로 집계함
재현 불가
Cannot Reproduce		 기록된 절차와 조건으로 재현되지 않아 원인을 확인할 수 없는 상태. 증거를 확인한 뒤에만 판정함
운영 유출 결함
Escaped Defect		 테스트를 거쳐 운영 환경에서 발견된 결함. 어느 테스트 범위에 있었는지 함께 기록함
근본 원인 분석
Root Cause Analysis, RCA		 증상이 아니라 결함이 생긴 원인과 놓친 원인을 찾는 분석
이슈 로그
Issue Log		 이슈 트래커(GitHub Issues, Linear 등)와 별도로 프로젝트에서 관리하는 이슈 기록
트래커와 1:1로 연결
조인 키
Join Key		 이슈 로그의 행과 트래커의 이슈를 연결하는 식별자(이슈 로그와 트래커의 조인 키)

테스트 레벨, 유형, 품질 표준

섹션 제목: “테스트 레벨, 유형, 품질 표준”
용어 뜻
테스트 레벨
Test Level		 테스트 대상의 범위로 나눈 단계. 컴포넌트, 컴포넌트 통합, 시스템, 시스템 통합, 인수(테스트 레벨과 테스트 유형)
테스트 유형
Test Type		 확인하려는 품질 특성(기능, 비기능)이나 설계 근거(블랙박스, 화이트박스)로 나눈 분류. 모든 레벨에서 수행할 수 있음
인수 테스트
Acceptance Testing		 사용자나 운영 관점에서 출시 가능 여부를 판단하는 테스트
확인 테스트
Confirmation Testing		 결함을 수정한 뒤 그 결함의 재현 절차를 다시 수행해 수정을 확인하는 테스트. 재테스트(Re-testing)라고도 함
회귀
Regression		 정상 동작하던 기능이 다른 변경의 영향으로 실패하는 현상
회귀 테스트
Regression Testing		 변경한 영역을 포함해 기존 동작에 의도하지 않은 영향이 없는지 확인하는 테스트(회귀 테스트 범위 선정)
스모크 테스트
Smoke Testing		 배포 직후나 대규모 변경 뒤 주요 기능이 기본적으로 동작하는지 짧게 확인하는 테스트
탐색적 테스트
Exploratory Testing		 테스트 대상을 학습하면서 설계, 실행, 결과 평가를 동시에 진행하는 경험 기반 기법(탐색적 테스트와 세션 기반 테스트 관리)
품질 특성
Quality Characteristic		 품질을 나누는 관점. ISO/IEC 25010:2023은 9개 특성과 부특성으로 구성됨(ISO/IEC 25010 품질 모델)
부특성
Subcharacteristic		 품질 특성을 측정할 수 있는 단위로 나눈 하위 항목
ISO/IEC/IEEE 29119 테스트 프로세스, 문서, 기법을 정한 국제 표준 묶음(ISO/IEC/IEEE 29119 테스트 표준)
WCAG Web Content Accessibility Guidelines. 웹 접근성 기준. 적합성 수준 A, AA, AAA(접근성 테스트 기본)
요구사항 추적성
Traceability		 요구사항, TC, 결함, 수행 결과를 서로 연결해 추적할 수 있는 성질. 표로 정리하면 RTM
테스트 베이시스
Test Basis		 테스트 분석과 설계의 근거가 되는 정보. 요구사항, 사용자 스토리, 설계 문서, 코드 등
검증
Verification		 산출물이 명세된 요구사항을 만족하는지 확인하는 것. “명세대로 만들었는가”
확인
Validation		 시스템이 운영 환경에서 사용자와 이해관계자의 필요를 만족하는지 확인하는 것. “맞는 것을 만들었는가”. 결함 수정을 확인하는 확인 테스트(Confirmation Testing)와는 다른 용어
정적 테스트
Static Testing		 소프트웨어를 실행하지 않고 리뷰나 정적 분석으로 산출물을 평가하는 테스트. 결함을 직접 찾음(ISTQB CTFL 실라버스 핵심 정리)
동적 테스트
Dynamic Testing		 소프트웨어를 실행해 장애를 일으키고 분석으로 결함을 찾는 테스트
리뷰 유형
Review Types		 형식 수준에 따라 비공식 리뷰, 워크스루(작성자 주도), 기술 리뷰(중재자 주도), 인스펙션(가장 형식적, 지표 수집)으로 나뉨
블랙박스 테스트
Black-box Testing		 명세 기반 테스트. 내부 구조와 무관한 문서에서 테스트를 도출하고 동작이 명세와 일치하는지 확인함(테스트 기법 분류)
화이트박스 테스트
White-box Testing		 구조 기반 테스트. 코드, 아키텍처, 워크플로, 데이터 흐름 같은 내부 구조에서 테스트를 도출하고 그 구조를 커버하는 것이 목적임
시프트 레프트
Shift Left		 테스트를 개발 수명주기의 더 이른 시점에 수행하는 접근법. 명세 리뷰, 코드 전 TC 작성, CI, 정적 분석 등
유지보수 테스트
Maintenance Testing		 운영 중인 시스템의 수정, 환경 이전, 폐기에 따른 변경을 테스트함
진입 기준과 종료 기준
Entry / Exit Criteria		 활동을 시작하기 위한 사전 조건과 완료를 선언하기 위한 조건. 애자일에서는 준비 정의(DoR)와 완료 정의(DoD)

테스트 설계

섹션 제목: “테스트 설계”
용어 뜻
테스트 케이스
Test Case, TC		 사전조건, 절차, 기대 결과로 구성된 확인 단위
사전조건
Precondition		 절차를 시작하기 전에 갖춰져 있어야 하는 상태
기대 결과
Expected Result		 정해진 사전조건과 입력에서 테스트 대상이 명세대로 동작했을 때 관측되어야 하는 결과. 거부 응답과 오류 문구, API 응답, 저장 값도 포함함. 화면 TC는 사용자가 보는 동작으로 작성함
테스트 오라클
Test Oracle		 실제 결과가 맞는지 판정하는 근거. 명세, 계산 결과, 이전 버전 결과 등
커버리지
Coverage		 커버리지 항목 중 테스트로 수행한 항목의 비율
커버리지 항목
Coverage Item		 기법이 정한 측정 단위. 동등 분할의 클래스, 경계값, 결정 테이블의 열, 상태 전이의 전이 등
동등 분할
Equivalence Partitioning		 같은 방식으로 처리될 것으로 기대되는 값(입력, 출력, 설정)을 클래스로 나누고 클래스마다 대표값을 테스트하는 기법(동등 분할)
경계값 분석
Boundary Value Analysis		 동등 분할의 경계값(각 분할의 최솟값과 최댓값)과 그 이웃 값을 테스트하는 기법. 2값 방식과 3값 방식이 있음(경계값 분석)
결정 테이블 테스트
Decision Table Testing		 조건 조합과 동작을 표로 정리해 열마다 TC를 도출하는 기법. 동작에 영향을 주지 않는 조건은 무관 기호(-)로 병합함(결정 테이블 테스트)
상태 전이 테스트
State Transition Testing		 상태와 사건을 정리한 표로 허용된 전이와 차단되어야 하는 전이를 테스트하는 기법(상태 전이 테스트)
조합 테스트(페어와이즈)
Pairwise Testing		 임의의 두 파라미터 값 쌍이 적어도 한 번 함께 나오도록 조합 수를 줄이는 2-way 조합 테스트 기법. 생성한 조합 표를 커버링 배열(Covering Array)이라고 함(조합 테스트(페어와이즈))
리스크 기반 테스트
Risk-Based Testing		 영향과 가능성으로 테스트의 순서와 깊이를 결정하는 방식(리스크 기반 테스트)
차터
Charter		 탐색적 테스트 세션의 대상, 수단, 찾을 정보를 한 문장으로 정한 것. 세션 시간 상한(타임박스)과 함께 정함
디브리핑
Debriefing		 탐색 세션이 끝난 뒤 기록을 검토해 결함, 질문, 다음 차터를 정리하는 단계
메타모픽 테스트
Metamorphic Testing		 정답을 알 수 없을 때 입력 변형과 출력 사이의 관계로 판정하는 기법. 예: 조건 순서를 변경해도 같은 필터가 나와야 함
거짓 PASS
False Pass		 기능이 동작하지 않는데 테스트가 PASS로 판정되는 현상
구문 커버리지
Statement Coverage		 테스트로 실행한 구문 수 / 실행 가능한 구문 수. 100%여도 모든 판단 결과를 확인한 것은 아님
분기 커버리지
Branch Coverage		 테스트로 수행한 분기 수 / 전체 분기 수. 100%이면 구문 커버리지도 100%임
오류 추측
Error Guessing		 과거 동작, 개발자가 자주 하는 실수, 비슷한 시스템의 장애에 대한 지식으로 결함이 생길 곳을 예상하는 경험 기반 기법
체크리스트 기반 테스트
Checklist-based Testing		 체크리스트의 테스트 조건을 수행하는 경험 기반 기법. 결함 분석 결과로 목록을 갱신함
사용자 스토리
User Story		 사용자나 구매자에게 가치 있는 기능. 카드, 대화, 확인(인수 기준) 세 요소로 구성되고 INVEST 조건을 만족해야 함
인수 기준
Acceptance Criteria		 사용자 스토리 구현이 인수되려면 충족해야 하는 조건. 시나리오형(Given/When/Then)과 규칙형으로 작성함
TDD, ATDD, BDD 테스트 우선 개발 방식. TDD는 단위 테스트를 먼저 작성해 코딩을 이끌고, ATDD는 인수 기준에서 테스트를 먼저 도출하며, BDD는 동작을 자연어 시나리오로 표현해 실행 가능한 테스트로 만듦

수행 결과

섹션 제목: “수행 결과”
  • PASS: 기대 결과와 일치
  • FAIL: 기대 결과와 불일치
  • BLOCK: 사전조건 실패(테스트 환경 장애 포함), 또는 절차는 수행했지만 다른 결함으로 차단되어 기대 결과를 판정할 수 없는 항목
    • 차단 원인 결함 번호(환경 장애면 장애 내용과 확인 시각)와 통과한 절차의 결과를 함께 기록
    • 결함 심각도 Blocker와 별개의 용어
  • N/A: 일정·범위 사정으로 수행하지 못한 항목과 이번 범위에 적용되지 않는 항목(Not Applicable)
    • 특정 계정·데이터가 있는 환경 전용이라 제외한 테스트 포함
    • 비고에 사유(수행하지 못한 사유 또는 적용 제외 근거) 기록
  • N/R: 회차에 포함됐지만 아직 결과를 입력하지 않은 항목(Not Run, 미수행)
    • 회차 진행 중의 임시 상태이고 결과 값으로 남기지 않음

결과 값은 PASS, FAIL, BLOCK, N/A 넷이다. 회차를 완료하거나 보고서를 작성하기 전에 N/R로 남은 TC를 N/A로 변경하고 비고에 사유를 기록한다.

  • 회차(Test Run): 정해진 빌드와 환경에서 TC 묶음을 한 번 수행한 단위. TCMS에서 결과를 기록하는 단위
  • TCMS(Test Case Management System): TC를 관리하고 회차별 수행 결과를 기록하는 시스템

자동화

섹션 제목: “자동화”
용어 뜻
E2E 테스트
End-to-End Test		 업무 흐름을 시작부터 끝까지 운영과 비슷한 조건에서 확인하는 테스트. 이 위키에서는 주로 화면을 조작하는 브라우저 E2E를 가리킴
로케이터
Locator		 자동화 테스트가 화면 요소를 찾는 기준. 역할과 이름 기준을 우선함(테스트 자동화 기본)
단언
Assertion		 테스트 코드에서 실제 값이 기대 값과 같은지 판정하는 문장
대역
Test Double		 테스트에서 실제 외부 서비스나 모듈 대신 사용하는 대체 구현. 모의 객체(Mock), 스텁(Stub) 등
Flaky 테스트 코드와 실행 환경이 같은데도 반복 실행 결과가 달라지는 테스트. 줄여서 Flake라고도 함(Flaky 테스트 관리)
격리
Quarantine		 원인이 테스트 코드나 실행 환경으로 확인된 Flaky 테스트를 수정 전까지 필수 게이트에서 분리하는 조치. 격리 중에도 실행과 결과 기록은 계속하고, 수정 이슈와 기한을 함께 정함
테스트 격리
Test Isolation		 테스트끼리, 그리고 테스트와 운영 환경 사이에 데이터, 상태, 자원을 공유하지 않도록 분리하는 것. Flaky 테스트의 격리(Quarantine)와는 다른 뜻
드라이런
Dry Run		 실제 변경 없이 수행할 작업만 출력하는 실행 방식. 실제로 아무것도 변경하지 않았는지 결과로 확인함(쓰기 작업 결과 대조)
실패 분류
Failure Triage		 자동화 실패를 결함으로 등록하기 전에 원인(테스트, 제품, 환경 등)별로 나누는 절차(E2E 실패 분류)
변이 테스트
Mutation Testing		 코드에 일부러 결함을 넣어 테스트가 실패하는지로 테스트의 검출력을 확인하는 방법(변이 주입으로 테스트 검출력 확인)
시각 회귀
Visual Regression		 화면 캡처를 기준 이미지와 비교해 의도하지 않은 화면 변화를 검출하는 테스트(시각 회귀 테스트)
베이스라인
Baseline		 시각 회귀에서 비교 기준이 되는 이미지
CI
Continuous Integration		 변경을 반영할 때마다 빌드와 테스트를 자동으로 실행하는 체계
테스트 피라미드
Test Pyramid		 테스트를 세분성에 따라 층으로 나눈 모델. 아래층(단위)일수록 많고 빠르며, 위층(E2E)일수록 적고 느림
테스트 사분면
Testing Quadrants		 비즈니스·기술 관점과 팀 지원·제품 비평 축으로 테스트를 네 영역으로 나눈 모델(Marick)
테스트 용이성
Testability		 시스템이 테스트를 지원하는 정도. 관측성, 제어성, 아키텍처 투명성으로 구성됨(테스트 자동화 기본)
테스트 하네스
Test Harness		 테스트 실행에 필요한 스텁, 드라이버, 러너의 묶음
테스트 픽스처
Test Fixture		 테스트 실행에 필요한 환경과 데이터, 사전·사후 조건. 테스트를 반복 가능하고 독립적으로 만듦
페이지 객체 모델
Page Object Model		 화면마다 클래스를 두어 로케이터와 조작을 모으는 자동화 설계 패턴. 화면이 바뀌면 한 곳만 수정함
데이터 주도 테스트
Data-driven Testing		 같은 스크립트를 데이터 파일의 여러 데이터로 반복 실행하는 자동화 방식
키워드 주도 테스트
Keyword-driven Testing		 사용자 관점 키워드와 데이터로 테스트 단계를 표처럼 작성하는 자동화 방식
캡처·재생
Capture/Playback		 수동 조작을 기록해 스크립트를 만드는 자동화 방식. 시작은 쉽지만 유지와 재사용이 어려움
오탐
False Positive		 검사가 문제가 없는 것을 문제로 표시한 경우
미탐
False Negative		 검사가 실제 문제를 검출하지 못한 경우. 검사 결과 0건만으로 이상 없음으로 판정하지 않는 근거(검사 결과 0건 검증)

API, 보안, 데이터

섹션 제목: “API, 보안, 데이터”
용어 뜻
인증
Authentication		 요청한 사람이 누구인지 확인하는 것. 로그인, 토큰 검증
인가
Authorization		 확인된 사용자가 대상 자원과 동작에 대한 권한이 있는지 확인하는 것
객체 수준 인가 실패
BOLA		 Broken Object Level Authorization. 요청의 객체 id만 변경하면 다른 사용자의 데이터에 접근할 수 있는 결함. OWASP API Security Top 10 2023의 API1(API 테스트 기본, 보안 테스트의 기본 관점)
데이터 격리
Data Isolation		 권한 경계를 넘어 다른 사용자, 조직, 프로젝트의 데이터를 조회하거나 변경할 수 없도록 분리하는 성질
멱등성
Idempotency		 같은 요청을 여러 번 보내도 서버 상태에 미치는 효과가 한 번 보낸 것과 같은 성질. 응답은 달라도 됨(예: 두 번째 DELETE의 404). 결제 중복 요청 처리의 기준(API 테스트 기본, 이커머스 테스트 관점)
요청 상한
Rate Limit		 정해진 시간 동안 허용하는 요청 수의 상한
웹훅
Webhook		 외부 서비스가 이벤트 발생 시 우리 서버로 보내는 HTTP 통지. 결제 결과 통지 등
대사
Reconciliation		 두 기록(예: 결제 승인 내역과 주문 내역)을 대조해 불일치를 찾는 처리
PIT
Point-in-Time		 과거 시점의 판단에 그 시점에 공개된 데이터만 사용하는 원칙(금융 데이터 검증의 함정)
수정주가
Adjusted Price		 분할, 배당 등을 소급 반영해 과거 가격을 보정한 값

AI와 QA

섹션 제목: “AI와 QA”
용어 뜻
LLM
Large Language Model		 대규모 텍스트로 학습해 문장을 생성하는 대규모 언어 모델(LLM 기능 테스트)
RAG Retrieval-Augmented Generation. 질문과 관련된 문서를 검색해 그 내용을 모델에 함께 제공하고 답을 생성하는 검색 증강 생성 구조(RAG 테스트)
LLM 심판
LLM-as-a-Judge		 LLM의 출력을 다른 LLM이 채점하는 평가 방식. 사람 판정과의 일치율을 측정해 사용함(LLM 평가셋과 LLM 심판)
평가셋
Evaluation Set		 질의, 기대 조건(구조 조건, 포함해야 할 사실, 금지 내용), 유형 라벨을 묶어 회차마다 같은 조건으로 실행하는 데이터. 골든셋(Golden Dataset)이라고도 함
기준선
Baseline		 비교 기준이 되는 이전 버전의 평가 결과. 시각 회귀의 베이스라인 이미지와는 다른 대상
데이터 오염
Contamination		 평가셋 질의가 프롬프트 예시나 학습 데이터에 들어가 점수가 실제보다 높게 나오는 상태
문맥 충실도
Faithfulness		 답의 주장이 제공한 문맥으로 뒷받침되는 정도. 문맥에 근거가 없는 주장은 사실 여부와 별개로 충실도 실패로 판정함(RAG 테스트)
허위 생성
Confabulation		 모델이 사실이 아닌 내용을 확신하는 어조로 생성하는 현상. 흔히 환각(Hallucination)이라고 부름
청크
Chunk		 RAG에서 검색 단위로 나눈 문서 조각
검색 적중률
Hit@K		 정답 근거 청크가 상위 K개 안에 1개 이상 있는 질의의 비율. 여러 정답 청크 중 검색된 비율은 Recall@K
프롬프트 인젝션
Prompt Injection		 입력이나 문서에 넣은 지시로 모델이 원래 지시를 벗어나게 하는 공격. 사용자가 직접 넣는 직접 인젝션과 문서·웹 페이지에 숨긴 간접 인젝션(LLM 보안 테스트)
가드레일
Guardrail		 모델의 입력과 출력을 검사해 허용하지 않는 내용을 차단하는 장치. 차단율과 과차단율을 함께 측정함
레드팀
Red Teaming		 공격자 관점에서 입력을 설계해 방어를 우회할 수 있는지 시험하는 활동
교차 검증
Cross Check		 서로 다른 검증자 둘을 독립적으로 배정해 사각지대를 줄이는 방식(AI 교차 검증)
머신러닝의 교차 검증(Cross-Validation)과는 별개
동어반복 테스트
Tautological Test		 기대값을 구현 코드에서 그대로 옮기거나 검증 대상을 대역으로 대체해, 구현에 결함이 있어도 항상 통과하는 테스트(AI가 생성한 TC와 테스트 코드 검토)
계약 테스트 함정 잘못된 동작을 기대값으로 고정하거나, 두 구현이 우연히 일치하는 입력만 검증해 실제 차이를 드러내지 못하는 테스트
업계 용어 계약 테스트(Contract Testing)와는 별개

형상관리

섹션 제목: “형상관리”
  • 형상관리(Configuration Management): 형상 항목을 식별하고, 변경을 통제하고, 상태를 기록하고, 요구사항 준수를 감사하는 체계
  • 형상 항목(Configuration Item): 형상관리 대상으로 지정한 단위. 소스 코드, 설정, 문서, 테스트 산출물, 테스트 환경
  • 베이스라인(Baseline): 정식 승인을 거쳐 특정 시점에 고정된 형상 항목의 버전. 정식 변경 통제로만 변경함
  • 변경 통제 위원회(CCB, Configuration Control Board): 변경 요청의 승인과 거부를 정하는 주체

개념과 QA 적용은 형상관리 기본에 있다.

혼동하기 쉬운 용어

섹션 제목: “혼동하기 쉬운 용어”
  • 심각도와 우선순위: 심각도는 영향의 크기, 우선순위는 처리 순서임. 오타는 심각도가 Trivial이어도 첫 화면 제목이면 우선순위가 높을 수 있음
  • BLOCK과 Blocker: BLOCK은 TC 수행 결과 값, Blocker는 결함 심각도 등급임. Blocker 결함 하나가 여러 TC를 BLOCK으로 만들 수 있음
  • 확인 테스트와 회귀 테스트: 확인 테스트는 수정한 결함 자체를, 회귀 테스트는 변경한 영역을 포함해 기존 동작에 의도하지 않은 영향이 없는지를 확인함. 결함 하나를 수정하면 둘 다 수행함
  • 인증과 인가: 인증은 누구인지, 인가는 그 사람이 이 자원에 이 동작을 할 수 있는지 확인함. 로그인한 사용자가 다른 사람의 주문을 조회할 수 있으면 인증은 통과하고 인가가 실패한 것임
  • 마스킹(Masking): 보안에서는 비밀값과 개인정보를 가리는 처리, 시각 회귀에서는 시각·난수 영역을 비교에서 제외하는 처리, 조합 테스트에서는 무효 값 때문에 같은 행의 다른 값 쌍이 실행되지 못한 채 커버된 것으로 집계되는 현상임
  • 검증(Verification), 확인(Validation), 확인 테스트(Confirmation Testing): 검증은 명세 충족, 확인은 사용자 필요 충족을 묻고, 확인 테스트는 수정한 결함이 해결되었는지 다시 수행하는 테스트임. 우리말 “확인”이 두 용어에 쓰여 혼동하기 쉬우므로 영문을 함께 적음
  • 테스팅과 QA: 테스팅은 제품 지향·교정적 활동으로 품질 관리의 주된 형태이고, QA는 프로세스 지향·예방적 활동으로 프로젝트의 모든 사람이 책임짐
  • 테스팅과 디버깅: 테스팅은 장애를 일으키거나 결함을 찾고, 디버깅은 장애의 원인을 찾아 분석하고 제거함. 디버깅은 테스트 활동이 아님
  • 블랙박스와 화이트박스: 구분 기준은 수행자가 아니라 TC를 도출한 근거(명세인가 내부 구조인가)임
  • 결함과 장애: 결함은 산출물에 있는 문제, 장애는 그 결함이 실행되어 드러난 현상임. 결함이 있어도 해당 코드가 실행되지 않으면 장애가 발생하지 않음
  • 테스트 레벨과 테스트 유형: 레벨은 대상의 범위, 유형은 확인하는 특성임. “API 테스트”는 둘 다 아니고 수행 방식이며, 컴포넌트 통합 레벨에서도 시스템 레벨에서도 수행함
  • 베이스라인과 기준선: 같은 영문(Baseline)이지만 형상관리에서는 승인되어 고정된 형상 항목의 버전, 시각 회귀에서는 비교 이미지, LLM 평가에서는 이전 버전의 점수임. 문서에서는 대상을 함께 적음
  • 재시도 통과와 PASS: 재시도로 통과한 테스트는 Flaky 후보이고, 첫 실행에 통과한 PASS와 같은 결과로 집계하지 않음
  • 교차 검증(Cross Check)과 Cross-Validation: 앞의 것은 검증자를 둘 두는 방식, 뒤의 것은 데이터를 나눠 모델 성능을 평가하는 머신러닝 기법임

팀에서 용어를 맞추는 방법

섹션 제목: “팀에서 용어를 맞추는 방법”
  • 이슈 라벨, 양식의 드롭다운 값, 이슈 로그의 칸 값은 글자까지 같게 유지함. 문자열 일치로 연결하는 도구(자동 라벨링 등)는 표기가 다르면 누락이나 불일치를 만듦. 맞출 수 없으면 변환표를 둠
  • 상태 값은 프로젝트마다 하나의 어휘 목록을 정하고, 대조 도구는 의미(완료인지 아닌지)로 비교함
  • 업계 표준 용어가 있으면 그 용어를 사용함. 개념을 우리말로 풀어 새 말을 만들지 않음(마스킹, 시각 회귀, 세션 타임아웃, 테스트 데이터)
  • 칸이나 상태의 이름을 변경하면 이전 이름을 사용하는 파일이 남아 있는 동안 도구가 두 이름을 모두 받게 함
  • 용어를 일괄 변경할 때는 화면 문구, 문서와 함께 테스트 코드의 셀렉터와 기대 문구도 변경 범위에 포함함(회귀 테스트 범위 선정)
  • 새 문서에서 이 목록에 없는 용어를 사용하면 영문 표기와 함께 이 목록에 추가함

현장 노트

  • 프로젝트마다 열린 이슈의 상태 값이 달랐음(한 곳은 미해결, 나머지는 진행중). 대조 도구가 진행중 문자열만 열린 상태로 보면 미해결 행을 모두 불일치로 판정함. 대조는 완료인지 아닌지만 비교하도록 정함
  • 이슈 트래커를 옮길 때 기본 라벨(Bug, Improvement, Feature)을 새로 만들지 않고 기존 라벨 어휘(bug, enhancement, etc)로 이름을 변경해 사용함. 트래커가 달라도 같은 라벨 값으로 집계할 수 있게 하기 위함
  • 이슈 로그의 조인 키 칸 이름을 트래커 이름(GitHub)에서 트래커로 변경하면서, 이전 이름을 사용하는 파일이 남아 있어 도구가 두 이름을 모두 받도록 함
  • 외부에 공개하는 문서에서 마스킹을 우리말로 직역한 조어가 문서 구조 검사를 모두 통과했고, 사람이 읽고서야 업계 표준 용어(마스킹)로 바로잡음. 이후 직역 조어 사전을 만들어 문서를 저장할 때마다 검사함

규칙

  • 같은 개념에는 문서 전체에서 같은 용어를 사용함
  • 영문 약어는 처음 나올 때 풀어 쓴 이름을 함께 적음
  • 결과 값(PASS, FAIL, BLOCK, N/A)과 심각도 등급(Blocker ~ Trivial)은 번역하지 않고 그대로 사용함

관련 문서

프로세스심각도 기준결함의 영향 크기(심각도)와 수정 순서(우선순위)를 기록하는 대표 방식(ISTQB, Bugzilla, Jira, GitHub 라벨)과 선택 기준. 운영 예로 버그 5단계와 하한 규칙을 둔다.테스트 설계리스크 기반 테스트실패했을 때의 피해와 실패할 가능성을 기준으로 무엇을 먼저, 얼마나 깊게 테스트할지 정하는 방식이다(Risk-Based Testing).기초와 용어테스트 레벨과 테스트 유형테스트 레벨은 시스템을 어느 통합 단계에서 검증하는지를, 테스트 유형은 어떤 품질 특성을 검증하는지를 나타내는 분류다. 두 분류는 서로 독립이며, 테스트마다 레벨을 하나 정하고 테스트 유형은 하나 이상 적용할 수 있다.
