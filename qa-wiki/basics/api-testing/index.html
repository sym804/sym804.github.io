API 테스트 기본

화면을 거치지 않고 API에 직접 요청을 보내 응답 계약, 상태 코드, 서버 측 검증, 인가를 확인하는 테스트다. 화면 제약만으로는 확인할 수 없는 서버 동작이 대상이다.

기본기난이도 기초백엔드 API최종 업데이트 2026-11-24

화면은 서버로 요청을 보내는 여러 경로 중 하나다. 입력 길이 제한, 비활성 버튼, 숨긴 메뉴로는 API를 직접 호출하는 요청을 차단할 수 없다. 서버가 지켜야 하는 규칙은 API를 직접 호출해 확인한다.

응답 계약과 상태 코드

섹션 제목: “응답 계약과 상태 코드”
  • 상태 코드, 응답 헤더(Content-Type, Content-Disposition 등), 본문의 필수 키·자료형·허용 값·null 허용 여부를 명세와 대조함. API TC는 응답 자체가 사용자(호출자)가 관측하는 결과라 이 값들을 기대 결과로 작성함
  • 스키마 검증(JSON Schema 등)은 형식만 확인함. 금액, 개수, 소유자 같은 값은 별도로 단언함
  • 목록 응답은 0건, 1건, 페이지 크기와 같은 개수, 페이지 크기 + 1에서 확인함(경계값 분석)
  • 오류 응답도 계약에 포함함. 오류 본문 형식과 스택 트레이스·내부 경로 노출 여부를 확인함

상태 코드의 의미는 RFC 9110(HTTP Semantics)을 따른다.

  • 200, 201, 204: 성공. 생성에 201, 본문 없는 성공에 204를 사용하는지는 명세와 대조함
  • 400: 요청 형식 오류. 422: 형식은 맞지만 처리할 수 없는 내용(Unprocessable Content). 둘 중 어느 쪽을 사용하는지는 명세 기준
  • 401: 유효한 인증 정보 없음. 토큰 누락, 만료, 폐기
  • 403: 서버가 요청을 이해했지만 수행을 거부함. RFC 9110은 권한 없는 자원의 존재를 숨기려고 404로 응답하는 것도 허용함
  • 409: 현재 상태와 충돌. 중복 생성, 이미 완료된 대상 변경
  • 5xx: 클라이언트 입력만으로 5xx가 발생하면 결함. 잘못된 입력은 4xx로 거부되어야 함

화면 제약을 우회한 서버 검증

섹션 제목: “화면 제약을 우회한 서버 검증”
  • 화면의 maxlength, disabled, 선택지 제한, 숨긴 버튼을 거치지 않고 같은 요청을 API로 전송함
  • 경계 밖 값, 잘못된 자료형, 필수 필드 누락, 정의되지 않은 필드 추가
  • 허용되지 않은 상태 전이 요청. 완료된 대상 수정, 삭제된 대상 참조(상태 전이 테스트)
  • 클라이언트가 계산해 보내는 값(금액, 소유자 id, 역할)을 서버가 다시 계산하거나 무시하는지 확인함

인증·인가와 객체 수준 격리

섹션 제목: “인증·인가와 객체 수준 격리”
  • 토큰 없음, 만료 토큰, 폐기 토큰(로그아웃·비밀번호 변경 뒤)으로 요청해 401을 확인함
  • 낮은 역할로 관리 기능을 호출해 403을 확인함. OWASP API5:2023 기능 수준 인가 실패(BFLA)
  • 경로·쿼리·본문의 객체 id를 다른 사용자·조직·프로젝트의 id로 변경해 조회·수정·삭제가 모두 차단되는지 확인함. OWASP API1:2023 객체 수준 인가 실패(BOLA)
  • id를 직접 받지 않는 목록, 검색, 내보내기, 첨부 파일 다운로드에도 같은 격리 기준을 적용함
  • 소유 관계가 서로 다른 테스트 계정을 둘 이상 준비함. 점검 범위는 TC 작성 원칙의 데이터 격리 항목과 같음

멱등성과 동시성

섹션 제목: “멱등성과 동시성”
  • RFC 9110 기준 GET, HEAD, OPTIONS, TRACE, PUT, DELETE는 멱등 메서드임. 같은 요청을 여러 번 보내도 서버에 의도한 효과는 한 번 보낸 것과 같아야 함
  • POST는 멱등 메서드가 아님. 생성·결제처럼 중복이 문제 되는 요청은 재시도와 연속 클릭으로 같은 요청을 다시 보내 중복 생성 여부를 확인함
  • 멱등 키(같은 요청임을 표시하는 값)를 사용하는 설계면 같은 키로 재전송해 서버 효과(생성, 결제)가 한 번만 발생하는지 확인함. 응답 본문까지 같아야 하는지는 해당 API 계약 기준
  • 같은 자원에 두 수정 요청을 동시에 보내 한쪽 변경이 조용히 덮어써지는지(갱신 손실), 409 등으로 거부되는지 확인함

규칙

  • 운영 환경을 호출하는 자동화는 상태 변경 메서드(POST, PUT, PATCH, DELETE)를 코드 수준에서 차단하고 조회만 수행함
  • 차단은 HTTP 클라이언트의 공통 설정에 구현함. 테스트마다 작성자가 주의하는 방식은 누락이 발생함
  • 운영 환경에서 응답을 가로채 오류를 주입하지 않음(E2E 실패 분류)

TC 예시

섹션 제목: “TC 예시”
점검 항목 TC 예시
응답 계약 본인 주문 id로 GET /orders/{id}를 요청해 200, Content-Type: application/json, 필수 키(id 정수, amount 0 이상 정수, status 명세의 허용 값 중 하나)를 확인하고 amount가 DB 저장 값과 같은지 단언함
목록 경계 페이지 크기가 20(예시 값)인 목록에 데이터 0건, 1건, 20건, 21건을 준비해 각각 항목 수와 다음 페이지 존재 표시가 명세와 같은지 확인함
페이징 연속성 1페이지 마지막 항목과 2페이지 첫 항목의 정렬 키가 이어지고, 두 페이지를 합친 결과에 중복과 누락이 없는지 확인함
페이지 크기 상한 명세의 상한 N(예: 100)을 기준으로 size를 N-1, N, N+1로 요청해 N+1에서 명세대로 400이 반환되거나 N개로 제한되는지 확인함
입력 길이 상한 상한이 100자(예시 값)인 이름 필드에 99자, 100자를 보내면 저장되고, 101자를 보내면 400 또는 422로 거부되어 저장되지 않는지 확인함. 5xx가 반환되면 결함으로 판정함
서버 재계산 주문 생성 요청 본문의 totalAmount를 1로 변조해 전송하고, 저장된 금액이 서버가 상품 가격으로 계산한 값이거나 요청이 거부되는지 확인함
토큰 폐기 로그인해 세션 쿠키와 리프레시 토큰을 발급받고 로그아웃한 뒤, 기존 세션 쿠키로 보호 API를, 기존 리프레시 토큰으로 토큰 갱신을 요청해 거부되는지 확인함. 서명만 검증하는 JWT 액세스 토큰은 만료 전까지 통과할 수 있어 명세의 폐기 정책(즉시 폐기 여부, 만료 시간)을 사전조건으로 확인함
멱등 키 같은 Idempotency-Key로 생성 요청을 2회 전송해 생성된 자원이 1건이고, 두 번째 응답이 API 계약에 정한 형식(첫 응답 재전송 또는 409)인지 확인함
갱신 손실 같은 버전 값으로 수정 요청 2건을 동시에 전송해 1건만 성공하고, 최종 저장 값이 성공한 요청의 값인지 확인함. 실패 응답은 If-Match 헤더 방식이면 412, 요청 본문의 version 필드 방식이면 API 명세의 충돌 응답(보통 409)으로 판정함

적용 예: 댓글 수정 API

섹션 제목: “적용 예: 댓글 수정 API”

기획서에 “작성자는 자신의 댓글을 수정할 수 있다. 댓글은 500자 이하다.“만 있고 API가 PATCH /comments/{id}인 경우, API 관점에서 도출되는 확인 항목은 다음과 같다.

  • 응답 계약: 성공 상태 코드(수정된 댓글을 반환하는 200 또는 본문 없는 204), 본문의 키, 수정 시각 필드의 갱신 여부
  • 입력 검증: 본문 0자, 공백만 입력, 499자·500자·501자, content 누락, 자료형 오류(숫자, 배열)
  • 정의되지 않은 필드: authorId, createdAt을 함께 보낼 때 무시하는지 거부하는지, 어느 경우에도 저장 값이 변경되지 않는지
  • 글자 수 기준: 500자를 문자 수와 바이트 수 중 무엇으로 세는지, 이모지와 결합 문자를 몇 자로 세는지, 화면의 글자 수 표시와 서버 판정이 같은지
  • 인증·인가: 토큰 없이 요청하면 401, 다른 사용자의 댓글 id로 요청하면 403 또는 404이고 원문이 그대로인지, 관리자의 타인 댓글 수정 허용 여부
  • 상태: 삭제된 댓글, 삭제된 게시글의 댓글, 잠긴 게시글의 댓글에 대한 수정 요청(상태 전이 테스트)
  • 동시성: 같은 댓글을 두 탭에서 동시에 수정할 때 마지막 저장 우선인지, 충돌 응답인지
  • 출력과 부수 효과: 스크립트가 포함된 내용의 저장·출력 정책(보안 테스트의 기본 관점), 수정 이력과 알림 발생 여부

글자 수 계산 기준, 관리자 권한, 충돌 처리처럼 명세로 답할 수 없는 항목은 기획과 확인할 항목으로 기록하고, 정해진 답을 TC의 기대 결과로 반영한다.

테스트 계획, 결함 기록, 보고에 적용

섹션 제목: “테스트 계획, 결함 기록, 보고에 적용”

테스트 계획

  • 엔드포인트를 행으로, 점검 항목(계약, 입력 검증, 인증, 인가, 상태 전이, 멱등성, 동시성)을 열로 둔 표로 범위를 정함. 해당 없는 칸은 사유를 기록함
  • 역할과 소유 관계가 다른 테스트 계정, 계정별 테스트 데이터를 준비 항목으로 계획함
  • 응답 시간 목표가 있으면 측정 위치(서버 로그 또는 클라이언트)와 측정 조건(워밍업 제외 여부, 반복 횟수)을 계획서에 기록함

결함 기록

  • 요청 원문(메서드, 경로, 쿼리, 본문, 인증 정보를 마스킹한 헤더)과 응답 원문(상태 코드, 헤더, 본문)을 첨부함. 재현 절차를 curl 명령 한 줄로 남기면 개발자가 그대로 실행할 수 있음
  • 기대 결과의 근거(API 명세의 해당 절, RFC 9110의 해당 절)를 함께 기록함
  • 사용한 계정의 역할과 대상 자원의 소유자를 기록함. 인가 결함은 이 정보가 없으면 재현할 수 없음

결함 분류와 보고

  • 원인 영역을 계약 위반, 입력 검증 누락, 인증, 인가, 동시성으로 분류하고, 인가 결함에는 OWASP API Security Top 10 번호(API1 등)를 라벨로 남김
  • 보고서에 엔드포인트별로 점검한 항목과 점검하지 않은 항목을 함께 기록함. “API 테스트 120건 통과”만으로는 인가와 동시성의 점검 여부가 보고서에 남지 않음

현장 노트

  • 외부 목록 API의 index 인자를 오프셋으로 가정하고 page * size를 전달했으나, 연속한 두 요청의 정렬 키를 확인하니 페이지 번호였음. index=30에서 한 달 분량을 건너뜀. 건너뛴 구간은 이전 수집기가 저장해 둔 데이터가 있어 DB만 확인해서는 공백이 드러나지 않았고, 수정 뒤 특정일 수집 건수가 13건에서 30건으로 증가함. 같은 API의 size 상한은 50이었고 60에서 400이 반환됨. 목록 조회 함수를 가짜로 대체한 테스트로는 인자의 의미를 확인할 수 없어 호출 인자를 단언하는 검사를 추가함
  • PowerShell Invoke-WebRequest로 같은 URL을 10회 연속 호출했을 때 첫 호출이 2,129ms였고, 같은 요청의 서버 기록은 7ms였음. 측정 라운드마다 첫 호출만 약 2.1초가 걸려 클라이언트 측 초기화 비용으로 판단함. 이 값을 서버 지연으로 기록한 이슈가 있었고, 실제 서버 처리 시간은 4~43ms였음. 이후 응답 시간은 서버 로그 기준으로 측정하고, 클라이언트에서 측정할 때는 첫 호출 시간(클라이언트 초기화 포함)과 이후 호출 시간을 구분해 기록함
  • DB를 SQLite에서 PostgreSQL로 전환한 뒤 동시 요청 테스트에서 결함 세 가지가 재현됨. 동시 가입 요청으로 관리자 계정 2~5개 생성, 같은 테스트 결과에 대한 동시 저장 요청의 전체 성공(먼저 저장한 값을 덮어씀), 1회용 코드 하나로 동시 요청 4건 성공임. 잠금을 추가해 수정함
  • 같은 동시성 테스트를 한 IP에서 전송하면 가입 횟수 제한의 잠금이 요청을 먼저 순차 처리해 계정 잠금 결함이 검출되지 않았음. 요청마다 IP를 다르게 설정해 실행함
  • 같은 전환 뒤 컬럼 길이(VARCHAR)를 넘는 입력이 DB 오류로 500을 반환함. API 스키마의 최대 길이를 DB 모델의 컬럼 길이와 대조하는 계약 테스트를 추가함. 422 응답의 detail이 배열 형식일 때 화면의 오류 문구 변환이 실패해 앱 화면 전체가 깨지는 결함도 함께 수정함

흔한 실수

섹션 제목: “흔한 실수”
  • 상태 코드가 200인지만 단언함. 본문이 비어 있거나 다른 사용자의 데이터, 노출하면 안 되는 필드(비밀번호 해시, 내부 메모)가 포함되어도 PASS로 판정됨. OWASP API3:2023 객체 속성 수준 인가 실패
  • 정상 요청만 자동화함. 필드 누락, 형식 오류, 권한 없는 요청을 보내는 부정 테스트가 빠짐
  • 테스트 계정 하나로만 확인해 객체 수준 격리를 검증하지 못함
  • 화면의 입력 제한 동작만 확인하고 서버 검증까지 통과로 판정함

관련 문서

테스트 설계경계값 분석처리 결과가 달라지는 경계와 그 바로 안팎의 값을 선택해 테스트하는 기법이다(Boundary Value Analysis).테스트 설계상태 전이 테스트대상이 가질 수 있는 상태와 상태를 변경하는 사건을 정리한 뒤, 허용된 전이와 차단되어야 하는 전이를 모두 테스트하는 기법이다(State Transition Testing).도메인별보안 테스트의 기본 관점접근 제어, 인증과 세션, 입력 처리, 비밀값 노출, 보안 설정에서 권한 없는 동작과 정보 노출이 발생하지 않는지 확인하는 테스트다. OWASP Top 10, ASVS, WSTG를 점검 기준으로 사용한다.프로세스TC 작성 원칙처음 보는 사람이 따라 할 수 있고 수행 직후 통과와 실패를 판정할 수 있는 테스트 케이스의 작성 기준. TC 형식(단계형, BDD 시나리오, 체크리스트, 탐색적 테스트 차터)의 선택 기준, 구성 요소별 작성법, 리뷰 점검 항목을 다룬다.
