테스팅의 7원칙

테스팅의 일반 원칙 7가지(ISTQB CTFL v4.0.1 1.3)는 테스트로 보장할 수 있는 것과 없는 것을 정한다. 원칙마다 뜻과 근거, 테스트 계획·설계·보고에 반영하는 방법을 사례와 함께 설명한다.

기본기난이도 기초최종 업데이트 2026-11-24

테스팅의 7원칙은 오랜 연구와 경험에서 나온 일반 지침으로, 어떤 제품과 개발 방식에도 적용된다. ISTQB CTFL v4.0.1(2024) 1.3절이 정리한 일곱 가지이며, 원칙마다 근거가 된 연구가 함께 제시되어 있다.

번호 원칙 근거 연구 실무에서 바뀌는 것
1 테스팅은 결함의 존재를 보여 줄 뿐 부재를 증명하지 못함 Buxton 1970 보고서 표현, 종료 기준
2 완벽한 테스팅은 불가능함 Manna 1978 기법과 우선순위로 범위를 정함
3 조기 테스팅이 시간과 비용을 줄임 Boehm 1981 요구사항 리뷰, 정적 분석 시점
4 결함은 일부에 집중됨 Enders 1975 리스크 평가, 회귀 범위
5 테스트는 반복할수록 효과가 떨어짐(구판 명칭: 살충제 역설) Beizer 1990 TC와 테스트 데이터 갱신
6 테스팅은 정황에 따라 달라짐 Kaner 2011 테스트 전략, 문서화 수준
7 결함이 없다고 성공하는 것은 아님(결함 부재의 오류) Boehm 1981 검증과 함께 확인(Validation) 수행

1. 결함의 존재 증명, 결함 부재는 증명 불가

섹션 제목: “1. 결함의 존재 증명, 결함 부재는 증명 불가”

테스팅은 결함이 있다는 것은 보여 줄 수 있지만 결함이 없다는 것은 증명하지 못한다. 테스트로 남은 결함이 발견되지 않을 확률을 낮출 수는 있어도, 결함이 하나도 나오지 않은 결과가 제품이 옳다는 증명은 아니다.

실무에서 하는 일

  • 보고서에 “결함 없음” 대신 “수행 범위에서 결함 미검출”로 쓰고, 수행 범위와 수행하지 않은 범위를 함께 적음
  • 종료 기준을 “결함 0건”이 아니라 커버리지, 남은 리스크, 미해결 결함의 심각도로 정함
  • 검사 도구의 결과 0건은 검사가 실제로 대상에 도달했는지 확인한 뒤에 신뢰함(검사 결과 0건 검증)

예: 회원 가입 기능 TC 120건을 수행해 FAIL이 0건이면, 보고서는 “TC 120건 수행, 결함 미검출. 비밀번호 재설정 메일 연동은 테스트 환경 미비로 미수행”처럼 미수행 범위를 함께 적는다.

2. 완벽한 테스팅의 불가능

섹션 제목: “2. 완벽한 테스팅의 불가능”

아주 단순한 경우를 빼면 모든 입력과 조합, 경로를 테스트할 수 없다. 대신 테스트 기법, TC 우선순위, 리스크 기반 테스트로 노력을 집중한다.

실무에서 하는 일

  • 입력은 동등 분할과 경계값 분석으로 대표값을 고름
  • 조합은 결정 테이블이나 조합 테스트(페어와이즈)로 줄임
  • 영향과 가능성으로 테스트 깊이를 정함(리스크 기반 테스트)

예: 6~8자이고 영문 대문자나 숫자로 구성되며 숫자를 1개 이상 포함하는 비밀번호의 경우의 수는 약 2.68조 개다. 1분에 TC 하나를 수행해도 끝낼 수 없는 수라서, 길이 경계(5, 6, 8, 9자), 문자 종류 클래스(숫자 없음, 허용되지 않는 문자 포함)로 TC를 도출한다. 이 계산 예는 『소프트웨어 테스트 자동화 구축과 6가지 핵심 활동』 4장에 나온다.

3. 조기 테스팅

섹션 제목: “3. 조기 테스팅”

결함을 앞 단계에서 제거하면 그 산출물에서 파생되는 뒤 단계 산출물에 결함이 옮겨 가지 않는다. 뒤 단계에서 발생하는 장애가 줄어 품질 비용이 감소한다. 정적 테스트와 동적 테스트를 모두 가능한 한 일찍 시작한다. 같은 원칙을 개발 수명주기 그림에서 왼쪽으로 옮긴다는 뜻에서 시프트 레프트(Shift Left)라고 부른다.

실무에서 하는 일

  • 요구사항과 기획서가 초안일 때 테스터 관점으로 리뷰함. 모호한 표현, 누락, 모순을 이 단계에서 찾음
  • 기획서를 읽으면서 TC 초안을 작성함. TC로 옮기지 못하는 문장은 명세가 모호하다는 신호임
  • 코드 리뷰와 정적 분석을 CI에 넣어 실행 전에 검사함

예: “답변이 달린 글은 수정할 수 없다”는 요구사항으로 결정 테이블을 작성하면, 관리자가 다른 사람의 글을 수정할 수 있는지가 명세에 없다는 사실이 개발 전에 드러난다(결정 테이블 테스트).

4. 결함 집중

섹션 제목: “4. 결함 집중”

발견되는 결함의 대부분, 또는 운영 장애의 대부분은 소수의 컴포넌트에서 나온다. 파레토 원리의 한 예다. 예측한 결함 집중 영역과 테스트·운영에서 실제로 관찰한 집중 영역은 리스크 기반 테스트의 중요한 입력이다.

실무에서 하는 일

  • 결함을 영역(모듈, 화면, API)별로 집계해 결함이 몰린 영역을 다음 회차의 리스크 평가에 반영함
  • 결함이 몰린 영역은 회귀 범위에 고정 포함하고 테스트 깊이를 높임
  • 결함 이력이 적은 영역이 실제로 결함이 적은지, 테스트가 덜 된 것인지 구분함

예: 같은 지표를 화면마다 따로 계산하는 코드 사본이 있으면, 한 곳의 계산 기준만 수정되어 화면 간 수치 불일치 결함이 반복해서 나온다. 이런 영역은 계산을 한 곳으로 모으고 화면 간 값을 비교하는 테스트를 회귀 범위에 둔다(회귀 테스트 범위 선정).

5. 테스트 효과 감소(살충제 역설)

섹션 제목: “5. 테스트 효과 감소(살충제 역설)”

같은 테스트를 여러 번 반복하면 새로운 결함을 찾는 효과가 점점 떨어진다. 이 효과를 극복하려면 기존 테스트와 테스트 데이터를 수정하고 새 테스트를 작성해야 한다. 다만 자동화된 회귀 테스트처럼 같은 테스트를 반복하는 것 자체가 목적인 경우도 있다. v3.1까지 “살충제 역설(Pesticide Paradox)“로 부르던 원칙을 v4.0(2023)에서 “Tests wear out”으로 바꿔 부른다.

실무에서 하는 일

  • 회귀 테스트는 반복하되, 새로 발견된 결함 유형이 있으면 같은 유형을 찾는 TC를 추가함
  • 체크리스트와 검사 규칙을 결함 분석 결과로 정기적으로 갱신함
  • 테스트 데이터를 고정값 하나로 두지 않고 경계값과 이상값을 바꿔 가며 사용함
  • 탐색적 테스트로 기존 TC가 다루지 않는 영역을 찾음(탐색적 테스트)

예: 매번 같은 기간의 데이터로 대조하는 검사는 계속 통과한다. 대조 범위를 넓히는 순간, 한 번도 대조된 적 없던 행에서 불일치가 나온다.

6. 정황 의존성

섹션 제목: “6. 정황 의존성”

모든 상황에 통하는 단일한 테스트 방법은 없다. 제품의 위험도, 도메인, 규제, 개발 방식, 팀 역량에 따라 테스트를 다르게 수행한다.

실무에서 하는 일

  • 도메인에 따라 심각도 기준을 다르게 둠. 예: 금융 데이터는 수치 오류를 Major 이상으로, 보안 이슈는 Minor 이상으로 분류함(심각도 기준)
  • 규제 대상 제품은 추적성과 문서화 수준을 높이고, 빠르게 배포하는 웹 서비스는 자동화된 회귀와 운영 모니터링에 비중을 둠
  • 다른 프로젝트의 테스트 전략을 그대로 복사하지 않고 위험과 제약을 다시 평가함

예: 같은 “목록 조회” 기능이라도 쇼핑몰 상품 목록은 정렬과 페이지 경계를, 금융 데이터 화면은 기준 시점과 데이터 누락을 우선 확인한다(금융 데이터 검증의 함정).

7. 결함 부재의 오류

섹션 제목: “7. 결함 부재의 오류”

명세를 모두 테스트하고 발견된 결함을 모두 수정해도, 시스템이 사용자의 필요와 기대를 채우지 못하거나 사업 목표에 도움이 되지 않거나 경쟁 제품보다 못할 수 있다. 결함을 없애는 것만으로 시스템의 성공을 기대하는 것은 오해다. 검증(Verification, 명세대로 만들었는가)과 함께 확인(Validation, 사용자에게 맞는 것을 만들었는가)을 수행해야 한다.

실무에서 하는 일

  • 인수 테스트와 사용성 확인에 실제 사용자 관점의 시나리오를 포함함
  • 명세를 만족해도 사용자가 이해하기 어려운 문구, 지나치게 긴 흐름은 개선 이슈로 기록함
  • 기획 단계에서 인수 기준에 사용자 목적을 함께 적음(“버튼이 있다”가 아니라 “주문 내역을 3번 이내 클릭으로 찾을 수 있다”)

예: 모든 입력 검증 TC가 통과한 회원 가입 화면이라도, 오류 문구가 “입력값 오류” 하나뿐이면 사용자는 어느 칸을 고쳐야 하는지 알 수 없다. 명세 위반은 아니지만 확인 관점의 결함이다.

원칙을 계획과 보고에 반영하는 방법

섹션 제목: “원칙을 계획과 보고에 반영하는 방법”
원칙 테스트 계획서 결과 보고서
1 결함 부재 증명 불가 종료 기준을 커버리지와 남은 리스크로 정의 “결함 없음” 대신 수행 범위와 미수행 범위 명시
2 완벽한 테스팅 불가 사용할 기법과 범위 제외 항목 명시 제외한 범위와 그 근거
3 조기 테스팅 요구사항 리뷰, 정적 분석 일정 포함 리뷰 단계에서 찾은 결함 수
4 결함 집중 이전 회차 결함 분포를 리스크 평가에 반영 영역별 결함 분포
5 테스트 효과 감소 TC 갱신 주기와 탐색적 테스트 시간 배정 새로 추가한 TC와 그 계기
6 정황 의존성 제품 위험도에 맞춘 문서화·자동화 수준 적용한 기준과 다른 프로젝트와의 차이
7 결함 부재의 오류 인수 테스트와 사용성 확인 포함 명세 충족과 사용자 관점 평가를 구분해 보고

현장 노트

  • 문서 검사기가 장식 기호 786회, 서술형 종결 2,322회가 들어간 릴리즈 노트에 종료코드 0을 냄. 검사기가 그 지표를 재지 않았기 때문이고, 이후 지표 세 개를 추가함. 검사 결과 0건을 “문제 없음”으로 읽은 사례임(원칙 1)
  • 같은 검사기가 종료코드 0을 낸 문서를 독자는 AI가 작성한 문서로 읽음. 검사기가 정한 조건(명세)은 만족했지만 독자의 기대(확인)는 만족하지 못한 사례이고, 외부 모델 두 개로 문체를 전수 검토하는 절차를 추가함(원칙 1, 7)
  • 데이터 대조 검사의 범위를 넓히자 한 번도 대조된 적 없던 256행이 나옴. 같은 범위만 반복해서 통과하던 검사였음(원칙 5)

규칙

  • 결과 보고서에 “결함 없음”을 단독으로 쓰지 않음. 수행 범위를 함께 적음
  • 같은 TC 세트만 반복하지 않음. 결함이 발견되면 같은 유형을 찾는 TC를 추가함
  • 명세 충족(검증)과 사용자 관점 평가(확인)를 구분해 보고함

흔한 오해

섹션 제목: “흔한 오해”
  • 원칙 2를 “어차피 다 못 하니 적당히 한다”로 읽음. 원칙의 요구는 기법과 리스크로 범위를 근거 있게 줄이는 것임
  • 원칙 5를 “같은 테스트를 반복하면 안 된다”로 읽음. 회귀 테스트의 반복은 필요하고, 새 결함을 찾는 테스트를 함께 늘리는 것이 요구임
  • 원칙 3을 테스터만의 활동으로 봄. 요구사항 리뷰와 정적 분석은 기획자, 개발자와 함께 수행함
