형상관리 기본

테스트 산출물과 테스트 대상을 형상 항목으로 식별, 통제, 추적하는 형상관리(Configuration Management)의 개념(형상 항목, 베이스라인, 변경 통제, 상태 기록, 감사)과 QA 업무에 적용하는 방법.

기본기난이도 기초최종 업데이트 2026-11-24

형상관리(CM, Configuration Management)는 형상 항목의 기능적·물리적 특성을 식별해 문서화하고, 그 특성의 변경을 통제하고, 변경 처리와 반영 상태를 기록·보고하고, 정해진 요구사항을 지키는지 검증하는 체계다. ISTQB CTFL v4.0.1(5.4)은 테스트에서의 형상관리를 테스트 계획서, 테스트 케이스, 테스트 스크립트, 테스트 결과, 테스트 로그, 테스트 보고서 같은 산출물을 형상 항목으로 식별, 통제, 추적하는 체계로 설명한다.

핵심 개념

섹션 제목: “핵심 개념”
용어 뜻
형상 항목(CI, Configuration Item) 형상관리 대상으로 지정해 관리하는 단위. 소스 코드, 설정 파일, 문서, 테스트 산출물, 테스트 환경
베이스라인(Baseline) 정식 승인을 거쳐 특정 시점에 고정된 형상 항목의 버전. 정식 변경 통제 절차로만 변경함
변경 통제(Change Control) 변경 요청을 접수, 평가, 승인 또는 거부하고 반영을 추적하는 절차
형상 상태 기록(Status Accounting) 형상 항목, 베이스라인, 항목 간 관계에 대한 정보를 기록하고 보고하는 활동
형상 감사(Configuration Audit) 형상 항목이 기능과 물리적 특성 요구사항을 만족하는지 확인하는 검토
  • 테스트 환경처럼 여러 요소로 구성된 형상 항목은 구성 요소, 요소 간 관계, 각 요소의 버전을 함께 기록함
  • 베이스라인과 그 베이스라인에 대해 승인된 모든 변경을 합친 것이 현재 승인된 형상임
  • 변경 승인 권한은 변경 통제 위원회(CCB, Configuration Control Board)가 가짐. 작은 프로젝트에서는 리더나 지정된 담당자 한 사람이 맡을 수 있음
  • 형상 감사에는 명세와 일치하는지 확인하는 기능 형상 감사(FCA)와, 설계·참조 문서가 실제로 만든 산출물과 일치하는지 확인하는 물리 형상 감사(PCA)가 있음

활동(SWEBOK v4.0a 8장)

섹션 제목: “활동(SWEBOK v4.0a 8장)”
  • 형상관리 프로세스 관리: 조직 맥락과 제약을 파악하고 형상관리 계획(SCMP)을 세움
  • 형상 식별: 관리할 형상 항목, 항목 간 관계, 베이스라인을 정함
  • 형상 변경 통제: 변경 요청의 평가, 승인, 반영을 관리함
  • 형상 상태 기록: 항목과 베이스라인의 상태를 기록하고 보고함
  • 형상 감사: 요구사항과 산출물의 일치를 확인함
  • 릴리즈 관리와 배포: 배포할 항목의 조합을 정하고, 릴리즈 노트와 설치 안내를 함께 배포함

CTFL은 테스트를 지원하려면 형상관리가 다음을 보장해야 한다고 정한다.

  • 테스트 항목(테스트 대상의 개별 부분)을 포함한 모든 형상 항목이 고유하게 식별되고, 버전이 관리되고, 변경이 추적되고, 다른 형상 항목과 연결되어 테스트 과정 전체에서 추적성이 유지됨
  • 식별된 문서와 소프트웨어 항목을 테스트 산출물에서 모호함 없이 참조함

새 베이스라인을 만들 때 변경된 형상 항목을 기록해 두면 이전 베이스라인으로 되돌려 이전 테스트 결과를 재현할 수 있다. CI/CD 파이프라인에는 보통 자동화된 형상관리가 포함된다.

관리 방식

섹션 제목: “관리 방식”
방식 내용 맞는 경우
개별 도구 조합 버전 관리 도구, 빌드 도구, 변경 관리 도구(이슈 트래커)를 각각 사용 작은 조직, 변형 제품이 없는 팀
프로젝트 지원 도구 작업 공간 관리, 병렬 개발, 분산 개발을 함께 지원 변형 제품과 병렬 개발이 있고 인증 요구사항이 없는 중대형 조직
전사 프로세스 도구 워크플로, 역할과 책임, 대량의 항목과 수명주기를 관리 여러 제품과 조직이 같은 절차를 따라야 하는 경우
  • 위 구분은 SWEBOK의 형상관리 도구 분류를 따름. 형상관리는 단일 도구가 아니라 도구 묶음으로 수행하는 경우가 많음
  • 승인 절차의 무게도 선택 사항임. 작은 프로젝트에서는 리더나 지정된 담당자가 변경 승인 권한을 맡을 수 있고, 정식 형상 감사(FCA, PCA)가 필요한지는 계약이나 규제 같은 요구사항에 따라 정함

QA에 적용

섹션 제목: “QA에 적용”

테스트 대상과 테스트 산출물

  • 결함 보고서에 발생 버전(빌드 번호, 커밋 식별자)을 기록함. 버전이 없는 결함은 어느 베이스라인에서 발생했는지 확인할 수 없음(이슈 양식)
  • 테스트 회차마다 대상 빌드와 환경(OS, 브라우저, 데이터 상태)을 기록함. 같은 TC의 결과를 비교할 때는 각 결과의 대상 빌드와 환경을 먼저 확인함
  • TC, 자동화 스크립트, 테스트 데이터, 환경 설정도 형상 항목으로 버전을 관리함. 테스트 데이터를 저장소 밖(공유 폴더 등)에 두더라도 버전을 식별하고 이전 버전을 복원할 수 있게 관리해야 이전 결과를 재현할 수 있음

변경과 회귀

  • 이전 베이스라인과 비교해 변경된 형상 항목을 회귀 범위 선정의 입력으로 사용함(회귀 테스트 범위 선정)
  • 배포하는 산출물이 테스트한 빌드와 같은지 확인함. 버전 표기가 화면, API, 태그, 릴리즈 노트에서 일치하는지 대조하는 방법이 있음(릴리즈 노트와 버전 번호). 설계·참조 문서와 실제 산출물의 일치를 확인하는 물리 형상 감사와는 대상이 다름

현장 노트

  • 검증 도구가 버전 관리에서 제외된(gitignore 대상) 모델 산출물을 표본 200건 결과에서 4건짜리로 덮어써, git으로 복구하지 못하고 다시 산출함. 재현에 필요한 산출물이 형상 항목에서 빠져 있으면 베이스라인으로 되돌릴 수 없음
  • 이미 추적 중인 파일은 .gitignore에 추가해도 계속 추적됨. 엑셀 산출물 몇 개를 추적에서 빼려고 .gitignore에 추가했지만 실제로는 계속 커밋되어, 어떤 파일이 형상 항목인지에 대한 기록과 실제 저장소가 6개월간 어긋남. 형상 항목 목록은 git ls-files로 실제 추적 상태와 대조함
  • 로컬에서 테스트를 통과한 작업 트리와 실제로 커밋된 내용이 달라 CI에서 실패한 사례는 작업 트리와 커밋 상태 구분에 있음

출처

섹션 제목: “출처”
  • ISTQB Certified Tester Foundation Level(CTFL) 실라버스 v4.0.1, 5.4 Configuration Management
  • IEEE Computer Society, SWEBOK Guide v4.0a, 8장 Software Configuration Management
  • 형상관리 표준: IEEE 828(소프트웨어·시스템 형상관리), ISO 10007(품질경영, 형상관리 지침). 유료 표준이라 위키는 공개 자료(CTFL, SWEBOK)의 내용만 옮김

관련 문서

도구Git 기본분산 버전 관리 시스템 Git의 핵심 개념(스냅샷, 세 가지 상태, 커밋, 브랜치, 태그, 원격, 병합과 리베이스), 자주 사용하는 명령, 브랜치 전략(Git Flow, GitHub Flow, 트렁크 기반)의 선택 기준.프로세스릴리즈 노트와 버전 번호버전 번호(SemVer, CalVer, 4자리 번호, 빌드 번호)와 릴리즈 노트(Keep a Changelog, Conventional Commits 자동 생성, 이슈 중심 형식)의 대표 방식과 선택 기준. 운영 예로 변경 크기 기준 A.B.C.D 규칙을 함께 둔다.프로세스회귀 테스트 범위 선정변경 뒤 기존 기능이 의도하지 않게 실패하는지 확인하기 위해, 회귀 스위트에서 이번 회차에 수행할 TC를 선택하는 절차다(Regression Test Selection).
