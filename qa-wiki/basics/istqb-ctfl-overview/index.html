ISTQB CTFL 실라버스 핵심 정리

ISTQB Certified Tester Foundation Level 실라버스 v4.0.1의 6개 장(테스팅 기초, 개발 수명주기와 테스팅, 정적 테스트, 테스트 분석과 설계, 테스트 활동 관리, 테스트 도구) 핵심 개념. 개념마다 실무에 적용한 위키 문서를 연결한다.

기본기난이도 기초최종 업데이트 2026-11-24

ISTQB(International Software Testing Qualifications Board)의 CTFL(Certified Tester Foundation Level)은 소프트웨어 테스팅의 기본 개념과 용어를 정한 국제 자격 체계의 기초 과정이다. 아래 절은 2024-09-15에 나온 실라버스 v4.0.1의 장 순서를 따르고, 개념마다 실무에 적용한 위키 문서를 연결한다. 실라버스 원문은 ISTQB 사이트에서 무료로 받을 수 있다.

장 주제 학습 시간 위키에서 이어 볼 문서
1 테스팅 기초 180분 테스팅의 7원칙
2 소프트웨어 개발 수명주기와 테스팅 130분 테스트 레벨과 테스트 유형, 회귀 테스트 범위 선정
3 정적 테스트 80분 TC 작성 원칙
4 테스트 분석과 설계 390분 테스트 기법 분류
5 테스트 활동 관리 335분 리스크 기반 테스트, 결함 생명주기
6 테스트 도구 20분 테스트 자동화 기본

1장. 테스팅 기초

섹션 제목: “1장. 테스팅 기초”

테스팅이란

섹션 제목: “테스팅이란”

소프트웨어 테스팅은 결함을 발견하고 소프트웨어 작업 산출물의 품질을 평가하는 활동의 묶음이다. 테스트하는 산출물을 테스트 대상(Test Object)이라고 한다. 실라버스는 두 가지 흔한 오해를 짚는다.

  • 테스팅은 테스트 실행만이 아님. 계획, 분석, 설계, 구현, 완료 같은 활동을 포함하고 개발 수명주기와 맞물려 진행함
  • 테스팅은 검증만이 아님. 명세된 요구사항을 만족하는지 확인하는 검증(Verification)과 함께, 운영 환경에서 사용자와 이해관계자의 필요를 만족하는지 확인하는 확인(Validation)을 포함함

테스팅은 동적 테스트(소프트웨어를 실행함)와 정적 테스트(실행하지 않음. 리뷰와 정적 분석)로 나뉜다.

테스트 목적

섹션 제목: “테스트 목적”
  • 요구사항, 사용자 스토리, 설계, 코드 같은 작업 산출물 평가
  • 장애를 일으키고 결함 발견
  • 테스트 대상의 필요한 커버리지 확보
  • 품질 부족으로 인한 리스크 수준 감소
  • 명세된 요구사항 충족 여부 검증
  • 계약, 법률, 규제 요구사항 준수 여부 검증
  • 이해관계자의 의사 결정에 필요한 정보 제공
  • 테스트 대상의 품질에 대한 신뢰 형성
  • 테스트 대상이 완전하고 이해관계자의 기대대로 동작하는지 확인

목적은 테스트 대상 산출물, 테스트 레벨, 리스크, 개발 수명주기, 사업 상황에 따라 달라진다.

테스팅과 디버깅

섹션 제목: “테스팅과 디버깅”

두 활동은 별개다. 동적 테스트가 장애를 일으키면 디버깅이 장애의 원인(결함)을 찾아 분석하고 제거한다. 디버깅은 장애 재현, 진단(결함 찾기), 결함 수정으로 진행된다. 수정 뒤 확인 테스트로 문제가 해결되었는지 확인하며, 처음 테스트한 사람이 수행하는 것이 바람직하다. 이어서 회귀 테스트로 수정이 다른 부분에 장애를 일으키지 않았는지 확인한다. 정적 테스트는 결함을 직접 찾으므로 재현과 진단 없이 제거한다.

테스팅과 QA

섹션 제목: “테스팅과 QA”

두 용어를 섞어 쓰는 경우가 많지만 같은 것이 아니다.

구분 테스팅 QA(품질 보증)
지향 제품 지향, 교정적 프로세스 지향, 예방적
초점 적절한 품질 수준 달성을 돕는 활동. 품질 관리(QC)의 주된 형태 프로세스의 구현과 개선. 좋은 프로세스를 올바르게 따르면 좋은 제품이 나온다는 전제
담당 주로 테스트 활동 수행자 프로젝트의 모든 사람
테스트 결과 사용 결함 수정 개발·테스트 프로세스가 얼마나 잘 동작하는지에 대한 피드백

오류, 결함, 장애, 근본 원인

섹션 제목: “오류, 결함, 장애, 근본 원인”
  • 사람이 오류(Error, 실수)를 하면 결함(Defect, Fault, Bug)이 만들어지고, 결함이 실행되면 장애(Failure)가 발생할 수 있음
  • 오류의 원인: 시간 압박, 산출물·프로세스·인프라의 복잡도, 피로, 교육 부족 등
  • 결함은 요구사항 명세, 테스트 스크립트, 소스 코드, 빌드 파일 등 어디에나 있음. 앞 단계 산출물의 결함은 뒤 단계 산출물의 결함으로 이어지기 쉬움
  • 실행하면 항상 장애가 되는 결함, 특정 조건에서만 장애가 되는 결함, 장애로 이어지지 않는 결함이 있음
  • 방사선, 전자기장처럼 환경 조건이 장애를 일으키기도 함
  • 근본 원인(Root Cause)은 문제가 발생한 근본적인 이유이고, 근본 원인 분석으로 찾음. 근본 원인을 제거하면 비슷한 장애와 결함을 예방하거나 줄일 수 있음

테스팅의 7원칙

섹션 제목: “테스팅의 7원칙”

결함 존재의 증명, 완벽한 테스팅의 불가능, 조기 테스팅, 결함 집중, 테스트 효과 감소, 정황 의존성, 결함 부재의 오류. 원칙마다 뜻과 실무 적용은 테스팅의 7원칙에 정리했다.

테스트 활동

섹션 제목: “테스트 활동”

테스트 프로세스는 아래 활동 묶음으로 구성된다. 순서대로 보이지만 실제로는 반복하거나 병행하며, 시스템과 프로젝트에 맞게 조정한다.

활동 하는 일 대표 산출물(테스트웨어)
테스트 계획 테스트 목적을 정하고 제약 안에서 목적을 가장 잘 달성할 접근법을 선택함 테스트 계획서, 일정, 리스크 목록, 진입·종료 기준
테스트 모니터링과 통제 진행 상황을 계획과 비교하고(모니터링) 목적 달성에 필요한 조치를 취함(통제) 진행 보고서, 통제 지시 기록
테스트 분석 테스트 베이시스를 분석해 테스트 가능한 기능과 테스트 조건을 정하고 우선순위를 매김. “무엇을 테스트할지” 우선순위를 매긴 테스트 조건, 테스트 베이시스의 결함 보고
테스트 설계 테스트 조건을 TC로 구체화하고 커버리지 항목, 테스트 데이터, 환경 요구를 정함. “어떻게 테스트할지” TC, 테스트 차터, 커버리지 항목
테스트 구현 실행에 필요한 테스트웨어를 만들고 절차와 스위트를 구성하며 환경을 준비함 테스트 절차, 수동·자동 스크립트, 테스트 데이터, 실행 일정, 스텁·드라이버
테스트 실행 일정에 따라 테스트를 실행하고 실제 결과와 기대 결과를 비교해 기록하며 이상을 분석함 테스트 로그, 결함 보고서
테스트 완료 마일스톤에서 미해결 결함을 변경 요청으로 넘기고 테스트웨어를 보관하며 교훈을 정리함 테스트 완료 보고서, 개선 조치 항목

테스트 베이시스(Test Basis)는 테스트 분석과 설계의 근거가 되는 정보(요구사항, 사용자 스토리, 설계 문서, 코드 등)다. 테스트 베이시스와 테스트웨어, 테스트 결과, 결함 사이의 추적성을 유지하면 커버리지를 평가하고 변경의 영향을 판단할 수 있다. 예를 들어 TC와 요구사항을 연결하면 요구사항이 TC로 커버되었는지 확인할 수 있고, 테스트 결과와 리스크를 연결하면 남은 리스크 수준을 평가할 수 있다.

테스트 프로세스의 모습은 이해관계자, 팀 역량, 도메인, 기술, 프로젝트 제약, 조직, 개발 수명주기, 도구 같은 정황 요인에 따라 달라진다.

역할, 역량, 독립성

섹션 제목: “역할, 역량, 독립성”
  • 테스트 관리 역할: 테스트 프로세스와 팀을 책임지고 계획, 모니터링, 통제, 완료에 집중함
  • 테스팅 역할: 테스트의 기술적 측면을 책임지고 분석, 설계, 구현, 실행에 집중함. 한 사람이 두 역할을 함께 맡을 수도 있음
  • 필요한 역량: 테스팅 지식, 꼼꼼함과 호기심, 의사소통과 경청, 분석적·비판적 사고와 창의성, 기술 지식, 도메인 지식
  • 테스터는 나쁜 소식을 전하는 사람이 되기 쉬움. 결함과 장애 정보는 건설적으로 전달함
  • 전체 팀 접근법(Whole Team Approach): 필요한 역량이 있는 팀원은 누구든 어떤 작업이든 수행하고, 품질은 모두의 책임임. 안전 필수 분야처럼 높은 독립성이 필요한 경우에는 맞지 않을 수 있음
독립성 수준 테스트 수행자
없음 작성자 본인
일부 같은 팀의 동료
높음 같은 조직의 다른 팀 테스터
매우 높음 조직 외부의 테스터

독립적인 테스터는 작성자와 다른 인지 편향을 가져 다른 종류의 결함을 찾는다. 반면 개발팀과 고립되거나, 개발자가 품질에 대한 책임감을 잃거나, 테스터가 출시 지연의 병목으로 비난받는 단점이 있다. 대부분의 프로젝트는 여러 수준의 독립성을 섞어 쓴다(개발자는 컴포넌트·컴포넌트 통합, 테스트 팀은 시스템·시스템 통합, 사업 담당자는 인수 테스트).

2장. 소프트웨어 개발 수명주기와 테스팅

섹션 제목: “2장. 소프트웨어 개발 수명주기와 테스팅”

개발 수명주기가 테스팅에 미치는 영향

섹션 제목: “개발 수명주기가 테스팅에 미치는 영향”

개발 수명주기(SDLC) 모델은 순차형(폭포수, V 모델), 반복형(나선형, 프로토타이핑), 점진형(통합 프로세스)으로 나뉜다. 선택한 모델에 따라 테스트 활동의 범위와 시점, 문서화 수준, 기법과 접근법, 자동화 정도, 테스터의 역할이 달라진다.

  • 순차형: 초기에는 요구사항 리뷰, 분석, 설계에 참여하고 실행 가능한 코드는 후반에 나와 동적 테스트는 늦게 시작함
  • 반복·점진형: 매 반복마다 정적·동적 테스트를 모든 레벨에서 수행하며 빠른 피드백과 대규모 회귀 테스트가 필요함
  • 애자일: 변경을 전제로 가벼운 문서와 광범위한 자동화를 선호하고, 수동 테스트는 주로 경험 기반 기법으로 수행함

모델과 무관한 좋은 실천

  • 모든 개발 활동에 대응하는 테스트 활동이 있음
  • 테스트 레벨마다 목적을 달리해 중복 없이 충분히 테스트함
  • 각 레벨의 테스트 분석과 설계를 대응하는 개발 단계에서 시작함
  • 산출물 초안이 나오는 즉시 리뷰에 참여함

테스트 우선 개발 방식

섹션 제목: “테스트 우선 개발 방식”
방식 핵심
TDD(테스트 주도 개발) TC로 코딩을 이끎. 테스트를 먼저 작성하고, 통과하도록 코드를 작성한 뒤, 테스트와 코드를 리팩터링함
ATDD(인수 테스트 주도 개발) 시스템 설계 과정에서 인수 기준으로부터 테스트를 도출하고, 해당 부분을 개발하기 전에 작성함
BDD(행위 주도 개발) 원하는 동작을 이해관계자가 읽을 수 있는 자연어(주로 Given/When/Then)로 TC에 표현하고, 이를 실행 가능한 테스트로 변환함

세 방식 모두 조기 테스팅 원칙을 구현하고, 테스트가 자동화 테스트로 남아 이후 변경과 리팩터링에서 코드 품질을 지킨다.

DevOps와 시프트 레프트

섹션 제목: “DevOps와 시프트 레프트”

DevOps는 개발(테스트 포함)과 운영이 공동 목표를 위해 함께 일하는 조직 접근법이다. 테스트 관점의 이점은 빠른 피드백, CI를 통한 시프트 레프트, 안정적인 테스트 환경, 비기능 특성의 가시성, 반복 수동 테스트 감소, 회귀 리스크 감소다. 반면 배포 파이프라인 정의, CI/CD 도구 도입과 유지, 자동화에 필요한 추가 자원이 부담이 된다. 자동화 비중이 높아도 사용자 관점의 수동 테스트는 여전히 필요하다.

시프트 레프트는 테스트를 개발 수명주기의 더 이른 시점에 수행하는 접근법이다. 뒤 단계 테스트를 소홀히 한다는 뜻은 아니다.

  • 테스터 관점에서 명세 리뷰
  • 코드 작성 전에 TC 작성, 구현 중 테스트 하네스에서 코드 실행
  • CI와 CD로 빠른 피드백과 자동 컴포넌트 테스트
  • 동적 테스트 전에 정적 분석 수행
  • 가능한 경우 컴포넌트 레벨부터 비기능 테스트 수행

회고

섹션 제목: “회고”

반복이나 프로젝트가 끝날 때 무엇이 잘 되었고, 무엇을 개선할지, 어떻게 유지하고 개선할지를 논의한다. 결과는 테스트 완료 보고서에 기록하고, 개선 항목은 후속 조치를 확인한다.

테스트 레벨, 테스트 유형, 확인·회귀 테스트

섹션 제목: “테스트 레벨, 테스트 유형, 확인·회귀 테스트”
  • 테스트 레벨 다섯: 컴포넌트, 컴포넌트 통합, 시스템, 시스템 통합, 인수. 레벨은 테스트 대상, 목적, 테스트 베이시스, 결함과 장애, 접근법과 책임으로 구분함
  • 테스트 유형 넷: 기능, 비기능, 블랙박스, 화이트박스. 모든 레벨에 적용할 수 있음
  • 확인 테스트: 원래의 결함이 제대로 수정되었는지 확인함
  • 회귀 테스트: 변경(이미 확인 테스트를 마친 수정 포함)이 나쁜 영향을 주지 않았는지 확인함. 범위를 정하기 전에 영향 분석을 수행하고, 반복 실행되므로 자동화의 우선 대상임

자세한 내용과 TC 예시는 테스트 레벨과 테스트 유형과 회귀 테스트 범위 선정에 있다.

유지보수 테스트

섹션 제목: “유지보수 테스트”

운영 중인 시스템의 변경을 테스트한다. 변경이 성공적으로 구현되었는지와 변경하지 않은 부분(대개 시스템의 대부분)에 회귀가 없는지를 함께 확인한다. 범위는 변경의 리스크, 기존 시스템의 크기, 변경의 크기로 정한다.

  • 계기 1, 수정: 계획된 기능 개선, 결함 수정, 핫픽스
  • 계기 2, 운영 환경의 업그레이드나 이전: 새 환경에서의 테스트, 데이터 이전 시 데이터 변환 테스트
  • 계기 3, 폐기: 데이터 보관 테스트, 보관 뒤 복원·조회 절차 테스트

3장. 정적 테스트

섹션 제목: “3장. 정적 테스트”

정적 테스트의 대상과 가치

섹션 제목: “정적 테스트의 대상과 가치”

정적 테스트는 소프트웨어를 실행하지 않고 산출물을 사람의 검토(리뷰)나 도구(정적 분석)로 평가한다. 읽고 이해할 수 있는 산출물은 모두 리뷰 대상이다(요구사항, 코드, 테스트 계획, TC, 백로그 항목, 계약서 등). 정적 분석은 구조가 정해진 산출물(코드, 모델, 형식이 있는 문서)에 적용한다.

  • 개발 수명주기 초기에 결함을 찾음
  • 동적 테스트로 찾을 수 없는 결함(도달할 수 없는 코드, 의도대로 구현되지 않은 설계 패턴, 실행할 수 없는 산출물의 결함)을 찾음
  • 이해관계자 사이에 공통 이해를 만들고 소통을 개선함
  • 리뷰에도 비용이 들지만, 리뷰하지 않을 때 뒤에서 결함을 수정하는 비용보다 대체로 적음
비교 정적 테스트 동적 테스트
결함 발견 방식 결함을 직접 찾음 장애를 일으킨 뒤 분석으로 결함을 찾음
적용 대상 실행할 수 없는 산출물 포함 실행 가능한 산출물만
잘 찾는 곳 거의 실행되지 않거나 도달하기 어려운 경로 실행해야 드러나는 동작
측정하는 품질 특성 실행과 무관한 특성(유지보수성 등) 실행에 의존하는 특성(성능 효율성 등)

정적 테스트로 더 쉽거나 싸게 찾는 결함

  • 요구사항 결함: 불일치, 모호함, 모순, 누락, 부정확, 중복
  • 설계 결함: 비효율적인 DB 구조, 잘못된 모듈화
  • 일부 코딩 결함: 값이 정해지지 않은 변수, 선언하지 않은 변수, 도달할 수 없거나 중복된 코드, 과도한 복잡도
  • 표준 위반: 명명 규칙 미준수
  • 인터페이스 명세 오류: 파라미터의 개수, 타입, 순서 불일치
  • 특정 보안 취약점: 버퍼 오버플로
  • 테스트 베이시스 커버리지 누락: 인수 기준에 대응하는 테스트 누락

리뷰 프로세스와 역할

섹션 제목: “리뷰 프로세스와 역할”

ISO/IEC 20246이 정한 일반 리뷰 프로세스의 활동은 다음과 같다. 형식을 갖춘 리뷰일수록 더 많은 작업을 수행한다.

  1. 계획: 목적, 대상 산출물, 평가할 품질 특성, 중점 영역, 종료 기준, 일정을 정의함
  2. 리뷰 착수: 참가자가 산출물에 접근하고 역할과 책임을 이해하도록 준비함
  3. 개별 리뷰: 리뷰어마다 체크리스트 기반, 시나리오 기반 등의 기법으로 이상, 제안, 질문을 기록함
  4. 의사소통과 분석: 이상이 결함인지 분석하고 상태, 담당자, 조치를 결정함
  5. 수정과 보고: 결함 보고서를 작성하고, 종료 기준을 만족하면 산출물을 승인함
역할 책임
관리자 리뷰 대상을 정하고 인력과 시간을 제공함
작성자 리뷰 대상 산출물을 작성하고 수정함
중재자(퍼실리테이터) 리뷰 회의를 효과적으로 진행하고 누구나 자유롭게 말할 수 있는 환경을 만듦
기록자 리뷰어의 이상을 모으고 결정 사항과 새로 찾은 이상을 기록함
리뷰어 리뷰를 수행함. 프로젝트 구성원, 전문가, 이해관계자 누구나 가능함
리뷰 리더 참가자, 일정, 장소를 정하는 등 리뷰 전체를 책임짐

리뷰 유형

섹션 제목: “리뷰 유형”
유형 형식 수준 주도 주된 목적
비공식 리뷰 정해진 프로세스와 문서 산출물 없음 정해지지 않음 이상 발견
워크스루 중간 작성자 품질 평가, 신뢰 형성, 리뷰어 교육, 합의, 아이디어, 이상 발견
기술 리뷰 중간 중재자. 기술 역량이 있는 리뷰어 참여 기술 문제에 대한 합의와 결정, 이상 발견
인스펙션 가장 높음. 일반 프로세스 전체 수행, 지표 수집 리뷰 리더(작성자는 리뷰 리더나 기록자를 맡을 수 없음) 최대한 많은 이상 발견

리뷰가 성공하려면 명확한 목적과 측정 가능한 종료 기준(참가자 평가는 목적이 될 수 없음), 목적에 맞는 리뷰 유형, 작은 단위로 나눈 리뷰, 충분한 준비 시간, 관리자의 지원, 참가자 교육, 회의 진행이 필요하다.

4장. 테스트 분석과 설계

섹션 제목: “4장. 테스트 분석과 설계”

기법을 블랙박스(동등 분할, 경계값 분석, 결정 테이블, 상태 전이), 화이트박스(구문 테스트, 분기 테스트), 경험 기반(오류 추측, 탐색적 테스트, 체크리스트 기반)으로 나누고, 협업 기반 접근법(협업 스토리 작성, 인수 기준, ATDD)을 다룬다. 정의, 커버리지 계산, 예시는 테스트 기법 분류와 기법별 문서에 정리했다.

5장. 테스트 활동 관리

섹션 제목: “5장. 테스트 활동 관리”

테스트 계획서

섹션 제목: “테스트 계획서”

계획서는 테스트 목적, 자원, 프로세스를 기술하고 이해관계자와 소통하는 수단이다. 전형적인 내용은 다음과 같다.

  • 테스트 정황: 범위, 목적, 테스트 베이시스
  • 가정과 제약
  • 이해관계자: 역할, 책임, 채용·교육 필요
  • 의사소통: 형식, 빈도, 문서 양식
  • 리스크 목록: 제품 리스크, 프로젝트 리스크
  • 테스트 접근법: 레벨, 유형, 기법, 산출물, 진입·종료 기준, 독립성, 수집할 지표, 테스트 데이터와 환경 요구, 테스트 정책·전략과 다른 점
  • 예산과 일정

반복형 개발에서 테스터는 릴리즈 계획(테스트 가능한 스토리와 인수 기준 작성, 리스크 분석, 테스트 노력 추정)과 반복 계획(스토리의 상세 리스크 분석, 테스트 용이성 판단, 테스트 작업 분해와 추정)에 참여한다.

진입 기준과 종료 기준

섹션 제목: “진입 기준과 종료 기준”
  • 진입 기준: 활동을 시작하기 위한 사전 조건. 예: 인력·도구·환경·데이터 확보, 테스트 가능한 요구사항 확보, 스모크 테스트 통과
  • 종료 기준: 활동 완료를 선언하기 위한 조건. 예: 커버리지 달성 수준, 미해결 결함 수, 결함 밀도, 실패 TC 수(철저함 측정), 계획한 테스트 실행 여부와 회귀 테스트 자동화 여부(예·아니요 판정)
  • 시간과 예산 소진도 종료 기준이 될 수 있음. 단, 이해관계자가 추가 테스트 없이 출시하는 리스크를 검토하고 수용한 경우에 한함
  • 애자일에서는 종료 기준을 완료 정의(DoD, Definition of Done), 스토리의 진입 기준을 준비 정의(DoR, Definition of Ready)라고 부름

추정 기법

섹션 제목: “추정 기법”
기법 방식 예
비율 기반 조직의 과거 프로젝트 비율을 사용함 이전 프로젝트의 개발 대 테스트 노력이 3:2이고 이번 개발 노력이 600인일이면 테스트 노력은 400인일
외삽 현재 프로젝트 초기 측정값으로 남은 작업을 추정함 직전 세 반복의 평균 테스트 노력으로 다음 반복을 추정
와이드밴드 델파이 전문가가 각자 추정하고, 편차가 크면 논의 후 다시 각자 추정하는 과정을 합의까지 반복함. 플래닝 포커는 그 변형 스토리 포인트 카드로 추정
3점 추정 낙관(a), 최빈(m), 비관(b) 추정의 가중 평균. E = (a + 4m + b) / 6, 표준편차 SD = (b - a) / 6 a=6, m=9, b=18이면 E=10, SD=2. 즉 10±2인시

큰 작업은 작은 작업으로 나눠 추정하면 정확도가 높아진다. 추정은 가정에 기반하고 오차가 있다는 점을 이해관계자에게 분명히 알린다.

TC 우선순위

섹션 제목: “TC 우선순위”
  • 리스크 기반: 리스크 분석 결과로 순서를 정하고 가장 중요한 리스크를 다루는 TC부터 실행함
  • 커버리지 기반: 커버리지(예: 구문 커버리지)가 가장 높은 TC부터 실행함. 변형인 추가 커버리지 우선순위는 매번 추가 커버리지가 가장 큰 TC를 다음으로 실행함
  • 요구사항 기반: 이해관계자가 정한 요구사항 우선순위를 따름

우선순위가 높은 TC가 낮은 TC에 의존하면 낮은 TC를 먼저 실행한다. 도구, 환경, 사람을 쓸 수 있는 시간대도 실행 순서에 반영한다. 위키의 우선순위 등급 예는 리스크 기반 테스트에 있다.

테스트 피라미드와 테스트 사분면

섹션 제목: “테스트 피라미드와 테스트 사분면”

테스트 피라미드는 테스트마다 세분성(Granularity)이 다르다는 것을 보여 주는 모델이다. 위로 갈수록 세분성과 격리 수준이 낮고 실행 시간이 길다. 아래층은 작고 격리되고 빠른 테스트라 많이 필요하고, 위층은 복잡한 E2E 테스트라 적은 수로 충분한 커버리지를 얻는다. 원래 모델(Cohn 2009)은 단위, 서비스, UI 세 층이고, 단위(컴포넌트), 통합(컴포넌트 통합), E2E로 나누는 모델도 많이 쓴다.

테스트 사분면(Marick)은 애자일에서 테스트 레벨, 유형, 활동을 두 축으로 묶는다. 축 하나는 비즈니스 관점과 기술 관점, 다른 하나는 팀 지원(개발을 안내함)과 제품 비평(기대와 비교해 평가함)이다.

사분면 관점 포함하는 테스트 수행 방식
Q1 기술, 팀 지원 컴포넌트, 컴포넌트 통합 테스트 자동화해 CI에 포함
Q2 비즈니스, 팀 지원 기능 테스트, 예시, 스토리 테스트, UX 프로토타입, API 테스트, 시뮬레이션 수동 또는 자동. 인수 기준 확인
Q3 비즈니스, 제품 비평 탐색적 테스트, 사용성 테스트, 사용자 인수 테스트 주로 수동
Q4 기술, 제품 비평 스모크 테스트, 비기능 테스트(사용성 제외) 주로 자동

리스크 관리

섹션 제목: “리스크 관리”

리스크는 발생하면 나쁜 영향을 주는 잠재적 사건이나 상황이다. 리스크 가능성(0보다 크고 1보다 작은 발생 확률)과 리스크 영향(발생 시 결과)이 리스크 수준을 정한다. 리스크 관리는 리스크 분석(식별과 평가)과 리스크 통제(완화와 모니터링)로 구성되고, 리스크 분석과 통제로 테스트 활동을 선택하고 우선순위를 정하는 접근법이 리스크 기반 테스트다.

구분 프로젝트 리스크 제품 리스크
관련 대상 프로젝트의 관리와 통제 제품 품질 특성
예 산출물 지연, 부정확한 추정, 인력 부족과 역량 부족, 범위 확대, 도구 지원 부족, 외부 공급자 문제 기능 누락·오류, 계산 오류, 런타임 오류, 목표 응답 시간 초과, 나쁜 사용자 경험, 보안 취약점
발생 시 영향 일정, 예산, 범위 사용자 불만, 매출·신뢰 손실, 제3자 피해, 유지보수 비용, 법적 처벌, 극단적으로 인명 피해
  • 제품 리스크 분석: 브레인스토밍, 워크숍, 인터뷰, 원인 결과 다이어그램으로 식별하고, 분류와 가능성·영향 평가로 우선순위를 정함. 정량 방식은 가능성 x 영향, 정성 방식은 리스크 매트릭스를 사용함
  • 분석 결과의 사용: 테스트 범위, 레벨과 유형, 기법과 커버리지, 작업별 노력 추정, 우선순위, 테스트 외 추가 활동을 정함
  • 리스크 대응: 테스트로 완화, 수용, 전가, 비상 계획 중에서 선택함. 테스트로 완화하는 방법은 적합한 테스터 배정, 적절한 독립성, 리뷰와 정적 분석, 적절한 기법과 커버리지, 해당 품질 특성의 테스트 유형, 회귀 테스트를 포함한 동적 테스트임

실무 적용은 리스크 기반 테스트에 있다.

모니터링, 통제, 완료와 보고

섹션 제목: “모니터링, 통제, 완료와 보고”
  • 모니터링: 테스트 정보를 모아 진행 상황과 종료 기준 충족 여부를 평가함
  • 통제 지시: 리스크가 현실화되면 우선순위를 재조정함. 재작업 후 진입·종료 기준을 재평가하고, 환경 지연에 맞춰 일정을 조정하고, 필요한 곳에 자원을 추가함
  • 완료: 레벨 완료, 반복 종료, 출시 같은 마일스톤에서 경험과 테스트웨어를 정리함
지표 분류 예
프로젝트 진행 작업 완료율, 자원 사용, 테스트 노력
테스트 진행 TC 구현 진행률, 실행·미실행 수, 통과·실패 수, 실행 시간
제품 품질 가용성, 응답 시간, 평균 고장 시간(MTTF, 장애 발생까지의 평균 동작 시간)
결함 발견·수정 결함 수와 우선순위, 결함 밀도, 결함 검출률
리스크 남은 리스크 수준
커버리지 요구사항 커버리지, 코드 커버리지
비용 테스트 비용, 조직의 품질 비용
  • 진행 보고서(정기): 기간, 진행 상황과 편차, 장애물과 우회책, 지표, 새로 생겼거나 바뀐 리스크, 다음 기간 계획
  • 완료 보고서(1회): 요약, 계획 대비 테스트와 제품 품질 평가, 계획과의 편차, 장애물, 지표, 완화되지 않은 리스크와 수정되지 않은 결함, 교훈
  • 전달 수단: 구두, 대시보드(CI/CD 대시보드, 작업 보드, 번다운 차트), 메일·채팅, 온라인 문서, 공식 보고서. 이해관계자마다 필요한 정보가 다르므로 맞춰서 전달함

형상 관리

섹션 제목: “형상 관리”

테스트 계획, TC, 스크립트, 결과, 로그, 보고서를 형상 항목으로 식별, 통제, 추적한다. 모든 형상 항목은 고유하게 식별되고 버전이 관리되며 다른 항목과 연결되어 추적성을 유지한다. 테스트 환경처럼 복잡한 항목은 구성 요소와 관계, 버전을 기록하고, 테스트용으로 승인되면 베이스라인이 되어 공식 변경 통제로만 바꾼다. 이전 베이스라인으로 돌아가 이전 테스트 결과를 재현할 수 있다.

결함 관리

섹션 제목: “결함 관리”

보고된 이상은 실제 결함일 수도, 다른 것(거짓 양성 결과, 변경 요청)일 수도 있다. 결함 관리 프로세스는 최소한 발견부터 종결까지의 워크플로와 분류 규칙을 포함하고, 모든 이해관계자가 따라야 한다.

동적 테스트에서 기록하는 결함 보고서의 전형적인 항목

  • 고유 식별자, 요약 제목
  • 관찰 날짜, 작성 조직과 작성자(역할 포함)
  • 테스트 대상과 테스트 환경
  • 정황(수행 중이던 TC, 테스트 활동, 개발 단계, 사용한 기법·체크리스트·데이터)
  • 재현과 해결에 필요한 장애 설명(절차, 로그, DB 덤프, 스크린샷, 녹화)
  • 기대 결과와 실제 결과
  • 심각도(영향 정도), 수정 우선순위
  • 상태(열림, 보류, 중복, 수정 대기, 확인 테스트 대기, 재개, 종결, 거부)
  • 참조(관련 TC 등)

위키의 양식과 상태 전이는 이슈 양식, 심각도 기준, 결함 생명주기에 있다.

6장. 테스트 도구

섹션 제목: “6장. 테스트 도구”

도구 유형: 테스트 관리, 정적 테스트, 테스트 설계·구현, 테스트 실행·커버리지 측정, 비기능 테스트, DevOps(파이프라인, 빌드 자동화, CI/CD), 협업, 확장성과 배포 표준화(가상 머신, 컨테이너), 그 밖에 테스트를 돕는 모든 도구(스프레드시트 포함).

도구를 도입하는 것만으로 성공이 보장되지는 않는다. 도입, 유지보수, 교육에 노력이 들고, 분석하고 완화해야 할 리스크가 있다. 자동화의 이점과 위험은 테스트 자동화 기본에 정리했다.

실무에서 이 실라버스를 사용하는 방법

섹션 제목: “실무에서 이 실라버스를 사용하는 방법”
  • 팀의 용어를 맞추는 기준으로 사용함. 결함과 장애, 확인 테스트와 회귀 테스트, 진입 기준과 종료 기준처럼 혼동하기 쉬운 용어를 실라버스 정의로 통일함(용어 사전)
  • 테스트 계획서 목차의 점검표로 사용함. 5장의 계획서 내용과 보고서 내용을 빠짐없이 다뤘는지 확인함
  • 신규 팀원 교육의 순서로 사용함. 1장(원칙과 활동), 4장(기법), 5장(계획과 보고) 순으로 익히고 위키의 실무 문서로 이어 감

규칙

  • 이 문서는 실라버스 v4.0.1의 내용을 정리한 것이며 학습 목표의 수준(K1~K3)과 시험 정보는 다루지 않음. 시험 준비는 원문과 공식 샘플 문제를 사용함
  • 실라버스 원문의 저작권은 ISTQB에 있음. 테스트 목적, 계획서 내용, 결함 보고서 항목 같은 목록은 원문의 항목 구성을 유지해 우리말로 옮겼고, 설명 문장은 요약함

관련 문서

기초와 용어테스팅의 7원칙테스팅의 일반 원칙 7가지(ISTQB CTFL v4.0.1 1.3)는 테스트로 보장할 수 있는 것과 없는 것을 정한다. 원칙마다 뜻과 근거, 테스트 계획·설계·보고에 반영하는 방법을 사례와 함께 설명한다.테스트 설계테스트 기법 분류: 블랙박스, 화이트박스, 경험 기반, 협업 기반테스트 기법은 블랙박스(명세 기반), 화이트박스(구조 기반), 경험 기반, 협업 기반으로 나뉜다. 분류마다 정의, 근거, 커버리지, 강점과 한계를 설명하고 구문·분기 커버리지 계산 예를 든다.기초와 용어테스트 레벨과 테스트 유형테스트 레벨은 시스템을 어느 통합 단계에서 검증하는지를, 테스트 유형은 어떤 품질 특성을 검증하는지를 나타내는 분류다. 두 분류는 서로 독립이며, 테스트마다 레벨을 하나 정하고 테스트 유형은 하나 이상 적용할 수 있다.자동화테스트 자동화 기본테스트 자동화는 도구로 테스트를 실행하고 결과를 판정하는 활동이다. 이점과 한계, 테스트 피라미드, 테스트 용이성, 자동화 아키텍처(gTAA)와 프레임워크 계층, 케이스 자동화 방식 7가지, 도입 절차와 파이프라인 배치, 작성 원칙을 ISTQB CTAL-TAE 기준으로 설명한다.
