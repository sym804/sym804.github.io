테스트 레벨과 테스트 유형

테스트 레벨은 시스템을 어느 통합 단계에서 검증하는지를, 테스트 유형은 어떤 품질 특성을 검증하는지를 나타내는 분류다. 두 분류는 서로 독립이며, 테스트마다 레벨을 하나 정하고 테스트 유형은 하나 이상 적용할 수 있다.

기본기난이도 기초최종 업데이트 2026-11-24

레벨은 “어디까지 조립한 상태에서 확인하는가”, 유형은 “무엇을 확인하는가”를 정한다. 두 분류를 하나의 순서로 취급하면 레벨별로 필요한 테스트 유형이 계획에서 누락된다.

테스트 레벨

섹션 제목: “테스트 레벨”

ISTQB CTFL v4.0.1은 다섯 레벨을 정의한다.

레벨 대상 주로 검출하는 결함
컴포넌트(Component) 함수, 클래스, 모듈을 격리한 단위 계산 오류
분기 누락
경계 처리 오류
컴포넌트 통합(Component Integration) 컴포넌트 사이의 인터페이스와 상호작용 인자 형식 불일치
호출 순서 오류
예외 전파 누락
시스템(System) 조립을 마친 시스템 전체의 동작 요구사항 미충족
종단 흐름 오류
비기능 특성 미달
시스템 통합(System Integration) 다른 시스템, 외부 서비스와의 인터페이스 외부 응답 형식 변화
타임아웃과 재시도 처리 오류
인수(Acceptance) 사용자와 운영 관점의 배포 가능 여부 업무 흐름과의 불일치
운영 절차(백업, 복구) 미비
  • 인수 테스트는 사용자 인수, 운영 인수, 계약·규제 인수, 알파·베타 테스트로 나뉨
  • 화면을 조작하는 E2E 테스트는 대개 시스템 레벨에 해당함. API를 직접 호출하는 테스트는 대상 범위에 따라 컴포넌트 통합 또는 시스템 레벨임

테스트 유형

섹션 제목: “테스트 유형”

ISTQB CTFL v4.0.1은 아래 넷을 다루며, 각각 특정 품질 특성과 관련된 테스트 활동의 묶음이다.

  • 기능 테스트(Functional Testing): 컴포넌트나 시스템이 수행해야 하는 기능, 즉 “무엇을 하는가”를 평가함. 기능 완전성, 기능 정확성, 기능 적절성을 확인함
  • 비기능 테스트(Non-functional Testing): 기능 외 특성, 즉 “얼마나 잘 동작하는가”를 평가함. ISO/IEC 25010:2023의 비기능 품질 특성(성능 효율성, 호환성, 상호작용 능력(이전 명칭 사용성), 신뢰성, 보안성, 유지보수성, 유연성(이전 명칭 이식성), 안전성)을 확인함. 많은 비기능 테스트는 기능 테스트를 그대로 수행하면서 비기능 제약(정해진 시간 안에 처리되는지 등)을 함께 확인하는 방식으로 도출됨. 특성 전체는 ISO/IEC 25010 품질 모델 참고
  • 블랙박스 테스트(Black-box Testing): 명세 기반 테스트. 테스트 대상의 내부 구조와 무관한 문서(요구사항, 사용자 스토리, API 명세)에서 테스트를 도출하고, 시스템의 동작이 명세와 일치하는지 확인하는 것이 주된 목적임. 구현이 바뀌어도 요구 동작이 같으면 TC를 그대로 사용함. 동등 분할, 경계값 분석, 결정 테이블, 상태 전이가 대표 기법임
  • 화이트박스 테스트(White-box Testing): 구조 기반 테스트. 시스템의 구현이나 내부 구조(코드, 아키텍처, 워크플로, 데이터 흐름)에서 테스트를 도출하고, 그 구조를 받아들일 수 있는 수준까지 테스트로 수행(커버)하는 것이 주된 목적임. 설계나 구현이 있어야 TC를 작성할 수 있고, 구문 커버리지와 분기 커버리지로 측정함

블랙박스와 화이트박스의 구분 기준은 수행자(테스터인지 개발자인지)가 아니라 TC를 도출한 근거다. 정의, 커버리지 계산 예, 경험 기반 기법은 테스트 기법 분류에 있다.

결함을 수정한 뒤에는 확인 테스트(원래 결함이 수정되었는지)와 회귀 테스트를 수행한다. 기능 추가나 환경 변경 뒤에도 변경한 영역을 포함해 기존 동작에 나쁜 영향이 없는지 회귀 테스트로 확인한다. 자세한 내용은 회귀 테스트 범위 선정에 있다.

모든 유형은 모든 레벨에서 수행할 수 있다. 함수 하나의 처리 시간을 측정하면 컴포넌트 레벨의 비기능 테스트이고, 외부 서비스 연동 코드의 오류 처리 분기를 모두 거치도록 설계하면 시스템 통합 레벨의 화이트박스 테스트다.

레벨별 검증 배분

섹션 제목: “레벨별 검증 배분”
  • 결함을 처음 검출할 수 있는 가장 낮은 레벨에 TC를 배치함
  • 입력 분기, 오류 처리, 계산 규칙은 컴포넌트·통합 레벨에서 모두 확인함. 화면 E2E에서는 같은 규칙을 대표 사례 하나로만 확인함
  • 시스템 레벨에는 여러 컴포넌트를 거치는 흐름과 실제 배포 구성에서만 드러나는 항목(설정, 외부 연동, 화면 표시)을 배치함
  • 상위 레벨 실패는 원인 후보가 넓어 분석 시간이 길어짐. 같은 결함을 하위 레벨에서 검출하면 실패한 위치가 바로 특정됨

규칙

  • 하위 레벨에서 확인할 수 있는 분기를 E2E 테스트에 모두 몰지 않음
  • 하위 레벨 통과만으로 연결 확인을 생략하지 않음. 규칙마다 화면이나 API 응답까지 이어지는지 상위 레벨에서 한 번 확인함

레벨별 TC 예시

섹션 제목: “레벨별 TC 예시”
레벨 TC 예시
컴포넌트 최소 주문 금액이 30,000원(예시 값)인 할인 계산 함수에 주문 금액 29,999원, 30,000원, 30,001원을 입력해 할인액 0원, 3,000원, 3,000원을 반환하는지 확인함
컴포넌트 통합 주문 서비스가 결제 모듈에 전달하는 금액, 통화, 주문 id가 주문 저장 값과 같은지 확인함. 결제 모듈이 예외를 던지면 주문 상태가 결제 대기로 유지되고 오류가 호출자에게 전달되는지 확인함
시스템 운영과 같은 배포 구성의 환경에서 화면으로 상품 담기부터 결제 완료까지 수행해 주문 내역 화면의 금액이 저장 값과 같은지 확인함
시스템 통합 외부 배송 조회 API를 대역으로 대체해 10초(예시 값) 지연과 503을 반환하게 하고, 재시도 횟수와 간격이 명세와 같고 화면에 조회 지연 안내가 표시되는지 확인함. 실제 외부 API와의 정상 연동은 별도 TC 1건으로 확인함
인수 운영 담당자가 운영 절차서대로 백업 복원을 수행해 지정한 시각 기준의 데이터가 복원되고, 목표 복구 시간(예: 1시간) 안에 서비스가 재개되는지 확인함

적용 예: 회원 가입 기능의 레벨·유형 배분

섹션 제목: “적용 예: 회원 가입 기능의 레벨·유형 배분”

기획서에 “이메일과 비밀번호로 가입한다. 비밀번호는 8자 이상 64자 이하이고, 가입하면 환영 메일을 발송한다.“만 있는 경우 레벨과 유형별로 배치할 TC는 다음과 같다.

  • 컴포넌트, 기능: 비밀번호 길이 7자, 8자, 64자, 65자의 판정. 이메일 형식 검증의 동등 분할(정상, @ 없음, 도메인 없음, 공백 포함)
  • 컴포넌트, 보안: 비밀번호가 해시로 저장되고, 같은 비밀번호를 두 번 저장했을 때 해시 값이 서로 다른지(솔트 적용)
  • 컴포넌트 통합: 가입 서비스가 저장소의 중복 키 예외를 409 응답으로 변환하는지. 메일 발송 모듈에 수신 주소와 템플릿 id가 정확히 전달되는지
  • 시스템, 기능: 화면에서 가입한 뒤 로그인까지 이어지는 대표 사례 1건. 서버 검증 오류 문구가 해당 입력란에 표시되는 사례 1건
  • 시스템, 보안·신뢰성: 같은 이메일로 가입 요청 2건을 동시에 전송해 계정이 1개만 생성되는지. 가입 응답 본문에 비밀번호 해시가 포함되지 않는지
  • 시스템 통합: 메일 서비스가 타임아웃이나 5xx를 반환할 때 가입이 완료되고 메일이 재발송 대상으로 기록되는지. 명세에 없으므로 기획과 확인할 항목으로 기록
  • 인수: 가입 직후 화면과 환영 메일의 문구가 운영 정책(약관 동의, 수신 거부 안내)과 맞는지
  • 변경 뒤: 비밀번호 규칙이 변경되면 새 규칙의 길이 판정 TC(컴포넌트)와 로그인·비밀번호 변경 흐름의 회귀 범위. 기존 결함을 수정한 경우에는 그 결함의 재현 절차가 확인 테스트 대상

비밀번호 길이 경계 4개는 컴포넌트 레벨에서 모두 확인하고, 화면 E2E에서는 오류 문구 표시 1건만 확인한다. 동시 가입, 외부 메일 서비스 장애, 응답의 민감 정보는 기능 테스트 관점만으로 도출되지 않는 항목이다.

테스트 계획, 결함 분류, 보고에 적용

섹션 제목: “테스트 계획, 결함 분류, 보고에 적용”

테스트 계획

  • 레벨마다 대상, 수행자, 환경, 시작 기준과 종료 기준을 기록함. 예: 컴포넌트 테스트는 개발자가 PR마다 실행하고 실패 0건을 병합 조건으로 두고, 시스템 테스트는 QA가 스테이징 환경에서 수행함
  • 레벨과 유형을 축으로 표를 작성해 빈칸을 확인함. 빈칸마다 다른 레벨에서 확인하는지, 이번 범위에서 제외하는지와 그 사유를 기록함
  • 시스템 통합 레벨은 항목마다 실제 외부 시스템을 연결하는지, 대역으로 대체하는지를 명시함. 대역으로만 확인한 항목은 실제 연동 확인을 별도로 계획함

결함 분류

  • 결함마다 검출한 레벨과, 명세나 코드 기준으로 검출할 수 있었던 가장 낮은 레벨을 함께 기록함
  • 두 레벨이 다른 결함을 릴리즈 단위로 집계해 하위 레벨 테스트의 누락 영역을 찾음. 예: 계산 오류가 E2E에서 주로 검출되면 해당 모듈의 컴포넌트 TC를 보강함
  • 운영에서 발견된 결함은 운영 유출 결함으로 별도 집계하고, 해당 조건이 인수 테스트 범위에 있었는지 함께 기록함

품질 보고

  • 결과를 레벨별로 나눠 보고함. 전체 통과 건수 하나로 보고하면 시스템 레벨 미수행 여부가 보고서에 남지 않음
  • 레벨과 유형 표의 빈칸을 미검증 범위로 보고서에 기록함. 예: “성능: 컴포넌트 레벨 측정만 수행, 시스템 부하 테스트 미수행”

현장 노트

  • 파일 업로드 기능에서 같은 File 객체를 다시 사용할 때만 발생하는 결함이 있었음. Playwright의 setInputFiles와 파일 선택 창은 매번 새 File 객체를 생성해 E2E로는 검출되지 않았고, 컴포넌트 레벨 단위 테스트에서만 검출됨
  • 수집 스크립트의 실패 판정 함수는 단위 테스트를 통과했지만, 진입점이 sys.exit(main())이 아니라 main()만 호출해 판정 결과 1이 프로세스 종료코드로 전달되지 않음. 배치는 종료코드 0이면 완료 표시를 갱신하므로 중단된 수집의 재시도가 다음 주기까지 실행되지 않음. 진입점 형태를 고정하는 테스트를 추가함
  • 다른 스크립트에서는 검사 4건이 모두 main([...])을 직접 호출해 if __name__ 블록을 한 번도 실행하지 않았음. 그 블록의 import sys 누락으로 배치 실행이 즉시 NameError로 실패하는 상태였는데 검사 4건은 모두 통과함. --help 인자로 스크립트를 하위 프로세스로 실행하는 검사를 추가함
  • 함수 테스트 4건이 모두 함수 내부만 확인하고, 함수를 호출하는 쪽의 조건이 잘못되어 매일 발행하는 글에서 카드 4종이 빠짐(3일치 확인 결과 0개). 호출 조건을 검증하는 컴포넌트 통합 레벨 테스트가 없었음
  • 백테스트 산출물을 재생성한 뒤에도 화면 카드에는 이전 수치가 표시됨. 같은 수치의 사본이 라우터 매핑, 캐시, 프리워밍, 월간 스냅샷, 소스 하드코딩 다섯 곳에 있었고, 그중 하나는 17.05와 17.26처럼 값이 비슷해 화면만 보고는 차이를 알기 어려웠음. 산출물을 재생성한 뒤 API를 직접 호출해 화면에 표시되는 값과 대조하는 단계를 추가함

흔한 실수

섹션 제목: “흔한 실수”
  • 레벨과 유형을 한 줄의 순서로 취급함. 예: “기능 테스트 다음이 통합 테스트”, “비기능 테스트는 시스템 테스트가 끝난 뒤에만 수행”
  • 입력 검증 규칙 전체를 화면 E2E로 반복 작성함. 실행 시간과 Flaky 테스트가 늘고 실패 원인 분석이 어려워짐
  • 화이트박스 커버리지가 높다는 이유로 요구사항 충족을 판정함. 코드 커버리지는 명세에 있는데 구현하지 않은 기능을 검출하지 못함

관련 문서

기초와 용어API 테스트 기본화면을 거치지 않고 API에 직접 요청을 보내 응답 계약, 상태 코드, 서버 측 검증, 인가를 확인하는 테스트다. 화면 제약만으로는 확인할 수 없는 서버 동작이 대상이다.프로세스회귀 테스트 범위 선정변경 뒤 기존 기능이 의도하지 않게 실패하는지 확인하기 위해, 회귀 스위트에서 이번 회차에 수행할 TC를 선택하는 절차다(Regression Test Selection).자동화E2E 테스트 전 빌드빌드 산출물을 대상으로 E2E 테스트를 실행하는 구성에서는 소스를 수정해도 다시 빌드하지 않으면 이전 번들로 테스트가 실행된다.테스트 설계테스트 기법 분류: 블랙박스, 화이트박스, 경험 기반, 협업 기반테스트 기법은 블랙박스(명세 기반), 화이트박스(구조 기반), 경험 기반, 협업 기반으로 나뉜다. 분류마다 정의, 근거, 커버리지, 강점과 한계를 설명하고 구문·분기 커버리지 계산 예를 든다.
