품질비용

품질 활동과 결함에 드는 총비용을 예방, 평가, 내부 실패, 외부 실패로 나누어 보는 품질비용(CoQ, Cost of Quality)의 정의와 구조, 결함 발견 시점별 수정 비용 연구의 근거와 반론, QA 리포팅에 적용하는 방법.

기본기난이도 기초최종 업데이트 2026-11-24

품질비용(CoQ, Cost of Quality)은 품질 활동과 결함 때문에 발생하는 비용의 합계다. ISTQB 용어집은 품질비용을 결함 예방 비용, 평가 비용, 내부 실패 비용, 외부 실패 비용으로 구성된 총비용으로 정의하고, 출처로 미국품질학회(ASQ)를 적는다. 이 네 분류 체계는 예방(Prevention), 평가(Appraisal), 실패(Failure)의 머리글자를 따서 PAF 모델이라고 부른다.

정의

섹션 제목: “정의”
출처 용어 구성 특징
ISTQB 용어집 cost of quality 예방, 평가, 내부 실패, 외부 실패 품질 활동과 결함에 드는 비용만 셈
SWEBOK v4.0a 12장 1.2절 소프트웨어 품질비용(CoSQ, Cost of Software Quality) 구현 비용, 예방 비용, 평가 비용, 부적합·재작업 비용(내부 실패, 외부 실패) 계획, 설계, 개발 같은 구현 비용까지 합계에 넣음
CTFL v4.0.1 5.3.1 organizational cost of quality 정의 없이 비용 지표의 예로 제시 테스트 비용(cost of testing)과 별도 항목으로 나열함
  • ISTQB와 SWEBOK 정의의 차이는 구현 비용의 포함 여부임. ISTQB 정의로 집계하면 품질 활동과 결함 처리 비용만 남고, SWEBOK 정의로 집계하면 프로젝트 비용 전체 중 품질과 관련된 몫을 보게 됨
  • SWEBOK은 SQA 도입에 대한 반대의 주된 이유로 높은 비용에 대한 인식을 들고, 기본 SQA 활동을 하지 않는 것도 비용이 든다는 점을 품질비용 개념으로 경영진에게 설명하라고 권함
  • SWEBOK 12장 1.2절의 주 참고문헌은 Laporte와 April의 Software Quality Assurance(IEEE Press, 2018) 2장 2절임

PAF 모델 구성

섹션 제목: “PAF 모델 구성”
분류 뜻 소프트웨어 개발의 예 적합/부적합
예방 비용(Prevention) 결함이 생기지 않게 하는 투자 프로세스 개선, 품질 도구, 작업 산출물 템플릿, 코딩 표준, 교육 적합 비용
평가 비용(Appraisal) 오류와 결함을 찾는 활동 테스트, 요구사항·설계·코드 리뷰, 감사, 정적 분석, 외주 산출물 평가 적합 비용
내부 실패 비용(Internal Failure) 납품 전에 발견한 결함을 처리하는 비용 출시 전 결함 수정, 확인 테스트, 수정에 따른 회귀 테스트, 빌드 재작업 부적합 비용
외부 실패 비용(External Failure) 납품 후 발견한 장애에 대응하는 비용 장애 대응, 핫픽스와 수정 릴리즈의 재작업·재테스트, 고객 지원, 배상, 평판 손실 부적합 비용

SWEBOK은 네 분류를 적합 비용(Conformance Cost)과 부적합 비용(Nonconformance Cost)의 두 상위 분류로 묶는다.

  • 적합 비용: 오류와 결함의 검출(평가)과 예방에 들인 투자의 합계. 예방 비용은 특정 프로젝트에 속하지 않고 조직 전체에 걸치는 경우가 많음
  • 부적합 비용: 이미 검출된 오류와 결함을 처리하는 데 쓴 지출의 합계. 납품 전 비용(평가 활동에서 찾은 결함의 수리)과 납품 후 비용(고객에게 납품한 뒤 발견된 장애 대응)으로 나눔
  • 외부 비용에는 수정 릴리즈를 고치고 테스트하는 재작업, 결함이 낳은 의도하지 않은 부작용의 수리가 들어감
  • SWEBOK은 고객이 입는 손실(생산성 손실, 데이터 손실, 시장 평판 손실)도 똑같이 중요하다고 보고 인정해서 계산에 넣으라고 적음. 영향이 고객을 넘어 사회와 환경에 미칠 수 있다는 점도 언급함

SWEBOK이 제시하는 목표는 최적 품질비용, 즉 정해진 품질 수준에서 총비용이 가장 작은 지점이다. 기준은 네 분류를 합친 총비용이므로, 적합 비용을 줄인 결과 부적합 비용이 더 늘었다면 품질비용은 오히려 커진 것이다.

결함 발견 시점과 수정 비용

섹션 제목: “결함 발견 시점과 수정 비용”

실라버스의 서술

섹션 제목: “실라버스의 서술”

CTFL v4.0.1은 비용 절감을 조기 테스팅의 근거로 든다.

  • 1.3 원칙 3: 앞 단계에서 제거한 결함은 그 산출물에서 파생되는 산출물에 결함을 남기지 않고, 개발 수명주기 후반의 장애가 줄어 품질비용이 감소함. 근거 문헌은 Boehm(1981)
  • 2.1.5 시프트 레프트: 시프트 레프트는 앞 단계에 교육, 노력, 비용을 더 들일 수 있지만 뒤 단계의 노력과 비용을 줄일 것으로 기대함. 뒤 단계의 테스트를 소홀히 해도 된다는 뜻은 아님
  • 3.1.2 정적 테스트의 가치: 리뷰는 도입 비용이 들지만 뒤에서 결함을 고치는 시간이 줄어 프로젝트 전체 비용이 보통 훨씬 낮음
  • 1.2.1: 테스팅은 결함을 찾는 비용 효율적인 수단임

ISTQB 용어집은 시프트 레프트를 테스트와 품질 보증 활동을 개발 수명주기에서 가능한 한 일찍 수행하는 접근으로 정의한다. 원칙 자체의 설명은 테스팅의 7원칙에 있다.

자주 인용되는 수치와 원 연구의 맥락

섹션 제목: “자주 인용되는 수치와 원 연구의 맥락”

“늦게 발견할수록 수십~백 배”라는 수치는 출처마다 대상 데이터가 다르다. 인용할 때는 아래 맥락을 함께 적는다. 문헌 제목과 링크는 출처 절에 있다.

출처 대상 데이터 결과
Boehm(1981) Menzies 외(2017)의 설명에 따르면 1970년대 후반 IBM, TRW, GTE, Bell Labs의 대형 시스템 데이터. 원 데이터 점은 공개되지 않음 단계가 늦을수록 수정 비용이 급격히 커지는 곡선
Boehm·Basili(2001) 1987년 목록을 갱신한 글(Software Defect Reduction Top 10 List, IEEE Computer) 납품 후 수정은 요구사항·설계 단계 수정보다 “흔히(often)” 100배 비쌈. 소규모·비핵심 시스템은 100:1보다 5:1에 가깝고, 좋은 아키텍처는 대형 핵심 시스템에서도 증가 폭을 줄임
NASA, Stecklein 외(2004) 대형 우주선, 군용기, 소형 통신위성과 비슷한 하드웨어/소프트웨어 시스템. 우주선 개조 5건의 비용 자료, 대형 항공기 프로그램 1건의 변경 231건, 가상의 소형 통신위성 모델 요구사항 단계 수정을 1로 두면 설계 3~8, 제작 7~16, 통합·시험 21~78, 운영 29~1,500 이상
Menzies 외(2017) 2006~2014년 171개 소프트웨어 프로젝트. 모두 TSP(Team Software Process)를 사용함 늦은 단계의 해결 노력이 일관되게, 또는 크게 많다는 증거를 찾지 못함
  • Boehm과 Basili는 2001년 갱신에서 “흔히”라는 단어를 일부러 추가했다고 밝힘. 저자 스스로 100배를 모든 시스템의 상수로 두지 않음
  • NASA 논문은 데이터 양과 결함 세부 정보가 제한적이었고 실제 데이터가 대형 항공우주 프로젝트 두 건에서 나왔다고 밝히며, 더 큰 표본과 다른 산업의 데이터를 후속 과제로 적음. 세 번째 방법의 수정 비용 추정은 저자의 경험에 크게 의존한다고 가정 절에 적음
  • NASA 논문은 기존 소프트웨어 연구 여러 건의 수치를 정규화한 표도 싣는데, 요구사항 단계를 1로 둔 중앙값은 설계 5, 코드 10, 테스트 50.5임. 같은 표에서 연구별 테스트 단계 값은 37부터 1,000까지 퍼져 있음
  • Menzies 외는 대상 프로젝트가 모두 공저자 두 명의 소속 기관(SEI)이 만든 TSP로 개발되었다는 점을 이해 상충으로 공개함. 결론은 지연 효과가 모든 프로젝트에 공통인 상수가 아니며 특정 종류의 프로젝트에서만 나타날 수 있다는 것임
  • Laurent Bossavit의 The Leprechauns of Software Engineering(Leanpub)은 소프트웨어 공학의 통념이 원 출처와 달라지는 과정을 추적하는 책임. 공개 샘플(2017-06-27판) 1장은 결함 수정 비용 주장을 “기껏해야 문제가 있는(at best problematic)” 주장으로 보고, 10장(The cost of defects: an illustrated history)과 부록 B(결함 비용 증가 곡선의 서지 분석)에서 다룬다고 밝힘

연구들이 공통으로 지지하는 것은 “늦게 발견한 결함은 더 비쌀 수 있고, 그 배율은 시스템 규모, 중요도, 아키텍처, 개발 방식에 따라 크게 다르다”는 범위까지다. 특정 배율을 자기 조직의 근거로 쓰려면 자기 조직의 결함 데이터로 측정한다.

자주 혼동하는 점

섹션 제목: “자주 혼동하는 점”
  • 품질비용과 테스트 비용을 같은 것으로 봄. CTFL v4.0.1 5.3.1은 비용 지표의 예로 테스트 비용과 조직의 품질비용을 따로 적고, 테스트는 평가 비용의 일부임
  • 같은 테스트 활동을 항상 평가 비용으로 분류함. 처음 수행하는 테스트는 평가 비용이지만, 결함 수정 뒤 확인 테스트와 수정 릴리즈의 재테스트는 SWEBOK 기준으로 부적합(실패) 비용임
  • 요구사항 리뷰의 분류를 하나로 고정함. SWEBOK은 리뷰를 평가 비용으로 분류하고, CTFL 원칙 3은 앞 단계의 결함 제거가 파생 산출물의 결함을 막는다고 설명함. 요구사항 산출물 기준으로는 평가이고, 이후 설계·코드 기준으로는 예방 효과를 냄
  • “100배”를 모든 프로젝트에 적용되는 상수로 인용함. 원 저자도 “흔히”로 한정했고 소규모 시스템은 5:1에 가깝다고 적음
  • 예방 비용을 프로젝트 예산에서만 찾음. SWEBOK은 예방 비용이 조직 전체에 걸치는 경우가 많다고 보므로, 프로젝트 단위로만 집계하면 교육이나 도구 투자가 빠짐

QA에서 적용

섹션 제목: “QA에서 적용”

결함 데이터 집계

  • 결함마다 발견 단계(요구사항 리뷰, 코드 리뷰, 단위, 통합, 시스템, 인수, 운영)를 기록함. 가능하면 유입 단계도 기록함. 결함 상태 흐름과 종결 시 기록 항목은 결함 생명주기를 따름
  • 발견 경로(QA, 모니터링, 사용자)를 함께 남김. 사용자가 먼저 발견한 결함은 외부 실패 비용의 사례이고, 그 앞단의 탐지 공백을 별도 이슈로 다룸(이슈 양식)
  • 외부 실패를 심각도별로 나누어 집계함. 같은 건수라도 Critical 장애와 Trivial 오타의 대응 비용은 다름(심각도 기준)

운영 유출 결함 비율

  • ISTQB 용어집의 결함 검출률(DDP, Defect Detection Percentage)은 한 테스트 레벨에서 찾은 결함 수를, 그 레벨과 이후 다른 수단으로 찾은 결함 수의 합으로 나눈 값임
  • 예: 시스템 테스트에서 45건, 출시 후 운영에서 5건이 나오면 시스템 테스트의 DDP는 45 / (45 + 5) = 90%임. 나머지 10%가 외부 실패 비용으로 이어진 유출 결함임
  • 출시 직후에는 운영 결함이 아직 쌓이지 않았으므로, DDP를 계산하는 관찰 기간(예: 출시 후 30일)을 정해 두고 보고함

예방과 평가 투자 근거

  • 외부 문헌의 배율 대신 자기 조직의 단계별 수정 비용(시간 기준)을 측정해 근거로 사용함
  • 결함이 몰리고 실패 영향이 큰 영역에 평가 활동을 집중함(리스크 기반 테스트)
  • 회귀 테스트는 평가 비용이지만, 결함 수정 때문에 다시 수행한 회귀는 실패 비용으로 분리해 기록함. 납품 전에 발견한 결함이면 내부 실패 비용, 납품 후에 발견한 결함이면 외부 실패 비용임. 회귀 범위를 줄이는 기준은 회귀 테스트 범위 선정에 있음

리포팅 시 주의

  • 측정 비용: 활동마다 시간을 기록하고 분류하는 작업 자체가 비용임. 처음에는 결함 수정 시간과 장애 대응 시간처럼 이미 기록되는 항목부터 시작함
  • 숨은 비용: 고객의 생산성 손실, 데이터 손실, 평판 손실은 금액으로 확정하기 어려움. 금액 대신 영향 받은 사용자 수, 장애 시간처럼 관찰 가능한 값을 함께 보고함
  • 비교 조건: 기간마다 분류 기준이 바뀌면 추이를 비교할 수 없음. 리뷰와 재테스트의 분류 기준을 보고서에 명시함

방식 선택

섹션 제목: “방식 선택”
방식 내용 맞는 경우
PAF 4분류(ISTQB 용어집, ASQ) 예방, 평가, 내부 실패, 외부 실패 비용을 각각 집계 품질 활동의 투자 대비 효과를 경영진에게 보고할 때
SWEBOK CoSQ 구현 비용까지 합산하고 적합·부적합 비용으로 나눔 프로젝트 전체 예산 중 품질 관련 몫을 보고 싶을 때
결함 기반 지표만 사용 DDP, 단계별 결함 수, 단계 내 제거(Phase Containment) 비용 데이터를 모으기 어려운 초기 단계
  • 단계 내 제거는 ISTQB 용어집(Advanced Test Management 등)의 용어로, 결함이 유입된 단계에서 그 결함을 제거하는 방침을 뜻함
  • 세 방식은 배타적이지 않음. 결함 기반 지표로 시작해 수정 시간을 붙이고, 이후 금액 환산으로 넓히는 순서가 가능함

한계

섹션 제목: “한계”
  • 분류의 주관성: 같은 활동(리뷰, 재테스트)이 관점에 따라 다른 분류에 들어가고, 조직마다 기준이 다르면 조직 간 비교가 어려움
  • 무형 비용: 평판 손실, 고객 신뢰 하락, 개발자의 맥락 전환 비용은 측정이 어렵고 추정치가 들어감
  • 시간과 비용의 차이: Menzies 외도 지적하듯 수정 시간과 수정 비용은 같지 않음. 비싼 도구나 고숙련 인력이 필요한 결함은 시간 대비 비용이 큼
  • 문헌 배율의 이전 가능성: 위 연구들은 대상 시스템과 시기가 달라 다른 조직에 그대로 적용할 수 없음

품질 보증과 품질 관리 활동의 구분은 QA, QC, QM에, 검증과 확인 활동의 구분은 검증과 확인에 있다.

관련 문서

기초와 용어테스팅의 7원칙테스팅의 일반 원칙 7가지(ISTQB CTFL v4.0.1 1.3)는 테스트로 보장할 수 있는 것과 없는 것을 정한다. 원칙마다 뜻과 근거, 테스트 계획·설계·보고에 반영하는 방법을 사례와 함께 설명한다.프로세스결함 생명주기결함이 등록된 시점부터 종결될 때까지 거치는 상태와, 상태 사이에 허용되는 전이를 정한 규칙이다(Defect Lifecycle).테스트 설계리스크 기반 테스트실패했을 때의 피해와 실패할 가능성을 기준으로 무엇을 먼저, 얼마나 깊게 테스트할지 정하는 방식이다(Risk-Based Testing).프로세스회귀 테스트 범위 선정변경 뒤 기존 기능이 의도하지 않게 실패하는지 확인하기 위해, 회귀 스위트에서 이번 회차에 수행할 TC를 선택하는 절차다(Regression Test Selection).
