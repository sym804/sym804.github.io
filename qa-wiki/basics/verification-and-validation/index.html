검증과 확인(V&V)

검증(Verification)은 산출물이 명세를 충족하는지, 확인(Validation)은 제품이 사용자의 필요와 의도된 사용에 맞는지를 판정하는 활동이다. ISTQB, SWEBOK, FDA, NASA의 정의를 비교하고 정적·동적 V&V, 수명주기 단계별 활동, 독립 V&V(IV&V)를 정리한다.

기본기난이도 기초최종 업데이트 2026-11-24

검증(Verification)은 작업 산출물이 명세를 충족하는지 판정하는 프로세스이고, 확인(Validation)은 작업 산출물이 이해관계자의 필요에 맞는지 검사로 판정하는 것이다(ISTQB 용어집). 두 활동을 묶어 V&V라고 부른다. ISTQB CTFL v4.0.1(1.1)은 테스팅에 검증과 확인이 모두 포함된다고 설명하며, 테스팅을 검증으로만 보는 것을 흔한 오해로 든다. 이 문서는 출처마다 다른 정의를 비교하고, 두 활동을 수명주기와 테스트 활동에 배치하는 방법을 정리한다.

정의

섹션 제목: “정의”
출처 검증(Verification) 확인(Validation)
ISTQB 용어집 작업 산출물이 명세를 충족하는지 판정하는 프로세스 작업 산출물이 이해관계자의 필요에 맞는지 검사(examination)로 판정하는 것
ISTQB CTFL v4.0.1, 1.1 시스템이 명세된 요구사항을 충족하는지 점검하는 것 시스템이 운영 환경에서 사용자와 다른 이해관계자의 필요를 충족하는지 점검하는 것
SWEBOK v4.0a, 12장 3.4 수명주기 한 단계의 출력 산출물이 앞 단계에서 부과한 명세를 충족하는 것. 함께 제시한 정의는 개발 단계의 산출물이 그 단계를 시작할 때 부과된 조건을 만족하는지 평가하는 프로세스(IEEE 1012:2016 인용) 의도된 목적을 충족하는 맞는 제품을 만드는 것. 함께 제시한 정의는 개발 중이나 개발이 끝날 때 시스템이나 컴포넌트가 명세된 요구사항을 만족하는지 평가하는 프로세스
FDA GPSV, 3.1.2 개발 수명주기 특정 단계의 설계 출력이 그 단계에 명세된 요구사항을 모두 충족한다는 객관적 증거를 제공하는 것 소프트웨어 명세가 사용자 필요와 의도된 사용에 부합하고, 소프트웨어로 구현한 요구사항이 일관되게 충족될 수 있음을 검사와 객관적 증거로 확인하는 것
NASA IV&V 개요 “Are we building the product right?” 한 단계의 소프트웨어 산출물이 그 단계에 정한 요구사항을 충족하는지 판단하는 프로세스 “Are we building the right product?” 수명주기 전체에서 산출물이 미션과 고객의 필요를 충족하는지 평가하는 것

출처별 차이

  • 검증의 기준은 모든 출처에서 명세, 요구사항, 앞 단계에서 정한 조건임
  • 확인의 기준은 출처마다 표현이 다름. 이해관계자의 필요(ISTQB 용어집), 운영 환경에서의 사용자 필요(CTFL), 사용자 필요와 의도된 사용(FDA), 미션과 고객의 필요(NASA)
  • SWEBOK은 같은 절 안에서 확인을 설명 문장에서는 “의도된 목적” 충족으로, 함께 제시한 정의에서는 “명세된 요구사항” 충족으로 적음. 정의 문장만 옮기면 확인과 검증의 구분이 흐려짐
  • FDA는 객관적 증거(objective evidence)와 일관된 충족(consistently fulfilled)을 확인의 정의에 포함함. 규제 대상 제품에서는 판정 근거를 기록으로 남기는 것이 정의의 일부임
  • FDA는 검증이 “소프트웨어가 확인되었다”는 이후 결론을 뒷받침한다고 설명함. 검증 결과를 확인의 근거로 사용하는 관계임
  • 같은 FDA 절은 품질 시스템 규정이 ISO 8402:1994에 맞춰 두 용어를 구분하는 반면, 많은 교재와 논문은 두 용어를 섞어 쓰거나 VV&T(verification, validation, and testing)를 하나의 개념처럼 쓴다고 지적함

CTFL 1.1.1은 테스트 목적에 “명세된 요구사항의 충족 여부 검증”과 “테스트 대상이 완전하고 이해관계자의 기대대로 동작하는지 확인”을 함께 넣는다. 1.3의 원칙 7(결함 부재의 오류)은 검증과 함께 확인을 수행해야 한다는 근거로 Boehm(1981)을 인용한다.

검증과 확인 비교

섹션 제목: “검증과 확인 비교”
항목 검증 확인
질문 명세대로 만들었는가 맞는 것을 만들었는가
판정 기준 명세, 요구사항, 앞 단계 산출물이 정한 조건 사용자와 이해관계자의 필요, 의도된 사용, 운영 환경
시점 단계마다 산출물이 나올 때 개발 중과 개발이 끝날 때 모두(FDA 3.1.2)
주된 수행 주체 작성자, 동료 리뷰어, 개발자, 테스터 사용자와 사용자 대표, 사업 담당자, 테스터
대표 활동 리뷰, 인스펙션, 워크스루, 정적 분석, 추적성 분석, 컴포넌트·통합·시스템 테스트 이해관계자가 참여하는 요구사항 리뷰, 프로토타입 시연, 사용자 인수 테스트, 알파·베타 테스트, 사용자 현장 테스트, 사용성 평가
산출물 리뷰 기록, 정적 분석 결과, 추적성 매트릭스, 테스트 결과 인수 테스트 기록과 공식 인수 기록, 사용자 현장 테스트 결과, 사용성 평가 결과

같은 활동이라도 판정 기준이 명세이면 검증, 사용자 필요이면 확인에 해당한다. 출처에 따라 같은 활동을 다른 쪽으로 설명하는 경우도 있다.

  • CTFL 3.1은 정적 테스트를 검증과 확인 모두에 적용할 수 있다고 설명함. 3.1.2는 이해관계자가 문서화된 요구사항을 리뷰하면서 그 요구사항이 실제 필요를 서술하는지도 확인할 수 있다고 적음
  • 인수 테스트를 CTFL(2.2.1)은 확인과 배포 준비 상태 시연에 초점을 둔 레벨로, SWEBOK(5장 2.1.4)은 요구사항과 최종 사용자의 기대를 충족하는지 verify하는 테스트로 설명함. 출처마다 동사가 다르므로 동사보다 판정 기준으로 구분함
  • FDA의 사용자 현장 테스트 산출물에는 사전에 작성한 계획, 테스트 결과 요약, 공식 인수 기록이 포함됨(5.2.6)

정적 V&V와 동적 V&V

섹션 제목: “정적 V&V와 동적 V&V”

SWEBOK(12장 3.4)은 V&V 작업을 정적, 동적, 정형 세 가지로 나눈다.

구분 소프트웨어 실행 기법 예
정적 실행하지 않음 요구사항·인터페이스 명세·설계·모델 리뷰, 코드 읽기, 동료 리뷰, 소스 코드 제어 흐름의 정적 분석, 감사
동적 실행하거나 시뮬레이션함 테스트(블랙박스 테스트 포함), 시뮬레이션, 모델 분석, 모델 검사
정형 수학적 모델을 분석함 정형 명세 언어로 작성한 요구사항의 분석. 주로 핵심 시스템의 안전·보안 요구사항 검증에 사용
  • SWEBOK은 세 구분의 경계가 뚜렷하지 않다고 설명함. 데이터 흐름 분석, 모델 검사처럼 정적·동적 기법도 정형적 배경을 갖는 경우가 많음
  • 실행되지 않는 코드는 동적 테스트로 검증할 수 없고 정적 분석으로만 찾을 수 있음
  • SWEBOK은 리뷰 유형을 ISO/IEC 20246:2017에 따라 애드혹, 체크리스트 기반, 시나리오 기반, 관점 기반, 역할 기반으로 나눔. 관점 기반과 역할 기반 리뷰는 리뷰어가 특정 이해관계자의 관점에서 산출물을 읽으므로 실행 전에 확인 관점의 결함을 찾는 데 사용할 수 있음
  • 감사(Audit)는 독립성을 위해 제3자가 수행하도록 요구되는 경우가 많은 형식적 활동임
  • 정적 테스트와 동적 테스트의 비교, CTFL의 리뷰 유형과 역할은 ISTQB CTFL 실라버스 핵심 정리 3장에 있음

수명주기 단계별 V&V 활동

섹션 제목: “수명주기 단계별 V&V 활동”

FDA GPSV 5.2는 수명주기 활동마다 확인을 뒷받침하는 대표 작업을 제시한다. 특정 수명주기 모델이나 수행 순서를 정하지 않으며, 수행할 작업과 시점은 선택한 수명주기 모델과 안전 리스크로 정한다. 리스크가 아주 낮은 소프트웨어는 일부 작업이 필요 없을 수 있지만, 각 작업을 검토하고 적용 여부를 문서로 남기도록 한다.

단계 대표 작업(FDA 5.2) 주된 관점
품질 계획 V&V 계획(작업과 인수 기준, 일정과 자원, 보고 요구사항), 리스크 관리 계획, 형상관리 계획, 문제 보고·해결 절차 검증과 확인의 계획
요구사항 예비 리스크 분석, 소프트웨어 요구사항과 시스템 요구사항의 양방향 추적성 분석, 사용자 특성 기술, 요구사항 평가, 모호성 리뷰, 시스템·인수 테스트 계획 작성 확인(사용자 특성, 의도된 사용)과 검증(상위 요구사항과의 일치)
설계 리스크 분석 갱신, 설계 명세와 요구사항의 양방향 추적성 분석, 설계 평가, 모듈·통합 테스트 계획, 테스트 설계 검증
구현(코딩) 소스 코드와 설계 명세의 추적성 분석, 소스 코드와 문서 평가, 인터페이스 분석, 테스트 절차와 TC 작성 검증
개발자 테스트 단위·통합·기능·시스템·인수 테스트 실행, 테스트와 설계·요구사항의 추적성 분석, 결과 평가, 최종 테스트 보고서 검증 중심, 인수 테스트는 확인
사용자 현장 테스트 사용 현장의 실제 하드웨어·소프트웨어로 인수 테스트 실행, 결과 평가, 최종 테스트 보고서 확인
유지보수와 변경 변경의 영향 범위 분석, 영향 범위에 맞춘 회귀 테스트(4.7) 검증과 확인
  • FDA는 사용자 현장 테스트를 소프트웨어 확인의 필수 부분으로 보고, 베타 테스트, 현장 확인(site validation), 사용자 인수 테스트, 설치 검증(installation verification)처럼 개발자가 통제하는 환경 밖에서 수행하는 테스트를 모두 이 범위에 포함함(5.2.6)
  • 사용자 현장 테스트는 시스템이 의도된 기능을 수행하는지와 함께 사용자가 시스템을 이해하고 올바르게 조작할 수 있는지도 평가함. 개발 현장에서 수행한 대용량 데이터, 부하, 보안, 오류 메시지 테스트 일부를 실제 사용 현장에서 반복함
  • 작은 변경도 시스템 전체에 영향을 줄 수 있으므로 변경할 때마다 확인 상태를 다시 수립함. 개별 변경의 확인과 함께 시스템 전체에 대한 영향을 분석하고, 그 결과로 회귀 테스트 수준을 정함(FDA 4.7, 회귀 테스트 범위 선정)
  • SWEBOK(12장 1.4.2, 3.4)은 소프트웨어 무결성 수준(Integrity Level)에 따라 최소 V&V 작업을 정하라고 설명함. 무결성 수준은 복잡도, 중요도, 리스크, 안전·보안 수준 같은 특성으로 정하는 값임. 리스크로 테스트 깊이를 정하는 방법은 리스크 기반 테스트에 있음
  • 개발 단계와 테스트 레벨을 짝지어 그리는 V 모델은 개발 수명주기와 V 모델에 있음

독립 V&V(IV&V)

섹션 제목: “독립 V&V(IV&V)”

SWEBOK(12장 3.4)은 치명도가 높은 소프트웨어(very critical software)의 V&V를 독립 조직이 수행할 수 있다고 설명하고, IV&V(Independent Verification and Validation)를 개발 조직과 기술적·관리적·재정적으로 독립된 조직이 수행하는 V&V로 정의한다(IEEE 1012:2016 인용). NASA IV&V 개요는 세 독립성을 다음처럼 설명한다.

독립성 뜻
기술적 독립성 IV&V 수행자가 자신의 전문성으로 개발자와 독립적으로 개발 프로세스와 산출물을 평가함
관리적 독립성 IV&V 책임을 시스템 구현 조직과 분리된 조직에 둠. 분석·테스트할 범위, 기법, 일정, 다룰 기술 문제를 IV&V 조직이 스스로 정함
재정적 독립성 IV&V 예산을 개발 조직과 독립된 조직에 둠
  • NASA IV&V 프로그램은 웨스트버지니아주 페어몬트의 Katherine Johnson IV&V Facility(1993년 설립)에서 운영됨. 예산은 NASA 미션 지원 본부(MSD, Mission Support Directorate)에서 나오고, 프로젝트가 서비스 비용을 직접 대기도 함
  • NASA는 소프트웨어 IV&V를 수명주기 전체에서 소프트웨어의 정확성과 품질을 평가하는 시스템 엔지니어링 프로세스로 설명하고, 프로젝트 특성에 맞춰 조정한다고 적음
  • FDA GPSV 4.9는 “검토의 독립성(independence of review)“을 품질 보증의 기본 원칙으로 들고, 자기 확인(self-validation)은 매우 어렵다고 설명함. 제3자 IV&V를 계약하기 어려우면 해당 설계와 구현에 참여하지 않았고 평가할 지식이 있는 내부 인원에게 V&V를 맡기는 방법을 제시함

독립성 수준 선택

섹션 제목: “독립성 수준 선택”
방식 맞는 경우 근거
개발 조직 안의 V&V(동료 리뷰, 개발자 테스트, 팀 내 테스터) 산출물을 잘 아는 사람이 결함을 효율적으로 찾는 컴포넌트·컴포넌트 통합 테스트, 동료 리뷰 CTFL 1.5.3
내부 독립 검토(설계·구현에 참여하지 않은 내부 인원) 독립 검토가 필요하지만 제3자 계약이 어려운 경우 FDA 4.9
IV&V(기술·관리·재정 독립) 치명도가 높은 소프트웨어, 산업 지침이 독립성을 요구하는 경우 SWEBOK 12장 1.4.2, 3.4
  • 항공, 철도, 원자력, 의료기기 같은 안전 필수 산업은 산업별 지침이 무결성 수준에 따라 독립성과 최소 V&V 기법을 요구할 수 있음(SWEBOK 12장 1.4.2)
  • CTFL은 독립성 수준을 작성자 본인, 같은 팀 동료, 같은 조직의 다른 팀, 조직 외부로 나누고 장단점을 함께 설명함(ISTQB CTFL 실라버스 핵심 정리의 “역할, 역량, 독립성”). 대부분의 프로젝트는 여러 수준을 섞어 사용함

자주 혼동하는 점

섹션 제목: “자주 혼동하는 점”
  • 한국어 번역: 위키는 Verification을 검증, Validation을 확인으로 옮김(용어 사전과 같음). 다른 번역도 사용됨. 예를 들어 식품의약품안전처 「우수 관리체계 인증 기준에 관한 규정」의 디지털의료기기소프트웨어 인증 기준([별표 1])은 “검증(Verification) & 밸리데이션(Validation)“으로 표기함. 한국어 단어만으로는 어느 용어인지 구분되지 않는 경우가 있어 처음 나올 때 영문을 함께 적음
  • 확인(Validation)과 확인 테스트(Confirmation Testing): 확인 테스트는 결함을 수정한 뒤 그 결함으로 인한 장애가 다시 발생하지 않는지 확인하는 변경 관련 테스트임(ISTQB 용어집, 동의어 재테스트). 사용자 필요를 판정하는 확인과는 다른 용어임. 회귀 테스트와의 차이는 용어 사전의 혼동 주의 절에 있음
  • 테스팅과 검증: CTFL 1.1은 테스팅이 검증만으로 이루어진다는 생각을 흔한 오해로 듦. 명세를 모두 테스트하고 결함을 모두 수정해도 사용자 필요를 충족하지 못할 수 있다는 결함 부재의 오류는 테스팅의 7원칙 원칙 7에 있음
  • 검증과 테스트: FDA(3.1.2)와 SWEBOK(12장 3.4.4)은 테스트를 여러 검증 활동 중 하나로 설명함. 리뷰, 인스펙션, 워크스루, 정적·동적 분석도 검증 활동임. SWEBOK은 대부분의 경우 테스트만으로는 소프트웨어가 의도된 사용에 맞는다는 신뢰를 얻기에 충분하지 않다고 적음
  • 의료·제약 분야의 밸리데이션: FDA GPSV 3.1.3에 따르면 업계 문서와 다른 FDA 지침은 사용 현장의 소프트웨어 확인을 공정 밸리데이션 용어인 IQ(Installation Qualification), OQ(Operational Qualification), PQ(Performance Qualification)로 설명하기도 함. GPSV는 이 용어가 소프트웨어 실무자에게 잘 알려지지 않았을 수 있다며 본문에서 사용하지 않지만, 용어 차이를 알고 정보를 주고받아야 한다고 적음
  • FDA GPSV의 현재 상태: 2002-01-11 발행 최종 지침임. 2025-09-24 발행된 “Computer Software Assurance for Production and Quality System Software” 지침이 GPSV 6절(자동화 공정 장비와 품질 시스템 소프트웨어의 확인)을 대체했고, 나머지 절은 계속 유효함(GPSV 첫 쪽 안내, 2026-11 기준)

QA에서 적용

섹션 제목: “QA에서 적용”

검증

  • 요구사항 리뷰에서 상위 문서, 다른 요구사항과의 일치 여부와 모호한 표현, 누락을 확인함. FDA 5.2.2의 모호성 리뷰와 추적성 분석에 해당함
  • TC마다 근거가 된 테스트 베이시스(요구사항, 사용자 스토리, 설계 문서) 항목을 연결해 추적성을 유지함. 테스트 베이시스의 정의는 ISTQB CTFL 실라버스 핵심 정리 1장, TC 작성 기준은 TC 작성 원칙에 있음
  • 테스트 결과는 명세된 기대 결과와 비교해 PASS, FAIL, BLOCK, N/A, N/R로 기록함

확인

  • 요구사항 리뷰에 사용자 대표, 기획자, 운영 담당자를 참여시켜 요구사항이 실제 업무 필요를 서술하는지 함께 확인함(CTFL 3.1.2)
  • 인수 테스트는 의도된 사용자가 수행하는 것이 바람직함(CTFL 2.2.1). 인수 테스트의 형태(사용자, 운영, 계약·규제, 알파·베타)는 테스트 레벨과 테스트 유형에 있음
  • 명세에 적히지 않은 사용 흐름은 사용자 관점의 차터를 정해 탐색적 테스트로 확인함(탐색적 테스트)
  • 실제 데이터 규모, 실제 기기, 운영과 같은 설정처럼 운영 환경에 가까운 조건에서 확인함. FDA 사용자 현장 테스트가 개발 현장의 테스트 일부를 실제 사용 현장에서 반복하도록 하는 것과 같은 취지임
  • 명세는 충족하지만 사용자가 목적을 달성하기 어려운 문제는 개선 이슈로 기록함(이슈 양식)

보고

  • 결과 보고서에서 명세 충족(검증)과 사용자 관점 평가(확인)를 구분해 적음(테스팅의 7원칙 원칙 7)
  • 결함 보고서의 기대 결과에 그 근거(명세 조항 또는 사용자 필요)를 적으면, 명세 위반 결함과 명세 자체의 결함을 구분할 수 있음

관련 문서

기초와 용어ISTQB CTFL 실라버스 핵심 정리ISTQB Certified Tester Foundation Level 실라버스 v4.0.1의 6개 장(테스팅 기초, 개발 수명주기와 테스팅, 정적 테스트, 테스트 분석과 설계, 테스트 활동 관리, 테스트 도구) 핵심 개념. 개념마다 실무에 적용한 위키 문서를 연결한다.기초와 용어테스팅의 7원칙테스팅의 일반 원칙 7가지(ISTQB CTFL v4.0.1 1.3)는 테스트로 보장할 수 있는 것과 없는 것을 정한다. 원칙마다 뜻과 근거, 테스트 계획·설계·보고에 반영하는 방법을 사례와 함께 설명한다.기초와 용어용어 사전이 위키에서 사용하는 QA 용어의 영문 표기와 뜻. 혼동하기 쉬운 용어 쌍과 팀에서 용어를 맞추는 방법을 함께 둔다.기초와 용어테스트 레벨과 테스트 유형테스트 레벨은 시스템을 어느 통합 단계에서 검증하는지를, 테스트 유형은 어떤 품질 특성을 검증하는지를 나타내는 분류다. 두 분류는 서로 독립이며, 테스트마다 레벨을 하나 정하고 테스트 유형은 하나 이상 적용할 수 있다.
