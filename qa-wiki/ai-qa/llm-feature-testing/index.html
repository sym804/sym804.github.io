LLM 기능 테스트

같은 입력에도 출력이 달라지는 LLM 기능을 구조 조건, 의미 평가, 반복 실행 통과율로 판정하는 테스트 방법이다. 정확한 문자열 대신 성립해야 하는 조건을 기대 결과로 쓴다.

기본기난이도 중급AI 제품최종 업데이트 2026-11-24

LLM 기능은 같은 질문에 매번 다른 문장으로 답한다. temperature를 0으로 두거나 시드를 고정해도 추론 환경에 따라 출력이 달라질 수 있어 “이 문장이 나와야 한다”는 기대 결과는 성립하지 않는다. 그래서 출력이 충족해야 하는 조건을 구조 조건, 의미 조건, 반복 통과율로 구분해 판정한다.

판정 기준

섹션 제목: “판정 기준”
  • 구조 조건: JSON 스키마, 필수 키, 자료형, 허용 값 목록, 길이 상한, 금지어 미포함. 일반 코드로 정확히 판정 가능함
  • 의미 조건: 근거 문서와의 일치, 정답 요소 포함 여부, 질문 범위 준수. 채점 기준표(루브릭)나 LLM 심판으로 판정함
  • 반복 통과율: 같은 입력을 N회 실행해 K회 이상 조건을 충족하는지 판정함. 1회 실행 결과로 통과나 실패를 확정하지 않음

구조 조건으로 판정할 수 있는 항목은 구조 조건으로 판정한다. 수치 계산, 날짜, 형식 검사를 LLM 심판에 맡기면 비용이 들고 판정 자체에 오차가 발생한다.

메타모픽 테스트

섹션 제목: “메타모픽 테스트”

정답을 미리 정하기 어려운 질의는 입력을 변형했을 때 두 출력 사이에 성립해야 하는 관계로 판정한다(Metamorphic Testing).

  • 의미를 보존하는 변형: 동의어 치환, 문장 순서 변경, 띄어쓰기 변경. 주요 답이 같아야 함
  • 조건을 추가하는 변형: “500자 이내로”, “표로” 같은 제약을 추가함. 기존 답의 사실은 유지되고 제약만 반영되어야 함
  • 무관한 정보 추가: 답과 상관없는 문장을 섞음. 답의 주요 내용이 유지되어야 함

확인할 비기능 항목

섹션 제목: “확인할 비기능 항목”
  • 응답 시간: 첫 토큰까지의 시간, 전체 응답 시간, 시간 초과 시 대체 응답
  • 비용: 입력·출력 토큰 상한, 사용자별 요청 상한, 에이전트의 최대 반복 횟수
  • 거부 동작: 범위 밖 질문과 유해 요청은 거부하고, 정상 질문은 거부하지 않는지 함께 확인함
  • 모르는 질문: 근거가 없을 때 지어내지 않고 확인 불가로 답하는지 확인함

기대 결과 작성 예

섹션 제목: “기대 결과 작성 예”

질문 “환불 기간을 알려줘”에 대한 기대 결과를 문장 하나로 쓰지 않고 조건으로 나눈다.

  • 응답 JSON에 answer, sources 키가 있음
  • answer에 정책 문서의 환불 기간 값이 포함됨
  • sources의 문서 번호가 실제 정책 문서를 가리킴
  • 같은 질문 10회 실행 중 10회 모두 위 조건을 충족함

TC 예시

섹션 제목: “TC 예시”
항목 TC 예시
구조 조건 응답을 JSON 스키마 검증기로 검사해 필수 키 누락, 자료형 오류, 허용 값 목록 밖의 값이 0건인지 확인함. 스키마를 벗어난 응답을 고정값으로 주입해 화면이 원문을 그대로 표시하지 않고 오류 안내를 표시하는지 확인함
길이 상한 명세의 상한(예: 요약 300자)에 맞춰 원문 길이를 변경해 가며 출력이 300자 이하인지 확인함. 초과 시 자르기나 재요청을 하는 후처리 코드는 299·300·301자 고정 입력으로 따로 확인함
반복 통과율 같은 입력을 반복(예: 10회) 실행해 조건 충족 횟수를 기록함. 기준이 “10회 중 9회 이상”이면 9회는 통과, 8회는 실패로 판정하고 실패한 회차의 출력 원문을 증거로 첨부함
메타모픽(의미 보존) “환불 기간 알려줘”와 “환불은 며칠 안에 가능해?“의 답에서 기간 값을 코드로 추출해 두 값이 같은지 확인함
메타모픽(조건 추가) 원 질문에 “3줄 이내로”를 추가해 답이 줄바꿈 기준 3줄 이하이고, 원래 답에 있던 기간 값이 유지되는지 확인함
모르는 질문 근거 문서에 없는 정책(예: 해외 배송 반품비)을 질문해 확인 불가 안내가 표시되고, 근거 없는 반품비 금액이나 기간을 확정적으로 제시하지 않는지 확인함
거부와 과차단 범위 밖 요청 묶음과 정상 요청 묶음(예: 각 30건)을 실행해 거부율과 과차단율을 함께 기록하고, 두 값이 모두 기준(예: 거부율 100%, 과차단율 5% 이하)을 충족하는지 판정함
응답 시간 첫 토큰 시간과 전체 응답 시간을 반복(예: 30회) 측정해 p95가 목표 이하인지 확인함. 모델 호출 지연을 모의로 발생시켜 시간 초과(예: 20초) 시 대체 응답과 재시도 버튼이 표시되는지 확인함
입력 토큰 상한 명세의 입력 상한이 N 토큰이면 N-1, N, N+1 토큰 입력을 보내 N+1에서 안내 문구와 함께 거부되고, 호출 로그에 모델 호출이 없는지 확인함

적용 예: 자연어 주문 검색

섹션 제목: “적용 예: 자연어 주문 검색”

기획서에 “주문 관리 화면의 검색창에 자연어로 입력하면 조건을 필터로 변환해 주문 목록을 조회한다”만 있는 경우다. 예를 들어 “지난주 서울 지점 5만원 이상 미배송 주문”을 모델이 date_from, date_to, store, min_amount, status 필드를 가진 필터 JSON(예: {"date_from": "2026-11-09", "date_to": "2026-11-15", "store": "서울", "min_amount": 50000, "status": "미배송"})으로 변환하고, 서버가 그 필터로 주문을 조회한다. 이 요구사항에서 도출되는 항목은 다음과 같다.

  • 구조 조건: 필터 JSON 스키마, 허용 필드 목록, 날짜 형식, 금액 자료형. 목록 밖 필드나 형식 오류가 있는 필터를 서버가 거부하는지 확인함
  • 정답 필터 평가셋: 질의와 기대 필터를 쌍으로 저장함. 출력이 구조화되어 있어 기대 필터와의 일치를 코드로 판정하며 LLM 심판이 필요하지 않음
  • 상대 날짜: “지난주”, “이번 달 초”의 정의(직전 7일인지, 지난 월요일부터 일요일까지인지)와 시간대를 기획과 확인함. 평가셋은 기준일을 고정해 기대 필터를 계산함
  • 모호한 질의: “큰 주문”, “최근 주문”처럼 기준이 없는 표현을 되묻는지, 필터 없이 조회하고 안내하는지 정함
  • 범위 밖 요청: “이 주문 취소해줘” 같은 입력에서 변환기가 필터 외의 동작을 만들지 않고 조회 API만 호출하는지 확인함(LLM 보안 테스트)
  • 권한: 필터에 다른 지점이 들어가도 서버가 로그인한 사용자의 권한 범위로 조회를 제한하는지 코드에서 확인함
  • 메타모픽: 조건 순서를 변경한 입력, “5만원 이상”과 “50,000원 이상”이 같은 필터로 변환되는지 확인함
  • 반복 통과율: 같은 질의를 반복 실행해 매번 같은 필터가 나오는지 확인함
  • 대체 동작: 변환 실패나 시간 초과 시 일반 키워드 검색으로 전환하는 기준을 정함
  • 결과 표시: 변환된 조건을 필터 칩으로 표시해 사용자가 확인하고 수정할 수 있는지 확인함

상대 날짜의 정의, 모호한 질의의 처리, 대체 동작이 정해지지 않으면 기대 필터를 계산할 수 없다. 이 세 가지를 기획에서 확정한 뒤 평가셋을 작성한다.

테스트 계획, 결함 분류, 보고에 적용

섹션 제목: “테스트 계획, 결함 분류, 보고에 적용”

테스트 계획

  • 모델 이름과 버전, 프롬프트 버전, 시스템 지시, 샘플링 설정, 후처리 코드 버전을 시험 대상 구성으로 기록함
  • TC마다 판정 방식(코드, 루브릭, LLM 심판)과 반복 횟수, 통과 기준(N회 중 K회)을 지정함
  • 스키마 검사와 후처리 코드는 고정 입력으로 매 빌드에 실행하고, 실제 모델을 호출하는 반복 실행과 의미 조건 판정은 평가셋 회차로 분리해 일정과 비용을 계획함

결함 분류

  • 재현 빈도를 “10회 중 3회 실패”처럼 실행 횟수와 실패 횟수로 기록함(이슈 양식)
  • 원인 단계를 입력 전처리(문서 추출, 질의 정규화), 프롬프트, 모델, 후처리와 화면 표시로 구분함
  • 잘못된 필터나 수치로 다른 데이터를 조회·표시하는 결함은 문체·표현 결함과 구분해 심각도를 정함(심각도)

보고

  • 판정 방식별로 나눠 보고함. 예: “구조 조건 200/200, 정답 필터 일치 188/200(상대 날짜 질의 실패 9건), 과차단 1/30, 응답 시간 p95 1.8초”
  • 반복 실행한 TC는 통과 기준과 실제 충족 횟수를 함께 적음. 1회 실행 결과만 있는 항목은 그 사실을 표시함

현장 노트

  • 표와 재무 수치가 많은 리서치 PDF를 LLM으로 요약하는 작업에서 반복된 오류 유형은 표의 연도별 열 혼동, 단위 환산(천원·십억원·억원), 원문에 없는 종목·수치, 줄바꿈으로 인한 행 매핑 오류와 부호 손실이었음. 요약에 나온 숫자를 하나씩 PDF 전문과 대조하는 전수 검사에서 한 회차(요약 236건, 숫자 10,735개)의 부호가 반대로 기재된 실제 오류 1건을 찾음. 같은 회차의 LLM 심판은 이 건을 검출하지 못함(LLM 평가셋과 LLM 심판)
  • 같은 날 같은 업종의 다른 보고서에 있는 수치를 인용한 요약이 있었음. 수치 자체는 실재해 전체 문서 검색으로는 확인되지 않았고, 해당 요약의 원본 PDF와 대조해서만 오류로 확인됨. 이후 같은 날 같은 업종의 보고서가 둘 이상이면 이 유형을 점검 대상에 포함함
  • 막대 차트의 종목별 수치를 잘못 짝지은 요약 오류의 원인은 모델이 아니라 요약 입력을 만드는 PDF 추출 단계였음. 이전 기록에는 몇 달간 다른 추출 경로가 원인으로 적혀 있었고, 추출 경로별 원시 텍스트를 비교해 원인을 확정함

규칙

  • 프롬프트, 모델 버전, 검색 설정, 시스템 지시를 변경하면 평가셋 전체로 회귀 테스트를 수행함
  • 결함 보고에는 입력, 모델 이름과 버전, 주요 설정값, 출력 원문, 실행 횟수와 실패 횟수를 함께 기록함

흔한 실수

섹션 제목: “흔한 실수”
