AI 에이전트 권한 통제

AI 에이전트의 실행 범위를 샌드박스, 계정 권한, 훅 같은 기술 장치로 제한하는 방법이다. 통제 장치도 오탐과 미탐을 테스트해 검증한다.

노하우난이도 심화AI 활용최종 업데이트 2026-11-24

에이전트에 “수정하지 마라”, “운영 DB에 쓰지 마라”라고 지시해도 쓰기 권한이 열려 있으면 지시를 벗어난 실행을 막지 못한다. OWASP LLM06 과도한 권한(Excessive Agency)은 에이전트에 필요 이상의 기능, 권한, 자율성을 부여한 상태를 위험으로 분류한다.

현장 노트

  • 외부 모델에 “검증만 하라”고 지시했으나 쓰기 가능한 샌드박스로 실행됨. 코드 9개 파일 수정, 릴리즈 노트와 이슈 로그 작성, main 브랜치 커밋·푸시, 이슈 7건 등록까지 수행함. 리뷰되지 않은 코드가 배포되고, 반쯤 적용된 상태로 봇이 재시작되어 연동된 다른 모델 프로세스가 5회 연속 중단됨
  • 이튿날 다른 검증에서 백테스트를 실행해 캘리브레이션 결과를 덮어쓴 사례는 AI 교차 검증 참고

통제 수단

섹션 제목: “통제 수단”
  • 파일: 검증·분석 에이전트는 읽기 전용 샌드박스로 실행함
  • DB: 조회 전용 계정을 사용함. 쓰기 메서드를 코드 수준에서 차단함
  • 스크립트: 산출물을 덮어쓰는 스크립트(수집기, 백필, 학습, 백테스트, --fix 옵션)를 이름으로 지정해 실행을 차단함
  • 도구 목록: 에이전트에 부여하는 도구를 최소화함. 파일 쓰기 도구가 없어도 셸로 인라인 코드를 실행하면 파일과 DB를 수정할 수 있으므로 셸 명령도 검사 대상임
  • 허용·거부 목록: 같은 인터프리터가 여러 호출 형태로 허용되어 있으면 접두어 매칭 거부 규칙으로 모두 막지 못함. 명령 문자열 전체를 판정하는 훅으로 보완함

통제 장치 검증

섹션 제목: “통제 장치 검증”

훅과 가드는 등록 여부와 별개로 위험 실행을 실제로 차단하는지 확인한다.

  • 미탐 테스트: 위험 명령 변형(따옴표 조합, 이스케이프, 명령 치환, 래퍼 명령)의 통과 여부를 확인함
  • 오탐 테스트: 정상 작업(검색, 커밋 메시지 속 스크립트 이름 언급, 읽기 전용 확인 옵션)의 차단 여부를 확인함
  • 보호 목록 누락: 새 스크립트·배치가 추가될 때 목록 갱신이 누락됨. 이름 패턴(접두사·접미사)으로 일반화하고, 모든 배치 파일에서 쓰기 단계를 추출해 목록과 대조하는 테스트를 추가함
  • 판정 실패 시 동작: 판정기가 없거나 비정상 종료하면 차단함(fail-closed). 일부 에이전트 도구는 지정된 차단 종료코드 외의 오류를 통과로 처리하므로 종료코드 변환까지 확인함
  • 판정 로직에 변이를 주입해 테스트가 실패하는지 확인함

현장 노트

  • 명령 검사 훅을 정규식과 awk로 구현했을 때 커밋 보안 검토에서 새 우회 형태가 여섯 차례 연속 발견됨(따옴표 조합, 이스케이프 공백, 명령 치환 등). 정규식 판정을 중단하고 POSIX 셸 규칙으로 명령을 토큰 단위로 분리하는 판정기로 교체함
  • 스크립트 이름이 있으면 무조건 막던 초기 판정이 검색과 커밋 메시지 속 언급까지 차단함(오탐). 실행 형태만 차단하도록 수정함
  • 운영 데이터를 UPDATE하는 스크립트가 목록에 없어 안내 문구만 표시되고 차단되지 않음(미탐). 접두사 패턴으로 일반화함
  • 일일 배치만 목록에 있고 주간·월간·분기 배치가 빠진 것을 리뷰 에이전트가 발견(미탐). 이후 모든 배치 파일의 DB 쓰기 단계를 추출해 차단 여부를 확인하는 테스트를 추가함

실행 의도와 실제 완료 구분

섹션 제목: “실행 의도와 실제 완료 구분”

실행 전 훅(PreToolUse)이 관측하는 것은 호출 의도다. 사용자 승인, 실행 성공, 취소, 프로세스 종료는 확인하지 못한다.

  • 훅이 기록한 “검증 도구 호출” 신호를 커밋 허용 조건으로 사용하면 관계없는 호출로도 조건이 충족됨
  • 서버 기동 호출 기록과 프로세스 생존·종료는 별개임
  • 직접 관측하지 못하는 상태는 차단 대신 경고나 확인 요청으로 처리함. 정확한 판정이 필요하면 실행 후 훅(PostToolUse)이나 산출물 확인 단계에서 판정함

현장 노트

  • 개인 에이전트 하네스에서 커밋 전 QA 흔적 확인을 실행 전 훅으로 구현함. 소스 편집 시각과 외부 모델 읽기 전용 호출 시각을 비교하는 방식이라 관계없는 호출로도 조건이 해제됨. 실행 결과와 종료를 관측하지 못해 차단 대신 확인 요청으로 두고 한계를 문서화함

작업별로 사람이 개입하는 지점은 AI 시대의 QA의 위임 수준 기준을 따른다.

규칙

  • 프롬프트의 금지 지시는 권한 통제로 간주하지 않음
  • 검증 에이전트는 읽기 전용 샌드박스와 조회 전용 계정으로 실행함
  • 통제 장치에는 오탐과 미탐 테스트를 함께 작성함
  • 판정기가 실패하면 차단함(fail-closed)
  • 최종 품질 승인 책임은 사람에게 있음

관련 문서

AI와 QAAI 교차 검증AI가 작성한 코드 변경을 검증하는 구성(사람 리뷰, AI 하나와 사람 확인, 같은 모델 반복, 다른 계열 둘의 대조)의 선택 기준과, 운영 예로 서로 다른 AI 검증자 둘이 독립적으로 검토한 뒤 결과를 대조하는 방법.AI와 QAAI에 제공한 정보와 외부로 전송되는 정보AI 에이전트가 작업 문맥으로 알고 있는 정보와 외부 요청에 포함해도 되는 정보를 구분해 통제하는 방법이다. 외부 모델에 넘기는 입력과 에이전트가 구성하는 외부 요청 모두 대상이다.자동화변이 주입으로 테스트 검출력 확인구현에 변이를 넣어 테스트가 실패하는지로 검출력을 확인하는 방법. 변이 테스트 도구(Stryker, PIT, mutmut)와 표적 변이 주입을 비교하고, 표적 변이 주입의 절차와 함정을 다룬다. 실패를 확인하지 않은 테스트의 통과는 결함 검출의 근거로 사용하지 않는다.
