AI가 작성한 문서 검사

AI가 작성한 문서의 구조, 어휘, 사실을 구분해 검사하는 방법이다. 문체 검사기의 결과는 측정한 지표 범위 안에서만 해석한다.

노하우난이도 중급AI 활용최종 업데이트 2026-11-24

구조, 어휘, 사실은 확인 방법이 서로 달라 각각 검사한다. 문체 검사기를 통과해도 어휘와 사실은 따로 확인한다.

검사 항목과 확인 방법

섹션 제목: “검사 항목과 확인 방법”
  • 구조: 볼드 리드인 반복, 불릿 개수 맞춤, 헤딩을 되풀이하는 첫 문장, 장식 기호, 기록 문서의 서술형 종결, 항목당 분량. 검사기로 측정함
  • 단어: 직역 조어, 상투어, 구어 동사, 의인화 표현, 조사 띄어쓰기. 사전과 정규식으로 일부 측정함. 사전은 정확한 구절만 찾으므로 활용형은 눈으로 확인함
  • 사실: 수치, 코드, 설정 키, 고유명사, 문서 간 표기 일치. 원 출처와 대조함

검사기 결과 해석

섹션 제목: “검사기 결과 해석”
  • 종료코드 0은 측정한 지표에서 위반이 없다는 뜻. 측정하지 않은 지표는 판정에 포함되지 않음
  • 리포트에서 표본 부족으로 제외된 지표를 확인함. 짧은 문서의 0은 측정할 표본이 없었다는 뜻일 수 있음
  • 0건 결과를 확인하는 방법은 검사 결과 0건 검증 참고

현장 노트

  • 한 릴리즈 노트가 장식 기호 786회, 서술체 종결 2,322회, 항목당 최대 30,332자인데도 문체 검사기에서 종료코드 0으로 통과함. 세 지표 모두 검사기가 측정하지 않던 항목이었음. 같은 날 세 지표를 검사기에 추가함

단어

섹션 제목: “단어”
  • 업계 표준 용어가 있으면 그 용어를 사용함. 예: 마스킹, 시각 회귀, 세션 타임아웃, 테스트 데이터, 리스크 기반, 교차 리뷰
  • 처음 나오는 영문 용어는 괄호로 원어를 한 번 병기함
  • 어휘 수준은 독자에 맞춰 정함. Microsoft Writing Style Guide는 기술 문서를 포함해 쉬운 단어와 짧은 문장을 권하고(예: utilize 대신 use), 한 개념에는 한 용어를 일관되게 쓰도록 안내함. 정해진 어휘 목록으로 표현을 통일하는 규칙을 따로 두는 팀도 있음
  • 운영 예: 이 위키 작성자는 기록·기술 문서에서 구어 동사를 기술 문서 어휘로 변경함(보다 -> 확인하다, 바꾸다 -> 변경하다, 생기다 -> 발생하다). 쉬운 단어를 권하는 위 지침과는 방향이 다르며, 사내 기록 문서와 표현을 통일하는 것을 우선한 선택임
  • 사람에게 쓰는 동사를 사물에 붙인 의인화 표현을 수정함. 예: “E2E는 빌드 뒤에 온다”

현장 노트

  • 구조 지표를 모두 통과한 공유 문서에 업계 용어(마스킹) 대신 직역 조어(비밀 값 가림)가 남아 있었음. 구조 지표는 단어를 측정하지 않으므로 조어 사전 검사를 추가하고, 검사 실행을 사람의 기억에 맡기지 않도록 문서 저장 시 검사기가 자동 실행되게 연결함

교열 범위와 정독

섹션 제목: “교열 범위와 정독”
  • 제목과 description 같은 frontmatter 문장도 교열 대상에 포함함. 사실 보호가 필요하면 “숫자·코드·설정 키는 유지, 문장은 정리 대상”으로 범위를 나눠 지시함
  • 검사 통과 뒤 문서 전체를 정독함. 일부 문서만 표본으로 읽고 완료로 판정하지 않음
  • 문구 하나를 변경하면 같은 뜻의 문구를 문서 전체에서 찾아 함께 수정함

현장 노트

  • 문서 13건을 정리하면서 사실 보호를 위해 AI 에이전트에 frontmatter를 변경하지 말라고 지시하자 제목과 정의가 교열 대상에서 빠짐. 검사기는 의인화와 구어를 측정하지 않았고, 조사 띄어쓰기 77곳은 어떤 기준에도 없었음. 이후 frontmatter 문장을 교열 범위에 포함하고, 조사 띄어쓰기를 문서 검사 스크립트에 추가하고, 표본이 아닌 전체 문서 정독과 독자 테스트를 완료 조건으로 둠

독자 테스트

섹션 제목: “독자 테스트”

작성자는 배경 지식을 이미 알고 있어 생략된 전제나 모호한 설명을 스스로 찾기 어렵다. 독자 테스트는 실제 대상 독자나 동료에게 읽히는 방법과, 작성 맥락이 없는 AI 모델로 먼저 점검하는 방법이 있다. 사람 독자는 실제 이해 수준을 확인할 수 있고, AI 모델 점검은 빠르고 반복하기 쉽다.

운영 예: 다른 계열 모델로 먼저 점검

  • 예상 질문 5~10개를 작성함
  • 작성 맥락이 없는 다른 계열 모델에 문서와 질문만 제공해 답을 받음
  • 답에서 드러난 모호한 표현, 전제 지식, 모순을 수정함
  • 모델의 답이 맞아도 사람 독자의 이해나 사실 정확성까지 확인된 것은 아님. 사실의 정확성은 원 출처와 대조해 따로 확인함

규칙

  • 구조, 단어, 사실을 각각 다른 수단으로 확인함
  • 검사기 0건을 문서 품질 통과로 보고하지 않음. 통과한 지표와 제외된 지표를 함께 보고함
  • 제목과 description을 교열 범위에 포함함
  • 검사 뒤 문서 전체를 정독함

출처

섹션 제목: “출처”
  • Microsoft Writing Style Guide: Use simple words, concise sentences

관련 문서

자동화검사 결과 0건 검증스캔이나 검사기가 0건을 반환했을 때 검사가 실제로 수행되었는지 확인하는 방법이다. 검사기가 대상을 읽지 못해도 결과는 0건이므로, 검출되어야 하는 가짜 값을 추가해 검사기가 찾는지 먼저 확인한다.AI와 QAAI 보고 확인AI 검토자나 에이전트가 낸 통과 판정, 반박, 재발 방지 주장을 실데이터와 산출물로 확인하는 방법이다. 결함 지적과 마찬가지로 통과 판정과 반박도 재현한 뒤 수용한다.프로세스릴리즈 노트와 버전 번호버전 번호(SemVer, CalVer, 4자리 번호, 빌드 번호)와 릴리즈 노트(Keep a Changelog, Conventional Commits 자동 생성, 이슈 중심 형식)의 대표 방식과 선택 기준. 운영 예로 변경 크기 기준 A.B.C.D 규칙을 함께 둔다.
