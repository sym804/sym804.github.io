AI 교차 검증

AI가 작성한 코드 변경을 검증하는 구성(사람 리뷰, AI 하나와 사람 확인, 같은 모델 반복, 다른 계열 둘의 대조)의 선택 기준과, 운영 예로 서로 다른 AI 검증자 둘이 독립적으로 검토한 뒤 결과를 대조하는 방법.

노하우난이도 심화AI 활용최종 업데이트 2026-11-24

검증 구성 선택

섹션 제목: “검증 구성 선택”
구성 장점 한계
사람 리뷰 요구사항과 제품 맥락을 기준으로 판단함 시간이 많이 들고, 변경량이 많으면 꼼꼼함이 떨어짐
AI 검증자 하나와 사람 확인 비용이 작음. 사람은 AI 지적의 진위를 확인하고, 변경 위험에 따라 원문을 직접 검토함 그 모델이 놓치는 유형은 사람도 지적 목록에서 보지 못함
같은 모델을 지시문을 바꿔 여러 번 실행 설정이 간단하고 관점(보안, 회귀, 테스트)을 나눠 검토할 수 있음 같은 학습 데이터와 편향을 공유해 놓치는 결함이 겹칠 수 있음
서로 다른 계열 둘의 독립 검토와 대조 실패 방식이 달라 한쪽의 사각지대를 다른 쪽이 잡을 수 있음 실행 비용과 두 보고서를 대조하는 시간이 듦

선택 기준

  • 변경이 데이터, 보안, 결제에 닿을수록 사각지대가 다른 검증자를 늘림. 렌더링 변경은 코드 검증자 수와 관계없이 화면을 직접 확인함
  • 문구, 주석처럼 런타임 동작이 없는 변경은 사람 확인이나 AI 하나로 충분한 경우가 많음
  • 어떤 구성이든 지적을 그대로 수용하지 않고 실제 데이터나 코드로 재현해 판정함. 코드만 읽는 검증자는 렌더링을 확인하지 못하므로 화면 캡처나 브라우저 확인을 따로 둠

운영 예: 다른 계열 둘의 독립 검토

섹션 제목: “운영 예: 다른 계열 둘의 독립 검토”

아래는 이 위키 작성자가 로직, 데이터, 렌더링이 바뀌는 변경마다 적용하는 구성이다. 구현에 사용한 모델을 검증자로 다시 쓰지 않는 이유는 LLM 평가자가 자기 출력을 알아보고 더 높게 평가한다는 연구와, 외부 신호 없이 스스로 추론을 고치지 못한다는 연구가 있기 때문이다.

구성

섹션 제목: “구성”
  • 검증자 1: 구현에 사용한 모델과 다른 외부 모델(예: Codex). 학습 데이터와 편향이 다른 모델을 선정함
  • 검증자 2: 프로젝트 맥락을 제공받은 리뷰 에이전트. 프로젝트 관행, 과거 사고 이력, 규칙 문서를 기준으로 검토함
  • 두 검증자는 서로의 보고서를 보지 않고 독립적으로 검토함. 앞 검증자의 보고서를 뒤 검증자의 입력에 포함하면 뒤 검증자가 그 결론을 따라갈 수 있음. 독립성은 실행 순서보다 보고서 노출 여부로 정해짐
  • 보고서를 직접 넘기지 않아도, 앞 보고서를 읽은 사람이 뒤 검증자의 지시문을 작성하면 검토 초점이 앞 결론 쪽으로 옮겨짐. 두 검증자의 지시문은 어느 보고서도 읽기 전에 확정함
  • 기본은 두 검증자를 동시에 실행하는 것임. 지시문 확정 시점을 지키기 쉽고 대기 시간도 줄어듦. 두 보고서가 모두 나온 뒤에 대조함

검증자마다 잡는 것과 놓치는 것

섹션 제목: “검증자마다 잡는 것과 놓치는 것”

두 검증자는 실패하는 방식이 다르다. 한쪽만 두면 그쪽의 사각지대가 그대로 남는다.

외부 모델

  • 프로젝트 맥락 없이 코드 자체를 읽어 계산 오류, 경계값 오류, 표시 누락 같은 결함을 찾음
  • 확인 없이 단정하거나, 제품이 제공하지 않는 기능을 기준으로 판정하는 오판이 있음
  • 검증 중 스크립트를 실행해 산출물을 덮어쓰고, 그 결과를 결함의 근거로 삼을 수 있음

리뷰 에이전트

  • 프로젝트 이력과 규칙을 알아 검증자 자신이 만든 부작용, 구현자 주장의 과장을 찾음
  • 테스트가 결함을 실제로 검출하는 구조인지(우연히 일치하는 경우만 검증하는지) 확인함

두 보고 대조

섹션 제목: “두 보고 대조”
  • 둘 다 지적: 우선순위 최상. 실제 결함일 가능성이 높음
  • 한쪽만 지적: 실데이터나 코드로 재현한 뒤 수용 여부를 결정함
  • 두 판정이 다름: 실데이터나 코드로 재현한 결과를 따름
  • 코드만 읽고 낸 지적은 실제 발생 여부를 확인함
    • 예: “상폐 종목의 0 종가로 -inf가 나온다”(상폐: 상장폐지, -inf: 음의 무한대) -> 실측 close <= 0 0행으로 발생하지 않음. 가드(방어 코드)는 추가함

규칙

  • 외부 모델은 읽기 전용 샌드박스로만 실행함. “수정하지 마라”는 지시만으로는 파일 수정을 방지하지 못함
  • 산출물을 덮어쓰는 스크립트(백테스트, 학습, 수집기, --fix 옵션)는 실행 금지 대상으로 이름을 명시함
  • 지적 내용이 검증자 자신의 부작용일 수 있음. 지적을 받으면 그 상태를 누가 언제 유발했는지(파일 수정 시각, git status)부터 확인함

리뷰 에이전트 점검 항목

섹션 제목: “리뷰 에이전트 점검 항목”

외부 모델이 알 수 없는 프로젝트 규칙, 과거 사고, 테스트 유효성은 리뷰 에이전트가 점검한다.

  • 이 프로젝트 규칙 위반 여부
  • 이 프로젝트의 과거 사고와 같은 유형인지 여부
  • 기존 테스트가 잘못된 동작을 기대값으로 고정하고 있는지 여부(계약 테스트 함정)
  • 새로 작성한 테스트가 실제 결함을 검출하는지 여부, 구현 로직을 그대로 옮긴 동어반복 테스트인지 여부
  • 코드 주석의 “불가피”, “한계” 서술이 현재 코드 기준으로 유효한지 여부

두 검증자의 공통 사각지대

섹션 제목: “두 검증자의 공통 사각지대”
  • 코드를 검토하는 두 검증자 모두 화면을 확인하지 못함. 시각 산출물이 변경되면 스크린샷을 캡처해 렌더링 결함을 직접 확인함

현장 노트

  • 같은 날 같은 코드를 두 검증자에게 맡김. 외부 모델만 지표 경계값 오류, 지표 계산의 가격 데이터 미반영, 차트 미래 구간 누락을 찾았음. 같은 외부 모델이 “수정주가 선택지가 없다”고 확인 없이 단정했는데(DB에는 이미 수정주가가 저장되어 있었음), “방향 적중률 50%는 실패”처럼 제품이 제공하지 않는 매매 신호 기능을 기준으로 판정하기도 했음
  • 같은 검증에서 외부 모델이 백테스트 스크립트를 실행해 입력 아티팩트(표본 200건의 캘리브레이션 결과)를 표본 4건짜리로 덮어쓰고, 바뀐 값을 근거로 표본 부족을 지적함. 이 상태를 만든 주체가 외부 모델이라는 사실은 리뷰 에이전트가 파일 수정 시각으로 확인함. 이후 검증 지시에는 산출물을 덮어쓰는 스크립트를 이름으로 실행 금지하고, 지적을 받으면 그 상태를 누가 언제 만들었는지부터 확인함. 구현 설명의 과장과, 두 방식이 우연히 일치하는 경우만 확인하는 테스트도 리뷰 에이전트가 찾음
  • 새로 작성한 테스트는 구현에 의도적으로 결함을 주입해 실패하는지 확인함
  • 이 운영 예에서는 런타임 동작이 없는 변경(오타, 주석, 문서)은 교차 검증을 생략하고, 로직, 데이터, 렌더링이 변경되면 예외 없이 적용함
