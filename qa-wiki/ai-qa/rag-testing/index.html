RAG 테스트

검색 증강 생성(RAG) 기능을 검색 단계와 생성 단계로 나눠 각각 검증하는 방법이다. 최종 답만 확인하면 오답의 원인이 검색인지 생성인지 구분할 수 없다.

기본기난이도 심화AI 제품최종 업데이트 2026-11-24

RAG는 질문과 관련된 문서 조각(청크)을 먼저 검색하고, 그 조각을 근거로 모델이 답을 생성하는 구조다. 오답의 원인은 정답 근거를 검색하지 못한 경우와, 검색한 근거를 모델이 잘못 사용한 경우로 나뉜다. 두 단계를 독립된 테스트 대상으로 분리한다.

검색 단계

섹션 제목: “검색 단계”
  • 문맥 재현율(Context Recall): 정답 근거가 든 청크가 상위 K개 안에 포함되는지 확인함
  • 문맥 정밀도(Context Precision): 상위 K개에 질문과 무관한 청크가 얼마나 섞이는지 확인함
  • 청크 경계: 표, 목록, 조건문이 청크 경계에서 잘려 의미가 변경되지 않는지 확인함
  • 최신성: 같은 문서의 이전 판과 새 판이 함께 검색될 때 새 판이 우선되는지 확인함
  • 검색 실패 처리: 관련 문서가 없는 질문에 관련도 기준(임계값)을 넘는 결과가 없고, 최종 답이 확인 불가 안내인지 확인함. 임계값 없이 상위 K개를 항상 반환하는 구성이면 관련 없는 청크가 반환되는 것은 정상임

질의마다 정답 근거 청크 목록을 기대 결과로 저장해 두고, 실제 검색 결과와 비교한다. 답 생성 단계를 거치지 않아 검색만 독립적으로 평가할 수 있다. 다만 임베딩, 질의 재작성, 재순위화에 모델을 사용하는 구성이면 검색 결과도 실행마다 달라질 수 있으므로, 구성별로 반복 실행해 결과가 같은지 먼저 확인한다.

생성 단계

섹션 제목: “생성 단계”

검색 결과를 고정한 입력(모의 문맥)으로 제공해 확인한다. 검색 설정을 변경해도 생성 단계의 판정 결과에는 영향이 없다.

  • 문맥 충실도(Faithfulness): 답의 주장이 제공한 문맥으로 뒷받침되는지 확인함. 문맥에 근거가 없는 주장은 사실 여부와 별개로 충실도 실패로 판정하고, 사실이 아닌 내용이면 허위 생성(Confabulation)으로 분류함
  • 인용 정확성: 답이 가리키는 문서 번호, 조항, 링크가 실제로 있고 본문과 일치하는지 확인함
  • 문맥 우선: 사전 학습 지식과 제공 문맥이 다를 때 문맥을 따르는지 확인함
  • 상충 문맥: 날짜나 판이 다른 근거가 함께 주어질 때 차이를 구분해 답하는지 확인함
  • 확인 불가 응답: 문맥에 답이 없으면 지어내지 않고 확인할 수 없다고 답하는지 확인함

권한과 격리

섹션 제목: “권한과 격리”

RAG는 의미가 비슷한 문서를 찾으므로, 권한 필터가 없으면 질문자가 볼 수 없는 문서도 검색 결과에 섞인다. 답에 직접 인용되지 않아도 생성 문맥에 포함되면 요약이나 추론 과정에서 내용이 노출될 수 있다.

  • 다른 사용자, 다른 조직, 비공개 문서에만 있는 고유 문구로 질문해 검색 결과에 포함되는지 확인함
  • 권한을 회수한 직후 같은 질문으로 다시 확인함. 권한 변경이 색인과 캐시에 반영되는지 확인함
  • 검색 요청 로그에 적용된 권한 조건이 남는지 확인함
  • 이 항목은 OWASP LLM08(벡터·임베딩 취약점)과 LLM02(민감 정보 노출)에 해당함

TC 예시

섹션 제목: “TC 예시”
항목 TC 예시
검색 적중률(Hit@K) 질의마다 정답 근거 청크 ID를 기대 결과로 두고, 정답 청크가 상위 K(예: 5)개 안에 1개 이상 있는 질의의 비율이 목표(예: 0.9) 이상인지 확인함. 정답 근거가 여러 청크이면 질의별로 검색된 정답 청크 수 / 전체 정답 청크 수(Recall@K)를 따로 계산함. 기준선에서는 상위 K개 안에 있었으나 이번 회차에 K개 밖으로 내려간 질의 목록을 함께 기록함
문맥 정밀도 상위 K개 중 정답 근거로 지정된 청크의 비율을 질의별로 계산해 평균이 목표(예: 0.6) 이상인지 확인하고, 최저값과 그 질의를 기록함
청크 경계 요율표가 두 청크로 나뉘는 문서에서 표 아래쪽 행의 값을 질문해, 검색된 청크에 해당 행과 열 머리글이 함께 있는지와 답의 값이 표와 일치하는지 확인함
최신성 같은 계약의 원계약(예: 요율 3%)과 변경 계약(예: 요율 2.5%, 시행일 지정)을 색인한 뒤 현재 요율을 질문해 변경 계약 값을 답하는지 확인함. 시행일 이전 기간을 질문하면 원계약 값을 답하는지 확인함
검색 실패 처리 어느 문서에도 없는 조항(예: 위약금)을 질문해 관련도 기준을 넘는 결과가 없고(임계값 없는 구성이면 무관한 청크가 반환되어도 됨), 답이 확인 불가 안내이며 근거 없는 위약금 금액이나 조항을 생성하지 않는지 확인함
문맥 충실도 검색 결과를 고정 문맥으로 주입하고 답의 문장마다 문맥에 근거가 있는지 판정함. 문맥에 없는 사실이 1건이라도 있으면 실패로 판정함
인용 정확성 답이 인용한 문서와 조항 번호를 열어 그 조항 본문에 답의 값과 조건이 있는지 확인함
문맥 우선 업계에서 흔히 쓰는 기준과 다른 값이 적힌 테스트용 계약서로 질문해, 사전 학습 지식이 아니라 계약서의 값을 답하는지 확인함
상충 문맥 본계약과 부속 합의서의 값이 다를 때 계약서의 우선순위 조항에 따라 답하고 두 값의 출처를 구분해 표시하는지 확인함
테넌트 격리 고객사 B 문서에만 넣은 테스트용 표식 문자열로 먼저 B 계정이 질문해 그 문서가 색인되어 검색되는지 확인함. 이어서 A 계정이 같은 질문을 보내 검색 로그에 A의 권한 조건이 적용되었는지, 검색 결과, 생성 문맥, 답 어디에도 B 문서가 없는지 확인함
권한 회수 회수 전에 해당 문서가 검색되는 것을 확인한 뒤, 문서 열람 권한을 회수한 직후와 명세의 반영 시간(예: 5분)이 지난 뒤 같은 질문을 보내, 반영 시간 이후에는 해당 문서가 검색되지 않는지 확인함. 캐시된 이전 답이 반환되지 않는지도 확인함

적용 예: 고객사별 계약 문서 질의응답

섹션 제목: “적용 예: 고객사별 계약 문서 질의응답”

기업 고객용 서비스에 “고객사 담당자가 자기 회사의 계약서와 부속 합의서를 근거로 질문하면 조항을 인용해 답한다”는 기능을 추가하는 경우, 단계별로 기획과 확인할 항목은 다음과 같다.

색인

  • 스캔 PDF, 표, 각주가 있는 문서의 텍스트 추출 방식과 추출 실패 시 처리
  • 청크 단위(조항 단위인지 고정 길이인지)와 표를 청크로 나누는 규칙
  • 새 계약서를 올린 뒤 검색에 반영되기까지의 시간 목표와 반영 확인 방법

검색

  • 질의별 정답 조항 ID를 담은 검색 평가셋과 K값, 목표 문맥 재현율
  • 원계약과 변경 계약, 본계약과 부속 합의서가 함께 검색될 때의 우선순위 규칙(계약서의 우선순위 조항 적용 또는 최신 문서 우선)
  • 고객사 필터의 적용 위치(검색 전 적용 또는 검색 후 적용)

검색 뒤에 고객사 필터를 적용하는 구조면 상위 K개가 다른 고객사 문서로 채워진 뒤 걸러져, 결과가 비거나 재현율이 떨어질 수 있다. 필터 적용 위치를 확인하고 고객사별 문서 수가 크게 다른 조건에서 재현율을 측정한다.

생성

  • 조항 번호 인용 형식과 인용한 조항으로 이동하는 링크
  • 근거가 없을 때의 안내 문구, 법률 자문이 아니라는 안내 표시 여부
  • 계약 금액, 요율, 기한처럼 수치가 들어간 답의 정확성 기준(근거 조항의 값과 일치)

권한과 격리

  • 고객사 간 격리, 같은 고객사 안의 부서별 열람 권한
  • 계약 해지 고객사와 퇴사한 담당자 계정의 처리 시점
  • 권한 변경이 색인과 답변 캐시에 반영되는 시간

우선순위 규칙과 반영 시간 목표가 정해지지 않으면 최신성, 상충 문맥, 권한 회수 TC의 기대 결과를 작성할 수 없다. 이 항목은 테스트 착수 전에 기획과 합의한다.

테스트 계획, 결함 분류, 보고에 적용

섹션 제목: “테스트 계획, 결함 분류, 보고에 적용”

테스트 계획

  • 검색 평가(정답 청크 비교)와 생성 평가(고정 문맥 주입), 종단 평가를 별도 단계로 계획함
  • 변경 종류별 실행 범위를 정함. 예: 청크·임베딩·색인 설정 변경은 검색 평가와 종단 평가를, 프롬프트·모델 변경은 생성 평가와 종단 평가를, 권한 로직 변경은 격리 TC 전체를 실행함
  • 색인 시점, 문서 버전, 임베딩 모델 버전을 측정 조건으로 기록함

결함 분류

  • 원인 단계를 색인(추출, 청크), 검색(재현율, 정밀도, 필터), 생성(충실도, 인용), 권한으로 구분해 라벨로 남김
  • 판정 기준을 정해 둠. 정답 근거 청크가 상위 K개에 없으면 원본 추출, 색인 존재, 검색 순위 순서로 원인을 확인하고, 있는데 답이 틀리면 생성에 전달된 문맥과 생성 단계를 확인함
  • 격리 실패는 데이터 노출이므로 보안 결함의 심각도 기준을 적용함(심각도)

보고

  • 단계별 지표를 나눠 보고함. 예: “문맥 재현율 0.92(K=5, 기준선 0.94), 충실도 실패 3/150, 인용 불일치 1/150, 격리 TC 20/20 통과”
  • 종단 정답률만 보고하지 않음. 종단 정답률이 같아도 검색 재현율이 떨어졌는지는 단계별 지표로만 확인할 수 있음

규칙

  • RAG 오답을 결함으로 등록할 때는 질문, 검색된 청크 목록, 생성된 답을 함께 기록함. 원인 단계(검색 또는 생성)를 구분할 수 있어야 함
  • 권한 격리 항목은 결함 시 데이터 노출이므로 우선순위를 매우 높음으로 둠

흔한 실수

섹션 제목: “흔한 실수”
  • 모든 오답을 프롬프트 문제로 보고 프롬프트만 수정함. 검색이 근거를 찾지 못한 경우는 프롬프트로 해결되지 않음
  • 정답 근거 문서를 지정하지 않고 최종 답만 채점해, 근거 없이 우연히 맞힌 답을 통과시킴
  • 권한 격리를 화면의 문서 목록에서만 확인하고 검색 결과와 답변 경로는 확인하지 않음
