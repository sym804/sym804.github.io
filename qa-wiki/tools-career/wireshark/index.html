Wireshark

네트워크 패킷 분석기 Wireshark의 캡처 구조(libpcap·Npcap, 인터페이스, 무차별 모드), 캡처 필터와 표시 필터, 패킷 목록·상세·바이트 창, Follow Stream, Statistics, TLS 복호화, tshark·dumpcap, pcap·pcapng 형식과 QA에서 사용하는 방법을 다룬다.

기본기난이도 중급임베디드보안최종 업데이트 2026-11-24

Wireshark는 네트워크 패킷을 캡처해 프로토콜별로 해석해 보여 주는 패킷 분석기다. GNU GPL v2로 배포되는 무료 오픈소스 프로젝트이고, 전 세계 기여자가 개발하며 공식 사이트의 후원 창구는 Wireshark Foundation이다. Windows, Linux, macOS, FreeBSD 등에서 실행된다. 2026-11 기준 안정 버전은 4.6 계열, 이전 안정 버전은 4.4 계열이다(공식 다운로드 페이지).

공식 User’s Guide는 용도로 네트워크 문제 해결, 보안 문제 조사, 네트워크 애플리케이션 검증(QA 엔지니어), 프로토콜 구현 디버깅을 든다. Wireshark는 트래픽을 관찰만 한다. 패킷을 보내거나 변조하지 않고(이름 확인 요청 제외, 끌 수 있음), 침입 탐지 시스템처럼 이상 징후를 경보하지도 않는다.

핵심 개념

섹션 제목: “핵심 개념”
개념 뜻
캡처 라이브러리 운영체제에서 패킷을 받아오는 계층. Linux·macOS는 libpcap, Windows는 Npcap(Nmap 프로젝트의 Windows용 캡처 드라이버와 라이브러리, WinPcap 후속)을 사용함
인터페이스 캡처할 네트워크 장치. 이더넷, 무선 LAN 외에 USB, Bluetooth, 루프백(Npcap의 루프백 어댑터) 등을 하드웨어와 OS에 따라 캡처함
무차별 모드(promiscuous mode) 자기 주소가 아닌 패킷도 받도록 인터페이스를 설정하는 모드. 인터페이스마다 켜고 끔
모니터 모드 무선 LAN의 802.11 헤더까지 원시 상태로 캡처하는 모드. 하드웨어, 드라이버, OS에 따라 지원 여부가 다르고 켜면 무선 연결이 끊길 수 있음
스냅샷 길이(snaplen) 패킷마다 저장할 최대 바이트 수. 성능이나 개인정보 보호 목적으로 줄일 수 있음
캡처 필터 캡처 시점에 저장할 패킷을 고르는 필터. BPF(libpcap 필터 언어) 문법
표시 필터 이미 캡처한 패킷 중 화면에 보일 패킷을 고르는 필터. Wireshark 고유 문법
스트림 하나의 연결에 속한 패킷 묶음. TCP는 tcp.stream 번호로 식별함

캡처 위치에 따라 보이는 패킷이 다르다. 스위치 네트워크에서는 무차별 모드를 켜도 캡처하는 PC 자신의 유니캐스트 트래픽과 브로드캐스트·멀티캐스트만 보인다. 다른 장비 사이의 통신을 보려면 스위치의 포트 미러링(SPAN), 네트워크 탭(tap)을 사용하거나, 통신하는 장비 중 한쪽에서 캡처한다. 미러링 포트는 감시 대상 포트보다 느리면 패킷이 유실된다.

화면 구성

섹션 제목: “화면 구성”
  • 패킷 목록(Packet List): 캡처한 패킷마다 요약을 한 줄로 표시함. 선택한 패킷이 아래 창의 내용을 결정함
  • 패킷 상세(Packet Details): 선택한 패킷을 프로토콜 계층별로 펼쳐 필드 단위로 표시함. 필드를 우클릭해 표시 필터를 만듦
  • 패킷 바이트(Packet Bytes): 패킷 원시 데이터를 표시하고 상세 창에서 선택한 필드의 바이트를 강조함
  • 패킷 다이어그램: 선택한 패킷의 헤더를 교과서식 도식으로 표시함
  • 필터 툴바와 상태 표시줄: 표시 필터를 입력하고, 패킷 수, 표시 중인 패킷 수, 전문가 정보를 표시함

캡처 필터와 표시 필터

섹션 제목: “캡처 필터와 표시 필터”
항목 캡처 필터 표시 필터
적용 시점 캡처 전. 조건에 맞지 않는 패킷은 저장하지 않음 캡처 후. 패킷은 그대로 두고 화면에서만 거름
문법 libpcap 필터 언어(pcap-filter). tcpdump와 같음 Wireshark 필드 이름 기반 문법
장점 파일 크기와 부하를 줄임 프로토콜 필드 단위로 세밀하게 거르고, 조건을 바꿔 다시 볼 수 있음
한계 걸러진 패킷은 복구할 수 없음 캡처 양은 줄이지 않음

캡처 필터는 host, net, port, src·dst, tcp·udp 같은 기본 식을 and, or, not으로 조합한다.

표시 필터는 프로토콜 이름과 필드 이름에 비교 연산자(==, !=, >, <, contains, matches)와 논리 연산자(and, or, not)를 사용한다. 집합 비교는 in {}을 사용한다.

  • ip.addr처럼 한 패킷에 값이 여러 개인 필드(출발지와 목적지)에서 ==는 “하나라도 같음”, !=는 “모두 같지 않음”을 뜻함. !=의 의미는 Wireshark 3.6에서 바뀌었으므로 이전 버전 기준 자료와 결과가 다를 수 있음
  • 패킷 상세 창에서 필드를 우클릭해 Apply as Filter(바로 적용)나 Prepare as Filter(입력만 하고 적용하지 않음)를 선택하면 필드 이름을 몰라도 표시 필터를 만들 수 있음. Apply as Column은 그 필드를 패킷 목록의 열로 추가함. 전체 필드 목록은 Display Filter Reference에서 확인함

분석 기능

섹션 제목: “분석 기능”

Follow Stream

섹션 제목: “Follow Stream”

Analyze > Follow에서 선택한 패킷이 속한 스트림을 애플리케이션 계층의 대화로 재구성해 보여 준다. TCP, UDP, DCCP, TLS, HTTP, HTTP/2, QUIC, WebSocket, SIP, USB CDC를 지원한다.

  • 실행하면 해당 스트림만 고르는 표시 필터(예: tcp.stream eq 5)가 적용됨
  • 클라이언트에서 서버 방향은 빨간색, 서버에서 클라이언트 방향은 파란색으로 표시함
  • Show data as에서 ASCII, HEX Dump, Raw, YAML 등을 선택함. 바이너리 프로토콜은 HEX Dump가 맞음
  • Save as로 대화 내용을 파일로 저장하고, Filter Out This Stream으로 해당 스트림을 화면에서 제외함
  • 실시간 캡처 중에는 내용이 갱신되지 않으므로 창을 다시 열어 확인함

Statistics

섹션 제목: “Statistics”
메뉴 용도
Conversations 두 끝점 사이의 트래픽을 계층별(Ethernet, IPv4, IPv6, TCP, UDP) 탭으로 집계함. 패킷 수, 바이트, 시작 시각, 지속 시간, 방향별 초당 비트 수를 보여 주고 Follow Stream, I/O Graph로 이어짐
Endpoints 계층별 끝점(IP 주소, IP와 포트 조합 등)마다 트래픽을 집계함. 예상하지 않은 통신 상대를 찾을 때 사용함
I/O Graphs 시간 구간별 패킷 수, 바이트, 비트를 그래프로 그림. 그래프마다 표시 필터를 지정하고, 필드 값의 SUM, MAX, MIN, AVG도 그림. 이미지나 CSV로 저장함
Expert Information 체크섬 오류, 비정상 패킷, 재전송 같은 특이 사항을 Chat, Note, Warn, Error 수준으로 모아 보여 줌

공식 문서는 전문가 정보를 조사의 출발점으로 설명한다. 항목이 표시되어도 실제 문제가 아닐 수 있고, 항목이 없어도 네트워크 정상을 보장하지 않는다.

TCP 분석 플래그

섹션 제목: “TCP 분석 플래그”

Wireshark는 TCP 순서 번호와 확인 응답을 분석해 패킷에 플래그를 붙인다. 표시 필터로 모아 볼 수 있다.

  • tcp.analysis.retransmission: 재전송으로 추정되는 세그먼트
  • tcp.analysis.fast_retransmission: 중복 ACK에 따른 빠른 재전송
  • tcp.analysis.duplicate_ack: 중복 ACK
  • tcp.analysis.zero_window: 수신 윈도가 0인 세그먼트. 대부분 수신 측의 성능이나 처리 용량 문제를 뜻함
  • tcp.analysis.lost_segment: 이전 세그먼트가 캡처되지 않음. 캡처 시작 직후에는 흔히 나타남
  • tcp.analysis.flags: 위 분석 플래그가 하나라도 붙은 패킷

공식 문서는 자동 분석이 어려운 캡처가 있고, 캡처 위치(서버 측, 클라이언트 측, 중간)에 따라 해석이 달라질 수 있다고 밝힌다.

TLS 복호화

섹션 제목: “TLS 복호화”

HTTPS 같은 TLS 트래픽은 그대로는 암호문만 보인다. 복호화에는 세 가지 방법이 있다.

방법 조건 한계
키 로그 파일 클라이언트가 SSLKEYLOGFILE 환경 변수에 지정한 파일로 세션 키를 기록함. Firefox, Chrome, curl, Chromium 기반 Edge, OpenSSL 3.4 이상 애플리케이션이 지원함 키를 내보내는 클라이언트나 서버가 필요함. Safari처럼 TLS 라이브러리가 지원하지 않으면 사용할 수 없음
RSA 개인 키 서버 인증서의 RSA 개인 키 (EC)DHE 키 교환, TLS 1.3, 세션 재개에는 사용할 수 없음
PSK 사전 공유 키를 사용하는 연결 PSK 연결에만 해당함

공식 위키는 키 로그 파일 방식이 모든 경우에 동작한다고 권장한다. 설정은 Preferences > Protocols > TLS의 (Pre)-Master-Secret log filename에 파일 경로를 지정한다.

--inject-secrets는 키를 pcapng의 DSB(Decryption Secrets Block)에 넣어 캡처 파일만으로 복호화되게 한다.

명령줄 도구와 파일 형식

섹션 제목: “명령줄 도구와 파일 형식”
도구 용도
dumpcap 캡처 전용 도구. 실시간 트래픽을 파일로 저장함. 기본 형식은 pcapng. -b로 시간·크기·개수 기준 파일 분할과 링 버퍼, -a로 자동 중지 조건을 지정함
tshark 명령줄 패킷 분석기. 실시간 캡처나 파일을 읽어 해석 결과를 출력함. -f 캡처 필터, -Y 표시 필터, -T fields -e로 필드 추출, -z로 통계(conv,tcp, io,stat, expert)
editcap 캡처 파일 편집. 키 삽입(--inject-secrets) 등
  • pcapng는 Wireshark·tshark·dumpcap의 기본 저장 형식이고, 공식 문서는 pcap보다 유연한 형식으로 설명함. 여러 인터페이스 동시 캡처에는 pcapng가 필요하고, TLS 키를 넣는 DSB도 pcapng에만 있음
  • tcpdump가 -w로 저장한 pcap 파일은 Wireshark에서 그대로 열 수 있음. 서버나 기기에서 tcpdump로 캡처하고 PC의 Wireshark로 분석하는 구성이 가능함
  • 내보내기는 File > Export Specified Packets(필요한 패킷만 새 파일로 저장), Export Packet Dissections(텍스트, CSV, JSON), Export Objects(HTTP 등에서 전송된 파일 추출)를 사용함

QA에서 사용하는 방법

섹션 제목: “QA에서 사용하는 방법”

비HTTP·임베디드 기기 통신

  • 브라우저 도구와 프록시가 보지 못하는 MQTT, 자체 TCP·UDP 프로토콜, DNS, DHCP 통신을 확인함(임베디드·단말 테스트)
  • 원시 프레임의 필드 배치, 바이트 순서, 길이를 패킷 바이트 창과 HEX Dump로 명세와 대조함. 프로토콜 해석기(dissector)가 없는 자체 프로토콜은 바이트 단위로 확인함
  • 통신 단절 시험에서 단절 구간 전후의 연결 종료(FIN, RST), 재연결 시각, 재전송된 데이터를 캡처로 확인함. 서버 로그만으로는 기기가 보내지 않은 것인지 서버가 받지 못한 것인지 구분할 수 없음
  • 장시간 시험은 dumpcap 링 버퍼로 디스크 사용량을 제한하고, 결함이 나온 시각의 파일만 보관함

재전송·지연·연결 끊김 분석

  • 응답 지연 결함은 I/O Graph와 TCP 분석 플래그로 네트워크 구간(재전송, 제로 윈도)의 문제인지, 요청을 받은 뒤 서버 응답까지의 지연인지 구분함. HTTP는 http.time(요청 후 응답까지 시간) 필드로 확인함
  • 연결 끊김은 tcp.flags.reset == 1로 RST를 보낸 쪽을 찾고, Follow Stream으로 직전 대화를 확인함
  • 간헐 결함은 재현될 때까지 캡처를 유지하고, 결함 시각 전후의 패킷만 Export Specified Packets로 잘라 이슈에 첨부함(이슈 양식)

보안 테스트

  • 로그인, 결제, 기기 인증 구간에서 비밀번호, 토큰, 개인정보가 평문으로 전송되는지 확인함. HTTP는 http.authorization, http.cookie, MQTT는 mqtt.username, mqtt.passwd 필드로 확인함(보안 테스트)
  • TLS 버전과 암호 스위트를 ClientHello, ServerHello 상세에서 확인해 보안 요구사항과 대조함
  • API 응답 계약 확인은 API 테스트 기본의 도구(Postman 등)로 하고, Wireshark는 그 아래 전송 계층의 확인에 사용함

비슷한 도구와 선택 기준

섹션 제목: “비슷한 도구와 선택 기준”
구분 대표 도구 볼 수 있는 계층 HTTPS 처리 설치·권한 모바일·기기 트래픽
패킷 캡처 Wireshark 인터페이스의 모든 패킷. 링크 계층부터 애플리케이션 계층까지, 비HTTP 포함 기본은 암호문. 키 로그 파일, RSA 키, PSK가 있어야 복호화됨 설치와 캡처 권한 필요(Windows는 Npcap, Linux·macOS는 캡처 장치 접근 권한) 같은 구간에서 캡처하거나 미러링·탭 필요. 기기 앱을 수정하지 않아도 됨
패킷 캡처(명령줄) tcpdump Wireshark와 같은 패킷. 출력은 텍스트 요약 복호화 기능 없음. 저장한 파일을 Wireshark로 분석함 캡처에 특수 권한 필요. GUI가 없는 서버·기기에서 실행 가능 기기나 게이트웨이에 직접 설치해 캡처함
프록시 Fiddler, Charles 프록시를 거치는 HTTP(S), WebSocket 등 프록시 루트 인증서를 클라이언트가 신뢰하면 평문으로 표시함 설치와 프록시 설정 필요 기기의 프록시를 PC로 지정함. Charles 문서 기준 Android 앱은 사용자 인증서를 신뢰하도록 앱 설정이 필요해 직접 관리하는 앱에서만 사용 가능함
브라우저 도구 브라우저 개발자 도구 그 브라우저의 HTTP 요청과 페이지 상태 브라우저 안에서 복호화된 내용을 그대로 표시함 설치 불필요 원격 디버깅으로 모바일 브라우저와 검사 가능한 WebView만 확인함

선택 기준

  • 웹 화면 결함은 브라우저 도구로 먼저 확인함. 요청·응답과 콘솔 오류를 한 화면에서 볼 수 있음
  • 앱의 HTTP(S) 요청을 확인하거나 가로채 수정하려면 프록시 도구가 맞음. 요청 변조와 재전송은 Wireshark에 없는 기능임
  • HTTP가 아닌 프로토콜, 연결 수립 실패, 재전송, 패킷 유실, 프록시 설정을 바꿀 수 없는 기기 통신은 패킷 캡처가 맞음
  • GUI가 없는 서버나 기기에서는 tcpdump나 dumpcap으로 캡처해 파일을 PC로 옮겨 Wireshark로 분석함

주의할 점

섹션 제목: “주의할 점”
  • 캡처 파일에는 쿠키, 토큰, 계정, 개인정보와 내부 IP·호스트 이름이 들어감. 키 로그가 포함된 pcapng는 암호화된 내용까지 복호화됨. 공유 전에 필요한 패킷만 Export Specified Packets로 잘라내고, 남는 민감 값은 마스킹하거나 공유 범위를 제한함
  • 캡처 대상과 범위는 회사가 승인한 범위로 제한함. 공식 FAQ에는 캡처 허가에 관한 항목이 없으므로, 회사 네트워크와 고객 장비의 캡처는 보안 담당 부서의 정책을 확인한 뒤 진행함. 같은 네트워크의 다른 사용자 트래픽이 섞이지 않도록 캡처 필터로 대상 기기를 지정하고, 공식 문서가 개인정보 보호 용도로 언급한 스냅샷 길이 제한을 함께 사용함
  • 키 로그 파일이 있으면 그 기간의 TLS 트래픽 전체를 복호화할 수 있음. 공식 위키는 SSLKEYLOGFILE을 Windows 전역 환경 변수로 지정하지 말라고 권하고(잊기 쉬움), 공유 전에 관련 없는 키를 걸러내도록 안내함. 테스트용 터미널이나 프로필에서만 지정하고 시험이 끝나면 파일을 삭제함
  • 서버 RSA 개인 키는 다른 TLS 세션 복호화와 서버 위장에 사용될 수 있어 키 로그보다 민감함. QA 환경에서도 운영 서버의 개인 키를 받지 않음
  • Wireshark를 관리자·root 권한으로 실행하지 않음. 공식 위키는 관리자도 제한된 사용자 계정으로 실행하도록 권하고, Linux에서는 dumpcap에만 캡처 권한(cap_net_raw, cap_net_admin)을 주는 방식을 안내함
  • 캡처하는 PC의 네트워크 카드가 체크섬 오프로딩을 하면 보내는 패킷의 TCP 체크섬이 틀린 것으로 표시됨. 체크섬 오류만으로 결함으로 판단하지 않음
  • tcp.analysis.lost_segment, 재전송 플래그는 캡처 위치와 캡처 누락의 영향을 받음. 캡처가 패킷을 놓친 것인지 실제 유실인지 양 끝점의 캡처로 대조함
  • 캡처 필터로 거른 패킷은 다시 볼 수 없음. 원인을 모를 때는 필터를 넓게 잡고 표시 필터로 좁힘

관련 문서

도메인별임베디드·디바이스 테스트 관점펌웨어나 단말 에이전트가 업데이트 중단, 전원·통신 단절, 하드웨어·OS 조합 차이, 장기 가동 같은 조건에서도 복구되고 데이터를 잃지 않는지 확인하는 테스트 관점이다.도메인별보안 테스트의 기본 관점접근 제어, 인증과 세션, 입력 처리, 비밀값 노출, 보안 설정에서 권한 없는 동작과 정보 노출이 발생하지 않는지 확인하는 테스트다. OWASP Top 10, ASVS, WSTG를 점검 기준으로 사용한다.기초와 용어API 테스트 기본화면을 거치지 않고 API에 직접 요청을 보내 응답 계약, 상태 코드, 서버 측 검증, 인가를 확인하는 테스트다. 화면 제약만으로는 확인할 수 없는 서버 동작이 대상이다.프로세스이슈 양식버그 이슈의 대표 양식(ISTQB 결함 보고서 항목, Bugzilla 요약·설명, GitHub 이슈 폼)과 선택 기준. 운영 예로 발견 블록과 종결 블록을 나눈 버그 양식과 작업(개선) 양식을 둔다.
