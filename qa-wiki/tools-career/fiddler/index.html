Fiddler

Progress Telerik의 웹 디버깅 프록시 Fiddler 제품군(Fiddler Everywhere, Fiddler Classic 등)의 현재 상태와 차이, 프록시 구조와 HTTPS 복호화, 세션 목록과 Inspectors, 규칙(Rules)과 AutoResponder, Composer, 지연 설정, 모바일 기기 캡처, 세션 저장과 공유, QA에서 사용하는 방법.

기본기난이도 중급최종 업데이트 2026-11-24

피들러

Fiddler는 Progress Telerik가 개발하는 웹 디버깅 프록시 제품군이다. 클라이언트와 서버 사이에서 HTTP(S) 트래픽을 중계하면서 요청과 응답을 기록하고, 확인하고, 수정한다. QA에서는 클라이언트가 실제로 보낸 요청과 받은 응답을 확인하고, 서버를 변경하지 않고 오류 응답이나 지연을 만들어 클라이언트의 오류 처리를 검증하는 데 사용한다.

2026-11 기준 공식 사이트에 있는 제품은 다음과 같다.

제품 지원 OS 상태와 라이선스
Fiddler Everywhere Windows, macOS, Linux 현재 권장 제품. 상업적 사용 라이선스(Lite, Pro, Enterprise)와 무료 체험
Fiddler Classic Windows 2026-08-03부터 비상업적 사용 전용 라이선스. 활발한 개발이 중단되어 릴리즈, 패치, 기술 지원을 약속하지 않음. 상업적 사용의 Fiddler Everywhere 전환 기한은 2026-09-17이었음
Fiddler Everywhere Reporter Windows, macOS 무료 트래픽 캡처 도구
FiddlerCore .NET 라이브러리 다른 애플리케이션에 프록시 기능을 넣는 임베드용 라이브러리

이 문서는 Fiddler Everywhere를 기준으로 설명하고, Fiddler Classic과 다른 부분은 따로 표시한다.

핵심 개념

섹션 제목: “핵심 개념”
  • 포워드 프록시: Fiddler는 클라이언트와 서버 사이의 중간자(MITM, man-in-the-middle) 포워드 프록시로 동작함. 기본 설정에서는 암호화되지 않은 HTTP만 캡처함
  • HTTPS 복호화: Fiddler가 서버별 인증서를 만들어 클라이언트에게는 서버처럼, 서버에게는 클라이언트처럼 동작함. 클라이언트가 이 인증서를 받아들이려면 Fiddler의 루트 CA(인증 기관)를 OS 신뢰 저장소에 등록해야 함. CA는 머신마다 고유하게 생성됨
  • 포트: Fiddler Everywhere의 기본 수신 포트는 8866이고 Settings > Connections에서 변경함
  • 프록시 체이닝: 호스트에 이미 설정된 시스템 프록시(회사 프록시 등)가 있으면 기본으로 그 프록시에 연결함
  • 세션: 요청 하나와 그 응답을 묶은 단위. 캡처한 세션은 Live Traffic 목록에 쌓임

캡처 방식

방식 동작
시스템 프록시 OS 프록시 설정을 Fiddler로 바꿔, 시스템 프록시를 따르는 애플리케이션의 트래픽을 캡처함
독립 브라우저 OS 프록시를 바꾸지 않고, Fiddler가 띄운 브라우저 인스턴스의 HTTPS 트래픽만 캡처함
터미널 Fiddler가 연 터미널 세션의 트래픽만 캡처함
원격 기기 모바일 기기나 다른 컴퓨터가 Wi-Fi 프록시로 Fiddler 호스트에 연결함

지원 프로토콜은 HTTP/1.1, HTTP/2, WebSocket, SSE(Server-Sent Events), gRPC, Socket.IO이고 TLS 1.2와 1.3을 처리한다.

주요 기능

섹션 제목: “주요 기능”

HTTPS 복호화와 루트 인증서

섹션 제목: “HTTPS 복호화와 루트 인증서”
  • Windows, macOS: Settings > HTTPS에서 사용자 저장소에 CA를 신뢰시킨 뒤 HTTPS 캡처를 켬. Windows에서 모든 사용자에게 적용하려면 관리자 권한으로 머신 저장소에 등록함
  • Linux: CA를 DER 형식으로 내보내 시스템 CA 디렉터리에 복사하고 CA 갱신 도구를 실행함
  • OS 인증서 관리자에는 Fiddler Root Certificate Authority라는 이름으로 표시됨
  • Certificate 메뉴에서 CA 신뢰, 초기화(기존 CA 삭제 후 새로 생성), 삭제를 수행함. 초기화와 삭제는 관리자 권한이 필요하고, 삭제하면 HTTPS 캡처가 중지됨
  • Firefox(Linux), Electron 앱, Python, AWS 도구처럼 자체 인증서 저장소를 사용하는 클라이언트는 CA를 내보내 그 저장소에 따로 추가함

Live Traffic과 Inspectors

섹션 제목: “Live Traffic과 Inspectors”

세션을 선택하면 요청과 응답을 Inspector로 나누어 보여 준다.

Inspector 내용
Headers 요청·응답 헤더. HTTP/2 의사 헤더(pseudo-header)는 원래 순서대로 표시함
Params 요청의 쿼리·경로 파라미터
Cookies 요청의 Cookie, 응답의 Set-Cookie, P3P 헤더
Raw 요청·응답 전체를 텍스트로 표시. 인코딩된 본문은 디코딩 버튼으로 풀어 봄
본문 Text, JSON(트리), HEX, XML, Form-Data, JavaScript, MessagePack, Protobuf(.proto 파일 추가), Socket.IO
Auth Authorization 헤더와 SAML 데이터를 디코딩함. Basic 인증과 JWT Bearer 토큰을 인식함
Trailers gRPC 서버 트레일러 헤더

규칙(Rules)

섹션 제목: “규칙(Rules)”

Fiddler Classic의 AutoResponder에 해당하는 기능이 Fiddler Everywhere의 Rules다. 규칙은 조건(Condition)과 동작(Action)으로 구성된다.

  • 조건: URL, Host, Path, Method, Status Code, 요청·응답 헤더, 요청·응답 본문, 쿠키, Process, Client IP, TLS Version 등
  • 최종 동작(final): Return File, Return Manual Response, Return Predefined Response, Do Not Decrypt, Close Gracefully, Close Non Gracefully 등. 적용되면 이후 규칙의 동작을 실행하지 않음
  • 비최종 동작(non-final): Update Status Code, Update Response Body, Update Request Header, Update Response Header, Update Request Cookies, Delay Request, Set Request Breakpoint, Set Response Breakpoint, Mark Session 등. 일치하는 여러 규칙의 동작이 모두 적용됨. 비최종 동작도 이후 규칙 처리를 멈추는 옵션을 켜면 최종 동작이 됨

QA에서 자주 구성하는 규칙의 예는 다음과 같다.

확인할 상황 조건 동작
주문 API 서버 오류 URL에 /api/orders 포함 Return Manual Response로 503 응답 반환
빈 목록 URL에 /api/products 포함, Method가 GET Return File로 {"items": []} 파일 반환
응답 지연 Host가 테스트 서버 Delay Request 5000(밀리초)
연결 끊김 URL에 /api/payment 포함 Close Non Gracefully

Return Manual Response에는 상태 줄, 헤더, 빈 줄, 본문 순서로 원시 HTTP 응답을 직접 입력한다.

Set Request Breakpoint, Set Response Breakpoint 동작을 사용하면 일치하는 요청이나 응답이 전달되기 전에 멈추고, 내용을 직접 수정한 뒤 진행시킨다.

Fiddler Classic의 AutoResponder는 매치 문자열과 동작 문자열로 규칙을 정의한다. 매치는 기본이 대소문자를 구분하지 않는 부분 일치이고, EXACT:, regex:, NOT:, METHOD: 접두어를 지원한다.

용도 매치 동작
주문 조회 응답 대체 regex:.+/api/orders/\d+$ C:\mock\order_empty.json(로컬 파일 반환)
로그인 응답 지연 METHOD:POST EXACT:https://test.example.com/api/login *delay:3000

동작에는 로컬 파일 경로, 다른 URL, *redir:, *delay:<밀리초>, *bpu(서버로 보내기 전 중단), *drop(응답 없이 연결 종료), *reset(TCP RST로 연결 재설정)이 있다. Fiddler Everywhere의 가져오기 마법사(5.20.0부터)는 현재 로드된 AutoResponder 규칙을 Rules로 옮긴다.

Composer

섹션 제목: “Composer”

REST, SOAP API 엔드포인트로 보낼 요청을 직접 작성하고 응답을 확인한다. 캡처한 세션을 오른쪽 클릭해 Edit in Composer를 선택하면 그 요청이 Composer에 열려, 헤더나 본문 일부만 바꿔 다시 보낼 수 있다.

  • HTTP 메서드, URL, HTTP 버전, 헤더, 파라미터, 본문을 지정함. 체크한 헤더만 전송됨
  • Host, User-Agent 같은 기본 헤더는 자동 생성됨. Host를 지우면 서버가 오류를 반환함
  • 저장한 요청은 Requests 목록에 컬렉션으로 쌓이고, 컬렉션을 다른 사용자와 공유함

지연과 대역폭

섹션 제목: “지연과 대역폭”

Fiddler Everywhere 규칙의 동작 목록에는 요청을 지정한 밀리초만큼 늦추는 Delay Request가 있고, 대역폭 제한 동작은 없다. Fiddler Classic은 FiddlerScript의 세션 플래그로 KB당 지연을 걸어 느린 회선을 흉내 낸다.

대역폭과 지연을 함께 조절해야 하면 Charles의 Throttling이나 브라우저 개발자 도구의 네트워크 쓰로틀링 프리셋을 검토한다.

모바일 기기 캡처

섹션 제목: “모바일 기기 캡처”

공통 절차

  1. Fiddler Everywhere의 Settings > Connections에서 원격 연결을 허용함
  2. 기기와 Fiddler 호스트를 같은 네트워크에 연결하고, 기기의 Wi-Fi 프록시를 수동으로 설정해 호스트 IP와 포트(기본 8866)를 입력함
  3. 기기 브라우저에서 http://<호스트 IP>:8866에 접속해 Fiddler CA 파일을 내려받음

Android

  • 내려받은 CA를 기기 저장소에서 Security > Encryption and Credentials 메뉴로 설치하고, Trusted Credentials의 User 탭에 표시되는지 확인함(메뉴 이름은 제조사와 버전에 따라 다름)
  • 에뮬레이터는 프록시 주소로 호스트의 루프백 주소(보통 10.0.2.2)를 사용함
  • API 24(Android 7.0) 이상을 대상으로 하는 앱은 사용자가 설치한 CA를 기본으로 신뢰하지 않음. 앱의 네트워크 보안 설정(network_security_config.xml)에 사용자 CA 신뢰를 추가해 다시 빌드해야 하므로, 소스를 관리하는 앱에만 적용됨. 설정 예는 Charles 문서에 있음

iOS

  • 내려받은 CA를 프로필로 설치한 뒤, iOS 10.3 이상에서는 설정의 Certificate Trust Settings에서 Fiddler Root Certificate Authority의 전체 신뢰를 켬
  • 인증서 고정을 사용하는 일부 Apple 서비스는 프록시가 켜진 동안 연결에 실패함. macOS에서는 Fiddler가 Apple 도메인을 우회 목록에 자동으로 추가하고, 다른 OS에서는 직접 추가함

테스트가 끝나면 기기의 Wi-Fi 프록시 설정을 해제한다. 해제하지 않으면 Fiddler를 종료한 뒤 기기의 네트워크 연결이 실패한다.

세션 저장과 공유

섹션 제목: “세션 저장과 공유”
  • 스냅샷: Live Traffic에서 선택한 세션을 스냅샷으로 저장함. 로컬 저장은 애플리케이션 로컬 저장소에, 클라우드 저장은 Fiddler 클라우드에 보관됨
  • 암호: 스냅샷에 암호를 지정해 암호화하면 암호를 아는 사용자만 세션을 열 수 있음
  • AutoSave: 캡처한 트래픽을 주기적으로 SAZ 파일로 내보냄
  • 내보내기 형식: SAZ(Fiddler Archive), HAR(HTTP Archive), WCAT, MeddlerScript, cURL 스크립트 등. 내보낼 때 AES-256 암호를 지정할 수 있음
  • 가져오기 형식: .saz, .har, .tstest, .cap(패킷 캡처), .xml(IE F12 NetXML) 파일을 가져올 수 있음
  • 마스킹: 내보내기의 Enable Sanitization 옵션은 Settings > Sanitization에 정의한 규칙에 따라 민감한 데이터를 마스킹하거나 제거함
  • 공유: 저장한 스냅샷을 협업자 이메일로 공유함. 공유한 세션은 항상 Fiddler 클라우드에 저장됨

SAZ 파일은 다른 Fiddler 사용자가 열어 같은 Inspector로 확인한다. Fiddler를 사용하지 않는 사람과 공유할 때는 Chrome 개발자 도구도 내보내는 형식인 HAR을 사용한다.

QA에서 사용하는 방법

섹션 제목: “QA에서 사용하는 방법”
  • 오류 처리 확인: 규칙으로 5xx 응답, 빈 목록, 잘못된 형식의 본문, 응답 지연, 연결 끊김을 만들어 화면의 오류 메시지, 재시도, 로딩 표시, 타임아웃 처리를 확인함. 서버 수정이나 테스트 데이터 준비 없이 재현할 수 있어 탐색적 테스트의 경계 상황 확인에 맞음
  • 모바일 앱 API 확인: 앱이 호출하는 엔드포인트, 파라미터, 인증 헤더, 호출 순서와 중복 호출 여부를 확인함. 화면에는 보이지 않는 요청 결함(필드 누락, 불필요한 반복 호출)을 찾을 수 있음
  • 캐시·쿠키 문제 재현: Cookies Inspector로 Set-Cookie 속성(만료, Secure, SameSite)을 확인하고, Update Response Header나 Update Request Cookies로 캐시 헤더와 쿠키를 바꿔 만료·누락 상황을 재현함
  • 결함 증거 첨부: 재현한 세션을 SAZ나 HAR로 내보내 결함 보고서에 첨부하고, 본문에는 요청 URL, 상태 코드, 핵심 응답 필드를 적음(이슈 양식). 첨부 전에 토큰과 개인정보를 마스킹함
  • API 테스트 연결: 캡처한 요청을 Composer에서 수정해 경계값과 잘못된 입력을 보내 보고, 반복할 확인은 Postman 같은 API 테스트 도구의 테스트로 옮김(API 테스트 기본)
  • 비개발 직군의 캡처 수집: 현장에서 재현한 사용자에게 무료 Fiddler Everywhere Reporter로 캡처를 받아 원인 분석에 사용함

선택 기준

  • 웹 화면 하나의 요청만 보면 되면 브라우저 개발자 도구로 충분함. 모바일 앱, 데스크톱 앱, 여러 클라이언트의 트래픽을 한곳에서 보거나 응답을 규칙으로 바꿔야 하면 프록시 도구가 필요함
  • 회사에서 사용하면 라이선스를 먼저 확인함. Fiddler Classic은 상업적 사용이 허용되지 않으므로 업무용은 Fiddler Everywhere나 다른 도구를 검토함
  • 응답 변조를 코드로 반복해야 하면 스크립트 언어(mitmproxy의 Python, Proxyman의 JavaScript, Fiddler Everywhere의 C#)를 기준으로 고름
  • HTTP가 아닌 프로토콜이나 TCP 재전송·TLS 핸드셰이크 같은 하위 계층 문제는 Wireshark가 맞음. 응답을 수정하는 기능은 없음
  • 팀이 같은 캡처 파일을 주고받는다면 HAR처럼 여러 도구가 읽는 형식으로 내보낼 수 있는지 확인함

주의할 점

섹션 제목: “주의할 점”
  • 루트 CA를 신뢰시킨 기기는 그 CA가 서명한 모든 인증서를 신뢰함. CA가 유출되면 그 기기의 HTTPS 통신을 다른 사람이 가로챌 수 있음. 공식 문서도 HTTPS 캡처가 더 필요 없으면 CA를 제거하라고 안내하고, 유출이 의심되면 Certificate 메뉴의 초기화로 새 CA를 생성함. 테스트 기기에서도 작업이 끝나면 CA와 Wi-Fi 프록시 설정을 제거함
  • 인증서 고정(certificate pinning)을 사용하는 앱은 Fiddler의 인증서를 받아들이지 않아 HTTPS를 복호화할 수 없음. Android 공식 문서는 앱이 신뢰할 공개 키를 pin-set으로 지정하는 방법을 설명하고, Fiddler 문서도 일부 Apple 서비스가 Fiddler 같은 서드파티 CA를 신뢰하지 않는다고 적음. 운영 빌드 앱의 트래픽이 필요하면 개발팀에 디버그 빌드(사용자 CA 신뢰를 허용한 네트워크 보안 설정)를 요청함
  • 세션 파일과 스냅샷에는 Authorization 헤더, 쿠키, 세션 토큰, 요청 본문의 개인정보가 그대로 들어 있음. Auth Inspector는 JWT를 디코딩해 보여 줌. 결함 보고서나 메신저에 첨부하기 전에 Sanitization으로 마스킹하거나 암호를 지정하고, 클라우드 공유가 회사 보안 정책에 맞는지 확인함
  • 규칙은 조건에 맞는 모든 트래픽에 적용됨. 운영 환경 도메인을 대상으로 응답을 변조하지 않고, 테스트가 끝나면 규칙을 비활성화함. 켜 둔 규칙이 다음 테스트 결과를 바꿀 수 있음
  • 회사 프록시 환경에서는 Fiddler가 기존 시스템 프록시에 연결되므로, 캡처가 되지 않으면 프록시 체인과 우회 목록을 먼저 확인함
  • 특정 호스트에서 인증서 오류가 반복되면 Do Not Decrypt 동작이나 Settings > Connections의 우회 목록으로 그 호스트를 복호화 대상에서 제외함. Do Not Decrypt는 새로 맺는 연결에만 적용됨

관련 문서

기초와 용어API 테스트 기본화면을 거치지 않고 API에 직접 요청을 보내 응답 계약, 상태 코드, 서버 측 검증, 인가를 확인하는 테스트다. 화면 제약만으로는 확인할 수 없는 서버 동작이 대상이다.프로세스이슈 양식버그 이슈의 대표 양식(ISTQB 결함 보고서 항목, Bugzilla 요약·설명, GitHub 이슈 폼)과 선택 기준. 운영 예로 발견 블록과 종결 블록을 나눈 버그 양식과 작업(개선) 양식을 둔다.테스트 설계탐색적 테스트와 세션 기반 테스트 관리테스트 대상을 학습하면서 테스트 설계, 실행, 결과 평가를 동시에 진행하는 경험 기반 기법이다(Exploratory Testing). ISTQB, Kaner, Bach·Bolton의 정의 차이, 테스트 아이디어(HTSM)와 판정 기준(FEW HICCUPPS) 휴리스틱, 세션 기반 테스트 관리의 차터, 세션 기록, TBS 지표를 다룬다.도메인별보안 테스트의 기본 관점접근 제어, 인증과 세션, 입력 처리, 비밀값 노출, 보안 설정에서 권한 없는 동작과 정보 노출이 발생하지 않는지 확인하는 테스트다. OWASP Top 10, ASVS, WSTG를 점검 기준으로 사용한다.
