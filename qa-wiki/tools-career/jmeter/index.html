Apache JMeter

프로토콜 수준에서 부하를 생성하는 오픈소스 성능 테스트 도구 Apache JMeter의 테스트 플랜 구성 요소, 요소 실행 순서와 범위 규칙, 추출기를 사용한 상관(correlation), CSV Data Set Config, CLI 모드 실행과 HTML 대시보드 리포트, 분산 테스트, QA에서 성능 합격 기준을 판정하는 방법.

기본기난이도 중급최종 업데이트 2026-11-24

Apache JMeter는 Apache Software Foundation이 관리하는 오픈소스 부하 테스트 도구다. 라이선스는 Apache License 2.0이고, 공식 사이트는 “기능 동작을 부하 테스트하고 성능을 측정하도록 설계된 100% 순수 Java 애플리케이션”으로 소개한다. JMeter는 브라우저가 아니라 프로토콜 수준에서 동작하므로 HTML 페이지 안의 JavaScript를 실행하지 않는다. 2026-11 기준 다운로드 페이지의 최신 릴리즈는 5.6.3이고, 5.6.x는 Java 8 이상에서 실행된다(Java 17 이상 권장, 다음 메이저 릴리즈는 Java 17 이상 필요 예정). 테스트 플랜은 GUI에서 작성해 .jmx 파일로 저장하고, 부하 테스트는 CLI 모드로 실행한다. HTTP뿐 아니라 JDBC, JMS, LDAP, FTP, TCP 같은 프로토콜용 샘플러를 기본으로 제공한다.

핵심 개념

섹션 제목: “핵심 개념”
요소 역할
테스트 플랜(Test Plan) 테스트 전체 설정을 담는 최상위 요소. 서버 이름처럼 반복되는 값을 변수로 정의함
스레드 그룹(Thread Group) 테스트의 시작점. 모든 샘플러와 컨트롤러는 스레드 그룹 아래에 있어야 함. 스레드 하나가 가상 사용자 하나에 해당함
샘플러(Sampler) 서버에 요청을 보내고 응답을 기다리는 요소. HTTP Request, JDBC Request, JMS Publisher 등
로직 컨트롤러(Logic Controller) 하위 요청을 언제, 몇 번 보낼지 정함. Loop, If, While, Once Only, Transaction, Module Controller 등
테스트 프래그먼트(Test Fragment) Module Controller나 Include Controller가 참조할 때만 실행되는 재사용 블록
설정 요소(Configuration Element) 요청에 기본값이나 상태를 추가함. 직접 요청을 보내지 않음. HTTP Request Defaults, HTTP Cookie Manager, CSV Data Set Config 등
전처리기(Pre-Processor) 샘플러 요청 전에 실행하는 동작
타이머(Timer) 범위 안의 각 샘플러 실행 전에 지연을 추가함
후처리기(Post-Processor) 샘플러 요청 후에 실행하는 동작. 주로 응답에서 값을 추출함
단언(Assertion) 응답이 기대한 내용인지 확인함. 실패하면 해당 샘플을 실패로 기록함
리스너(Listener) 실행 중 수집한 결과를 표시하거나 저장함

스레드 그룹 설정

섹션 제목: “스레드 그룹 설정”
  • 스레드 수: 동시에 실행할 가상 사용자 수. 각 스레드는 테스트 플랜을 독립적으로 실행함
  • Ramp-up 기간: 모든 스레드를 시작하는 데 걸리는 시간. 공식 문서는 Ramp-up을 스레드 수와 같게 시작해 조정하라고 권함
  • 반복 횟수(Loop Count): 스레드 그룹의 요소를 반복할 횟수. 기본값은 1회
  • 스케줄러: 지속 시간과 시작 지연을 지정함. 반복 횟수와 지속 시간 중 먼저 도달한 조건에서 종료함. 종료 조건은 샘플 사이에서만 확인하므로 응답을 기다리는 샘플러가 있으면 종료가 늦어질 수 있음
  • setUp, tearDown Thread Group: 일반 스레드 그룹 전과 후에 실행하는 스레드 그룹. 테스트 데이터 준비와 정리에 사용함. tearDown은 정상 종료(shutdown) 시 기본으로 실행되지 않으며 테스트 플랜의 “Run tearDown Thread Groups after shutdown of main threads” 옵션을 켜야 실행됨. 중지(Stop)하면 옵션과 관계없이 실행되지 않음

스레드 그룹은 스레드 수를 기준으로 부하를 만든다. 도착률 기준 부하를 만들려면 Open Model Thread Group을 사용하며, rate(1/sec) random_arrivals(2 min) rate(3/sec)처럼 부하 일정을 지정한다. 공식 문서는 이 스레드 그룹을 실험 기능으로 표시하고 이후 릴리즈에서 바뀔 수 있다고 안내한다.

요소 실행 순서와 범위 규칙

섹션 제목: “요소 실행 순서와 범위 규칙”

공식 사용자 매뉴얼(Test Plan 장)이 정한 한 샘플러 기준의 실행 순서는 다음과 같다.

  1. 설정 요소
  2. 전처리기
  3. 타이머
  4. 샘플러
  5. 후처리기(SampleResult가 null이면 실행하지 않음)
  6. 단언(SampleResult가 null이면 실행하지 않음)
  7. 리스너(SampleResult가 null이면 실행하지 않음)

트리에서의 위치가 적용 범위를 정한다. 부모가 샘플러이면 그 샘플러에만 적용되고, 부모가 컨트롤러이면 그 컨트롤러 아래의 모든 샘플러에 적용된다.

  • 같은 종류의 설정 요소가 여러 단계에 있으면 하위 분기에 있는 요소가 우선함
  • Defaults 계열 설정 요소는 병합됨. Test Plan 장은 Cookie Manager, Authorization Manager가 병합되지 않고 범위 안의 하나만 사용되며 어느 것을 사용할지 지정할 수 없다고 설명함
  • Header Manager는 Test Plan 장에 위 두 Manager와 함께 병합되지 않는 요소로 적혀 있지만, Component Reference는 여러 Header Manager의 항목을 병합하고 같은 이름의 헤더는 나중 항목으로 대체한다고 설명함. 기본 헤더를 상위에 두고 특정 샘플러에서 일부만 바꾸는 구성이 가능함
  • 타이머를 여러 개 두면 지연 시간이 합산됨. 특정 샘플러에만 지연을 주려면 그 샘플러의 하위에 둠
  • 단언은 기본적으로 메인 샘플에만 적용되고 하위 샘플(내장 리소스 등)에는 적용되지 않음. 단언이 모두 실행된 뒤 JMeterThread.last_sample_ok 변수에 성공 여부가 기록됨

섹션 제목: “주요 기능”

상관과 추출기

섹션 제목: “상관과 추출기”

녹화하거나 처음 작성한 스크립트에는 세션 ID, CSRF 토큰, 주문 번호처럼 서버가 매번 새로 발급하는 값이 고정값으로 들어가 있다. 이 값을 이전 응답에서 추출해 다음 요청에 변수로 넣는 작업을 상관(correlation)이라고 부른다. JMeter에서는 후처리기로 값을 추출해 변수에 저장하고, 다음 요청에서 ${변수명}으로 사용한다.

후처리기 추출 방식
JSON Extractor JSON-PATH 식으로 JSON 응답에서 추출함
JSON JMESPath Extractor JMESPath 식으로 JSON 응답에서 추출함
Regular Expression Extractor Perl 방식 정규식으로 추출함
Boundary Extractor 왼쪽 경계와 오른쪽 경계 사이의 값을 추출함
CSS Selector Extractor, XPath2 Extractor HTML, XML 문서에서 선택자나 XPath로 추출함

쿠키로 유지하는 세션은 HTTP Cookie Manager가 브라우저처럼 저장하고 다시 전송하므로 따로 추출하지 않는다. 각 스레드는 자기 쿠키 저장소를 가지므로 스레드마다 별도 세션이 생긴다. URL에 세션 ID를 붙이는 애플리케이션은 HTTP URL Re-writing Modifier를 스레드 그룹에 추가한다. HTTP 요청은 HTTP(S) Test Script Recorder로 녹화할 수 있고, 녹화한 뒤 동적 값을 찾아 상관을 적용한다.

CSV Data Set Config

섹션 제목: “CSV Data Set Config”
  • 파일의 줄을 읽어 구분자로 나눈 뒤 변수에 넣음. 줄은 각 반복이 시작될 때 읽음
  • 기본값(공유 모드 All threads)은 파일을 한 번 열고 스레드마다 다른 줄을 사용함. 어느 스레드가 어느 줄을 받는지는 실행 순서에 따라 반복마다 달라질 수 있음
  • 공유 모드: All threads, Current thread group, Current thread, 식별자 지정 중에서 선택함. 스레드마다 별도 파일이 필요하면 test${__threadNum}.csv와 Current thread 모드를 사용함
  • Variable Names를 비우면 첫 줄을 열 이름으로 읽음
  • 파일 끝(EOF)에 도달하면 Recycle on EOF(기본 true)는 처음부터 다시 읽고, Recycle이 false이고 Stop thread on EOF가 true이면 스레드를 멈춤. 둘 다 false이면 변수에 <EOF>가 들어감
  • 공식 문서는 실행 중에 고유값이나 무작위값을 만들면 CPU와 메모리를 사용하므로, 테스트 데이터를 미리 파일로 만들어 두라고 권함

CLI 모드 실행

섹션 제목: “CLI 모드 실행”

공식 Getting Started 문서는 “GUI 모드는 테스트 스크립트 작성에만 사용하고, 부하 테스트에는 CLI 모드(NON GUI)를 사용해야 한다”고 정한다.

  • -n: CLI 모드, -t: 테스트 플랜 파일, -l: 결과 파일(.jtl), -e -o: 종료 후 HTML 대시보드를 지정한 폴더에 생성함
  • -J로 지정한 속성은 테스트 플랜에서 ${__P(threads,10)}처럼 읽음. 두 번째 인자는 속성이 없을 때의 기본값임
  • 모범 사례(Best Practices) 문서는 최신 버전 사용, 리스너 최소화, 결과는 XML이 아니라 CSV로 저장, 필요한 데이터만 저장을 권함
  • 스크립트가 필요한 요소는 JMeter 3.1부터 BeanShell 대신 JSR223 요소와 Groovy를 권장함. Groovy는 컴파일 결과를 캐시할 수 있음

HTML 대시보드 리포트

섹션 제목: “HTML 대시보드 리포트”

실행 후에 결과 파일로 만들려면 jmeter -g result.jtl -o report/를 실행한다. 출력 폴더는 비어 있거나 없어야 한다. 리포트에는 다음이 포함된다.

  • APDEX 표: 만족(기본 500ms)과 허용(기본 1500ms) 기준으로 트랜잭션별 점수를 계산함
  • 통계 표: 트랜잭션별 지표 요약. 설정 가능한 백분위 3개(기본 90, 95, 99)를 포함함
  • 오류 표와 샘플러별 상위 5개 오류
  • 시간별 응답 시간, 활성 스레드, 초당 요청 수, 처리량, 응답 시간 분포 그래프

공식 용어집 기준으로 경과 시간(Elapsed time)은 요청 직전부터 마지막 응답 수신 직후까지이고 렌더링과 클라이언트 JavaScript 실행은 포함하지 않는다. 지연 시간(Latency)은 첫 응답 수신까지, 연결 시간(Connect Time)은 SSL 핸드셰이크를 포함한 연결 수립 시간이다. 90% Line(90백분위)은 표본의 90%가 그 값 이하인 값이다. Transaction Controller를 사용하면 “Generate parent sample”을 해제한 상태(기본값)로 두어야 리포트가 정확하다.

분산 테스트

섹션 제목: “분산 테스트”
  • 컨트롤러(클라이언트) 하나가 여러 원격 JMeter 서버(jmeter-server)를 제어하고 결과를 모음
  • 모든 노드는 정확히 같은 JMeter 버전을 사용해야 하고, Java 버전도 같게 맞추는 것을 권장함
  • 원격 서버마다 테스트 플랜 전체를 실행함. 스레드 1000개 플랜을 서버 6대에서 실행하면 스레드는 6000개가 됨
  • CSV 같은 데이터 파일은 클라이언트가 전송하지 않으므로 각 서버의 올바른 상대 경로에 복사해 둠
  • JMeter 4.0부터 RMI 통신은 기본으로 SSL을 사용함. create-rmi-keystore 스크립트로 키스토어를 만들어 모든 노드에 복사함
  • 실행은 jmeter -n -t plan.jmx -r(remote_hosts 속성의 서버) 또는 -R server1,server2로 하고, -G는 모든 서버에 속성을 지정하고 -X는 테스트 후 서버를 종료함

QA에서 사용하는 방법

섹션 제목: “QA에서 사용하는 방법”
  • 성능 테스트 유형(스모크, 평균 부하, 스트레스, 스파이크, 내구, 한계점)의 정의는 Grafana k6 문서의 표를 참고하고, JMeter에서는 스레드 그룹의 스레드 수, Ramp-up, 지속 시간 또는 Open Model Thread Group의 부하 일정으로 구성함. 비기능 테스트의 위치는 테스트 레벨과 유형, 성능 효율성 특성은 ISO/IEC 25010 품질 모델 참고
  • 합격 기준을 실행 전에 측정 가능한 값으로 정함. CTFL v4.0.1(5.1.3)의 종료 조건에 해당하며, 예를 들어 “주문 트랜잭션 p95 1초 이하, 오류율 1% 미만”처럼 트랜잭션 이름, 백분위, 오류율을 함께 적음
  • 결과는 평균만 보지 않고 통계 표의 95, 99백분위와 오류율을 함께 확인함. Duration Assertion은 샘플마다 시간 초과를 실패로 기록하므로, 백분위 기준 판정은 결과 파일이나 대시보드의 통계로 수행함
  • 단언은 부하 중 응답이 정상인지 확인하는 수준으로 둠. 상태 코드와 핵심 필드만 확인하고, 상세한 기능 검증은 API 테스트에서 수행함
  • 부하 대상 트랜잭션은 장애 영향과 트래픽이 큰 경로부터 선정함(리스크 기반 테스트)
  • CI에서는 CLI 모드로 실행하고 .jtl 결과와 HTML 리포트를 빌드 산출물로 보관함(Jenkins, GitHub Actions). .jmx와 CSV 데이터를 저장소에서 버전 관리하고 실행한 커밋과 대상 빌드를 결과와 함께 기록함(형상관리 기본)
  • 기준을 넘은 결과를 결함으로 등록할 때 트랜잭션 이름, 백분위와 오류율, 스레드 설정, 실행 명령, 리포트를 첨부함(이슈 양식, 심각도)

선택 기준

  • 코드 작성 경험이 적은 구성원이 많거나 녹화로 시작해야 하면 JMeter의 GUI와 HTTP(S) Test Script Recorder가 진입 비용이 낮음
  • 테스트 스크립트를 코드 리뷰하고 CI에서 종료코드로 판정하려면 k6, Gatling, Locust처럼 텍스트 코드로 작성하는 도구가 변경 내용을 확인하기 쉬움
  • DB, 메시지 큐, 디렉터리 서비스 같은 비HTTP 프로토콜을 추가 개발 없이 다뤄야 하면 JMeter의 샘플러나 Gatling의 프로토콜 문서를 확인함
  • 팀의 주 언어(JavaScript, JVM 언어, Python)와 기존 빌드 도구에 맞추면 테스트 코드를 같은 저장소에서 관리하기 쉬움
  • 목표 처리량을 검증해야 하면 개방형 부하 모델을 지원하는지, 그 기능이 정식 기능인지 확인함

주의할 점

섹션 제목: “주의할 점”
  • 공식 문서는 GUI 오버헤드를 줄이도록 부하 테스트를 CLI 모드로 실행하라고 정함. GUI는 스크립트 작성과 디버깅에 사용함
  • View Results Tree와 Assertion Results 리스너는 메모리와 CPU를 많이 사용하므로 공식 문서가 부하 테스트 중 사용을 금지함. 스크립트 디버깅에만 사용하고 실행 전에 비활성화함
  • 테스트 플랜의 Functional Testing 옵션을 켜면 모든 결과 파일에 응답 데이터가 저장되어 자원 사용이 늘어남. 기본값은 꺼짐
  • 공식 모범 사례 문서는 스레드 수를 잘못 정하면 coordinated omission 문제가 생긴다고 경고함. 스레드 기반 모델에서는 대상이 느려질수록 스레드가 응답을 기다리는 시간이 늘어 요청 빈도가 줄어듦(k6 문서의 폐쇄형 모델 설명과 같은 현상)
  • JMeter는 브라우저가 아니므로 클라이언트 렌더링과 JavaScript 실행 시간은 측정값에 포함되지 않음. 화면 체감 성능은 브라우저 기반 도구로 따로 측정함
  • 처리량은 샘플러 이름(label) 단위로 집계함. 같은 요청에 다른 이름을 붙이면 처리량이 나뉘어 표시되므로 이름 규칙을 먼저 정함
  • JSON Extractor의 Match No. 기본값 0은 결과가 여러 개일 때 무작위로 하나를 고름. 특정 값이 필요하면 번호를 지정하고, Default Values에 실패 표시 값을 넣어 추출 실패를 단언으로 확인함
  • CSV 변수는 반복 시작 시점에 정의되므로 JDBC Connection Configuration처럼 설정 단계에서 값을 처리하는 요소에는 사용할 수 없음
  • 분산 테스트에서는 스레드 수가 서버 수만큼 곱해지고, 데이터 파일은 서버마다 따로 배치해야 함
  • 부하 생성기의 CPU, 메모리, 네트워크가 포화되면 측정값이 대상 시스템의 성능을 반영하지 않음. 생성기 자원을 실행 중에 함께 기록함
  • 스테이징이나 운영 환경에 부하를 줄 때는 대상 시스템 담당자와 일정, 범위, 중단 기준을 사전에 합의함

관련 문서

기초와 용어테스트 레벨과 테스트 유형테스트 레벨은 시스템을 어느 통합 단계에서 검증하는지를, 테스트 유형은 어떤 품질 특성을 검증하는지를 나타내는 분류다. 두 분류는 서로 독립이며, 테스트마다 레벨을 하나 정하고 테스트 유형은 하나 이상 적용할 수 있다.테스트 설계리스크 기반 테스트실패했을 때의 피해와 실패할 가능성을 기준으로 무엇을 먼저, 얼마나 깊게 테스트할지 정하는 방식이다(Risk-Based Testing).기초와 용어API 테스트 기본화면을 거치지 않고 API에 직접 요청을 보내 응답 계약, 상태 코드, 서버 측 검증, 인가를 확인하는 테스트다. 화면 제약만으로는 확인할 수 없는 서버 동작이 대상이다.도구Grafana k6JavaScript로 부하 시나리오를 작성하는 오픈소스 성능 테스트 도구 Grafana k6의 테스트 수명주기, 가상 사용자와 반복, 시나리오와 실행기, 체크와 임계값, 메트릭, 태그와 그룹, 결과 출력, 브라우저 모듈과 QA에서 성능 합격 기준을 판정하는 방법.
