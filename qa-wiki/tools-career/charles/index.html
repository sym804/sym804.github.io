Charles

상용 웹 디버깅 프록시 Charles의 프록시 구조, SSL Proxying과 루트 인증서, Map Local, Map Remote, Rewrite, Breakpoints, Throttling, No Caching, Block Cookies, Repeat, 모바일 기기 설정(Android 네트워크 보안 설정 포함), 세션 저장과 QA에서 사용하는 방법.

기본기난이도 중급최종 업데이트 2026-11-24

Charles(Charles Web Debugging Proxy)는 컴퓨터와 인터넷 사이의 HTTP, HTTPS 트래픽을 중계하면서 요청, 응답, 헤더를 기록하고 보여 주는 웹 디버깅 프록시다. Windows, macOS, Linux용 데스크톱 앱이고, 기기 안에서 직접 트래픽을 캡처하는 iOS 앱(Charles for iOS)이 따로 있다. 상용 소프트웨어로 30일 체험 뒤 라이선스를 구매해야 하며, 라이선스는 사용자 라이선스, 사이트 라이선스, 다중 사이트 라이선스로 나뉘고 구매한 주 버전(2026-11 기준 5.x)의 업데이트에 적용된다. 공식 사이트 기준 최신 버전은 5.2.3이다.

QA에서는 클라이언트가 보낸 요청과 받은 응답을 확인하고, 응답을 로컬 파일로 바꾸거나 지연을 걸어 서버를 변경하지 않고 오류 상황을 재현하는 데 사용한다.

핵심 개념

섹션 제목: “핵심 개념”
  • 프록시: 브라우저나 앱이 Charles를 프록시로 지정하면 모든 요청이 Charles를 거쳐 서버로 감. Windows와 macOS에서는 Charles가 시스템 프록시 설정을 자동으로 구성함. Windows에서는 시작할 때와 종료할 때 설정을 갱신함
  • 포트: HTTP 프록시 포트는 보통 8888이고 Proxy 메뉴의 Proxy Settings에서 확인함. cURL은 curl --proxy localhost:8888처럼 직접 지정함
  • Recording: 기록을 켠 동안 지나간 요청이 세션에 쌓임. 세션은 기록한 정보 전체를 담는 단위임
  • 보기 방식: Structure 보기는 호스트 이름별 트리로, Sequence 보기는 발생 순서대로 요청을 보여 줌
  • 뷰어: 헤더, 쿼리·폼 파라미터, 쿠키, 인증 정보, JSON, XML, 압축 데이터를 해석해 보여 주고, 원본을 텍스트나 16진수로 확인함
  • Access Control: Charles를 사용할 수 있는 호스트(IP, 서브넷) 목록. localhost는 항상 허용되고, 목록에 없는 기기가 처음 연결하면 Charles가 연결을 막고 그 IP를 경고로 표시함

SSL Proxying과 루트 인증서

섹션 제목: “SSL Proxying과 루트 인증서”

HTTPS 요청 내용을 보려면 SSL Proxying을 켜야 한다. Charles는 중간자(man-in-the-middle)로 동작해, 서버별 인증서를 직접 만들고 자신의 루트 인증서로 서명해 클라이언트에 전달한다. 클라이언트는 실제 서버 인증서가 아니라 Charles가 만든 인증서를 받는다.

  • 루트 인증서는 Charles 설치마다 고유하게 생성됨
  • 클라이언트가 Charles 루트 인증서를 신뢰하지 않으면 인증서 경고가 표시됨. Help > SSL Proxying > Install Charles Root Certificate로 설치함
  • Windows: 가져오기 마법사에서 “신뢰할 수 있는 루트 인증 기관” 저장소를 직접 선택해야 함
  • macOS: 키체인 접근에서 인증서의 신뢰 설정을 “항상 신뢰”로 변경함
  • 복호화 대상 호스트를 SSL Proxying 설정에 직접 지정함. *를 입력하면 모든 호스트를 복호화하고, Structure 보기에서 호스트를 오른쪽 클릭해 켜고 끌 수도 있음
  • SSL Proxying을 끄면 Charles는 HTTPS 트래픽을 내용 확인 없이 서버로 그대로 전달함

목록에 없는 호스트의 HTTPS 트래픽은 복호화하지 않고 그대로 전달하므로, 테스트 대상 호스트만 지정하면 다른 애플리케이션의 연결에 주는 영향을 줄일 수 있다.

응답과 요청을 바꾸는 도구

섹션 제목: “응답과 요청을 바꾸는 도구”
도구 동작 QA에서 확인하는 것
Map Local 요청이 매핑과 일치하면 로컬 파일을 응답으로 반환함. 파일이 없으면 원래 서버로 보냄 빈 목록, 필드 누락, 긴 문자열 같은 응답 데이터에 대한 화면 처리
Map Remote 요청 위치를 다른 호스트·경로로 바꾸고, 클라이언트에는 원래 요청의 응답처럼 전달함. HTTP와 HTTPS 사이 매핑도 가능함 운영 화면에서 일부 API나 리소스만 개발·스테이징 서버로 보내 새 버전 확인
Rewrite 규칙에 따라 헤더, URL, 쿼리 파라미터, 본문을 추가·수정·삭제함. 요청, 응답, 양쪽 중 적용 대상을 고름 캐시 헤더 변경, 응답 필드 값 치환, 특정 파라미터 제거
Breakpoints 일치하는 요청이나 응답을 멈추고, 내용을 편집한 뒤 Execute로 진행하거나 Abort로 막아 클라이언트에 오류를 보냄 한 번만 필요한 응답 변경, 요청 중단 시 클라이언트 동작
No Caching 요청에서 If-Modified-Since, If-None-Match를 지우고 Pragma: no-cache, Cache-Control: no-cache를 추가함. 응답에서는 Expires, Last-Modified, ETag를 지우고 Expires: 0, Cache-Control: no-cache를 추가함 캐시 때문에 이전 리소스가 표시되는 문제와 캐시가 없을 때의 동작 구분
Block Cookies 요청의 Cookie, 응답의 Set-Cookie 헤더를 제거함 쿠키 없이 접속했을 때의 로그인·세션 처리

Map Local과 Map Remote의 일치 조건은 프로토콜, 호스트, 포트, 경로로 지정하고 와일드카드를 쓸 수 있다. Map Local은 일치를 판정할 때 쿼리 문자열을 보지 않는다. 같은 경로에 쿼리만 다른 요청은 모두 같은 로컬 파일과 일치한다. 로컬 파일은 그대로 반환되므로 서버 측 스크립트가 들어 있는 파일은 실행되지 않고 소스가 전달된다. 동적인 응답이 필요하면 Map Remote를 사용한다.

Rewrite는 Perl 형식 정규식을 지원하고, 찾은 그룹을 바꿀 값에서 $1, $2로 참조한다. 예를 들어 응답 본문의 재고 수량을 0으로 바꾸는 규칙은 다음과 같다.

항목 값
적용 위치 test.example.com, 경로 /api/products/*
규칙 유형 Body, Response
찾을 값 "stock":\s*\d+(정규식 사용)
바꿀 값 "stock": 0

Throttling과 Repeat

섹션 제목: “Throttling과 Repeat”

Throttling은 대역폭을 초당 바이트 단위로, 지연 시간을 밀리초 단위로 지정해 느린 회선을 흉내 낸다. 로딩 표시, 타임아웃, 중복 클릭 방지처럼 느린 네트워크에서만 드러나는 동작을 확인할 때 사용한다.

Repeat는 선택한 요청을 서버에 다시 보내고, 응답을 Charles 안에 새 요청으로 표시한다. 브라우저나 앱은 그 응답을 받지 않는다. Repeat Advanced는 반복 횟수와 동시 실행 수를 지정하는 기능이고 주로 간단한 부하 확인에 사용한다.

  • 같은 요청을 다시 보내 서버의 멱등성(같은 결제·주문 요청이 두 번 처리되는지)을 확인함
  • 동시 실행으로 중복 생성, 재고 차감 같은 경합 상황을 확인함. 테스트 환경에서만 실행함
  • 본격적인 부하 테스트는 k6나 JMeter처럼 시나리오와 지표를 관리하는 도구를 사용함

모바일 기기 설정

섹션 제목: “모바일 기기 설정”

공통 절차

  1. 컴퓨터와 기기를 같은 Wi-Fi에 연결함
  2. 기기의 Wi-Fi 설정에서 HTTP 프록시를 수동으로 지정하고, 서버에 Charles가 실행 중인 컴퓨터의 IP, 포트에 Charles 포트(보통 8888)를 입력함
  3. 기기가 처음 연결하면 Charles가 허용 여부를 묻거나 경고를 표시함. 허용하거나 Access Control 목록에 기기 IP를 추가함
  4. 기기 브라우저에서 chls.pro/ssl에 접속해 Charles 루트 인증서를 설치함

iOS

  • 인증서 프로필을 설치한 뒤, iOS 10.3 이상에서는 설정 > 일반 > 정보 > 인증서 신뢰 설정에서 Charles 인증서의 전체 신뢰를 켬
  • iOS 시뮬레이터는 Help 메뉴의 Install Charles CA SSL Certificate in iOS Simulators로 설치함

Android

  • Android 에뮬레이터는 호스트 컴퓨터를 가리키는 특수 주소 10.0.2.2:8888을 프록시로 지정함
  • Android 7.0(API 24) 이상을 대상으로 하는 앱은 기본 설정에서 시스템 CA만 신뢰함. 사용자가 설치한 CA(Charles 루트 인증서 포함)를 기본으로 신뢰하는 것은 Android 6.0(API 23) 이하를 대상으로 하는 앱뿐임
  • 따라서 Charles 인증서를 기기에 설치해도 API 24 이상을 대상으로 하는 앱의 HTTPS는 복호화되지 않음. 앱의 네트워크 보안 설정에 사용자 CA 신뢰를 추가해 빌드해야 하므로, 소스를 관리하는 앱에만 적용할 수 있음

개발팀에 요청할 설정은 디버그 빌드에만 적용되는 debug-overrides다. 이 항목은 android:debuggable이 true인 빌드에서만 적용되고 릴리즈 빌드에서는 무시된다. 서버 인증서 체인이 debug-overrides에 지정한 신뢰 앵커를 사용하면 인증서 고정(pin-set)도 적용되지 않는다.

매니페스트의 <application> 요소에 android:networkSecurityConfig="@xml/network_security_config"를 추가해 이 파일을 연결한다. 테스트가 끝나면 기기의 HTTP 프록시 설정을 해제한다. 해제하지 않으면 Charles를 끈 뒤 앱의 네트워크 요청이 실패한다.

Charles for iOS를 사용하면 Wi-Fi 프록시를 설정하지 않고 기기 안에서 HTTP, HTTPS 트래픽을 캡처하며, 셀룰러 데이터 트래픽도 캡처한다. 캡처한 요청이나 세션 전체를 데스크톱 Charles로 보낼 수 있다.

세션 저장

섹션 제목: “세션 저장”
  • 세션은 File 메뉴에서 저장하고 다시 열 수 있어 동료와 주고받는 데 사용함
  • 내보내기 형식은 CSV(요청·응답의 시간과 크기 요약, 다시 가져오기 불가), Trace(Charles 전용 텍스트 형식), XML(다른 소프트웨어와 교환용, DTD 제공)임. Trace와 XML은 다시 가져올 수 있음
  • 저장한 세션에는 헤더, 쿠키, 본문이 그대로 들어 있음

QA에서 사용하는 방법

섹션 제목: “QA에서 사용하는 방법”
  • 오류 처리 확인: Map Local로 빈 목록과 필드가 빠진 응답을, Breakpoints로 직접 편집한 응답을, Throttling으로 느린 응답을 만들어 화면의 오류 메시지, 재시도, 로딩 표시를 확인함. 서버 수정이나 테스트 데이터 준비 없이 재현할 수 있어 탐색적 테스트에서 경계 상황을 빠르게 확인함
  • 모바일 앱 API 확인: 앱이 호출하는 엔드포인트, 파라미터, 인증 헤더, 호출 순서를 Sequence 보기로 확인하고, 화면에는 보이지 않는 중복 호출과 불필요한 요청을 찾음
  • 캐시·쿠키 문제 재현: No Caching과 Block Cookies를 켜고 끄며 결과를 비교해, 증상이 캐시나 쿠키 때문인지 구분함. Rewrite로 Cache-Control 값을 바꿔 특정 캐시 정책을 재현함
  • 결함 증거 첨부: 재현한 요청과 응답을 세션으로 저장하거나 내보내 결함 보고서에 첨부하고, 본문에는 요청 URL, 상태 코드, 핵심 응답 필드를 적음(이슈 양식)
  • API 테스트 연결: 캡처한 요청을 Repeat로 다시 보내거나, 반복해서 확인할 요청은 Postman 같은 API 테스트 도구로 옮겨 단언을 붙임(API 테스트 기본)
  • 새 버전 확인: Map Remote로 일부 요청만 스테이징 서버로 보내, 배포 전 API와 현재 클라이언트의 조합을 확인함

선택 기준

  • 웹 화면 하나의 요청만 보면 되면 브라우저 개발자 도구로 충분함. 모바일 앱, 데스크톱 앱처럼 브라우저 밖의 클라이언트는 프록시 도구가 필요함
  • 응답 변경을 UI 규칙으로 처리하면 Charles, Fiddler로 충분함. 변경 로직을 코드로 관리하고 반복 실행해야 하면 mitmproxy(Python)나 Proxyman(JavaScript)을 검토함
  • 라이선스 비용과 회사 승인 절차를 확인함. 오픈소스 도구는 비용이 없지만 사내 보안 검토 대상인지 확인함
  • iOS 기기에서 Wi-Fi 프록시를 설정하기 어렵거나 셀룰러 환경의 트래픽이 필요하면 기기 안에서 캡처하는 앱(Charles for iOS, Proxyman iOS 앱)을 검토함
  • TCP 연결, TLS 핸드셰이크처럼 HTTP 아래 계층의 문제는 Wireshark가 맞음. 응답을 수정하는 기능은 없음

주의할 점

섹션 제목: “주의할 점”
  • 루트 인증서를 신뢰시킨 기기는 그 인증서로 서명된 모든 HTTPS 인증서를 신뢰함. 루트 인증서와 개인 키가 유출되면 그 기기의 HTTPS 통신을 다른 사람이 가로챌 수 있음. 개인 기기에는 설치하지 않고, 테스트가 끝나면 기기와 컴퓨터에서 인증서와 프록시 설정을 제거함
  • 인증서 고정(certificate pinning)을 사용하는 앱은 Charles 인증서를 받아들이지 않음. Charles 공식 FAQ는 앱이 루트 인증서를 직접 검증하므로 연결이 실패한다고 설명하고, Safari에서는 복호화되는데 특정 앱만 실패하면 인증서 고정이 원인일 가능성이 높다고 안내함. Android 앱은 네트워크 보안 설정의 pin-set으로 고정을 선언함. 고정을 사용하는 앱은 개발팀에 debug-overrides를 적용한 디버그 빌드를 요청함
  • 세션 파일에는 Authorization 헤더, 쿠키, 세션 토큰, 요청 본문의 개인정보가 그대로 들어 있음. 결함 보고서나 메신저에 첨부하기 전에 해당 값을 마스킹하고, 세션에는 재현에 필요한 요청만 포함함
  • Map Local, Rewrite, Breakpoints, Throttling은 켜 둔 동안 일치하는 모든 트래픽에 적용됨. 운영 환경 도메인의 응답을 변조하지 않고, 테스트가 끝나면 각 도구를 끔. 켜 둔 규칙이 다음 테스트 결과를 바꿀 수 있음
  • Repeat Advanced로 운영 서버에 반복 요청을 보내지 않음. 주문, 결제처럼 상태를 바꾸는 요청은 테스트 환경에서만 반복함
  • Access Control에 넓은 서브넷을 추가하면 같은 네트워크의 다른 기기도 Charles를 프록시로 사용할 수 있음. 테스트 기기의 IP만 추가함

관련 문서

기초와 용어API 테스트 기본화면을 거치지 않고 API에 직접 요청을 보내 응답 계약, 상태 코드, 서버 측 검증, 인가를 확인하는 테스트다. 화면 제약만으로는 확인할 수 없는 서버 동작이 대상이다.프로세스이슈 양식버그 이슈의 대표 양식(ISTQB 결함 보고서 항목, Bugzilla 요약·설명, GitHub 이슈 폼)과 선택 기준. 운영 예로 발견 블록과 종결 블록을 나눈 버그 양식과 작업(개선) 양식을 둔다.테스트 설계탐색적 테스트와 세션 기반 테스트 관리테스트 대상을 학습하면서 테스트 설계, 실행, 결과 평가를 동시에 진행하는 경험 기반 기법이다(Exploratory Testing). ISTQB, Kaner, Bach·Bolton의 정의 차이, 테스트 아이디어(HTSM)와 판정 기준(FEW HICCUPPS) 휴리스틱, 세션 기반 테스트 관리의 차터, 세션 기록, TBS 지표를 다룬다.도메인별보안 테스트의 기본 관점접근 제어, 인증과 세션, 입력 처리, 비밀값 노출, 보안 설정에서 권한 없는 동작과 정보 노출이 발생하지 않는지 확인하는 테스트다. OWASP Top 10, ASVS, WSTG를 점검 기준으로 사용한다.
