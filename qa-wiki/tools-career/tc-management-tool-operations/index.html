TC 관리 도구 운영 기준

TC 관리 도구(TCMS)를 운영할 때 결과 집계, TC ID, 회차 이월, 동시 편집, 가져오기, 자동화 계정에서 확인할 기준. 결과 값 체계와 합격률 정의는 도구별 방식을 비교하고 운영 예를 둔다. 도구를 새로 고를 때 확인 항목으로도 사용한다.

노하우난이도 중급최종 업데이트 2026-11-24

결과 값과 집계

섹션 제목: “결과 값과 집계”

결과 값의 이름과 수는 도구마다 다르고, Azure Test Plans처럼 Blocked, Not Applicable을 통과와 실패 어느 쪽에도 세지 않는 도구도 있다. 도구를 바꾸거나 여러 도구의 수치를 비교할 때는 이름보다 정의를 먼저 맞춘다.

도구 기본 결과 값 미수행 표기 특징
TestRail Passed, Blocked, Untested, Retest, Failed Untested 결과를 한 번 기록하면 Untested로 되돌릴 수 없음
QMetry Passed, Failed, Blocked, Not Run, Not Applicable Not Run 사용자 정의 상태를 추가할 수 있음(엔터티나 폴더를 만들기 전까지). 기본 상태는 이름과 아이콘을 바꿀 수 있고 보관할 수 없음
Azure Test Plans Active, Passed, Failed, Blocked, Not Applicable, Paused Active(보고서의 Not Run 열) 진행 보고서에서 Blocked, Not Applicable, 일시 중지는 Run%에는 포함되고 Passed%, Failed%에는 반영되지 않음

선택 기준

  • 재시험이 잦으면 TestRail의 Retest처럼 재수행 대상을 별도 값으로 두는 방식이 맞음. 별도 값이 없으면 비고나 필터로 재수행 대상을 관리함
  • BLOCK을 합격률 분모에 넣으면 막힌 TC가 많을수록 합격률이 낮아져 차단 상황이 수치에 드러남. 분모에서 빼면 판정한 TC 중 통과 비율만 나타나므로 차단 건수를 따로 보고해야 함
  • N/A를 합격률 분모에서 빼는 규칙을 두면 제외한 건수와 사유를 함께 보고함. 그렇지 않으면 범위를 줄여 합격률을 높인 것과 구분되지 않음. Azure Test Plans는 이 값들을 Passed%, Failed% 어느 쪽에도 세지 않아 Run%와 두 값의 합이 달라짐

운영 예

섹션 제목: “운영 예”

아래는 이 위키 작성자가 사용하는 TC 관리 도구의 기준이다.

  • 결과 값은 PASS, FAIL, BLOCK, N/A 넷이고, 아직 결과를 입력하지 않은 TC는 N/R(Not Run, 미수행) 상태임. 회차 진행 중에 수행하지 않은 TC는 N/R로 두고 FAIL이나 N/A로 미리 기록하지 않음
  • 회차를 완료하거나 보고서를 작성하기 전에 N/R로 남은 TC는 비고에 사유를 적고 N/A로 변경함(E2E 실패 분류의 「결과 기록」 절에 일반 원칙이 있음)
  • 합격률의 분모는 판정된 결과(PASS, FAIL, BLOCK)이며, 화면에 분모를 함께 표기함
  • 판정이 하나도 없는 회차의 합격률은 0%가 아니라 값 없음(-)으로 표시함
  • 합격률과 함께 진행률과 N/R 건수를 표시함. 합격률만 보면 일부만 수행한 회차가 완료된 것처럼 보임
  • 여러 회차를 합친 집계는 TC마다 N/R을 제외한 가장 최근 결과를 사용함. N/A도 결과로 보므로 이전 회차 PASS 뒤 새 회차에서 N/A로 기록한 TC는 N/A로 집계함. 새 회차의 미수행 행은 이전 회차의 결과를 덮지 않아야 함
  • 현황 수치 옆에 그 수치를 계산한 회차(이름, 진행 중 또는 완료)를 표시함

규칙

  • 회차 완료는 합격률이 아니라 N/R 0건을 기본 조건으로 판단함. BLOCK 건은 막은 결함이나 원인을 기록하고 재수행 여부를 정한 뒤 완료함
  • 새 회차를 만든 직후 현황 수치가 0이나 -로 바뀌면 결과 유실로 보기 전에 집계 기준이 최신 회차 하나인지 확인함

현장 노트

  • 프로젝트 TC 689건 중 이전 회차에서 PASS 504건을 기록했는데, 전부 N/R인 새 회차를 만들자 대시보드 전체 집계가 PASS 0건, N/R 689건으로 표시됨. 원인은 TC별 최신 회차를 고를 때 미수행 행까지 포함한 것이었고, 미수행을 제외하도록 수정함
  • 397건 중 23건만 수행한 회차의 리포트가 PASS Rate 100%만 표시해 완료된 것처럼 읽힘. 리포트에 N/R과 N/A 카드를 추가하고 PASS Rate 카드에 분모가 실행 건수임을 표기함
  • 메인 화면(프로젝트 목록)의 합격률을 최근 회차 하나로 계산해, 판정이 없는 새 회차를 만들면 0%가 표시됨. 판정이 없으면 -로 표시하고, 이후 메인 화면이 진행 중인 회차와 최근 완료 회차를 나눠 표시하도록 변경함

TC ID와 회차 이월

섹션 제목: “TC ID와 회차 이월”
  • TC ID는 프로젝트 안에서 유일해야 함. 가져오기, 복제, 삭제 후 복원이 모두 중복을 만드는 경로이므로 화면 검사가 아니라 저장소 제약으로 막음
  • 사전조건 참조는 TC ID로 대상을 찾음. TC ID가 중복되면 참조가 다른 TC의 사전조건을 가리킴
  • 삭제한 TC의 ID를 다시 사용할 수 있는지 확인함. 삭제 표시만 하는 도구는 삭제된 행이 ID를 계속 차지할 수 있음
  • 다음 회차로 이월할 때 삭제한 TC와 수행 범위 밖 TC를 제외함

현장 노트

  • 한 프로젝트에 같은 TC ID가 둘 이상 생겨, 내보내기의 펼친 사전조건이 참조 대상이 아닌 다른 TC의 내용을 담음. 가져오기, 복제, 복원 세 경로가 모두 열려 있었고 DB 유니크 제약도 없었음. 삭제되지 않은 행에만 적용하는 유니크 인덱스를 추가하고 기존 중복은 -2, -3을 붙여 정리함
  • 다음 회차 생성이 원본 회차의 결과를 거르지 않고 복사해, 삭제한 TC가 N/R로 남아 진행률이 100%에 도달하지 않음. 이 상태가 다음 회차마다 이어짐

동시 편집

섹션 제목: “동시 편집”
  • 같은 TC의 같은 칸이나 같은 결과 행을 두 사람이 저장하면 나중 저장이 앞의 값을 덮을 수 있음
  • 도구가 저장 시 이전 값을 대조해 충돌을 알리는지 확인함. 충돌 시 저장을 거부하고 최신 값을 보여 주는 방식이어야 함
  • 충돌 검사가 없는 도구는 시트나 TC 범위를 사람별로 나눠 배정함

현장 노트

  • 두 사람이 같은 시트에서 같은 칸을 고치면 나중 저장이 알림 없이 앞의 값을 덮어씀. 변경 이력에는 양쪽이 남았지만 화면에는 표시가 없어 덮어쓴 사람도 알지 못함. 저장 요청에 이전 값을 함께 보내고, 서버 값이 바뀌었으면 409와 현재 값을 돌려주도록 변경함

가져오기(엑셀, CSV)

섹션 제목: “가져오기(엑셀, CSV)”
  • 가져오기 직후 원본과 건수, 빈 칸 수를 대조함. 성공 메시지만으로 판단하지 않음
  • 헤더 매핑 결과를 확인함. 인식하지 못한 열이 경고 없이 빠지면 기대 결과가 비어 있는 TC가 생성됨
  • 덮어쓰기 기준 키(예: 프로젝트, 시트, TC ID)를 확인하고, 같은 키의 기존 TC가 어떻게 처리되는지 시험 프로젝트에서 먼저 확인함
  • 칸 길이 상한을 넘는 값이 있으면 어느 행과 칸인지 알려 주는지 확인함

현장 노트

  • Expected result, Test steps처럼 대소문자나 공백만 다른 헤더를 매핑하지 못해 그 열이 경고 없이 빠지고 기대 결과가 빈 TC가 생성됨. 엑셀 파일은 헤더 행 자체를 찾지 못함
  • DB를 PostgreSQL로 옮긴 뒤 결과 칸에 Not Applicable(14자) 한 행만 있어도 수천 행 가져오기 전체가 서버 오류로 롤백됨. SQLite는 칸 길이를 검사하지 않아 이전에는 드러나지 않았음. 넘는 칸을 행과 글자 수로 모아 400으로 알리도록 변경함

자동화 연동 계정

섹션 제목: “자동화 연동 계정”
  • 자동화는 사람 계정이 아니라 최소 권한의 전용 신원을 사용함. 도구가 지원하는 방식(서비스 계정, 관리 ID, 단기 토큰, API 키) 중에서 고름. 이 위키 작성자의 도구는 결과 업로드에 API 키를 사용함
  • 자동화 신원의 권한은 작업 목적에 필요한 범위로 제한함. 결과 업로드 전용 신원에는 계정 승인, 역할 변경, 멤버 관리, 사용자 목록 조회 같은 관리 권한을 부여하지 않음. 관리 작업을 자동화해야 하면 별도 신원에 그 작업에 필요한 최소 권한만 부여함
  • 이 위키 작성자의 도구는 결과 업로드 키에 결과 업로드만 허용하고, 관리 기능은 로그인 세션에서만 허용함
  • DB를 이관하거나 운영 환경으로 옮길 때 사용자 표를 그대로 복사하지 않음. 이관 전에 관리자 목록을 확인하고 테스트용, 자동화용 계정은 사용 중지함

규칙

  • 키가 유출되었을 때 할 수 있는 일을 기준으로 범위를 정함. 결과 업로드 키로 다른 사용자의 권한을 올릴 수 없어야 함

현장 노트

  • 일괄 가져오기, 자동화용 계정은 사람 계정과 분리하고 관리자 권한을 주지 않음. DB 이관 스크립트가 사용자 표를 그대로 옮기지 않는지 확인함
  • 테스트 계정 비밀번호를 공개 저장소의 테스트 코드 값과 같게 두지 않음
  • API 키에 범위(전체, 결과 업로드 등)를 두고 새 키의 기본값을 가장 좁은 범위로 둠. 대기 계정 승인, 역할 변경, 사용자 목록 조회 같은 계정 관리 기능은 키가 아니라 로그인 세션에서만 허용함

흔한 실수

섹션 제목: “흔한 실수”
  • 합격률만 보고 회차 완료를 판단함
  • 새 회차를 만든 뒤 바뀐 현황 수치를 결과 유실로 오해하거나, 반대로 집계 오류를 놓침
  • 가져오기 성공 메시지만 확인하고 건수와 빈 칸을 대조하지 않음
  • 자동화 업로드에 관리자 계정이나 관리자 권한 키를 공유함
  • 충돌 검사가 없는 도구에서 같은 시트를 여러 명에게 동시에 배정함

관련 문서

프로세스TC 작성 원칙처음 보는 사람이 따라 할 수 있고 수행 직후 통과와 실패를 판정할 수 있는 테스트 케이스의 작성 기준. TC 형식(단계형, BDD 시나리오, 체크리스트, 탐색적 테스트 차터)의 선택 기준, 구성 요소별 작성법, 리뷰 점검 항목을 다룬다.프로세스이슈 로그와 트래커의 조인 키이슈를 어디에 기록할지(트래커만, 로그만, 두 곳)의 선택 기준과, 두 곳에 기록할 때 로그의 행과 트래커의 이슈를 연결하는 식별자(조인 키). 조인 키가 없으면 두 기록이 1:1로 대응하는지 확인할 수 없다.자동화쓰기 작업 결과 대조파일 저장, 덮어쓰기, 드라이런은 예외 없이 끝나도 데이터가 손실될 수 있다. 임시 파일에 저장해 기대값과 대조한 뒤 교체하고, 실패나 드라이런 뒤에는 대상 파일의 실제 상태를 확인한다.
