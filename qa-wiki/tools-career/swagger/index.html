Swagger와 OpenAPI

REST API 기술 형식 OpenAPI Specification(OAS)과 SmartBear의 Swagger 도구의 관계, OAS 버전별 차이(2.0, 3.0, 3.1, 3.2), 명세 구조와 예시, Swagger UI·Editor·Codegen과 OpenAPI Generator, 명세를 테스트 베이스로 사용하는 방법과 운영 시 주의할 점.

기본기난이도 기초백엔드 API최종 업데이트 2026-11-24

OpenAPI Specification(OAS)은 REST API의 엔드포인트, 메서드, 파라미터, 요청과 응답 형식, 인증 방식을 YAML 또는 JSON으로 기술하는 표준 형식이다. 원래 이름은 Swagger Specification이었다. SmartBear Software가 2015년에 Swagger 2.0 명세를 기증했고, 2016년부터 OpenAPI Initiative(OAI)가 별도 프로젝트로 관리한다. OAI는 2015년 11월 Linux Foundation 산하의 오픈소스 프로젝트로 설립되었다. Swagger는 현재 OAS를 다루는 도구의 이름으로 남아 있고, Swagger 상표는 SmartBear가 소유한다. 오픈소스 도구 Swagger UI, Swagger Editor, Swagger Codegen은 Apache-2.0 라이선스이고, 팀 단위 설계·문서 포털 같은 상용 제품도 같은 Swagger 이름으로 제공한다.

QA에서 OAS 문서는 기대 결과의 근거가 되는 명세이자, 문서화·코드 생성·테스트 생성 도구의 입력이다. 명세로 확인할 API 점검 항목(응답 계약, 상태 코드, 인가)은 API 테스트 기본에, 명세를 가져와 요청을 실행하는 방법은 Postman에 정리되어 있다. 이 문서는 명세 자체와 명세를 다루는 도구를 설명한다.

핵심 개념

섹션 제목: “핵심 개념”
용어 뜻
OAS(OpenAPI Specification) API 기술 형식의 규격. OAI가 버전을 관리함
OpenAPI 문서(OpenAPI Description, OAD) 이 규격으로 특정 API를 기술한 파일. 흔히 openapi.yaml, openapi.json
Swagger SmartBear의 도구 브랜드. 2.0까지는 명세 이름이기도 했음
작업(operation) 경로 하나와 HTTP 메서드 하나의 조합. GET /orders/{orderId}
스키마(Schema Object) 요청·응답 본문과 파라미터의 자료 구조. JSON Schema 기반
컴포넌트(components) 여러 곳에서 재사용하는 스키마, 파라미터, 응답, 보안 방식 정의
$ref 다른 위치의 정의를 가리키는 참조. 값은 URI 형식(#/components/schemas/Order)

OAS 버전

섹션 제목: “OAS 버전”

spec.openapis.org의 개정 이력 기준 2026-11 최신 버전은 3.2.1(2026-09-10)이다.

버전 발표 주요 특징
2.0 2014-09-08, 2015-12-31 루트 필드 swagger: "2.0". host, basePath, schemes로 서버를, definitions로 공용 스키마를 정의함. swagger, info, paths가 필수
3.0.x 3.0.0은 2017-07-26, 3.0.4는 2024-10-24 루트 필드 openapi. servers와 components로 구조 변경. 스키마는 JSON Schema의 확장된 부분집합이고 null 허용은 nullable 필드로 표시함
3.1.x 3.1.0은 2021-02-15, 3.1.2는 2025-09-19 스키마가 JSON Schema Draft 2020-12와 호환됨. paths, components, webhooks 중 하나 이상이 있으면 됨
3.2.x 3.2.0은 2025-09-19, 3.2.1은 2026-09-10 query 메서드, additionalOperations, 쿼리 파라미터 전체를 스키마 하나로 정의하는 querystring, 스트리밍 응답과 itemSchema, 태그의 summary·parent·kind, OAuth 2.0 Device Authorization Flow

3.0에서 3.1로 올릴 때 명세 파일 수정이 필요한 항목은 OAI의 업그레이드 안내에 정리되어 있다.

  • null 허용: nullable: true 대신 type: [string, "null"]처럼 type 배열을 사용함
  • exclusiveMinimum, exclusiveMaximum: 불리언이 아니라 숫자 값을 받음. 짝이던 minimum, maximum은 삭제함
  • 스키마 예시: OAS 전용 example 대신 JSON Schema의 examples(배열)를 사용함
  • 파일 업로드: format: binary 대신 contentMediaType, contentEncoding을 사용함

명세 구조

섹션 제목: “명세 구조”
필드 내용
openapi 사용한 OAS 버전. 필수
info 제목, API 버전, 설명, 연락처, 라이선스. 필수
servers API 서버 주소 목록. 환경별 주소를 나열함
paths 경로별 작업 정의. 작업마다 parameters, requestBody, responses, security를 둠
webhooks API 사용자가 받을 수 있는 수신 웹훅(3.1부터)
components schemas, responses, parameters, examples, requestBodies, headers, securitySchemes, links, callbacks 등 재사용 정의
security 문서 전체에 적용할 기본 보안 요구사항
tags, externalDocs 작업 묶음과 외부 문서 링크
  • 파라미터 위치(in): path, query, header, cookie. 3.2에서 querystring이 추가됨
  • 응답(responses): 상태 코드별로 설명과 미디어 유형별 스키마를 정의함
  • 예시: Parameter, Header, Media Type 객체에서는 example과 examples를 함께 쓸 수 없음. Schema 객체에서는 examples를 권장하고 example은 호환성을 위해 남아 있음. 명세는 예시 값이 스키마와 호환되어야 한다(SHOULD)고 정하고, 도구가 예시를 검증할지는 선택(MAY)임

주문 조회와 주문 생성 두 작업을 기술한 OAS 3.1 예다.

이 명세에서 바로 도출되는 테스트 항목이 있다. quantity의 경계값 0, 1, 99, 100, status의 허용 값 세 개, memo의 null 허용, 토큰 없이 요청했을 때의 401, 없는 orderId의 404다.

Swagger 도구 구성

섹션 제목: “Swagger 도구 구성”
도구 내용 라이선스
Swagger UI OpenAPI 문서로 대화형 API 문서를 생성함. Try it out으로 브라우저에서 실제 요청을 보냄. npm 패키지 swagger-ui, swagger-ui-dist, swagger-ui-react로 제공 Apache-2.0
Swagger Editor 브라우저에서 OpenAPI 문서를 작성하고 미리 보는 편집기. 현재 버전 5는 OpenAPI 2.0, 3.0, 3.1, 3.2와 AsyncAPI 2.x, 3.x를 지원함. 온라인판은 editor.swagger.io Apache-2.0
Swagger Codegen 명세에서 서버 스텁과 클라이언트 라이브러리를 생성함. 2.x는 명세 2.0까지, 3.x는 OAS 3.0까지 지원함 Apache-2.0
상용 제품 2026-11 기준 공식 사이트는 팀 단위 설계·거버넌스 도구 Swagger Studio, 문서 포털 Swagger Portal, API 탐색 도구 Swagger Explore를 소개함. SaaS 또는 자체 설치(Kubernetes)로 제공 상용
  • Swagger UI의 OAS 지원 범위는 버전마다 다름. README 호환성 표 기준 3.1은 5.0.0부터, 3.2.0은 5.32.0(2026-02-27)부터 지원함
  • swagger.io 문서는 이 밖에 Java 라이브러리 Swagger Core, 문서 파서 Swagger Parser를 함께 소개함
  • 예전 SwaggerHub 주소(swagger.io/tools/swaggerhub/)는 2026-11 기준 위 상용 제품 소개 페이지로 연결되고, 본문에 SwaggerHub라는 이름은 나오지 않음
  • OpenAPI Generator는 Swagger Codegen 2.4.0-SNAPSHOT에서 갈라진 커뮤니티 포크임. Swagger Codegen 3.0이 2.x의 방향에서 멀어진 점, 2.x와 3.x 두 갈래 유지 부담, 더 빠른 릴리즈 주기, 커뮤니티 주도 로드맵을 이유로 Swagger Codegen 상위 기여자 40명 이상이 참여함. 클라이언트 SDK, 서버 스텁, 문서, 설정 파일을 생성하고, OAS 3.1 지원은 베타임(Apache-2.0)

QA에서 사용하는 방법

섹션 제목: “QA에서 사용하는 방법”
  • 테스트 베이스: 작업별 파라미터 제약(minimum, maximum, maxLength, enum, required)과 상태 코드별 응답 정의를 TC의 입력 조건과 기대 결과로 옮김. 명세에 없는 상태 코드나 오류 형식은 개발과 확인할 항목으로 기록함(TC 작성 원칙)
  • 응답 스키마 검증: 응답 본문을 components.schemas의 스키마로 검증해 필수 키, 자료형, 허용 값을 확인함. 스키마 검증은 형식만 확인하므로 금액·소유자 같은 값은 별도로 단언함(API 테스트 기본)
  • 명세와 구현의 불일치 탐지: 추가 속성을 금지한 스키마(additionalProperties: false)에서 정의하지 않은 필드를 반환하거나, 명세의 필수 키를 빠뜨리거나, 문서화하지 않은 상태 코드를 반환하면 결함으로 기록함. 결함 보고서에는 명세 파일의 버전(info.version 또는 커밋 해시)과 해당 작업의 operationId를 함께 남김(이슈 양식)
  • 명세 린트: Spectral(Apache-2.0)은 JSON·YAML 린터로, 내장 규칙 집합 spectral:oas로 OpenAPI 2.0, 3.0, 3.1 문서를 검사함. 팀 규칙은 .spectral.yaml에 정의함. 명세 변경 PR마다 CI에서 실행하면 설명 누락, 잘못된 $ref 같은 명세 오류를 병합 전에 확인할 수 있음
  • 명세 기반 테스트 생성: Schemathesis(MIT)는 OpenAPI 2.0~3.2와 GraphQL 스키마로 속성 기반 테스트를 생성함. 경계 입력에서 발생하는 5xx, 명세와 다른 응답, 거부해야 할 입력을 받아들이는 경우, 객체 수준 인가 실패를 찾음
  • 계약 테스트: Pact는 컨슈머 테스트 중에 생성한 요청·응답 쌍을 계약으로 사용하는 코드 우선 컨슈머 주도 계약 테스트 도구임. Pact 문서는 OAS 같은 스키마를 리소스의 가능한 모든 상태를 기술한 정적 산출물로, Pact 계약을 실제 사용하는 상호작용의 예시로 구분함. 명세 검증과 컨슈머 계약 검증은 확인하는 범위가 달라 함께 운영할 수 있음
  • Postman 가져오기: OpenAPI 문서를 컬렉션으로 가져오거나 명세와 컬렉션을 함께 생성함. 생성된 요청에 단언과 데이터 파일을 추가해 회귀 컬렉션으로 사용함(Postman)
  • 코드 기반 API 테스트: Playwright의 request 픽스처는 baseURL과 extraHTTPHeaders 설정을 적용해 페이지 없이 API를 호출함. 명세의 servers 주소와 보안 방식을 이 설정에 맞추고, 스키마 검증은 별도 JSON Schema 검증 라이브러리로 수행함(Playwright)
  • 회귀 범위: 릴리즈 사이 명세 파일의 diff(추가·삭제된 작업, 바뀐 스키마)를 회귀 범위 선정의 입력으로 사용함(회귀 테스트 범위 선정, Git 기본)

선택 기준

  • 동기 요청·응답 HTTP API는 OpenAPI, 메시지 브로커를 거치는 이벤트 API는 AsyncAPI로 기술함. 한 시스템에 둘이 섞여 있으면 두 형식을 함께 사용함
  • 테스트 담당자가 문서 화면에서 직접 요청을 보내야 하면 Try it out이 있는 Swagger UI가 맞음. 읽기 전용 공개 문서로 요청 실행이 필요 없으면 Redoc도 후보임
  • 명세 버전을 올리기 전에 사용 중인 도구(문서, 린트, 코드 생성, 테스트 생성)가 그 버전을 지원하는지 확인함. 2026-11 기준 Swagger Codegen은 OAS 3.0까지, OpenAPI Generator의 3.1 지원은 베타임

주의할 점

섹션 제목: “주의할 점”
  • Swagger UI의 Try it out은 브라우저에서 실제 요청을 보냄. 운영 환경에 문서를 둘 때는 supportedSubmitMethods를 빈 배열로 설정해 Try it out을 끄거나 조회 메서드만 남김. tryItOutEnabled(기본값 false)는 Try it out의 기본 활성 여부만 정하므로 실행을 막는 설정으로 사용하지 않음. 상태 변경 메서드 차단 기준은 API 테스트 기본의 운영 환경 주의 항목과 같음
  • Swagger UI의 validatorUrl 기본값은 swagger.io 온라인 검증기임. 외부에 공개하지 않는 명세는 none으로 설정해 검증을 끔
  • Swagger UI의 persistAuthorization을 true로 설정하면 입력한 인증 정보가 브라우저를 닫거나 새로 고쳐도 유지됨. 공용 PC나 공유 화면에서는 기본값(false)을 유지함
  • OAS 3.2.1의 보안 고려사항은 인증 여부에 따라 paths를 비우거나 제거하는 보안 필터링을 허용함. 내부 관리용 작업을 공개 문서에서 숨겨도 엔드포인트 자체의 인가는 별도로 테스트함(보안 테스트의 기본 관점)
  • 예시 값(example, examples)은 스키마 호환이 권고 사항이고 검증은 도구 선택이라, 실제 응답이나 스키마와 다를 수 있음. 예시를 응답으로 반환하는 모의 서버로 통과한 테스트는 실제 서버에서 다시 실행함
  • 명세가 구현보다 늦게 갱신되면 명세 기준 테스트가 정상 동작을 결함으로 판정하거나 새 필드를 확인하지 못함. 테스트 실행 기록에 사용한 명세 버전을 남기고, 불일치가 나오면 명세와 구현 중 어느 쪽이 기준인지 먼저 확인함
  • Schemathesis는 데이터를 생성, 변경, 삭제하는 실제 요청을 보냄. 운영 환경이 아니라 개발 또는 스테이징 환경에서 실행함
  • 외부 파일을 가리키는 $ref는 도구가 자동으로 내려받을 수 있고, 순환 참조는 도구가 감지해야 함(OAS 3.2.1 보안 고려사항). 신뢰할 수 없는 외부 명세를 CI에서 처리할 때 참조 대상을 확인함

관련 문서

기초와 용어API 테스트 기본화면을 거치지 않고 API에 직접 요청을 보내 응답 계약, 상태 코드, 서버 측 검증, 인가를 확인하는 테스트다. 화면 제약만으로는 확인할 수 없는 서버 동작이 대상이다.도구PostmanAPI 요청을 작성, 전송, 테스트하는 도구 Postman의 워크스페이스와 컬렉션, 변수 범위, pre-request·post-response 스크립트와 단언, 컬렉션 러너와 데이터 파일, Postman CLI와 Newman의 차이, 모의 서버, 모니터, API 명세 가져오기와 QA에서 사용하는 방법.도구PlaywrightMicrosoft가 유지하는 웹 브라우저 자동화 도구 Playwright와 테스트 러너 Playwright Test의 핵심 개념(브라우저 엔진, 컨텍스트 격리, 로케이터, 자동 대기, 웹 우선 단언, 픽스처, 프로젝트)과 설정, 인증 재사용, 네트워크 가로채기, 트레이스, 리포터, 시각 비교, API 테스트를 다룬다.도메인별보안 테스트의 기본 관점접근 제어, 인증과 세션, 입력 처리, 비밀값 노출, 보안 설정에서 권한 없는 동작과 정보 노출이 발생하지 않는지 확인하는 테스트다. OWASP Top 10, ASVS, WSTG를 점검 기준으로 사용한다.
