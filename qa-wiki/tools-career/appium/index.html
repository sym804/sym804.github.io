Appium

W3C WebDriver 프로토콜로 Android, iOS 같은 모바일 앱과 데스크톱 앱을 자동화하는 오픈소스 도구 Appium의 구조(서버, 클라이언트, 드라이버, 플러그인), capabilities와 세션, 컨텍스트 전환, 로케이터 전략, Appium Inspector, 병렬 실행과 QA에서 사용하는 방법.

기본기난이도 중급최종 업데이트 2026-11-24

Appium은 네이티브, 하이브리드, 모바일 웹, 데스크톱 앱의 UI 자동화를 여러 플랫폼과 언어에서 지원하는 오픈소스 도구다. 개발은 GitHub 저장소 appium/appium에서 이루어지고, 라이선스는 Apache-2.0이며, 공식 문서 사이트의 저작권 표기는 OpenJS Foundation과 Appium 기여자다. 2026-11 기준 최신 서버 릴리즈는 appium@4.0.0(2026-11-15)이다. 주 용도는 모바일 앱의 E2E 테스트와 회귀 자동화다.

Appium 2부터 서버 설치에 드라이버가 포함되지 않고, 드라이버와 플러그인을 확장(extension)으로 따로 설치한다. 이 문서는 Appium 2 이후 구조를 기준으로 설명한다.

핵심 개념

섹션 제목: “핵심 개념”
개념 뜻
서버 HTTP 기반 WebDriver 프로토콜 요청을 받는 Node.js 서버. 플랫폼별 작업을 드라이버에 위임함. 기본 주소는 http://127.0.0.1:4723/
클라이언트 언어별 라이브러리. 테스트 코드의 명령을 HTTP 요청으로 서버에 보냄. 서버와 같은 기기에 있지 않아도 됨
W3C WebDriver 프로토콜 Selenium에서 나와 웹 브라우저 표준이 된 자동화 프로토콜. Appium은 이 명세를 API로 사용하고 확장 명령을 추가함
드라이버 특정 플랫폼에 대해 WebDriver 명령을 구현하는 모듈. 플랫폼의 자동화 기술(XCUITest, UiAutomator2 등)로 명령을 변환함
플러그인 Appium의 핵심 동작을 변경하거나 기능을 추가하는 선택 모듈
capabilities 세션을 시작할 때 보내는 키-값 묶음. 어떤 드라이버로 어떤 기기와 앱을 자동화할지 지정함
세션 capabilities로 시작한 자동화 단위. 시작한 뒤에는 capabilities를 변경할 수 없음
컨텍스트 세션 안에서 명령이 적용되는 모드. 네이티브 컨텍스트(NATIVE_APP)와 웹뷰별 컨텍스트가 있음

공식 클라이언트는 Java, Python, Ruby, .NET(C#)용이 있고, JavaScript는 공식 빠른 시작에서 WebdriverIO를 사용한다. 여러 Appium 클라이언트가 같은 언어의 Selenium 클라이언트 위에 만들어져 있어, 전체 API를 확인하려면 두 문서를 함께 참조한다.

구성

섹션 제목: “구성”

드라이버와 플러그인 설치

섹션 제목: “드라이버와 플러그인 설치”

드라이버와 플러그인은 APPIUM_HOME(기본값 ~/.appium) 아래에 설치된다. 서버와 드라이버는 따로 릴리즈되므로 버전을 각각 관리한다.

  • appium setup은 UiAutomator2, Espresso, XCUITest(macOS에서) 같은 모바일 드라이버를 한 번에 설치함
  • appium driver doctor <드라이버>는 Android SDK, ANDROID_HOME, JDK 같은 사전 조건을 점검함
  • 프로젝트가 이미 npm을 사용하면 package.json에 드라이버를 의존성으로 선언해 관리할 수 있음
  • 플러그인은 설치 후 서버 시작 시 --use-plugins로 활성화함

Appium 팀이 관리하는 공식 드라이버

드라이버 대상 모드
UiAutomator2 Android 앱(모바일, TV, Wear 등) 네이티브, 하이브리드, 웹
Espresso Android 앱 네이티브, 하이브리드, 웹
XCUITest iOS, iPadOS, tvOS, watchOS 앱 네이티브, 하이브리드, 웹
Mac2 macOS 앱 네이티브
WinCore Windows 앱 네이티브
Chromium, Gecko, Safari 각 엔진 기반 브라우저 웹
  • UiAutomator2와 XCUITest 드라이버는 블랙박스 테스트용임. Espresso 드라이버는 그레이박스 드라이버로, 화면 밖 요소나 IdlingResource처럼 블랙박스 드라이버가 접근하지 못하는 앱 내부 정보를 사용함. 대신 테스트 작성자가 앱 소스 코드를 알아야 하고, 앱과 Espresso 서버의 버전이 맞지 않으면 세션이 생성되지 않음
  • 공식 플러그인은 execute-driver, images, inspector, relaxed-caps, storage, universal-xml임

capabilities

섹션 제목: “capabilities”

W3C 표준 capabilities(platformName, browserName, browserVersion)를 제외한 모든 capabilities에는 공급자 접두사가 필요하고, Appium의 접두사는 appium:이다. 여러 항목을 appium:options 객체 하나로 묶으면 안쪽에서는 접두사를 생략할 수 있고, 같은 항목이 안팎에 모두 있으면 안쪽 값이 우선한다.

  • appium:automationName: 사용할 드라이버. UiAutomator2 드라이버는 UiAutomator2
  • appium:udid: 자동화할 기기의 고유 식별자. Android는 adb devices로 확인함
  • appium:app: 설치할 앱 파일의 경로나 URL. UiAutomator2는 .apk, .apks
  • appium:deviceName: UiAutomator2에서는 기기를 선택하지 않음. 실기기는 appium:udid, 에뮬레이터는 appium:avd로 선택함
  • appium:noReset, appium:fullReset: 세션 시작 전 앱 데이터 초기화와 재설치 여부. 테스트 간 상태 공유 여부가 이 값으로 결정되므로 스위트 전체에서 기준을 하나로 맞춤

드라이버마다 추가 capabilities와 제약이 있다. 예를 들어 XCUITest는 앱을 자동 설치하거나 실행하려면 browserName, appium:app, appium:bundleId 중 하나 이상이 필요하다.

세션 시작과 로케이터

섹션 제목: “세션 시작과 로케이터”

Python 클라이언트로 세션을 시작하고 accessibility id로 요소를 찾는 최소 예다.

로케이터 전략은 드라이버가 정한다. 두 주요 드라이버의 공식 문서는 전략별 속도 등급을 함께 제공한다.

드라이버 전략 속도 등급(5점) 대응 속성과 공식 문서의 안내
UiAutomator2 id 5 View.id(리소스 이름) 정확 일치
UiAutomator2 accessibility id 5 View.contentDescription 정확 일치
UiAutomator2 -android uiautomator 4 UiSelector 구문. 스크롤 같은 동작을 포함할 수 있음. Google이 UiSelector 계열 클래스를 폐기·제거할 계획이라 이 전략의 로케이터가 모두 무효가 될 수 있음
UiAutomator2 xpath 3 페이지 소스 XML을 조회함. 형제·자손 요소를 거쳐야만 찾을 수 있을 때처럼 다른 전략으로 식별할 수 없을 때 사용
XCUITest accessibility id, id, name 5(accessibility id) 세 전략 모두 name 속성 기준(id, accessibility id는 name의 별칭)
XCUITest -ios predicate string, -ios class chain - 요소 자체 속성만으로 식별하면 predicate, 부모·자손 관계가 필요하면 class chain
XCUITest xpath 2 다른 전략보다 최대 10배 느릴 수 있어 더 빠른 전략 사용을 강하게 권장함. XPath 1.0만 지원

XCUITest 드라이버는 시스템 접근성 프레임워크가 제공하는 정보로 화면 요소를 구분한다. 앱에 접근성 정보가 빠진 요소는 드라이버에 보이지 않을 수 있다. accessibility id를 앱 코드에 지정해 두면 두 플랫폼에서 같은 전략으로 요소를 찾을 수 있다.

컨텍스트와 앱 유형

섹션 제목: “컨텍스트와 앱 유형”
  • 네이티브 앱: 기본 컨텍스트 NATIVE_APP에서 드라이버의 로케이터로 요소를 찾음
  • 하이브리드 앱: 네이티브 화면 안에 웹 콘텐츠(웹뷰)를 넣은 앱. 웹뷰마다 컨텍스트가 하나씩 생기고, Get Contexts로 목록을 확인한 뒤 Set Context로 전환해야 웹뷰 요소를 조작할 수 있음
  • 모바일 웹: browserName capability로 브라우저를 지정해 처음부터 웹 컨텍스트로 세션을 시작함

Android 웹 컨텍스트에서 UiAutomator2 드라이버는 명령을 ChromeDriver로 전달한다. ChromeDriver의 메이저 버전이 웹뷰의 Chromium 버전과 맞지 않으면 연결에 실패한다. 웹뷰는 디버깅 가능하도록 설정되어 있어야 드라이버가 접근할 수 있다. 맞는 ChromeDriver를 자동으로 내려받는 기능은 보안상 허용이 필요한 기능(insecure feature)이라 서버 시작 시 --allow-insecure로 허용한다. Appium 3부터 이 옵션에는 범위 접두사가 필수다(예: uiautomator2:chromedriver_autodownload).

Appium Inspector

섹션 제목: “Appium Inspector”

Appium Inspector는 테스트 대상 앱을 시각적으로 검사하는 GUI 도구다. 스크린샷과 페이지 소스로 요소를 찾고, 요소와 상호작용하고, 드라이버 명령을 실행하고, 사용자 동작을 기록한다. Windows, macOS, Linux용 데스크톱 앱과 Appium 서버 플러그인(inspector, 브라우저에서 http://127.0.0.1:4723/inspector) 두 형태로 제공한다. 연결할 Appium 서버와 capabilities가 있어야 세션을 시작할 수 있고, 서버 메이저 버전별 권장 Inspector 버전이 따로 있다(Appium 4는 2026.11.5 이상).

실기기, 에뮬레이터, 시뮬레이터

섹션 제목: “실기기, 에뮬레이터, 시뮬레이터”
  • Android: Android SDK와 Platform-Tools, JDK, ANDROID_HOME과 JAVA_HOME 설정이 필요함. 에뮬레이터는 Android Studio에서 AVD를 만들어 실행하고, 실기기는 개발자 옵션과 USB 디버깅을 켜서 연결함
  • iOS: XCUITest 드라이버는 macOS 호스트와 Xcode가 필요함. Windows와 Linux 호스트는 지원이 제한적임. 실기기는 추가 수동 구성(프로비저닝 프로파일 등)이 필요하고, watchOS는 시뮬레이터만 지원함

병렬 실행

섹션 제목: “병렬 실행”

UiAutomator2 드라이버는 여러 세션을 동시에 실행할 수 있다. 서버 프로세스마다 세션 하나를 두거나, 서버 하나에서 여러 세션을 실행할 수 있고, 후자가 자원을 적게 사용한다. 기기 하나는 한 번에 한 세션에서만 사용한다.

드라이버 세션마다 고유해야 하는 값
UiAutomator2 appium:udid(실기기) 또는 appium:avd(에뮬레이터), appium:systemPort, 웹뷰를 쓰면 appium:chromedriverPort, MJPEG 스트림을 쓰면 appium:mjpegServerPort
XCUITest appium:udid(시뮬레이터는 appium:deviceName과 appium:platformVersion 조합도 가능), appium:wdaLocalPort, appium:derivedDataPath, 영상 스트림을 쓰면 appium:mjpegServerPort

QA에서 사용하는 방법

섹션 제목: “QA에서 사용하는 방법”
  • 테스트 레벨: 앱 전체를 기기에서 실행하는 시스템·E2E 레벨 테스트에 해당함. 실행이 느리고 실패 원인 특정이 어려워 핵심 사용자 흐름에 한정하고, 계산 규칙과 API 계약은 아래 레벨에서 확인함(테스트 레벨과 테스트 유형, 테스트 자동화 기본의 테스트 피라미드)
  • 테스트 용이성: 자동화 대상 화면의 요소에 accessibility id(Android contentDescription, iOS 접근성 식별자)를 지정하도록 개발 단계에서 요청함. XPath 로케이터는 두 드라이버 모두 속도 등급이 가장 낮음. 접근성 정보가 빠진 요소는 접근성 테스트 관점에서도 확인 대상임
  • 기기 매트릭스: 회귀 대상 기기 모델과 OS 버전은 사용자 분포와 장애 이력으로 정함. 조합 선정 방식은 임베디드·디바이스 테스트 관점의 하드웨어·OS 조합 항목과 같음
  • 결함 기록: Appium 서버 버전, 드라이버 이름과 버전, 기기 모델·OS 버전·udid, 앱 빌드 번호, 사용한 capabilities를 함께 기록함. 실패 시점의 스크린샷과 페이지 소스(Inspector의 Source 탭 또는 클라이언트의 페이지 소스 명령)를 첨부함(이슈 양식)
  • 병렬 실행 실패: 같은 기기나 같은 포트를 두 세션이 사용하면 실행 순서에 따라 결과가 달라짐. 세션마다 고유 값을 할당하는 설정을 공통 픽스처에 두고, 실패가 재현되지 않으면 자원 경합부터 확인함(Flaky 테스트 관리)
  • CI 연동: 파이프라인에서 서버를 띄우기 전에 appium driver doctor로 환경을 점검하고, 서버 로그를 실행 산출물로 보관함. Appium 4의 기본 로그 수준은 info라 실패 분석에 상세 로그가 필요하면 --log-level debug를 지정함(GitHub Actions, Jenkins)

비슷한 도구와 선택 기준

섹션 제목: “비슷한 도구와 선택 기준”
도구 유지 주체 대상 플랫폼 테스트 작성 방식 특징
Appium Appium 프로젝트(Apache-2.0) Android, iOS, macOS, Windows, 브라우저(드라이버별) Java, Python, Ruby, C#, JavaScript 클라이언트 앱 밖에서 WebDriver 프로토콜로 제어함. 한 언어로 여러 플랫폼을 다룸
Espresso Google(Android 테스트 라이브러리) Android Kotlin·Java 테스트 코드 메시지 큐, AsyncTask, IdlingResource가 유휴 상태가 될 때까지 기다린 뒤 동작과 단언을 수행함. 테스트 대상 코드를 아는 개발자를 대상으로 함
XCUITest(XCTest와 XCUIAutomation) Apple iOS, iPadOS 등 Apple 플랫폼 Swift·Objective-C, Xcode의 UI 테스트 XCTest로 테스트를 작성하고 XCUIAutomation으로 앱 UI를 제어함. visionOS SDK로 빌드한 앱에는 UI 테스트를 사용할 수 없음
Maestro GitHub mobile-dev-inc 조직(Apache-2.0) Android, iOS, 웹 YAML 플로(launchApp, tapOn, assertVisible 등) 플로를 해석 실행해 컴파일 단계가 없음. 자동 대기를 내장함. iOS 실기기는 아직 지원하지 않음

선택 기준

  • Android와 iOS를 한 테스트 코드베이스와 한 언어로 다뤄야 하면 Appium이 맞음. 플랫폼별 드라이버, 로케이터, 기기 설정은 따로 관리해야 함
  • 앱 코드베이스를 아는 개발자가 테스트를 작성하고 UI 동기화를 프레임워크에 맡기려면 Espresso, XCUITest 같은 플랫폼 네이티브 프레임워크가 맞음. 대신 플랫폼마다 테스트를 따로 작성함
  • 프로그래밍 언어 없이 짧은 시나리오를 빠르게 작성하려면 Maestro를 검토함. 지원 플랫폼과 기기 종류(iOS 실기기 미지원)가 요구사항에 맞는지 먼저 확인함
  • Espresso 드라이버로 Appium 안에서 그레이박스 방식을 사용하는 방법도 있음. 이 경우 앱 소스 코드와 버전 호환을 관리해야 함

주의할 점

섹션 제목: “주의할 점”
  • Appium 1 기준 자료의 설정은 현재 서버에서 동작하지 않음. 기본 경로가 /wd/hub에서 /로 변경되었고(옛 경로가 필요하면 --base-path=/wd/hub), JSONWP·MJSONWP 프로토콜과 TouchAction·MultiAction 엔드포인트가 제거되었고, 접두사 없는 비표준 capabilities는 거부됨. Appium 3부터 세션 생성 요청의 desiredCapabilities도 받지 않으므로 capabilities를 사용함
  • 서버, 드라이버, Inspector, 클라이언트의 버전 호환을 함께 확인함. UiAutomator2 드라이버는 9.0.0부터 Appium 4 전용이고, Appium 4는 Node.js ^22.22.2 || ^24.15.0 || >=26.0.0이 필요함
  • Appium 4는 driver, plugin, setup 명령의 오류가 아닌 출력을 stderr에서 stdout으로 옮김. 명령 출력을 파싱하는 CI 스크립트는 갱신해야 함
  • 세션을 시작한 뒤에는 capabilities를 변경할 수 없음. 기기나 앱 설정을 바꾸려면 세션을 새로 시작함
  • XPath와 -android uiautomator 로케이터에 의존하는 스위트는 속도와 향후 호환성 위험이 있음. 위 로케이터 표의 공식 경고 참조
  • XCTest는 성능상 스냅샷의 요소 속성 값을 512바이트로 제한함. 긴 텍스트를 단언할 때는 해당 속성을 조회하는 API로 값을 가져옴
  • 웹뷰 컨텍스트 실패는 앱 결함이 아니라 ChromeDriver 버전 불일치나 웹뷰 디버깅 설정 누락인 경우가 있음. 실패 분류 전에 드라이버 로그를 확인함

관련 문서

자동화테스트 자동화 기본테스트 자동화는 도구로 테스트를 실행하고 결과를 판정하는 활동이다. 이점과 한계, 테스트 피라미드, 테스트 용이성, 자동화 아키텍처(gTAA)와 프레임워크 계층, 케이스 자동화 방식 7가지, 도입 절차와 파이프라인 배치, 작성 원칙을 ISTQB CTAL-TAE 기준으로 설명한다.자동화Flaky 테스트 관리코드와 환경이 같은데도 실행마다 결과가 달라지는 테스트(Flaky 테스트)의 원인을 분류하고 탐지, 격리, 수정하는 절차다.기초와 용어테스트 레벨과 테스트 유형테스트 레벨은 시스템을 어느 통합 단계에서 검증하는지를, 테스트 유형은 어떤 품질 특성을 검증하는지를 나타내는 분류다. 두 분류는 서로 독립이며, 테스트마다 레벨을 하나 정하고 테스트 유형은 하나 이상 적용할 수 있다.도구Selenium웹 브라우저 자동화 프로젝트 Selenium의 구성(WebDriver, Grid, IDE)과 핵심 개념(W3C WebDriver 표준, 브라우저 드라이버와 Selenium Manager, 언어 바인딩, 로케이터 전략, 명시적·암묵적 대기, 페이지 객체 모델, WebDriver BiDi), 옛 API 정리, QA 적용 방법을 다룬다.
