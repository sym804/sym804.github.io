Postman

API 요청을 작성, 전송, 테스트하는 도구 Postman의 워크스페이스와 컬렉션, 변수 범위, pre-request·post-response 스크립트와 단언, 컬렉션 러너와 데이터 파일, Postman CLI와 Newman의 차이, 모의 서버, 모니터, API 명세 가져오기와 QA에서 사용하는 방법.

기본기난이도 기초백엔드 API최종 업데이트 2026-11-24

Postman은 API 요청을 작성해 보내고, 응답에 대한 테스트 스크립트를 실행하고, 요청 묶음을 반복 실행하는 상용 API 도구다. Windows, macOS, Linux용 데스크톱 앱과 웹 앱, 명령줄 도구 Postman CLI로 제공한다. 무료 플랜과 유료 플랜이 있고, GraphQL·gRPC 컬렉션 실행처럼 유료 플랜에서만 제공하는 기능이 있다(2026-11 기준, 공식 문서). 컬렉션은 오픈소스 컬렉션 형식을 기반으로 한다. QA에서는 수동 API 확인, API 회귀 테스트, CI 파이프라인의 API 검증에 사용한다.

화면을 거치지 않고 API를 직접 호출해 확인할 항목(응답 계약, 상태 코드, 서버 측 검증, 인가)은 API 테스트 기본에 정리되어 있다. 이 문서는 그 항목을 Postman으로 구성하고 실행하는 방법을 다룬다.

핵심 개념

섹션 제목: “핵심 개념”
개념 뜻
워크스페이스 작업을 정리하고 팀과 협업하는 공간. API, 컬렉션, 환경, 모의 서버, 모니터를 담음. 공유 워크스페이스의 변경은 팀에 실시간으로 동기화됨
컬렉션 API 요청을 저장하고 정리하는 기본 단위. 실행, 모의 서버, 모니터의 대상이 됨
폴더 컬렉션 안에서 요청을 묶는 단위. 스크립트를 폴더 단위로 둘 수 있음
요청 메서드, URL, 헤더, 본문, 인증 설정과 스크립트를 담은 하나의 API 호출
예시(example) 요청에 저장해 둔 응답 예. 모의 서버가 이 예시를 응답으로 반환함
환경 대상 서버 주소, 계정처럼 실행 대상마다 바뀌는 값을 묶은 변수 집합
변수 {{base_url}}처럼 요청에서 참조하는 값. 범위가 다섯 가지임

워크스페이스 유형은 Internal(초대한 사람이나 팀에 공개, 초대 전용 Private 포함), Partner(엔터프라이즈 플랜에서 외부 파트너와 공유), Public(누구나 접근)이 있다.

변수 범위

섹션 제목: “변수 범위”

범위는 넓은 쪽부터 전역, 컬렉션, 환경, 데이터, 로컬 순이다. 같은 이름의 변수가 여러 범위에 있으면 가장 좁은 범위의 값을 사용한다.

범위 용도 스크립트 API
전역(global) 여러 컬렉션, 요청, 스크립트, 환경에서 함께 사용하는 값 pm.globals.get(), pm.globals.set()
컬렉션 한 컬렉션의 요청 전체에서 사용하는 값. 환경과 독립적임 pm.collectionVariables.get(), pm.collectionVariables.set()
환경 로컬 개발, 테스트, 운영처럼 대상 환경마다 다른 값 pm.environment.get(), pm.environment.set(), pm.environment.unset()
데이터 컬렉션 러너나 Postman CLI로 실행할 때 외부 CSV, JSON 파일에서 읽은 값 pm.iterationData.get(), pm.iterationData.toObject()
로컬 스크립트에서 설정하는 임시 값. 요청 하나 또는 컬렉션 실행 한 번 동안 유지되고 실행이 끝나면 사라짐 pm.variables.set()
  • pm.variables.get()은 범위를 가리지 않고 가장 좁은 범위의 값을 반환함
  • 변수 값은 공유 값(shared value)과 로컬 값(local value)으로 나뉨. 요청을 보낼 때는 로컬 값을 사용하고, 로컬 값은 Postman 클라우드에 동기화되지 않음. 공유 값은 클라우드에 동기화되어 팀원에게 보임. 예전 문서의 초기 값(initial value)과 현재 값(current value)은 이전 방식의 용어임
  • 토큰, 비밀번호 같은 민감 정보는 Vault에 비밀 값(vault secret)으로 저장해 워크스페이스 간에 재사용할 수 있음

주요 기능

섹션 제목: “주요 기능”

스크립트와 단언

섹션 제목: “스크립트와 단언”

스크립트는 두 종류다. pre-request 스크립트는 요청을 보내기 전에, post-response 스크립트는 응답을 받은 뒤에 실행된다. 요청뿐 아니라 컬렉션과 폴더에도 둘 수 있고, 실행 순서는 컬렉션, 폴더, 요청 순이다. 런타임은 Node.js 기반의 Postman Sandbox이고, 팀에서 자주 사용하는 스크립트는 Package Library에 패키지로 등록해 pm.require로 가져온다.

테스트는 pm.test(이름, 함수)로 정의하고, 함수 안에서 Chai BDD 문법의 pm.expect나 pm.response.to 단언을 사용한다. 주문 조회 응답을 확인하는 post-response 스크립트 예다.

컬렉션 러너와 데이터 파일

섹션 제목: “컬렉션 러너와 데이터 파일”

컬렉션 러너는 컬렉션의 요청 전체나 일부를 정한 순서로 보내고, 요청마다 테스트 결과를 기록한다. 주요 실행 옵션은 다음과 같다.

  • 반복 횟수(Iterations): 컬렉션을 실행할 횟수
  • 반복 데이터(Iteration data): 실행에 사용할 CSV 또는 JSON 데이터 파일
  • 요청 간 지연(Add a delay of): 요청 사이 대기 시간(밀리초)
  • 응답 보존(Persist responses for a session): 실행 뒤 응답 헤더와 본문을 확인할 수 있게 보존함. 본문은 300KB 미만일 때만 저장됨(2026-11 기준)
  • 변수 값 유지(Keep variable values): 실행 중 변경된 변수 값을 실행이 끝난 뒤에도 유지함
  • 실행 순서: 요청을 끌어 순서를 바꾸거나 체크를 해제해 제외함

수동 실행 외에 Postman 클라우드에서 정한 시각에 실행하는 예약 실행과, 같은 요청으로 가상 사용자 수와 초당 요청 수를 측정하는 성능 실행도 있다.

데이터 파일의 CSV는 첫 행에 변수 이름을 두고, 그 뒤 각 행을 데이터 행으로 사용한다. JSON은 키-값 객체의 배열로 작성한다. 변수 이름은 대소문자를 구분한다.

요청 URL에는 {{orderId}}를, 테스트에는 pm.iterationData.get("expectedStatus")를 사용하면 행마다 다른 입력과 기대 결과로 같은 요청을 실행한다.

Postman CLI와 Newman

섹션 제목: “Postman CLI와 Newman”
항목 Postman CLI Newman
성격 Postman의 공식 서명된 명령줄 도구 Postman 컬렉션을 실행하는 오픈소스 명령줄 도구(Apache-2.0)
설치 npm install -g postman-cli npm install -g newman
실행 postman collection run <경로 또는 ID> newman run <컬렉션 파일> -e <환경 파일>
컬렉션 형식 v3 YAML 형식 포함 최신 형식 v2.1 JSON 형식만 실행함
리포터 cli(기본값), json, junit, html 내장 cli, json, junit, progress, emojitrain. HTML 리포터는 외부 패키지
그 밖의 기능 모니터 실행, 모의 서버 관리, API 거버넌스 검사(postman spec lint) OAuth 2.0 인증과 Package Library 스크립트를 지원하지 않음
유지 상태 현재 권장 도구 공식 문서 기준 더 이상 업데이트나 수정을 받지 않음. 스크립트와 CI 파이프라인을 Postman CLI로 교체하도록 안내함
  • Postman CLI는 ID로 실행한 컬렉션의 결과를 Postman에 업로드함. 결과를 보내려면 postman login, --postman-api-key 옵션, POSTMAN_API_KEY 환경 변수 중 하나로 인증함
  • 두 도구 모두 환경(-e), 데이터 파일(-d), 반복 횟수(-n), 첫 오류에서 중단(--bail) 옵션을 같은 형태로 제공함. Postman CLI는 Newman 옵션 대부분을 같은 문법으로 지원함. 폴더 실행은 Newman의 --folder <폴더>가 Postman CLI에서 -i <폴더>로 바뀜
  • 저장소에 있는 기존 컬렉션 파일은 postman collection migrate로 v3 YAML 형식으로 변환함. Postman v12 이후의 Native Git 워크플로는 이 형식이 필요함

모의 서버, 모니터, API 명세 가져오기

섹션 제목: “모의 서버, 모니터, API 명세 가져오기”
  • 모의 서버(mock server): 고정 URL에서 항상 응답하는 호스팅된 대역. 컬렉션으로 만들면 저장된 예시 중 요청과 가장 가까운 것을 매칭 알고리즘으로 골라 반환함. 백엔드가 준비되기 전에 API를 사용하는 쪽을 개발하거나, 팀원과 테스트, CI 파이프라인이 실제 백엔드 없이 호출하는 용도
  • 모니터(monitor): 컬렉션이나 API 명세의 요청을 Postman 클라우드에서 일정에 따라 자동 실행함. 테스트가 실패하면 알림을 받고, 결과에서 성능과 오류를 분석함. Postman CLI로 실행을 시작할 수 있고, 내부망 API는 러너를 사용하는 Private API Monitoring으로 실행함
  • 가져오기(import): 파일, 폴더, cURL 명령, 원문 텍스트, URL, 저장소(GitHub, Bitbucket, GitLab, Azure DevOps)에서 가져옴. OpenAPI 명세는 컬렉션으로 가져오거나 명세와 컬렉션을 함께 만들 수 있음. GraphQL 같은 형식은 명세로만 가져옴

QA에서 사용하는 방법

섹션 제목: “QA에서 사용하는 방법”
  • 컬렉션 구성: API 테스트 범위표(엔드포인트 x 점검 항목)를 폴더 구조로 옮김. 엔드포인트별 폴더 아래에 정상, 입력 검증, 인증, 인가 요청을 두면 폴더 목록으로 점검하지 않은 항목을 확인할 수 있음(API 테스트 기본의 테스트 계획)
  • 인가 테스트: 역할과 소유 관계가 다른 계정마다 환경을 따로 만들고, 같은 컬렉션을 환경만 바꿔 실행해 다른 사용자의 객체 접근이 차단되는지 확인함
  • 기대 결과: 상태 코드만 단언하지 않고 필수 키, 자료형, 금액·소유자 같은 값을 함께 단언함. 상태 코드만 확인하는 테스트의 문제는 API 테스트 기본의 흔한 실수 항목 참조
  • 회귀: 릴리즈마다 변경된 엔드포인트의 폴더를 우선 실행하고, 전체 컬렉션은 CI에서 정기적으로 실행함(회귀 테스트 범위 선정)
  • CI 연동: Postman CLI의 junit 리포터로 결과 파일을 만들어 파이프라인의 테스트 리포트로 게시함. 컬렉션과 환경 파일은 저장소에 두어 테스트 코드와 같이 버전을 관리함(GitHub Actions, Jenkins, Git 기본)
  • 결함 기록: Postman Console의 요청·응답 원문(인증 헤더는 마스킹)과 사용한 환경 이름, 데이터 행을 첨부함. 개발자가 다른 도구로 재현할 수 있도록 cURL 명령을 함께 남김(이슈 양식)
  • 모니터: 운영 환경에 거는 모니터는 조회 요청만 사용함. 상태 변경 메서드를 운영에 보내지 않는 기준은 API 테스트 기본의 운영 환경 주의 항목과 같음

선택 기준

  • 코드 작성 없이 요청을 탐색하고, 비개발 직군과 같은 워크스페이스에서 컬렉션을 공유하려면 GUI 도구(Postman, Insomnia, Bruno)가 맞음
  • 컬렉션을 클라우드에 두지 않고 Git 저장소에서 코드처럼 리뷰해야 하면 Bruno나 Insomnia의 Git 동기화를 검토함. Postman도 Postman CLI와 함께 사용하는 Native Git 워크플로를 제공하므로 같은 요구사항으로 비교함
  • API 테스트를 개발 언어의 테스트 스위트와 같은 저장소, 같은 리포트로 관리하려면 코드 기반 도구가 맞음. Java 백엔드는 REST Assured, 웹 E2E를 Playwright로 작성하는 팀은 UI 테스트 전 상태 준비와 브라우저 동작 뒤 서버 상태 확인까지 같은 도구로 처리할 수 있음(Playwright)
  • 모니터와 모의 서버를 별도 인프라 없이 쓰려면 Postman이 맞음. 일부 기능은 유료 플랜 대상이라 도입 전에 공식 요금제 문서를 확인함

주의할 점

섹션 제목: “주의할 점”
  • Newman은 v2.1 JSON 형식만 실행하므로 최신 Postman에서 만들거나 수정한 컬렉션을 실행하지 못할 수 있음. 새 파이프라인은 Postman CLI로 구성함
  • 공유 값은 Postman 클라우드에 동기화됨. 토큰, 비밀번호는 로컬 값이나 Vault에 두고, 저장소에 커밋하는 환경 파일에도 넣지 않음
  • 요청이 앞 요청의 응답 값(orderId 등)을 변수로 받아 이어지면 앞 요청 하나의 실패가 뒤 요청 전체의 실패로 이어짐. 실패 분석은 처음 실패한 요청부터 확인함
  • 변수 값 유지(Keep variable values)를 켜면 실행이 남긴 값이 다음 실행의 입력이 됨. 반복 실행 결과가 달라지면 이전 실행이 남긴 변수부터 확인함(Flaky 테스트 관리의 상태 공유)
  • 컬렉션·폴더 스크립트는 그 아래 모든 요청에서 요청 스크립트보다 먼저 실행됨. 특정 요청에만 필요한 처리를 상위 스크립트에 두면 같은 폴더의 모든 요청 결과에 영향을 줌
  • 응답 시간 단언은 Postman이 측정한 클라이언트 기준 값임. 서버 처리 시간과 구분해 기록함(API 테스트 기본)

관련 문서

기초와 용어API 테스트 기본화면을 거치지 않고 API에 직접 요청을 보내 응답 계약, 상태 코드, 서버 측 검증, 인가를 확인하는 테스트다. 화면 제약만으로는 확인할 수 없는 서버 동작이 대상이다.자동화테스트 자동화 기본테스트 자동화는 도구로 테스트를 실행하고 결과를 판정하는 활동이다. 이점과 한계, 테스트 피라미드, 테스트 용이성, 자동화 아키텍처(gTAA)와 프레임워크 계층, 케이스 자동화 방식 7가지, 도입 절차와 파이프라인 배치, 작성 원칙을 ISTQB CTAL-TAE 기준으로 설명한다.프로세스회귀 테스트 범위 선정변경 뒤 기존 기능이 의도하지 않게 실패하는지 확인하기 위해, 회귀 스위트에서 이번 회차에 수행할 TC를 선택하는 절차다(Regression Test Selection).도구PlaywrightMicrosoft가 유지하는 웹 브라우저 자동화 도구 Playwright와 테스트 러너 Playwright Test의 핵심 개념(브라우저 엔진, 컨텍스트 격리, 로케이터, 자동 대기, 웹 우선 단언, 픽스처, 프로젝트)과 설정, 인증 재사용, 네트워크 가로채기, 트레이스, 리포터, 시각 비교, API 테스트를 다룬다.
