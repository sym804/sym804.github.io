Jira

Atlassian의 작업 관리 도구 Jira Cloud의 작업 유형, 워크플로와 상태 전이, 필드와 해결(resolution), 우선순위, JQL, Scrum·Kanban 보드, 필터와 대시보드, 자동화 규칙을 정리하고 결함 관리에 연결하는 방법을 다룬다.

기본기난이도 중급최종 업데이트 2026-11-24

지라

Jira는 Atlassian이 개발하는 상용 작업 관리 도구다. Atlassian이 호스팅하는 Jira Cloud와 조직이 직접 설치해 운영하는 Jira Data Center가 있고, 같은 플랫폼 위에 서비스 데스크용 Jira Service Management가 있다. 소프트웨어 팀은 백로그, 스프린트, 결함을 한곳에서 관리하는 데 사용한다. 이 문서는 Jira Cloud 기준이다.

현재 Jira Cloud 문서는 이슈(issue)를 작업 항목(work item), 이슈 유형을 작업 유형(work type), 프로젝트를 스페이스(space)라고 부른다. Data Center 11.3 문서는 issue라는 이름을 그대로 사용한다. 이 문서는 Cloud 문서의 이름을 따른다.

핵심 개념

섹션 제목: “핵심 개념”
개념 뜻
스페이스 작업 항목을 담는 단위. 작업 항목 키는 SHOP-123처럼 대문자 두 자 이상의 스페이스 키, 하이픈, 번호로 구성함
작업 유형 소프트웨어 스페이스의 기본값은 Epic, Bug, Story, Task, Subtask
계층 기본 3단계(에픽, 표준 작업 항목, 하위 작업). Premium과 Enterprise는 단계를 추가할 수 있음
상태와 상태 카테고리 모든 상태는 To do(회색), In progress(파랑), Done(초록) 중 한 카테고리에 속함. 목록, 보드, 보고서가 카테고리로 진행 여부를 판단함
해결(resolution) 작업 항목을 닫은 사유. 값이 있으면 생명주기가 끝난 것으로, 비어 있으면 미해결(Unresolved)로 간주함. 기본값은 Done, Won’t do, Duplicate, Cannot reproduce
우선순위 기본값은 Highest, High, Medium, Low, Lowest. 관리자가 이름과 의미를 변경할 수 있음

스페이스에는 두 종류가 있다.

  • 팀 관리형(team-managed): 팀이 직접 설정하고 유지함. 설정을 다른 스페이스와 공유하지 않음
  • 회사 관리형(company-managed): Jira 관리자가 설정하고 유지함. 스킴과 화면을 여러 스페이스가 공유하므로 관리자가 스킴을 변경하면 그 스킴을 사용하는 모든 스페이스가 함께 변경됨

주요 기능

섹션 제목: “주요 기능”

워크플로와 상태 전이

섹션 제목: “워크플로와 상태 전이”

워크플로는 작업 항목이 거치는 상태와 상태 사이의 전이(transition)로 구성된다. 두 상태 사이에 전이가 있어야 이동할 수 있고, 전이는 한 방향이라 되돌리려면 반대 방향 전이를 따로 만든다.

  • 조건(condition): 전이를 사용자에게 표시할지 정함. 예: 종결 전이를 QA 그룹에만 표시함
  • 검증(validator): 전이 전에 입력을 확인함. 예: 수정 버전이 비어 있으면 수정 완료로 이동하지 못하게 함
  • 사후 함수(post function): 전이 뒤에 필드를 설정함. 예: 종결 전이에서 해결 값을 설정하고, 재개 전이에서 해결 값을 지움
  • 전이 화면(transition screen): 전이할 때 입력받을 필드를 표시함
  • 워크플로 스킴: 워크플로를 스페이스와 작업 유형에 연결함. 여러 스페이스가 사용하는 활성 워크플로를 편집하면 그 스페이스 모두에 반영되고, 변경은 게시(publish)해야 적용됨
  • 기본 제공 워크플로는 직접 편집할 수 없어 복사한 뒤 편집함

필드와 링크

섹션 제목: “필드와 링크”

결함 관리에 자주 사용하는 시스템 필드는 요약, 설명, 환경(Environment), 영향 버전(Affects version), 수정 버전(Fix version), 구성 요소(Component), 레이블(Labels), 우선순위, 해결이다. 기본 필드에 심각도는 없어 관리자가 사용자 정의 필드로 추가한다.

  • 사용자 정의 필드는 만들 때 정한 필드 유형을 나중에 변경할 수 없음
  • 한 값을 고르는 필드는 팀 관리형에서 Dropdown, 회사 관리형에서 select list (single choice)라고 부름
  • 작업 항목 링크의 기본 유형에는 blocks, clones, duplicates, causes, relates to 등이 있고 관리자가 유형을 구성함. 확인 테스트 중 발견한 새 결함은 원 결함에 링크함

JQL

섹션 제목: “JQL”

JQL(Jira Query Language)은 고급 검색에 사용하는 질의 언어다. 절(clause)은 필드, 연산자, 값(또는 함수)으로 구성하고 AND, OR, NOT, ORDER BY 키워드로 잇는다. 결합 우선순위는 괄호, 비교 연산자(=, IN, ~ 등), NOT, AND, OR 순이라 AND가 OR보다 먼저 묶인다. 의도한 묶음은 괄호로 명시한다.

용도 JQL
미해결 결함을 우선순위순으로 project = SHOP AND type = Bug AND resolution = Unresolved ORDER BY priority DESC, created ASC
특정 버전에서 발견되었으나 수정 버전이 없는 결함 type = Bug AND affectedVersion = "2.3.0" AND fixVersion is EMPTY
진행 중인 스프린트의 결함 type = Bug AND sprint in openSprints()
이번 주에 재개된 결함 type = Bug AND status CHANGED TO "Reopened" AFTER startOfWeek()
한 번이라도 수정 완료를 거친 결함 type = Bug AND status WAS "Resolved"
최근 3일 안에 등록된 결함 type = Bug AND created > startOfDay("-3d")
완료 카테고리인데 해결 값이 없는 항목 statusCategory = Done AND resolution is EMPTY
  • WAS, WAS IN, CHANGED 연산자는 담당자, 수정 버전, 우선순위, 보고자, 해결, 상태 필드에만 사용함
  • 버전 필드의 비교 연산자(>, <=)는 숫자나 문자 순서가 아니라 관리자가 정한 버전 순서를 따름
  • 서비스 팀 관리형 스페이스에는 해결 필드가 없어 statusCategory = Done으로 완료 여부를 판단함
  • OR, NOT, EMPTY, 비교 연산자를 사용한 질의는 기본 검색 화면으로 되돌려 표시할 수 없음

보드

섹션 제목: “보드”

보드는 작업 항목을 카드로 열에 배치한다. 각 열은 하나 이상의 상태에 매핑한다.

구분 Scrum 보드 Kanban 보드
계획 단위 스프린트. 백로그에서 계획함 스프린트 없음. 작업 흐름을 계속 관리함
기본 열 To Do, In Progress, Done Backlog, Selected for Development, In Progress, Done
열 제약 사용 가능 최소·최대 개수 제약을 흐름 관리의 핵심으로 사용함
  • 매핑하지 않은 상태의 작업 항목은 보드와 백로그에 표시되지 않음
  • 가장 오른쪽 열의 작업 항목만 완료로 간주함. Blocked나 Canceled처럼 스프린트를 닫을 때 완료로 보내야 하는 상태는 그 열에 매핑함
  • 열 제약을 넘으면 열 머리글이 빨간색(최대 초과)이나 노란색(최소 미달)으로 표시되고, 빠른 필터로 숨긴 항목도 개수에 포함함

필터와 대시보드

섹션 제목: “필터와 대시보드”

검색 결과를 필터로 저장하면 다시 사용하고, 공유하고, 정한 일정에 이메일로 받을 수 있다. 보드와 대시보드 가젯도 필터를 입력으로 사용한다.

  • Filter Results: 필터 결과 목록
  • Pie Chart: 상태, 우선순위, 담당자 같은 통계 기준별 비율
  • Two Dimensional Filter Statistics: 두 기준(예: 구성 요소와 심각도)의 교차 표
  • Created vs Resolved: 기간별 등록 건수와 해결 건수 비교
  • Average Age: 미해결 상태로 남아 있는 평균 일수

자동화 규칙

섹션 제목: “자동화 규칙”

규칙은 트리거로 시작하고, 조건으로 대상을 거르고, 액션을 실행한다. 분기(branch)를 사용하면 관련 작업 항목(하위 작업, 같은 버전의 항목 등)에 액션을 반복 적용한다.

  • 트리거 예: Work item created, Work item transitioned, Field value changed, Scheduled(주기 실행, JQL로 대상 지정), Incoming webhook
  • 예: Work item transitioned로 결함이 Reopened가 되면 마지막 개발 담당자에게 다시 할당하고 코멘트를 남김
  • 예: Scheduled 트리거에 statusCategory = Done AND resolution is EMPTY를 지정해 매일 담당자에게 알림

커밋과 연결

섹션 제목: “커밋과 연결”

GitHub, Bitbucket 같은 저장소를 연결하면 스마트 커밋(Smart Commits)으로 커밋 메시지에서 작업 항목을 조작할 수 있다.

  • 커미터 이메일이 해당 권한을 가진 Jira 사용자 한 명과 정확히 일치해야 함. #time은 관리자가 시간 추적을 켜야 동작함
  • 전이 명령은 전이 이름의 첫 공백 앞부분만 인식함. 위 예의 #resolve는 이름이 Resolve로 시작하는 전이를 가리킴. 이름이 모호하면 #finish-work처럼 하이픈으로 이음
  • 전이에 코멘트 외의 필수 필드가 있으면 전이가 알림 없이 실패함. 워크플로에 없는 전이(예: To Do에서 바로 Done)도 실패함

QA에서 사용하는 방법

섹션 제목: “QA에서 사용하는 방법”

결함 생명주기

  • 결함 생명주기의 상태를 Jira 상태에 대응시킨 표를 팀 문서에 둠. 예: 등록=Open, 수정 완료=Resolved, 종결=Closed, 재개=Reopened
  • 개발자의 전이(스마트 커밋 포함)는 수정 완료까지만 허용하고, 종결 전이는 조건으로 QA 그룹에만 표시함
  • 결함 아님, 재현 불가, 중복은 상태를 늘리지 않고 해결 값(Won’t do, Cannot reproduce, Duplicate)으로 구분할 수 있음. 근거는 전이 화면의 필수 코멘트로 받음
  • 재개 전이에는 해결 값을 지우는 사후 함수를 둠. 지우지 않으면 재개된 결함이 해결된 결함으로 집계됨

심각도와 우선순위

  • 우선순위(수정 순서)는 기본 필드를 사용하고, 심각도(영향 크기)는 사용자 정의 Dropdown 필드로 추가함. 두 값을 한 필드에 섞지 않음(심각도 기준)
  • 심각도 옵션 이름은 이슈 양식, 대시보드 가젯, 집계 스크립트가 같은 값을 사용하도록 글자까지 맞춤

이슈 양식과 버전

  • 이슈 양식의 발견 블록 필드는 생성 화면에, 종결 블록 필드(원인, 수정 내용, 재발 방지)는 종결 전이 화면에 배치함
  • 영향 버전은 발생 버전, 수정 버전은 수정 버전 칸으로 사용함. 릴리즈 단위 회귀 범위를 수정 버전 필터로 확인함

보고와 이슈 로그

  • 미해결 결함 추이는 Created vs Resolved 가젯으로, 구성 요소별 심각도 분포는 Two Dimensional Filter Statistics로 보고함
  • 이슈 로그를 따로 운영하면 작업 항목 키(SHOP-123)를 로그의 트래커 칸에 기록함(이슈 로그와 트래커의 조인 키)

섹션 제목: “비슷한 도구와 선택 기준”
항목 Jira Linear GitHub Issues
제공 형태 Cloud, Data Center SaaS GitHub 저장소 기능

선택 기준

  • 전이마다 권한, 필수 입력, 자동 필드 설정을 강제해야 하거나 여러 팀이 같은 절차를 따라야 하면 Jira의 회사 관리형 워크플로가 맞음
  • 변경 이력 기반 집계(재개 횟수, 특정 상태를 거친 결함)를 질의 하나로 뽑아야 하면 JQL의 WAS, CHANGED가 필요함
  • 설정 부담을 줄이고 정해진 흐름 안에서 빠르게 운영하려면 Linear, 코드와 이슈를 한 저장소에서 관리하는 작은 팀은 GitHub Issues가 단순함
  • 설치형 운영이 필요하면 Jira Data Center를 검토함. Cloud와 Data Center는 문서와 기능이 다르므로 사용하는 배포판의 문서를 확인함

주의할 점

섹션 제목: “주의할 점”
  • 완료 카테고리 상태로 옮겨도 해결 값이 비어 있으면 미해결로 집계되어 Created vs Resolved 같은 보고서와 Open Issues 필터에 계속 남음. 종결 전이에 해결 값을 설정하는 사후 함수나 전이 화면을 둠
  • 해결 필드에 “Unresolved” 같은 자리표시 값을 추가하면 Jira는 값이 있다는 이유로 해결된 것으로 판단함
  • API로 실행한 전이는 전이 화면을 거치지 않음. 필수 입력은 화면이 아니라 검증으로 강제함
  • 회사 관리형 스킴을 변경하면 같은 스킴을 사용하는 다른 스페이스도 함께 변경됨. 변경 전에 사용 중인 스페이스 목록을 확인함
  • 보드의 열 매핑에서 빠진 상태가 있으면 그 상태의 결함이 보드에서 보이지 않음. 새 상태를 추가하면 보드 매핑도 함께 확인함
  • 스마트 커밋의 전이 실패는 알림이 없을 수 있음. 커밋 뒤 작업 항목의 상태를 확인함
