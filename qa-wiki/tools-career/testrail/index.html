TestRail

웹 기반 TC 관리 도구 TestRail의 프로젝트 유형(단일 스위트, 기준선, 다중 스위트), 섹션, 테스트 케이스 템플릿, 테스트 런과 테스트 플랜, 구성, 마일스톤, 결과 상태, 리포트, API, TestRail CLI로 JUnit XML 결과를 올리는 방법과 Xray, Zephyr, Qase와의 비교.

기본기난이도 중급최종 업데이트 2026-11-24

TestRail은 Gurock Software GmbH가 개발하는 상용 웹 기반 TC 관리 도구다. 테스트 케이스를 작성하고 섹션과 스위트로 정리한 뒤, 테스트 런을 만들어 결과를 기록하고 마일스톤과 리포트로 진행 상황을 추적한다. 배포 방식은 TestRail이 호스팅하는 Cloud와 자체 인프라(Windows, Linux, Docker)에 설치하는 Server 두 가지다. Cloud는 새 기능(TestRail AI 등)을 먼저 받고, Server는 AD/LDAP 인증과 사용자 정의 리포트·결함 플러그인 같은 Server 전용 옵션을 사용할 수 있다.

결과 값 집계, TC ID, 회차 이월, 가져오기, 자동화 계정 같은 운영 기준은 도구와 무관하게 TC 관리 도구 운영 기준에 정리되어 있다. 이 문서는 TestRail 자체의 구조와 기능을 다룬다.

핵심 개념

섹션 제목: “핵심 개념”
개념 뜻
프로젝트 최상위 단위. 테스트 런, 결과, 마일스톤 등 다른 데이터는 모두 특정 프로젝트에 속함. 실제 소프트웨어 프로젝트마다 하나씩 만드는 것을 권장함
테스트 스위트(저장소) 테스트 케이스를 담는 저장소. 프로젝트 유형에 따라 하나 또는 여러 개
섹션 스위트 안에서 케이스를 묶는 폴더. 하위 섹션을 둘 수 있음. 보통 모듈이나 화면 단위로 나눔
테스트 케이스 사전조건, 테스트 단계, 기대 결과로 구성됨. 한 사람이 짧은 시간에 확인할 수 있는 크기가 적당함
테스트 런 케이스를 실제로 수행하는 회차. 같은 스위트로 여러 런을 동시에 만들 수 있음
테스트 런에 포함된 개별 케이스. 결과는 테스트에 기록됨
테스트 플랜 여러 테스트 런을 한 번에 만들고 묶어 관리하는 단위
구성(Configuration) 브라우저, OS, 기기처럼 같은 케이스를 반복 수행할 환경 값
마일스톤 릴리즈, 내부 테스트 버전, 베타처럼 추적할 시점. 런과 플랜을 연결함

스위트는 “무엇을 테스트할지”를 정한 계획이고, 런은 그 계획을 특정 시점에 수행한 기록이다. 릴리즈마다 같은 스위트로 새 런을 만들고, OS별로 같은 스위트의 런을 여러 개 동시에 열어 둘 수 있다.

프로젝트 유형

섹션 제목: “프로젝트 유형”

케이스를 저장하는 구조와 한 런에 담을 수 있는 범위가 유형마다 다르다.

유형 구조 맞는 경우
단일 저장소 Single Repository. 스위트 하나에 모든 케이스를 두고 섹션으로 정리함. 한 런에서 전체를 E2E로 수행할 수 있음 동시에 관리하는 버전이 적은 대부분의 프로젝트. 버전별 수행은 마일스톤과 테스트 플랜으로 나눔
기준선 지원 단일 저장소 Single Repository with Baseline Support. 마스터 케이스 세트를 기준선(baseline)으로 복사해 분기함. 기준선의 수정은 마스터에 반영되지 않음 여러 제품 버전을 병렬로 테스트해야 하는 경우
다중 스위트 Multiple Test Suites. 기능 영역이나 모듈별로 스위트를 나누고, 스위트마다 섹션을 둠 테스트 영역을 엄격히 분리해야 하는 팀. 한 런에 둘 이상의 스위트 케이스를 넣을 수 없음
  • 단일 저장소에서 다중 스위트나 기준선 유형으로 바꾸는 것은 유형 변경만으로 끝남. 기존 스위트가 첫 번째 스위트가 됨
  • 다중 스위트에서 단일 저장소로 되돌리려면 빈 스위트를 만들고, 진행 중인 런과 플랜을 닫고, 케이스를 복사 또는 이동한 뒤 기존 스위트를 삭제하고 유형을 변경해야 함
  • 이동(move)은 원본을 사용하는 닫히지 않은 런의 결과를 삭제함. 이력을 남기려면 복사(copy)를 사용함
  • 스위트를 삭제하면 그 스위트의 케이스, 진행 중인 런, 결과가 영구 삭제됨. 결과를 남기려면 런을 먼저 닫음

테스트 케이스 템플릿

섹션 제목: “테스트 케이스 템플릿”

템플릿은 케이스 입력 화면의 필드 구성을 정한다. 기본 제공 템플릿은 다섯 가지다.

템플릿 구성
Test Case (Text) 사전조건(Preconditions), 단계(Steps), 기대 결과(Expected Result)를 각각 자유 텍스트로 작성함
Test Case (Steps) 단계마다 설명과 기대 결과를 따로 두고, 단계별 결과 상태와 결함·요구사항 링크를 기록함. 공유 단계(shared steps)를 가져올 수 있음
Exploratory Session 미션(Mission)과 목표(Goals)를 적는 탐색적 테스트용 템플릿
Behaviour Driven Development Gherkin 문법(Feature, Rule, Scenario, Given, When, Then, Examples)으로 시나리오를 작성함. 시나리오별 결과를 기록하고 .feature 파일로 내보내거나 가져올 수 있음
AI Evaluation AI 기능처럼 통과/실패로 나누기 어려운 출력을 0~5점 품질 평가(Quality Rating)로 기록함
  • 관리자는 Admin > Customizations에서 템플릿을 추가하거나 수정하고, 기본 템플릿과 적용 프로젝트를 지정함
  • Text와 AI Evaluation은 수정만 가능하고, BDD는 수정과 삭제가 모두 불가능함. BDD에 필드가 필요하면 사용자 정의 케이스 필드를 BDD 템플릿에 적용함
  • 탐색적 세션의 미션과 목표 작성은 탐색적 테스트의 차터와 같은 역할을 함

테스트 런, 테스트 플랜, 구성, 마일스톤

섹션 제목: “테스트 런, 테스트 플랜, 구성, 마일스톤”

테스트 런을 만들 때 스위트의 모든 케이스, 직접 선택한 케이스, 케이스 필드 값 기준의 동적 필터 중 하나로 범위를 정한다. 테스트는 담당자에게 배정되어 각자의 할 일 목록에 표시된다.

  • 수행이 끝난 런은 닫을 수 있음. 닫힌 런의 테스트는 수정할 수 없고, 이후 원본 케이스를 수정해도 닫힌 런에는 반영되지 않음
  • 테스트 플랜은 여러 런을 한 번에 만들고, 다중 스위트 프로젝트에서 스위트별 런을 묶을 때 사용함. 진행 중인 플랜을 같은 구성으로 다시 실행(Rerun Test Plan)할 수 있음
  • 구성은 그룹(예: 브라우저)과 값(예: Chrome, Firefox)으로 정의함. 플랜에서 런에 구성을 선택하면 구성 조합마다 런이 생성됨. 구성은 프로젝트별로 관리함
  • 마일스톤에 런과 플랜을 연결하면 마일스톤 단위로 진행률과 결과를 확인할 수 있음. 마일스톤 안에 하위 마일스톤을 두어 스프린트나 하위 릴리즈를 나눔
  • 마일스톤은 시작일이 지나기 전까지 Upcoming, 시작 후 Open 상태임. 플랜은 종료일이 지나도 자동으로 완료되지 않으므로 직접 완료 처리함

결과 상태

섹션 제목: “결과 상태”

기본 상태는 Untested, Passed, Failed, Retest, Blocked 다섯 가지다. 새 테스트는 Untested로 시작하고, 결과를 한 번 기록하면 다시 Untested로 돌아갈 수 없다. Retest는 수정 후 재수행이 필요한 테스트에, Blocked는 외부 의존성(먼저 수정되어야 하는 결함 등) 때문에 수행할 수 없는 테스트에 사용한다.

  • 관리자는 Admin > Customizations > Result Statuses에서 기본 상태의 이름과 색을 바꾸고, 사용자 정의 상태를 최대 7개 추가함(전체 12개)
  • 사용자 정의 상태마다 최종(final) 상태인지 지정함. 최종 상태로 지정한 값만 런, 플랜, 마일스톤 통계에 집계됨. Untested는 최종 상태가 아님
  • 위키 표기(PASS, FAIL, BLOCK, N/A, N/R)와 대응시키려면 N/A에 해당하는 사용자 정의 상태를 추가하고, 미수행(N/R)은 Untested로 둠. 결과 값 정의를 맞추는 기준은 TC 관리 도구 운영 기준에 있음

리포트

섹션 제목: “리포트”

프로젝트의 Reports 메뉴에서 즉시 생성하거나 일정을 지정해 정기적으로 생성한다. 여러 프로젝트를 합친 리포트(Cross-Project)는 Enterprise 플랜에서만 제공된다.

분류 리포트 예 용도
Cases Activity Summary, Coverage for References, Property Distribution, Status Tops 케이스 작성 진행, 참조(요구사항) 대비 커버리지, 실패나 차단이 잦은 케이스 확인
Defects Summary, Summary for Cases, Summary for References 마일스톤·플랜·런에서 발견된 결함과 원래 테스트의 최신 상태 대조
Results Comparison for Cases, Comparison for References, Property Distribution 여러 런과 구성의 결과 비교, 요구사항별 결과 추적 매트릭스
Summary Milestone, Plan, Project, Run 마일스톤, 플랜, 프로젝트, 런 단위 요약
Users Workload summary 담당자별 배정 현황

API

섹션 제목: “API”

요청과 응답은 HTTP와 JSON(UTF-8)을 사용한다. Admin > Site Settings > API에서 활성화한다. 읽기는 GET, 쓰기는 POST이며 요청 경로는 index.php?/api/v2/<메서드>/<인자> 형식이다.

  • 인증은 HTTP 기본 인증이며, 사용자 이름(보통 이메일)과 비밀번호 또는 API 키를 사용함. API 키는 My Settings > API Keys에서 용도별로 여러 개 만들고 개별 삭제할 수 있음
  • Cloud는 요청 수 제한이 있고, 초과하면 429와 대기 시간(Retry-After)을 반환함. Server 설치에는 기본 제한이 없음
  • 결과를 많이 올릴 때는 add_results_for_cases 같은 일괄 엔드포인트를 사용함
  • Cloud의 목록 조회는 페이지 단위이며 기본 250건, limit으로 최대 500건까지 받음(500건 상한과 커서 방식은 TestRail 10.10 이상). Server는 Admin > Site Settings > API의 페이지 처리 설정이 꺼져 있으면 전체 결과를 한 응답으로 반환하고, 켜져 있으면 기본 250건임

CI 결과 업로드(TestRail CLI)

섹션 제목: “CI 결과 업로드(TestRail CLI)”

TestRail CLI(trcli)는 JUnit 형식 XML 결과를 파싱해 TestRail에 올리는 오픈소스 명령줄 도구다(Mozilla Public License 2.0, Python 패키지). JUnit XML을 출력하는 프레임워크(Playwright, Cypress, pytest, JUnit, TestNG 등)는 모두 사용할 수 있다.

JUnit 요소는 <testsuites>가 스위트, <testsuite>가 섹션, <testcase>가 케이스에 대응한다. 결과를 TestRail 케이스와 맞추는 방식(--case-matcher)은 세 가지다.

방식 매칭 기준 접근
auto 케이스의 automation_id 필드와 classname.name 코드 우선(code-first). 매칭되지 않는 케이스를 자동 생성할 수 있음
name 테스트 이름 안의 케이스 ID(예: [C123] 로그인 성공) 명세 우선(specification-first)
property <property name="test_id" value="C123"/> 명세 우선. 쉼표로 여러 케이스에 같은 결과를 기록할 수 있음
  • -y는 매칭되지 않은 케이스를 자동 생성하고, -n은 생성하지 않음. 명세 우선 방식에서는 -n으로 의도하지 않은 케이스 생성을 막음
  • --run-id는 기존 런에 결과를 추가하고, --plan-id와 --config-ids는 플랜의 구성별 런에 결과를 기록함
  • auto 방식에서 자동화 테스트 이름을 바꾸면 automation_id가 달라져 새 케이스가 생성됨
  • 다중 스위트 프로젝트는 --suite-id를 지정해야 함. 지정하지 않으면 CLI가 스위트를 찾거나 새로 만듦

QA에서 사용하는 방법

섹션 제목: “QA에서 사용하는 방법”
  • 회귀 스위트를 섹션과 케이스 필드(우선순위, 자동화 여부)로 정리하고, 동적 필터로 회차별 회귀 범위를 런에 담음(회귀 테스트 범위 선정)
  • 릴리즈마다 마일스톤을 만들고 그 아래 런과 플랜을 연결해, 릴리즈 판단 시 마일스톤 요약 리포트를 근거로 사용함
  • 브라우저·OS 조합은 케이스를 복제하지 않고 구성으로 나눔. Results - Comparison for Cases 리포트로 구성별 결과를 비교함
  • FAIL 결과에서 결함을 연결하고, Defects 리포트로 결함과 원래 테스트의 최신 상태를 대조함(결함 생명주기)
  • CI는 Playwright 등의 JUnit XML을 TestRail CLI로 올림. 테스트가 실패해도 업로드 단계가 실행되도록 구성함(GitHub Actions의 if: ${{ !cancelled() }}, Jenkins의 post { always })
  • 업로드용 계정과 API 키는 결과 기록에 필요한 권한만 부여하고 CI 시크릿에 저장함(TC 관리 도구 운영 기준)

비슷한 도구와 선택 기준

섹션 제목: “비슷한 도구와 선택 기준”
도구 형태 케이스 저장 수행 단위 자동화 결과 연동
TestRail 독립 웹 애플리케이션(Cloud, Server) 스위트와 섹션 테스트 런, 테스트 플랜, 구성 REST API, TestRail CLI(JUnit XML)
Xray Jira 앱 Test, Precondition, Test Set이 Jira 작업 항목 유형. Test Repository 폴더로 정리 Test Execution(작업 항목) 안의 Test Run(내부 엔터티), Test Plan REST API로 JUnit, TestNG, NUnit, Robot Framework, Cucumber 등 결과 가져오기
Zephyr SmartBear의 Jira 앱(Zephyr Squad와 Zephyr Scale을 통합) Jira 스페이스의 테스트 라이브러리와 폴더 테스트 사이클, 테스트 플랜(여러 사이클 묶음) CI/CD와 자동화 프레임워크 결과 연동
Qase 독립 웹 애플리케이션 프로젝트별 저장소와 중첩 스위트 테스트 런, 선택 사항인 테스트 플랜 REST API, 프레임워크별 리포터(qase-playwright, qase-pytest 등)

선택 기준

  • 요구사항과 결함을 Jira에서 관리하고 테스트 산출물도 Jira 이슈 검색, 워크플로, 권한으로 다뤄야 하면 Xray나 Zephyr가 맞음. Xray는 테스트 산출물이 Jira 작업 항목이라 Jira 워크플로와 사용자 정의 필드를 그대로 적용함
  • 이슈 트래커와 TC 저장소를 분리하거나 Jira 밖에서 여러 트래커와 연동해야 하면 TestRail이나 Qase가 맞음
  • 같은 케이스를 여러 환경에서 반복하는 비중이 크면 구성 모델을 확인함. TestRail은 구성 조합별로 런을 생성하고, Zephyr는 테스트 환경을 실행 결과의 속성으로 기록하고, Qase는 런에 환경과 구성을 지정함
  • 자동화 결과 연동은 사용하는 프레임워크의 출력 형식(JUnit XML 등)과 각 도구의 가져오기 방식(CLI, REST, 전용 리포터)을 기준으로 시험 프로젝트에서 먼저 확인함
  • 사내 설치가 필요하면 Server 또는 Data Center 제공 여부와 기능 차이를 확인함. TestRail은 Cloud와 Server의 기능 차이를 버전별 표로 공개함

주의할 점

섹션 제목: “주의할 점”
  • 다중 스위트 프로젝트는 스위트를 넘는 런을 만들 수 없어, 전체 회귀를 하나의 런으로 보려면 테스트 플랜을 사용해야 함
  • 결과를 기록한 테스트는 Untested로 되돌릴 수 없음. 수행하지 않은 테스트에 결과를 미리 입력하지 않음
  • 사용자 정의 상태를 최종 상태로 지정하지 않으면 통계에 포함되지 않음. 합격률 정의와 함께 어떤 상태가 집계되는지 문서로 남김
  • 케이스를 다른 스위트나 프로젝트로 이동하면 닫히지 않은 런의 결과가 삭제됨. 이동 전에 런을 닫음
  • TestRail CLI -y는 매칭되지 않은 결과마다 새 케이스를 생성함. 명세 우선 운영에서 CI에 -y를 두면 케이스 ID 오타나 누락이 중복 케이스로 이어짐
  • 자동 생성 케이스와 수동 케이스가 같은 섹션에 섞이면 리뷰 범위가 불분명해짐. --section-id로 자동 생성 섹션이 만들어질 상위 섹션을 지정함

관련 문서

도구TC 관리 도구 운영 기준TC 관리 도구(TCMS)를 운영할 때 결과 집계, TC ID, 회차 이월, 동시 편집, 가져오기, 자동화 계정에서 확인할 기준. 결과 값 체계와 합격률 정의는 도구별 방식을 비교하고 운영 예를 둔다. 도구를 새로 고를 때 확인 항목으로도 사용한다.프로세스TC 작성 원칙처음 보는 사람이 따라 할 수 있고 수행 직후 통과와 실패를 판정할 수 있는 테스트 케이스의 작성 기준. TC 형식(단계형, BDD 시나리오, 체크리스트, 탐색적 테스트 차터)의 선택 기준, 구성 요소별 작성법, 리뷰 점검 항목을 다룬다.프로세스회귀 테스트 범위 선정변경 뒤 기존 기능이 의도하지 않게 실패하는지 확인하기 위해, 회귀 스위트에서 이번 회차에 수행할 TC를 선택하는 절차다(Regression Test Selection).프로세스결함 생명주기결함이 등록된 시점부터 종결될 때까지 거치는 상태와, 상태 사이에 허용되는 전이를 정한 규칙이다(Defect Lifecycle).
