GitHub Actions

GitHub에 내장된 CI/CD 플랫폼 GitHub Actions의 워크플로, 이벤트, 잡, 스텝, 액션, 러너(GitHub 호스팅, 자체 호스팅), 매트릭스, 캐시, 아티팩트, 시크릿과 GITHUB_TOKEN 권한, concurrency, 재사용 워크플로, 필수 상태 검사와 Playwright 테스트 실행 예시, Jenkins, GitLab CI/CD와의 비교.

기본기난이도 중급최종 업데이트 2026-11-24

GitHub Actions는 GitHub가 제공하는 CI/CD 플랫폼이다. 저장소의 .github/workflows 디렉터리에 YAML 파일로 워크플로를 정의하면, 풀 리퀘스트 생성이나 푸시 같은 이벤트가 발생할 때 GitHub 호스팅 가상 머신(Linux, Windows, macOS) 또는 직접 운영하는 자체 호스팅 러너에서 빌드와 테스트를 실행한다. 이슈에 라벨을 붙이는 것처럼 CI 외의 저장소 자동화에도 사용한다.

QA에서는 풀 리퀘스트마다 자동화 테스트를 실행하고, 실패 증거(리포트, 스크린샷, 트레이스)를 아티팩트로 보관하고, 테스트 결과를 필수 상태 검사로 지정해 실패한 변경이 병합되지 않게 하는 데 사용한다.

핵심 개념

섹션 제목: “핵심 개념”
개념 뜻
워크플로(Workflow) 하나 이상의 잡을 실행하는 자동화 프로세스. 저장소에 여러 개를 둘 수 있음
이벤트(Event) 워크플로 실행을 시작하는 활동. 푸시, 풀 리퀘스트, 일정, 수동 실행, REST API 호출 등
잡(Job) 같은 러너에서 실행되는 스텝의 묶음. 기본적으로 잡끼리는 의존 관계 없이 병렬 실행됨
스텝(Step) 셸 스크립트 하나 또는 액션 하나. 같은 잡의 스텝은 순서대로 실행되고 파일 시스템을 공유함
액션(Action) 저장소 체크아웃, 도구 설치처럼 반복되는 작업을 묶은 재사용 단위. 직접 만들거나 GitHub Marketplace에서 가져옴
러너(Runner) 워크플로의 잡을 실행하는 서버. 러너 하나는 한 번에 잡 하나를 실행함
워크플로 실행(Workflow run) 워크플로가 한 번 실행된 기록. 커밋, 이벤트, 잡별 로그와 결과가 남음

주요 기능

섹션 제목: “주요 기능”

이벤트와 실행 조건

섹션 제목: “이벤트와 실행 조건”
  • push, pull_request에는 branches, paths 필터로 실행 범위를 좁힘
  • pull_request 실행의 GITHUB_SHA는 풀 리퀘스트 병합 브랜치의 마지막 병합 커밋임. 풀 리퀘스트 head 브랜치의 마지막 커밋은 github.event.pull_request.head.sha로 얻음
  • schedule은 POSIX cron 문법이며 기본 시간대는 UTC이고 timezone으로 지정할 수 있음. 최소 간격은 5분이고, 기본 브랜치의 최신 커밋에서만 실행됨
  • schedule은 부하가 많은 시간대(매시 정각 등)에 지연되거나 대기 중인 잡이 취소될 수 있음. 공개 저장소에서 60일간 활동이 없으면 일정 워크플로가 자동으로 비활성화됨
  • workflow_dispatch는 화면이나 API로 수동 실행하고, workflow_call은 다른 워크플로에서 호출함
  • 잡 사이 순서는 needs, 실행 여부는 if로 정함. timeout-minutes의 기본값은 360분임

러너

섹션 제목: “러너”
구분 특징
GitHub 호스팅 러너 잡마다 새 가상 머신으로 시작함(단일 CPU 러너는 공유 VM의 컨테이너). 이미지와 설치 도구 목록은 actions/runner-images 저장소에서 관리되며 매주 갱신됨. 유지보수와 업그레이드는 GitHub가 맡음
자체 호스팅 러너 직접 배포하고 관리하는 머신(물리, 가상, 컨테이너, 사내, 클라우드). 하드웨어, OS, 도구를 자유롭게 구성함. OS와 소프트웨어 업데이트는 운영자 책임이고, 잡마다 깨끗한 환경이 보장되지 않음
  • runs-on: ubuntu-latest처럼 -latest 레이블은 GA된 최신 OS 이미지를 가리키며, 새 OS로 바뀔 때는 1~2개월에 걸쳐 단계적으로 전환됨. ubuntu-24.04처럼 버전 레이블을 지정하면 전환 영향을 받지 않음
  • runner-images 공지(#14748)에 따르면 ubuntu-latest는 2026-10-19부터 2026-11-19까지 Ubuntu 24.04에서 Ubuntu 26.04로 전환됨. 26.04 이미지는 기본 Java가 25로 바뀌는 등 설치 도구 버전이 다름
  • 워크플로 로그의 Set up job > Runner Image에서 실제로 사용한 이미지 버전과 설치 도구 목록을 확인함

매트릭스

섹션 제목: “매트릭스”

strategy.matrix는 변수 조합마다 같은 잡을 생성한다. 워크플로 실행 하나에서 최대 256개 잡까지 만들 수 있다.

  • include로 조합을 추가하거나 기존 조합에 값을 더하고, exclude로 특정 조합을 제외함
  • fail-fast의 기본값은 true이며, 매트릭스의 잡 하나가 실패하면 진행 중이거나 대기 중인 나머지 잡이 취소됨. 환경별 결과를 모두 받으려면 false로 둠
  • continue-on-error는 잡 단위로 적용되어, 실험 중인 조합이 실패해도 나머지 잡에 영향을 주지 않게 함
  • max-parallel로 동시에 실행할 잡 수를 제한함

캐시와 아티팩트

섹션 제목: “캐시와 아티팩트”
구분 용도 동작
캐시(actions/cache, setup-node의 cache 입력 등) 실행 사이에 자주 바뀌지 않는 의존성이나 중간 산출물을 재사용함 key가 정확히 일치하면 복원(cache hit). 없으면 restore-keys로 부분 일치를 찾고, 잡이 성공하면 새 캐시를 저장함. 기존 캐시 내용은 변경할 수 없음
아티팩트(actions/upload-artifact, download-artifact) 잡이 만든 파일을 실행이 끝난 뒤 확인하거나 잡 사이에 전달함 테스트 결과, 스크린샷, 로그, 커버리지 결과를 보관함. 기본 보존 기간은 90일이고 retention-days로 줄임
  • 캐시는 현재 브랜치와 기본 브랜치(풀 리퀘스트는 기준 브랜치 포함)에서 만든 것만 복원함. 하위 브랜치나 형제 브랜치의 캐시는 복원하지 않음
  • 읽기 권한이 있으면 풀 리퀘스트로 캐시 내용에 접근할 수 있으므로 토큰이나 로그인 정보를 캐시 경로에 두지 않음
  • upload-artifact v4부터 아티팩트는 수정할 수 없고, 같은 실행 안에서 이름이 겹치면 안 됨. 매트릭스에서는 이름에 매트릭스 값을 넣음
  • 업로드할 파일이 없으면 기본은 경고만 출력함(if-no-files-found: warn). 리포트가 반드시 있어야 하면 error로 지정함

시크릿과 GITHUB_TOKEN

섹션 제목: “시크릿과 GITHUB_TOKEN”

시크릿은 조직, 저장소, 환경(environment) 단위로 저장하며, 워크플로에 명시적으로 포함한 시크릿만 읽을 수 있다. 환경 시크릿에는 필수 검토자를 두어 승인 전까지 잡이 접근하지 못하게 할 수 있다.

  • 로그에 출력된 시크릿 값은 자동으로 마스킹됨. 값이 변형되면 마스킹이 보장되지 않고, 현재 잡에서 사용한 시크릿만 마스킹됨
  • 포크 저장소에서 시작된 워크플로에는 GITHUB_TOKEN을 제외한 시크릿이 전달되지 않음. 포크 풀 리퀘스트의 GITHUB_TOKEN은 읽기 전용임
  • GITHUB_TOKEN은 잡마다 자동 생성되는 GitHub App 설치 토큰으로, 워크플로가 있는 저장소에만 권한이 있고 잡이 끝나면 만료됨
  • permissions 키로 워크플로 또는 잡 단위 권한을 지정함. 하나라도 지정하면 지정하지 않은 권한은 모두 none이 됨. 테스트 잡에는 contents: read처럼 필요한 권한만 둠
  • GITHUB_TOKEN으로 발생시킨 이벤트는 새 워크플로 실행을 만들지 않음(workflow_dispatch, repository_dispatch 제외). 자동화가 만든 풀 리퀘스트의 CI는 승인 대기 상태로 생성됨
  • pull_request_target은 포크에서 시작되어도 쓰기 권한 토큰과 시크릿에 접근하는 권한 있는 실행이므로, 신뢰할 수 없는 풀 리퀘스트 코드를 체크아웃하지 않음

concurrency

섹션 제목: “concurrency”

같은 group 값을 가진 잡이나 워크플로는 한 번에 하나만 실행된다. 새 실행이 대기하면 같은 그룹의 기존 대기 실행은 취소되고, cancel-in-progress: true면 진행 중인 실행도 취소된다. 풀 리퀘스트에 커밋을 연속으로 푸시할 때 이전 커밋의 테스트를 취소하는 데 사용한다. 그룹 이름은 대소문자를 구분하지 않는다.

재사용 워크플로

섹션 제목: “재사용 워크플로”

on: workflow_call로 정의한 워크플로는 다른 워크플로의 잡에서 uses: <owner>/<repo>/.github/workflows/<파일>.yml@<ref>로 호출한다. inputs, secrets, outputs를 정의할 수 있고 호출은 최대 10단계까지 연결된다.

  • 호출된 워크플로의 actions/checkout은 호출한 쪽 저장소를 체크아웃함
  • 여러 스텝을 한 스텝으로 묶는 복합 액션(composite action)과 달리, 재사용 워크플로는 잡을 포함하고 잡과 스텝별 로그가 따로 남음
  • 여러 저장소가 같은 테스트 단계(설치, 실행, 리포트 업로드)를 사용하면 재사용 워크플로로 모아 수정 지점을 하나로 둠

필수 상태 검사

섹션 제목: “필수 상태 검사”

브랜치 보호 규칙이나 룰셋에서 상태 검사를 필수로 지정하면, 검사가 success, skipped, neutral 상태여야 병합할 수 있다.

  • Strict(기본, “Require branches to be up to date before merging”)는 브랜치가 기준 브랜치의 최신 상태를 포함해야 병합됨. Loose는 최신화하지 않아도 병합되지만 병합 후 충돌하는 변경으로 실패할 수 있음
  • if 조건으로 건너뛴 잡은 Success로 보고되어 필수 검사여도 병합을 막지 않음. 실패한 잡에 needs로 의존하는 잡도 건너뛰어져 병합을 막지 않을 수 있으므로 always()와 함께 사용함
  • paths나 branches 필터로 워크플로 자체가 실행되지 않으면 해당 검사는 Pending으로 남아 병합을 막음. 건너뛸 수 있는 워크플로는 필수 검사로 지정하지 않음
  • 같은 이름의 검사와 커밋 상태가 있으면 둘 다 통과해야 함

예시: Playwright 테스트와 리포트 아티팩트

섹션 제목: “예시: Playwright 테스트와 리포트 아티팩트”

아래 예는 풀 리퀘스트와 main 푸시에서 Playwright 테스트를 브라우저별로 실행하고, 테스트가 실패해도 HTML 리포트를 아티팩트로 올린다. playwright.config에 chromium, firefox 프로젝트와 html 리포터(출력 폴더 playwright-report/)가 정의되어 있고, webServer가 빌드 결과를 띄우는 구성이라고 가정한다. html 리포터를 설정하지 않으면 CI의 기본 리포터는 dot이라 올릴 리포트 폴더가 생성되지 않는다.

  • if: ${{ !cancelled() }}는 앞 스텝이 실패해도 실행이 취소되지 않았으면 리포트를 올림. Playwright 공식 CI 예제도 같은 조건을 사용함
  • npm run build는 E2E가 빌드 결과를 대상으로 실행될 때 필요함. 빠지면 이전 산출물로 테스트하거나 산출물이 없어 실패함(E2E 테스트 전 빌드)
  • concurrency 그룹은 풀 리퀘스트에서는 head 브랜치 이름, 그 밖의 이벤트에서는 실행 ID로 정해져, main 푸시 실행끼리는 서로 취소하지 않음
  • 아티팩트 이름에 매트릭스 값을 넣어 브라우저별 리포트를 구분함

QA에서 사용하는 방법

섹션 제목: “QA에서 사용하는 방법”
  • 풀 리퀘스트에는 빠른 테스트와 변경 영향 범위의 테스트를, schedule과 main 푸시에는 전체 회귀를 배치함. paths 필터로 나눈 워크플로는 필수 검사 지정 여부를 함께 정함(회귀 테스트 범위 선정)
  • 결함 보고서와 테스트 기록에는 실행 URL과 커밋 SHA를 남김. 풀 리퀘스트 실행은 병합 커밋 기준이라 head 커밋과 SHA가 다름
  • 실패 판정 전에 같은 커밋에서 재실행 결과를 비교하고, 결과가 오가는 테스트는 Flaky 테스트 관리 절차로 넘김. 재실행으로 통과시킨 결과만 남기지 않음
  • 시각 회귀 베이스라인은 CI와 같은 OS·브라우저·글꼴 환경에서 생성함(시각 회귀 테스트)
  • CI는 커밋된 파일만 체크아웃함. 로컬 통과와 CI 실패가 다르면 커밋에 빠진 수정부터 확인함(작업 트리와 커밋 상태 구분)
  • TC 관리 도구로 결과를 올릴 때는 if: ${{ !cancelled() }} 스텝에서 JUnit XML을 업로드하고, API 키는 시크릿에 둠(TestRail)

비슷한 도구와 선택 기준

섹션 제목: “비슷한 도구와 선택 기준”
도구 설치와 운영 파이프라인 정의 실행 환경 테스트 결과 표시
GitHub Actions GitHub에 내장 .github/workflows/*.yml(이벤트, 잡, 스텝) GitHub 호스팅 러너 또는 자체 호스팅 러너 잡 로그와 상태 검사, 아티팩트, 작업 요약(GITHUB_STEP_SUMMARY)
Jenkins 직접 설치·운영하는 오픈소스 서버(MIT) 저장소의 Jenkinsfile(선언형, 스크립트형) 직접 연결하거나 클라우드 플러그인으로 생성한 에이전트 JUnit 플러그인의 결과 화면과 추이 그래프
GitLab CI/CD GitLab.com, GitLab Self-Managed, GitLab Dedicated에 내장 저장소 루트의 .gitlab-ci.yml(stages, jobs) GitLab 호스팅 러너(GitLab.com, Dedicated) 또는 자체 관리 러너 artifacts:reports:junit으로 머지 리퀘스트에서 소스와 대상 브랜치의 테스트 결과 차이를 표시함

선택 기준

  • 코드를 GitHub에 두고 풀 리퀘스트 흐름에 테스트를 붙이려면 GitHub Actions가 설정이 가장 적음. 상태 검사와 브랜치 보호가 같은 화면에서 연결됨
  • 코드를 GitLab에 두면 GitLab CI/CD가 같은 역할을 함. JUnit 리포트를 머지 리퀘스트 화면에서 바로 비교하는 기능이 기본 제공됨. 단, 리포트는 잡 상태에 영향을 주지 않으므로 실패 판정은 스크립트 종료코드로 함
  • 여러 호스팅을 함께 사용하거나 사내망 안에서만 운영해야 하고, 서버와 플러그인을 직접 관리할 인력이 있으면 Jenkins가 맞음
  • 장비 연결, 사내 인증서, 고정 IP가 필요한 테스트는 세 도구 모두 자체 러너(에이전트)로 실행함. GitHub 공식 보안 지침은 누구나 풀 리퀘스트를 열 수 있는 공개 저장소에는 자체 호스팅 러너를 거의 사용하지 않도록 안내함

주의할 점

섹션 제목: “주의할 점”
  • 서드파티 액션은 저장소의 시크릿과 GITHUB_TOKEN에 접근할 수 있음. 공식 문서는 워크플로 의존성 잠금 파일(lockfile)을 가장 강한 보호로, 그 다음으로 전체 길이 커밋 SHA 고정을 권장함. 태그는 이동하거나 삭제될 수 있음
  • ${{ github.event.pull_request.title }} 같은 신뢰할 수 없는 입력을 run 스크립트에 직접 넣으면 스크립트 주입이 발생할 수 있음. 중간 환경 변수로 받아 사용함
  • 매트릭스 fail-fast 기본값 때문에 한 브라우저의 실패가 다른 브라우저의 잡을 취소함. 취소된 잡은 실패가 아니라 미수행이므로 결과 집계에서 구분함
  • -latest 레이블은 이미지 OS가 바뀌면 같은 커밋도 다른 결과를 낼 수 있음. 재현성이 필요한 잡은 버전 레이블을 사용하고, runner-images 공지를 확인함
  • 공식 문서는 캐시가 없어도 잡이 파일을 다시 받거나 생성할 수 있어야 한다고 안내함. 캐시 복원 여부에 따라 테스트 결과가 달라지면 캐시 키와 경로 설정을 확인함
  • 자체 호스팅 러너는 잡마다 깨끗한 환경이 보장되지 않아, 이전 잡이 남긴 파일과 프로세스가 다음 테스트에 영향을 줄 수 있음
  • GITHUB_TOKEN으로 푸시한 커밋은 새 워크플로를 실행하지 않음. 자동 수정 커밋 뒤에 테스트가 돌았다고 가정하지 않음

현장 노트

  • ubuntu-latest 러너 이미지가 새 Ubuntu 버전(26.04, 공지 #14748)으로 바뀐 뒤 Playwright 브라우저 설치 단계가 실패함. 러너 레이블이 가리키는 이미지가 바뀔 수 있어, 재현성이 필요한 잡은 ubuntu-24.04처럼 버전을 고정함
  • 시각 회귀 스냅샷을 로컬 Windows에서만 생성하고 푸시해 ubuntu 러너의 시각 비교 잡이 실패함. 베이스라인은 CI와 같은 플랫폼에서 생성함(시각 회귀 테스트)
  • 로컬 검사가 모두 통과했는데 CI가 실패한 적이 있어, 푸시 뒤 gh run list로 해당 커밋(headSha)의 실행 결과를 확인한 뒤 완료로 처리함. 실패하면 직전 커밋에서도 실패했는지 비교해 이번 변경 때문인지 구분함

관련 문서

자동화작업 트리와 커밋 상태 구분로컬 테스트는 작업 트리의 파일로 실행되고 원격 저장소와 CI는 커밋된 파일을 받는다. 스테이징하지 않은 수정은 로컬 테스트를 통과해도 커밋에 포함되지 않는다.자동화E2E 테스트 전 빌드빌드 산출물을 대상으로 E2E 테스트를 실행하는 구성에서는 소스를 수정해도 다시 빌드하지 않으면 이전 번들로 테스트가 실행된다.자동화시각 회귀 테스트화면 캡처를 베이스라인과 비교해 의도하지 않은 화면 변화를 검출하는 테스트다. 캡처 환경, 허용 오차, 베이스라인 갱신 절차를 고정해야 결과를 판정 근거로 사용할 수 있다.자동화Flaky 테스트 관리코드와 환경이 같은데도 실행마다 결과가 달라지는 테스트(Flaky 테스트)의 원인을 분류하고 탐지, 격리, 수정하는 절차다.
