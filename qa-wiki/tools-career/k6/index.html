Grafana k6

JavaScript로 부하 시나리오를 작성하는 오픈소스 성능 테스트 도구 Grafana k6의 테스트 수명주기, 가상 사용자와 반복, 시나리오와 실행기, 체크와 임계값, 메트릭, 태그와 그룹, 결과 출력, 브라우저 모듈과 QA에서 성능 합격 기준을 판정하는 방법.

기본기난이도 중급최종 업데이트 2026-11-24

Grafana k6는 Grafana Labs가 GitHub 저장소 grafana/k6에서 개발하는 오픈소스 성능 테스트 도구다. 라이선스는 AGPL-3.0이고, 엔진은 Go로 작성되었으며 테스트 스크립트는 JavaScript로 작성한다. v0.57부터 TypeScript 파일(.ts)도 별도 설정 없이 실행하지만, esbuild로 타입 정보를 제거할 뿐 타입 검사는 하지 않는다. 2026-11 기준 GitHub Releases의 최신 릴리즈는 v2.4.0이고, v2.0.0에서 폐기 예정이던 API와 명령이 제거되었다. 주 용도는 HTTP API와 웹 서비스의 부하 테스트이며, 임계값(threshold)으로 합격과 불합격을 판정해 CI 파이프라인에서 성능 회귀를 확인하는 데 사용한다.

핵심 개념

섹션 제목: “핵심 개념”
개념 뜻
가상 사용자(VU, Virtual User) 스크립트의 VU 코드를 반복 실행하는 실행 단위. 각 VU는 독립적으로 동작함
반복(iteration) VU가 default 함수(또는 시나리오가 지정한 함수)를 한 번 실행하는 것. 반복 사이에 VU의 쿠키가 초기화되고 TCP 연결이 닫힐 수 있음
시나리오(scenario) VU와 반복을 어떻게 배치할지 정한 실행 단위. 한 스크립트에 여러 개를 두면 기본적으로 병렬 실행됨
실행기(executor) 시나리오의 부하 생성 방식. VU 수, 반복 횟수, 도착률(arrival rate) 중 무엇을 기준으로 부하를 만들지 정함
체크(check) 응답 상태나 본문 같은 조건을 확인하는 단언. 실패해도 테스트는 계속 진행되고 종료코드에 영향을 주지 않음
임계값(threshold) 메트릭에 대한 합격 기준. 하나라도 어기면 k6는 0이 아닌 종료코드로 끝남
메트릭(metric) 실행 중 수집하는 측정값. 내장 메트릭과 사용자 정의 메트릭이 있음
태그(tag)와 그룹(group) 메트릭을 분류해 필터링하는 표시. 그룹은 스크립트 구간을 묶고 group 태그를 붙임

테스트 수명주기

섹션 제목: “테스트 수명주기”
단계 실행 횟수 용도와 제약
init 코드 VU마다 한 번 모듈 가져오기, 로컬 파일 읽기, options 정의, 사용자 정의 메트릭 생성. HTTP 요청은 보낼 수 없음
setup() 테스트 전체에서 한 번 테스트 데이터 준비, 로그인 토큰 발급처럼 테스트 전 작업. HTTP 요청 가능. 반환값은 VU 코드와 teardown()에 전달됨
VU 코드(default) 반복마다 실제 부하 로직(요청, 체크). 로컬 파일을 읽거나 모듈을 가져올 수 없음
teardown() 테스트 전체에서 한 번 테스트 후 정리, 완료 알림. setup()이 비정상 종료되면 실행되지 않음

setup()에서 다른 단계로 넘길 수 있는 값은 JSON으로 표현되는 데이터뿐이고 함수는 넘길 수 없다. 각 VU는 이 데이터의 사본을 받으므로 VU 코드에서 값을 바꿔도 teardown()에는 반영되지 않는다. setup()은 setupTimeout(기본 60초) 안에 끝나야 하며, 넘기면 VU가 시작되기 전에 테스트가 실패한다.

성능 테스트 유형

섹션 제목: “성능 테스트 유형”

ISTQB CTFL v4.0.1(2.2.2)은 비기능 테스트를 시스템이 “얼마나 잘 동작하는가”를 평가하는 테스트로 정의하고, 대상 특성의 하나로 ISO/IEC 25010의 성능 효율성을 든다(테스트 레벨과 유형, ISO/IEC 25010 품질 모델). CTFL은 부하, 스트레스 같은 하위 유형을 따로 정의하지 않으므로, 아래는 k6 공식 테스트 가이드(Test types)의 정의를 따른다.

유형 목적(k6 가이드) k6 구성 예(작성 예시)
스모크(smoke) 최소 부하에서 스크립트가 동작하고 시스템이 정상 응답하는지 확인 적은 VU, 짧은 시간
평균 부하(average-load) 예상되는 평상시 부하에서의 성능 평가 stages로 목표 VU까지 증가 후 유지
스트레스(stress) 평균보다 높은 부하, 즉 한계 근처에서의 성능 평가 평균 부하보다 높은 목표값
스파이크(spike) 갑작스럽고 짧은 대량 증가에서의 동작과 생존 확인 짧은 구간에 급격한 증가와 감소
내구(soak) 장시간 지속되는 부하에서의 신뢰성과 성능 평가 평균 부하를 장시간 유지
한계점(breakpoint) 부하를 점진적으로 올려 용량 한계 확인 ramping-vus나 ramping-arrival-rate로 계속 증가

합격 기준은 CTFL(5.1.3)의 종료 조건(exit criteria)에 해당한다. 성능 테스트에서는 “p95 응답 시간 500ms 미만, 오류율 1% 미만”처럼 측정 가능한 값으로 정하고, k6에서는 이 값을 임계값으로 작성한다.

주요 기능

섹션 제목: “주요 기능”

스크립트 구조와 임계값

섹션 제목: “스크립트 구조와 임계값”

k6 run -e BASE_URL=https://stg.example.com -e PERF_PW=... script.js로 실행한다. -e로 넘긴 값은 __ENV로 읽는다. 임계값 식은 <집계 방법> <연산자> <값> 형식이고, Trend 메트릭은 avg, min, max, med, p(N)을 집계 방법으로 사용한다. 임계값을 어긴 즉시 테스트를 멈추려면 긴 형식의 abortOnFail: true를 사용하고, 초반의 적은 표본으로 중단되지 않도록 delayAbortEval을 함께 지정한다.

옵션과 실행기

섹션 제목: “옵션과 실행기”

vus와 duration만 지정하면 constant-vus 실행기 하나로, vus와 iterations는 shared-iterations로, stages는 ramping-vus로 실행된다. 옵션이 여러 곳에 있으면 기본값, 설정 파일(--config), 스크립트 options, 환경 변수(K6_ 접두어), CLI 플래그 순으로 뒤의 것이 앞의 것을 덮어쓴다.

실행기 부하 기준 동작
shared-iterations 반복 횟수 정해진 반복 횟수를 여러 VU가 나눠 실행함
per-vu-iterations 반복 횟수 각 VU가 정해진 횟수만큼 실행함
constant-vus VU 수 고정 VU 수가 정해진 시간 동안 가능한 만큼 반복함
ramping-vus VU 수 VU 수를 stages에 따라 늘리거나 줄임
constant-arrival-rate 도착률 단위 시간당 고정 횟수의 반복을 시작함
ramping-arrival-rate 도착률 단위 시간당 반복 시작 횟수를 단계별로 변경함

k6 문서는 이전 반복이 끝나야 다음 반복이 시작되는 방식을 폐쇄형 모델(closed model)로, 응답 시간과 관계없이 일정에 따라 반복을 시작하는 방식을 개방형 모델(open model)로 구분한다. 개방형 모델은 두 도착률 실행기가 구현한다. 폐쇄형 모델에서는 대상 시스템이 느려지면 반복이 길어져 도착률이 함께 떨어지는데, 이를 coordinated omission이라고 부른다. 초당 요청 수 같은 목표 처리량을 검증하려면 도착률 실행기를 사용한다.

도착률 실행기는 비어 있는 VU가 없으면 예정된 반복을 실행하지 못하고 dropped_iterations 메트릭에 기록한다. 테스트 초반에 발생하면 VU 할당이 부족한 것이고, 후반에 발생하면 대상 시스템의 응답이 느려져 반복 시간이 늘어난 것일 수 있다. 시나리오에는 startTime(시작 시점), gracefulStop(기본 30초), exec(실행할 함수), env, tags를 지정할 수 있다.

메트릭

섹션 제목: “메트릭”
유형 집계
Counter 값을 누적 합산함
Gauge 최소, 최대, 마지막 값을 기록함
Rate 0이 아닌 값이 나온 비율을 계산함
Trend 평균, 중앙값, 백분위 같은 통계를 계산함

k6가 자동으로 수집하는 값 중 HTTP 테스트에서 주로 확인하는 항목은 다음과 같다.

  • http_req_duration: 요청 전체 시간(Trend). http_req_sending + http_req_waiting + http_req_receiving이며 DNS 조회와 연결 수립 시간은 포함하지 않음
  • http_req_waiting: 첫 바이트 수신까지 대기 시간(TTFB)
  • http_req_failed: 실패한 요청 비율(Rate). 실패 판정은 setResponseCallback 설정을 따름
  • 그 밖에 http_reqs(요청 수), iterations(반복 수), vus(현재 VU 수), vus_max, checks(체크 성공 비율), dropped_iterations를 기록함

사용자 정의 메트릭은 k6/metrics에서 Counter, Gauge, Rate, Trend를 가져와 init 코드에서 생성하고 VU 코드에서 add()로 값을 기록한다. Trend의 두 번째 인자 true는 값이 시간 값임을 표시한다.

태그와 그룹

섹션 제목: “태그와 그룹”
  • 시스템 태그: status, method, url, name, group, check, scenario 등이 자동으로 붙음
  • 사용자 정의 태그: 요청 옵션의 tags, check()의 세 번째 인자, add()의 두 번째 인자로 지정함
  • 테스트 전체 태그: CLI --tag NAME=VALUE, 환경 변수 K6_TAGS, options.tags로 지정함. 기본적으로 출처끼리 병합되지 않고 우선순위가 높은 쪽이 전체를 대체함
  • 그룹: group() 안에서 발생한 메트릭에 ::그룹명 형식의 group 태그가 붙고, 그룹마다 group_duration 메트릭이 기록됨

URL에 ID가 들어가는 요청은 URL마다 별도 메트릭으로 나뉘므로 tags: { name: '...' }로 같은 이름을 지정한다. 공식 문서는 요청마다 그룹을 만드는 방식을 권하지 않는다.

결과 출력

섹션 제목: “결과 출력”
  • 종료 요약: 테스트가 끝나면 표준 출력에 임계값 결과, 체크, 메트릭 집계를 출력함. --summary-mode로 compact(기본), full, disabled를 선택함
  • summaryTrendStats: Trend 메트릭에 표시할 통계. 기본값은 avg,min,med,max,p(90),p(95)로 p99가 없음
  • handleSummary(data): 요약 데이터를 받아 stdout이나 파일 경로를 키로 하는 객체를 반환해 원하는 형식으로 저장함. 이 함수를 정의하면 기본 요약은 출력되지 않음
  • 실시간 출력: --out json=result.json 형식으로 지정함. 파일(CSV, JSON)로 저장하거나 Prometheus remote write, InfluxDB, OpenTelemetry, Grafana Cloud k6 등으로 전송할 수 있음
  • 웹 대시보드: K6_WEB_DASHBOARD=true로 실행하면 localhost:5665에서 실시간으로 확인하고, K6_WEB_DASHBOARD_EXPORT=report.html로 종료 시 HTML 리포트를 저장함

브라우저 모듈

섹션 제목: “브라우저 모듈”

k6/browser 모듈은 실제 Chromium 계열 브라우저를 구동해 프런트엔드 성능을 측정한다. API는 Playwright 등 프런트엔드 테스트 프레임워크를 참고해 설계되었고(Playwright), async/await로 작성한다. 시나리오에 실행기를 지정하고 options.browser.type을 chromium으로 설정해야 실행된다. 결과에는 browser_web_vital_lcp, browser_web_vital_inp, browser_web_vital_cls 같은 Web Vitals 메트릭이 기록된다. 페이지는 finally에서 page.close()로 닫아야 자원이 해제되고 Web Vitals가 정확히 계산된다.

브라우저 VU는 프로토콜 수준 VU보다 자원을 많이 사용한다. 공식 문서는 부하 대부분을 프로토콜 수준 스크립트로 만들고 브라우저 VU는 전체의 10% 이하로 함께 실행하는 혼합 방식을 권한다.

QA에서 사용하는 방법

섹션 제목: “QA에서 사용하는 방법”
  • 성능 요구사항을 임계값으로 옮김. “목록 조회 p95 2초 이하”는 'http_req_duration{name:list}': ['p(95)<=2000']가 되고, 요구사항이 없으면 측정 대상과 목표값을 먼저 합의함(ISO/IEC 25010 품질 모델)
  • 부하 대상을 리스크로 선정함. 결제, 로그인, 검색처럼 장애 영향이 크고 트래픽이 몰리는 경로를 우선 시나리오로 만듦(리스크 기반 테스트)
  • CI에서 스모크 수준의 짧은 부하를 실행하고, 임계값 위반 시 0이 아닌 종료코드로 파이프라인을 실패시킴(GitHub Actions, Jenkins). 긴 부하와 내구 테스트는 운영과 비슷한 전용 환경에서 별도 일정으로 실행함
  • 결과는 평균만 보지 않고 p95, p99, 오류율(http_req_failed)을 함께 확인함. Grafana의 기준선(baseline) 학습 문서는 평균에는 이상값이 드러나지 않으므로 기준선에 백분위를 사용하고, 정상 기준선의 오류율은 0에 가깝다고 설명함
  • 릴리즈마다 같은 스크립트, 같은 데이터, 같은 환경으로 실행해 이전 결과와 비교함. 결과에 스크립트 커밋, 대상 빌드, 실행기와 부하 설정을 함께 기록함(형상관리 기본)
  • 임계값 위반을 결함으로 등록할 때 위반한 메트릭과 값, 태그, 부하 설정, 재현 명령을 증거로 첨부함(이슈 양식, 심각도)
  • 기능 단언은 API 테스트에서 검증하고, k6의 체크는 부하 중 응답이 정상인지 확인하는 용도로 둠

선택 기준

  • 팀이 사용하는 언어로 고름. JavaScript 중심이면 k6, Python이면 Locust, JVM 언어면 Gatling이 테스트 코드와 같은 저장소에서 관리하기 쉬움
  • 코드 리뷰와 CI 판정이 중요하면 스크립트가 텍스트 코드인 도구가 변경 이력을 확인하기 쉬움. GUI 편집과 녹화로 시작하려면 JMeter의 HTTP(S) Test Script Recorder를 사용할 수 있음
  • HTTP 외에 JDBC, JMS, LDAP, FTP 같은 프로토콜을 기본 기능으로 다뤄야 하면 JMeter의 샘플러 목록을 확인함. Gatling도 JDBC, JMS, Kafka, MQTT, gRPC 문서를 제공함
  • 목표 처리량(초당 요청 수)을 검증해야 하면 개방형 모델을 지원하는지 확인함
  • 라이선스 조건(AGPL-3.0, Apache 2.0, MIT)을 조직 정책과 대조함. 도구를 수정해 배포하거나 서비스로 제공할 계획이 있으면 법무 검토 대상임

주의할 점

섹션 제목: “주의할 점”
  • init 코드에서는 HTTP 요청을 보낼 수 없고, VU 코드에서는 로컬 파일을 읽을 수 없음. 테스트 데이터 파일은 init 코드에서 읽고, 로그인 같은 사전 요청은 setup()에서 보냄
  • 체크 실패만으로는 테스트가 실패하지 않음. checks: ['rate>0.99'] 같은 임계값을 함께 두어야 종료코드에 반영됨
  • http_req_duration은 DNS 조회와 연결 수립 시간을 제외함. 사용자 체감 시간과 비교할 때 http_req_connecting, http_req_tls_handshaking 같은 세부 메트릭을 함께 확인함
  • 기본 종료 요약에는 p99가 없음. p99를 판정 기준으로 쓰면 summaryTrendStats에 추가해야 요약에서 값을 확인할 수 있음
  • 폐쇄형 실행기로 처리량을 판정하면 대상이 느려질 때 부하도 함께 줄어 결과가 실제보다 좋게 나올 수 있음. 도착률 실행기에서는 dropped_iterations가 0인지 확인함
  • 부하 생성기 자체의 CPU, 메모리, 네트워크가 포화되면 측정값이 대상 시스템의 성능을 반영하지 않음. 브라우저 VU는 특히 자원을 많이 사용함
  • v2.0.0에서 externally-controlled 실행기, --no-summary 플래그, browser_web_vital_fid 메트릭, k6 login 등 일부 명령이 제거됨. v1.x 시기 자료의 스크립트와 CI 명령을 그대로 옮기지 않음
  • 스테이징이나 운영 환경에 부하를 줄 때는 대상 시스템 담당자와 일정, 범위, 중단 기준을 사전에 합의함

관련 문서

기초와 용어테스트 레벨과 테스트 유형테스트 레벨은 시스템을 어느 통합 단계에서 검증하는지를, 테스트 유형은 어떤 품질 특성을 검증하는지를 나타내는 분류다. 두 분류는 서로 독립이며, 테스트마다 레벨을 하나 정하고 테스트 유형은 하나 이상 적용할 수 있다.테스트 설계리스크 기반 테스트실패했을 때의 피해와 실패할 가능성을 기준으로 무엇을 먼저, 얼마나 깊게 테스트할지 정하는 방식이다(Risk-Based Testing).기초와 용어API 테스트 기본화면을 거치지 않고 API에 직접 요청을 보내 응답 계약, 상태 코드, 서버 측 검증, 인가를 확인하는 테스트다. 화면 제약만으로는 확인할 수 없는 서버 동작이 대상이다.도구Apache JMeter프로토콜 수준에서 부하를 생성하는 오픈소스 성능 테스트 도구 Apache JMeter의 테스트 플랜 구성 요소, 요소 실행 순서와 범위 규칙, 추출기를 사용한 상관(correlation), CSV Data Set Config, CLI 모드 실행과 HTML 대시보드 리포트, 분산 테스트, QA에서 성능 합격 기준을 판정하는 방법.
