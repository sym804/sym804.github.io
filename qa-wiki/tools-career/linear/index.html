Linear

이슈 트래커 Linear의 팀, 이슈, 워크플로 상태와 카테고리, 라벨과 라벨 그룹, 우선순위, 사이클, 프로젝트, 트리아지, 필터와 보기, GitHub 연동, GraphQL API를 정리하고 결함 관리에 적용하는 방법을 다룬다.

기본기난이도 기초최종 업데이트 2026-11-24

Linear는 Linear Orbit, Inc.가 개발해 클라우드 서비스로 제공하는 상용 이슈 트래커다. 소프트웨어 팀의 이슈, 반복 계획(사이클), 프로젝트를 관리하는 데 사용한다. 상태 흐름과 우선순위처럼 많은 부분이 정해진 틀로 제공되고, 팀은 그 안에서 상태 이름, 라벨, 템플릿을 설정한다. 외부 연동은 GraphQL API, 웹훅, 공식 MCP 서버로 한다.

핵심 개념

섹션 제목: “핵심 개념”
개념 뜻
워크스페이스 한 회사의 팀, 이슈, 설정을 담는 최상위 단위. linear.app/example 형식의 고유 URL을 가짐
팀 기본 조직 단위. 팀마다 워크플로 상태, 사이클, 라벨, 템플릿을 따로 가짐. 상위 팀과 하위 팀으로 구성하면 하위 팀이 일부 설정을 상속함
이슈 작업의 기본 단위. 반드시 한 팀에 속하고, 식별자는 팀 식별자와 번호를 합친 ENG-123 형식
워크플로 팀별로 정한 이슈 상태의 순서. 목록의 그룹과 보드의 열이 됨
사이클 팀이 반복하는 계획 기간. 스프린트와 비슷하지만 릴리즈와 연결되지 않음
프로젝트 명확한 결과나 완료 예정일이 있는 이슈 묶음. 여러 팀이 공유할 수 있고 마일스톤으로 단계를 나눔
이니셔티브 여러 프로젝트를 상위 목표로 묶는 단위
보기(view) 같은 이슈를 필터와 표시 옵션으로 다르게 보는 방법. 이슈 자체는 변경하지 않음

주요 기능

섹션 제목: “주요 기능”

워크플로 상태와 카테고리

섹션 제목: “워크플로 상태와 카테고리”

상태는 팀마다 정하고, 모든 상태는 카테고리 하나에 속한다. 카테고리의 순서는 고정이고, 카테고리 안에서 상태의 순서만 바꿀 수 있다. 각 카테고리에는 상태가 하나 이상 있어야 한다.

카테고리 API의 type 값 기본 상태 용도
Triage(선택) triage Triage 다른 팀이나 연동이 만든 이슈를 검토하는 받은편지함
Backlog backlog Backlog 착수 계획이 없는 이슈
Unstarted unstarted Todo 착수 예정
Started started In Progress 진행 중
Completed completed Done 완료
Canceled canceled Canceled 하지 않기로 한 이슈
Duplicate(시스템) duplicate Duplicate 중복으로 표시하면 자동 이동. 이름을 변경할 수 없음
  • 새 이슈의 기본 상태는 첫 번째 Backlog 상태이고, Backlog나 Unstarted 카테고리의 다른 상태로 변경할 수 있음
  • API로 상태를 지정하지 않고 이슈를 생성하면 첫 Backlog 상태가 되고, 팀에 트리아지가 켜져 있으면 Triage가 됨
  • Linear 공식 문서는 자사 예로 Started에 In Progress, In Review, Ready to Merge를, Canceled에 Canceled, Could not reproduce, Won’t Fix를 둔 구성을 소개함
  • 자동 종료(auto-close)는 정한 기간 동안 갱신되지 않은 이슈를 닫음. 자동 보관(auto-archive)은 닫힌 이슈를 정한 기간 뒤 보관함
  • 보관은 자동으로만 일어나고 수동 보관 기능은 없음. 보관된 이슈는 검색과 복원이 가능함

우선순위

섹션 제목: “우선순위”

값은 No priority, Urgent, High, Medium, Low 다섯 개로 고정이다. Linear는 사용자 정의 우선순위를 제공하지 않으며, 더 세분화가 필요하면 상태나 라벨을 추가하도록 안내한다.

  • API 값은 0(No priority), 1(Urgent), 2(High), 3(Medium), 4(Low). lte: 2 같은 필터는 0도 포함하므로 neq: 0을 함께 지정함
  • Urgent로 지정하면 담당자에게 알림을 보내고, 이메일 알림을 켠 경우 긴급 이메일도 보냄
  • 우선순위순 보기에서 끌어 놓은 순서는 워크스페이스 전체에 저장됨

라벨과 라벨 그룹

섹션 제목: “라벨과 라벨 그룹”
  • 라벨은 워크스페이스 수준(모든 팀 공통) 또는 팀 수준으로 생성함. 모든 팀이 사용하는 라벨(예: Bug)은 워크스페이스 수준에 둠
  • 라벨 그룹은 라벨에 한 단계의 중첩을 만듦. 이슈에는 그룹이 아니라 그룹 안의 라벨을 붙임
  • 그룹은 기본이 단일 선택(그룹 안에서 라벨 하나만 붙일 수 있음)이고, 다중 선택으로 변경할 수 있음. 그룹당 라벨은 250개까지
  • 라벨을 붙이는 입력창에 심각도/major나 심각도:major를 입력하면 그룹과 라벨을 함께 생성함
  • priority, status, estimate 같은 이름은 기존 기능과 겹쳐 라벨 이름으로 쓸 수 없음
  • 라벨 보관은 이미 붙은 이슈에 라벨을 남기고 새로 붙이지 못하게 함. 라벨 삭제는 되돌릴 수 없고 이슈에서도 제거됨
  • 하위 이슈는 부모 이슈의 팀, 우선순위, 프로젝트를 상속하지만 라벨은 상속하지 않음. 결함을 하위 이슈로 나누면 심각도 라벨을 하위 이슈마다 붙임

사이클

섹션 제목: “사이클”
  • 팀 설정에서 켜면 1~8주 길이의 사이클이 정한 요일에 자동으로 반복 생성됨. 미래 사이클은 최대 15개까지 미리 만듦
  • 사이클 사이에 쿨다운 기간을 둘 수 있고, 쿨다운에는 이슈를 배정할 수 없음
  • 끝나지 않은 이슈는 다음 사이클로 자동으로 넘어감
  • 사이클 그래프는 범위, 시작한 이슈, 완료한 이슈를 표시함. 완료된 사이클의 그래프는 종료 시점의 기록이라, 이후 이슈가 재개되거나 옮겨지면 이슈 목록과 달라질 수 있음

프로젝트

섹션 제목: “프로젝트”
  • 이슈는 한 번에 한 프로젝트에만 속함. 프로젝트는 여러 팀이 공유할 수 있고, 그중 한 팀이 리드 팀임
  • 마일스톤으로 프로젝트 안의 단계(예: Alpha, Beta, GA)를 나누고 단계별 진행률을 확인함
  • 프로젝트에 이슈 보기를 붙일 수 있음. 예: bug 라벨만 거른 결함 보기

트리아지

섹션 제목: “트리아지”

트리아지는 팀의 받은편지함이다. Slack, Sentry 같은 연동으로 만든 이슈와 팀 밖의 구성원이 만든 이슈가 Triage 상태로 들어온다.

  • 처리: 수락(팀 기본 상태로 이동), 거절(Canceled 카테고리로 이동, 사유 코멘트 가능), 중복 표시(기존 이슈로 병합), 다시 알림(snooze)
  • 이슈가 트리아지를 떠나기 전에 우선순위 지정을 필수로 설정할 수 있음
  • 트리아지 이슈는 기본적으로 모든 보기에서 빠짐. 보기에 포함하려면 상태 필터에 Triage를 명시함
  • 트리아지 담당자 순번, 트리아지 규칙(조건에 따라 팀·상태·담당자·라벨·우선순위 설정), Triage Intelligence는 Business와 Enterprise 플랜 기능

필터와 보기

섹션 제목: “필터와 보기”
  • 필터는 담당자, 상태, 라벨, 프로젝트, 사이클, 날짜 등으로 이슈를 거름. 고급 필터는 조건을 AND/OR로 묶고 그룹을 중첩함
  • 적용한 주요 필터는 브라우저 URL에 들어가 링크로 공유됨. 보기 옵션과 빠른 필터는 URL에 들어가지 않음
  • 라벨이 없는 이슈를 거르려면 모든 라벨을 선택한 뒤 연산자를 does not include로 바꿈
  • 사용자 정의 보기(custom view)는 필터를 저장한 보기. 워크스페이스나 팀 범위로 공유하고, 보기에 이슈가 추가되거나 완료·취소될 때 개인 알림이나 Slack 채널 알림을 받을 수 있음
  • URL의 /issues/ 뒤에 ENG-123,ENG-456처럼 식별자를 쉼표로 나열하면 그 이슈만 담은 보기가 열림

이슈 템플릿

섹션 제목: “이슈 템플릿”
  • 워크스페이스 템플릿은 모든 팀에서, 팀 템플릿은 그 팀에서만 사용함. 팀을 기본 템플릿으로 지정하면 새 이슈가 그 템플릿으로 생성됨
  • 폼 템플릿은 텍스트, 긴 텍스트, 드롭다운, 체크박스, 날짜 필드와 함께 라벨 그룹, 우선순위, 제목 같은 이슈 속성을 입력받음

GitHub 연동

섹션 제목: “GitHub 연동”

풀 리퀘스트(PR)와 커밋을 이슈에 연결하고, PR 상태에 따라 이슈 상태를 변경하고, GitHub 이슈와 동기화한다.

  • 연결 방법: 브랜치 이름에 이슈 식별자 포함, PR 제목에 식별자 포함, PR 설명이나 제목에 매직 워드와 식별자를 작성함(Fixes ENG-123)
  • 닫기 매직 워드(close, fix, resolve, complete, implement와 활용형)는 병합 시 “On PR or commit merge”로 설정한 상태로 이동시킴. 닫지 않는 매직 워드(ref, refs, references, part of, contributes to, toward, towards)는 병합 상태를 적용하지 않음
  • Ignore ENG-123이나 skip으로 특정 이슈의 자동 연결을 막음
  • 기본 자동화는 PR이 열리면 In Progress, 병합되면 Done. 팀 설정이라 팀마다 구성함
  • 브랜치별 규칙으로 대상 브랜치마다 이동할 상태를 정함. 예: staging에 병합되면 In QA, main에 병합되면 Deployed
  • 커밋 연결: 커밋 메시지에 매직 워드와 식별자를 작성하면 푸시 시 In Progress, 기본 브랜치에 도달하면 Done
  • GitHub Issues 동기화는 단방향(GitHub에서 만든 이슈를 Linear에 복사) 또는 양방향을 선택함. 동기화는 연결 이후 새로 만든 이슈만 대상이고, 기존 이슈는 가져오기(importer)로 옮김

API

섹션 제목: “API”

Linear의 공개 API는 GraphQL이다. 엔드포인트는 https://api.linear.app/graphql이고, 개인 API 키는 Authorization: <API_KEY> 헤더로, OAuth 토큰은 Authorization: Bearer <ACCESS_TOKEN> 헤더로 보낸다.

QA 팀(QA)의 미완료 결함과 심각도 라벨을 조회하는 예:

  • GraphQL은 일부 필드만 실패해도 HTTP 200과 함께 errors 배열을 반환할 수 있음. 응답의 errors를 먼저 확인함
  • 목록 질의는 기본적으로 보관된 이슈를 제외함. 보관 이슈까지 집계하려면 includeArchived: true를 지정함
  • issueDelete는 이슈를 휴지통으로 옮기고 30일 뒤 영구 삭제함. 휴지통의 이슈는 보관 상태이기도 하며 trashed 필드가 true임. permanentlyDelete: true는 유예 기간 없이 삭제하고 별도 권한이 필요함
  • 웹훅은 이슈, 코멘트, 프로젝트, 사이클, 라벨 등의 생성과 변경을 HTTP로 알림
  • 공식 MCP 서버(https://mcp.linear.app/mcp, 읽기 전용은 /mcp/readonly)는 이슈, 프로젝트, 코멘트를 찾고 만들고 수정하는 도구를 제공함

QA에서 사용하는 방법

섹션 제목: “QA에서 사용하는 방법”

결함 생명주기

  • 결함 생명주기의 상태를 카테고리에 대응시킴. 예: 등록=Triage 또는 Backlog, 할당=Todo, 수정 중=In Progress, 수정 완료=Started 카테고리에 추가한 In QA, 종결=Done, 중복=Duplicate
  • 결함 아님, 재현 불가는 Canceled 카테고리에 상태를 따로 추가해 구분함. 보류는 Backlog 카테고리에 Deferred 같은 상태를 둠
  • 기본 GitHub 자동화는 PR 병합 시 Done으로 이동시켜 확인 테스트 전에 종결됨. “On PR or commit merge” 상태를 In QA로 변경하거나, 브랜치별 규칙으로 스테이징 병합 시 In QA로 이동시킴

심각도와 우선순위

  • Linear의 우선순위는 수정 순서로 사용하고, 심각도는 단일 선택 라벨 그룹(예: 심각도 그룹 안에 blocker부터 trivial까지)으로 기록함(심각도 기준)
  • 단일 선택 그룹이라 한 이슈에 심각도가 두 개 붙지 않음. 유형, 심각도, 영역을 각각 그룹으로 구성하면 라벨 체계를 그대로 옮길 수 있음

이슈 양식과 보고

  • 이슈 양식의 발견 블록을 팀의 폼 템플릿으로 작성하고, 심각도는 라벨 그룹 필드로 입력받음
  • 미해결 결함 보기와 Urgent 결함 보기를 사용자 정의 보기로 저장하고 Slack 채널 알림을 연결함
  • 이슈 로그를 따로 운영하면 이슈 식별자(ENG-123)를 로그의 트래커 칸에 기록함(이슈 로그와 트래커의 조인 키)

선택 기준

  • 정해진 상태 카테고리와 고정 우선순위로 충분하고 설정 관리 부담을 줄이려면 Linear가 맞음
  • 전이별 권한과 필수 입력을 강제해야 하거나 변경 이력으로 질의해야 하면 Jira가 맞음
  • 이슈가 대부분 코드 저장소 단위로 생기고 외부 기여자가 이슈를 등록하는 공개 저장소는 GitHub Issues가 맞음
  • 플랜마다 팀 수, 이슈 수, 트리아지 자동화 같은 기능 범위가 다르므로 공식 요금 페이지를 확인함. 2026-11 기준 무료 플랜은 팀 2개, 이슈 250건이고 보관된 이슈는 이 한도에 포함되지 않음

주의할 점

섹션 제목: “주의할 점”
  • 유료 구독을 해지해도 데이터는 삭제되지 않지만, 무료 플랜의 이슈 한도를 넘은 상태면 새 이슈를 생성할 수 없음
  • 트리아지 이슈는 기본 보기에서 빠짐. 결함 집계 보기에 Triage 상태를 포함했는지 확인함
  • 팀 라벨은 이름이 같으면 화면 필터에서 하나처럼 동작하지만 API에서는 팀마다 다른 라벨 식별자를 사용해야 함. API로 집계할 때 팀별 라벨 식별자를 모두 포함했는지 확인함
  • 자동 종료를 켜면 오래 갱신되지 않은 결함이 확인 없이 닫힐 수 있음. 활성 사이클이나 끝나지 않은 프로젝트에 속한 이슈는 자동 종료되지 않음
  • 완료된 사이클 그래프와 현재 이슈 목록은 다를 수 있음. 사이클 실적을 보고할 때 어느 쪽 값인지 밝힘
  • GitHub Issues 동기화는 연결 뒤 새로 만든 이슈만 동기화함. 기존 이슈를 옮기려면 가져오기를 따로 실행함

현장 노트

  • 무료 플랜은 보관된 이슈를 제외한 이슈 수에 한도가 있어, 닫힌 이슈 이력이 많은 저장소는 Linear로 옮기지 못하고 GitHub Issues에 남김
  • 정리 작업으로 issueDelete를 실행한 뒤 includeArchived: true로 조회하니 삭제한 이슈가 그대로 보였음. 삭제한 이슈는 휴지통에 들어가 보관 상태로 남기 때문임. 정리 결과를 확인할 때는 조회 조건(includeArchived)과 trashed 값을 함께 확인함
  • 작업 당시 공식 MCP 서버로는 이슈 템플릿 생성, 라벨 삭제, 워크플로 상태 편집이 되지 않아 GraphQL API를 직접 호출함
  • 이슈 로그와 트래커를 함께 운영하면서 트래커 이슈 제목 앞에 로그 이슈번호를 붙이는 관행이 끊긴 구간에서 조인 실패가 7.5%에서 82.5%로 늘었음. 자세한 내용은 이슈 로그와 트래커의 조인 키에 있음
