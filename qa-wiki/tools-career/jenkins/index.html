Jenkins

오픈소스 자동화 서버 Jenkins의 구조(컨트롤러, 에이전트, 익스큐터), 잡과 파이프라인, Jenkinsfile 선언형 문법(pipeline, agent, stages, steps, post, when, parallel, matrix), 트리거, 크리덴셜, 플러그인, JUnit 결과 보고, 아티팩트 보관, 멀티브랜치 파이프라인과 GitHub Actions, GitLab CI/CD와의 비교.

기본기난이도 중급최종 업데이트 2026-11-24

Jenkins는 빌드, 테스트, 배포를 자동화하는 오픈소스 자동화 서버다. Jenkins 프로젝트가 개발하며, 프로젝트는 Continuous Delivery Foundation(CDF)에 속해 있다. 코어는 MIT 라이선스이고, 기능 대부분은 별도 플러그인으로 제공된다. 릴리즈는 12주마다 기준 버전을 정하고 4주마다 버그·보안 수정을 내는 LTS(Stable)와, 매주 나오는 weekly 두 계열이다. 배포 형태는 WAR 파일, OS 패키지, 설치 프로그램, Docker 이미지이며, 2026-11 기준 실행에는 Java 21 또는 Java 25가 필요하다(Java 17은 2.541.3 LTS가 마지막).

QA에서는 커밋이나 풀 리퀘스트마다 자동화 테스트를 실행하고, 결과를 수집해 추이를 보고, 실패 증거(로그, 스크린샷, 리포트)를 빌드에 보관하는 데 사용한다.

핵심 개념

섹션 제목: “핵심 개념”
개념 뜻
컨트롤러(Controller) 설정을 저장하고 플러그인을 불러오고 웹 UI를 제공하는 중앙 프로세스. 예전 이름은 master
에이전트(Agent) 컨트롤러에 연결되어 지시받은 작업을 실행하는 머신이나 컨테이너
노드(Node) 작업을 실행할 수 있는 머신. 에이전트와 컨트롤러 안의 빌트인 노드(Built-in Node)를 모두 포함함
익스큐터(Executor) 노드에서 작업 하나를 실행하는 슬롯. 노드의 익스큐터 수가 동시에 실행할 수 있는 작업 수임
레이블(Label) 에이전트를 기능별로 묶는 이름(예: linux, docker). 작업이 실행될 에이전트를 고를 때 사용함
잡(Job) Jenkins가 수행할 작업을 사용자가 설정한 것. 예전 이름은 프로젝트
빌드(Build) 잡을 한 번 실행한 결과
파이프라인(Pipeline) 소스 관리에서 사용자까지의 전달 과정을 코드로 정의한 모델
스테이지, 스텝 스테이지는 파이프라인의 구분된 단계(Build, Test, Deploy), 스텝은 Jenkins에 지시하는 작업 하나
워크스페이스(Workspace) 노드에서 작업이 사용하는 디렉터리. 정리 정책이 없으면 빌드 뒤에도 남음
아티팩트(Artifact) 빌드가 만든 파일 중 컨트롤러에 보관해 나중에 내려받는 파일

빌드 상태

  • Successful: 컴파일 오류 없이 끝남
  • Unstable: 빌드는 성공했지만 퍼블리셔(Publisher)가 불안정으로 보고함. JUnit 퍼블리셔가 테스트 실패를 발견한 경우가 대표적임
  • Failed: 치명적 오류로 실패함
  • Aborted: 사용자가 중지하거나 시간 제한에 걸려 중단됨

파이프라인과 Jenkinsfile

섹션 제목: “파이프라인과 Jenkinsfile”

파이프라인 정의를 Jenkinsfile이라는 텍스트 파일로 저장소에 커밋하는 방식을 Pipeline as Code라고 한다. 파이프라인 변경도 코드처럼 리뷰하고 이력이 남으며, 브랜치와 풀 리퀘스트마다 같은 정의로 빌드가 생성된다. 웹 UI에 직접 정의할 수도 있지만 공식 문서는 Jenkinsfile을 저장소에 두는 방식을 권장한다.

Jenkinsfile 문법은 두 가지다.

  • 선언형(Declarative): pipeline { } 블록 안에 정해진 섹션과 지시어로 작성함. 읽고 쓰기 쉽도록 설계됨. Pipeline: Declarative 플러그인이 필요함
  • 스크립트형(Scripted): node { } 블록 안에 Groovy 코드로 조건문, 반복문, try/catch를 자유롭게 작성함

선언형의 주요 구성 요소

요소 위치 역할
agent 최상위(필수), 스테이지 실행 위치. any, none(스테이지마다 지정), label, node(사용자 정의 워크스페이스 등), docker
stages, stage, steps pipeline 안 스테이지 목록, 스테이지 하나, 스테이지에서 실행할 스텝
post 최상위, 스테이지 실행이 끝난 뒤의 조건부 스텝. always, changed, fixed, regression, aborted, failure, success, unstable, unsuccessful, cleanup
environment 최상위, 스테이지 환경 변수 정의. credentials()로 크리덴셜을 연결함
options 최상위, 스테이지 timeout, buildDiscarder, disableConcurrentBuilds, parallelsAlwaysFailFast 등
triggers 최상위 한 번 cron, pollSCM, upstream
when 스테이지 스테이지 실행 조건. branch, changeRequest, changeset, buildingTag, environment, expression, not, allOf, anyOf 등
parallel 스테이지 하위 스테이지를 병렬 실행함. failFast true면 하나가 실패할 때 나머지를 중단함
matrix 스테이지 axes의 값 조합(셀)마다 같은 스테이지를 병렬 실행함. excludes로 일부 조합을 제외함
  • post 조건 블록은 위 표의 순서대로 평가됨. fixed는 이전 실행이 실패 또는 불안정이고 이번에 성공한 경우, regression은 이전에 성공했고 이번에 실패·불안정·중단된 경우에 실행됨
  • 한 스테이지에는 steps, stages, parallel, matrix 중 하나만 둘 수 있고, parallel이나 matrix 안의 스테이지에 다시 parallel이나 matrix를 둘 수 없음
  • when { branch 'main' }은 멀티브랜치 파이프라인에서만 동작함
  • 선언형은 pipeline { } 블록 코드 크기에 상한이 있음(공식 문서에 열린 이슈로 안내됨). 스크립트형에는 이 제한이 없음

예시: E2E 테스트 결과 게시

섹션 제목: “예시: E2E 테스트 결과 게시”

아래 예는 linux 레이블 에이전트에서 Playwright 테스트를 실행하고, JUnit XML을 게시하고, 실패 증거를 아티팩트로 보관한다. 에이전트에 Node.js와 브라우저 실행 환경이 준비되어 있다고 가정한다.

  • sh 스텝은 종료코드가 0이 아니면 파이프라인을 실패로 만듦. 공식 예제처럼 || true를 붙이면 테스트 실패 시에도 junit 스텝이 실행되고, 실패한 테스트가 있으면 빌드가 Unstable로 표시됨
  • || true를 쓰면 테스트 러너가 리포트를 만들지 못하고 종료된 경우도 성공 종료코드가 됨. junit 스텝은 결과 파일이 없거나 비어 있으면 기본적으로 빌드를 실패시키므로 allowEmptyResults를 켜지 않음
  • test-results는 Playwright가 실패한 테스트의 스크린샷과 트레이스를 저장하는 기본 출력 폴더임. 통과한 빌드에는 비어 있을 수 있어 allowEmptyArchive: true를 지정함

트리거

섹션 제목: “트리거”
  • 소스 저장소(GitHub, Bitbucket 등)와 연동한 파이프라인은 보통 웹훅으로 빌드가 시작되어 triggers가 필요하지 않음
  • cron은 정해진 주기로 실행함. H를 사용하면 잡 이름의 해시로 시각이 정해져 여러 잡의 실행 시각이 분산됨(예: 평일 2시대 한 번 cron('H 2 * * 1-5'))
  • pollSCM은 주기적으로 저장소를 확인해 변경이 있을 때만 실행함
  • upstream은 지정한 잡이 기준 결과(예: SUCCESS) 이상으로 끝나면 실행함. 빌드 뒤 회귀 스위트를 이어서 돌릴 때 사용함
  • 사용자가 수동으로 실행하는 빌드에는 parameters 지시어로 입력 값을 받음

크리덴셜

섹션 제목: “크리덴셜”

Jenkins에 저장한 비밀번호, 토큰, SSH 키, 인증서는 파이프라인에서 ID로 참조한다(Credentials). 선언형 environment의 credentials('<ID>')는 비밀 텍스트, 비밀 파일, 사용자 이름과 비밀번호(_USR, _PSW 변수가 추가됨), SSH 개인 키를 지원한다. 그 밖의 유형은 withCredentials 스텝으로 연결한다.

  • 콘솔 로그에 크리덴셜 값이 출력되면 ****로 마스킹됨. 공식 문서는 이것이 실수로 노출될 위험을 줄일 뿐 악의적인 사용자의 탈취를 막지 못한다고 명시함
  • Groovy 문자열 보간(큰따옴표 "${TOKEN}")을 크리덴셜에 사용하지 않음. 보간하면 값이 명령 인자에 복사되어 ps 같은 도구로 보이고, 값 안의 셸 메타 문자가 실행됨. 작은따옴표로 셸에 그대로 넘기고 셸이 환경 변수에서 읽게 함
  • 같은 이유로 사용자 입력(브랜치 이름, 파라미터)을 큰따옴표 보간으로 sh, bat, powershell에 넘기면 SQL 인젝션과 같은 유형의 명령 주입이 발생할 수 있음

플러그인

섹션 제목: “플러그인”
  • Update Center에서 의존 플러그인과 함께 내려받음. 웹 UI의 플러그인 관리 화면이나 Jenkins CLI로 설치함
  • 파이프라인 자체, 선언형 문법, Git 연동, JUnit 결과 보고, 브랜치 소스(GitHub Branch Source 등)도 모두 플러그인임. JUnit 기능은 1.577 버전에서 코어에서 분리되어 플러그인이 됨
  • 플러그인마다 필요한 Jenkins 버전과 의존 관계가 있으므로 코어를 올리기 전에 플러그인 호환성을 확인하고 시험 환경에서 먼저 업그레이드함

테스트 결과 보고(JUnit 플러그인)

섹션 제목: “테스트 결과 보고(JUnit 플러그인)”

JUnit 플러그인은 빌드 중 생성된 JUnit XML(TestNG도 같은 형식)을 수집해 빌드별 테스트 결과 화면, 실패 추적, 결과 추이 그래프를 제공한다. 파이프라인에서는 junit 스텝으로 사용한다.

옵션 동작
testResults Ant glob 패턴(예: **/build/test-reports/*.xml). 리포트가 아닌 XML이 섞이지 않게 지정함
allowEmptyResults 켜면 결과 파일이 없거나 비어도 빌드 상태를 바꾸지 않음. 설정 오류를 놓치기 쉬워짐
skipMarkingBuildUnstable 켜면 실패한 테스트가 있어도 빌드는 성공으로 둠. 스테이지는 여전히 Unstable로 표시됨
skipMarkingStageUnstable 켜면 스테이지와 빌드 모두 Unstable로 표시하지 않음
healthScaleFactor 테스트 실패가 빌드 건강 점수에 반영되는 비율. 기본 1.0
skipPublishingChecks GitHub Checks API로 결과를 게시하지 않음. 게시하려면 GitHub Checks 플러그인과 GitHub App 크리덴셜이 필요함

JUnit Platform의 Open Test Reporting 형식(open-test-report.xml)도 읽고, archiveAttachments: true로 테스트에 첨부된 파일을 빌드 아티팩트로 보관할 수 있다.

아티팩트 보관

섹션 제목: “아티팩트 보관”

archiveArtifacts는 패턴에 맞는 파일을 컨트롤러에 저장해 빌드 화면에서 내려받게 한다. fingerprint: true를 지정하면 파일 해시로 어느 빌드가 어떤 산출물을 사용했는지 추적한다.

  • 공식 문서는 아티팩트 보관이 Artifactory, Nexus 같은 저장소를 대신하지 않으며 기본적인 보고와 파일 보관용이라고 안내함
  • 보관 파일과 콘솔 로그는 options { buildDiscarder(logRotator(...)) }로 최근 빌드 수만큼만 남김
  • 빌드 산출물처럼 신뢰할 수 없는 내용은 Jenkins URL과 분리된 Resource Root URL로 제공하도록 설정할 수 있음

멀티브랜치 파이프라인

섹션 제목: “멀티브랜치 파이프라인”

저장소를 스캔해 Jenkinsfile이 있는 브랜치마다 파이프라인을 자동으로 생성하고 관리하는 프로젝트 유형(Multibranch Pipeline)이다. 브랜치별로 다른 Jenkinsfile을 둘 수 있다.

  • 빌드에는 BRANCH_NAME(브랜치 이름), CHANGE_ID(풀 리퀘스트 번호 등) 환경 변수가 추가됨
  • 풀 리퀘스트 검증은 GitHub Branch Source, Bitbucket Branch Source, GitLab Branch Source 같은 플러그인이 제공함
  • 조직 폴더(Organization Folder)가 아니면 브랜치 추가와 삭제를 자동으로 다시 인덱싱하지 않으므로 주기적 재인덱싱을 설정함
  • when { changeRequest() }로 풀 리퀘스트 빌드에서만, when { branch 'main' }으로 기본 브랜치에서만 실행할 스테이지를 나눔

QA에서 사용하는 방법

섹션 제목: “QA에서 사용하는 방법”
  • 풀 리퀘스트 빌드에는 빠른 스모크와 변경 영향 범위의 테스트를, 기본 브랜치나 야간 cron 빌드에는 전체 회귀를 배치함(회귀 테스트 범위 선정)
  • matrix의 축(브라우저, OS)으로 같은 테스트를 환경별로 병렬 실행하고, excludes로 지원하지 않는 조합을 제외함
  • 테스트 실패와 인프라 실패를 구분함. 테스트 실패는 JUnit 결과에 의해 Unstable, 설치·빌드 실패는 Failed로 남도록 스텝을 나눔(E2E 실패 분류)
  • 결과 추이와 post { fixed }, post { regression }을 사용해 새로 실패한 테스트와 다시 통과한 테스트를 알림으로 받음. 같은 커밋에서 결과가 오가는 테스트는 Flaky 테스트 관리 절차로 넘김
  • 빌드 산출물을 대상으로 E2E를 실행하는 구성이면 테스트 스테이지 앞에 빌드 스테이지를 둠(E2E 테스트 전 빌드)
  • Jenkins는 커밋된 내용을 체크아웃해 실행함. 로컬 통과와 CI 실패가 다르면 커밋에 빠진 파일부터 확인함(작업 트리와 커밋 상태 구분)
  • 결과를 TC 관리 도구에 기록할 때는 post { always }에서 업로드함(TestRail)

비슷한 도구와 선택 기준

섹션 제목: “비슷한 도구와 선택 기준”
도구 설치와 운영 파이프라인 정의 실행 환경 테스트 결과 표시
Jenkins 직접 설치·운영(WAR, 패키지, Docker, Kubernetes) 저장소의 Jenkinsfile(Groovy 기반 선언형·스크립트형) 직접 연결한 에이전트, 클라우드 플러그인으로 동적 생성한 에이전트 JUnit 플러그인의 결과 화면과 추이 그래프
GitHub Actions GitHub에 내장 .github/workflows/*.yml GitHub 호스팅 러너(Linux, Windows, macOS) 또는 자체 호스팅 러너 잡 로그와 상태 검사. 리포트 파일은 아티팩트로 올리고, 요약은 작업 요약(GITHUB_STEP_SUMMARY)에 기록함
GitLab CI/CD GitLab.com, GitLab Self-Managed, GitLab Dedicated에 내장 저장소 루트의 .gitlab-ci.yml(stages, jobs) GitLab 호스팅 러너(GitLab.com, Dedicated) 또는 자체 관리 러너 artifacts:reports:junit으로 JUnit XML을 머지 리퀘스트와 파이프라인 화면에 표시함

선택 기준

  • 저장소 호스팅과 CI를 한 곳에서 관리하려면 각 호스팅의 내장 CI(GitHub Actions, GitLab CI/CD)가 설치와 운영 부담이 적음
  • 여러 저장소 호스팅을 함께 쓰거나, 사내망에서 외부 접속 없이 운영하거나, 플러그인으로 사내 도구와 연동해야 하면 Jenkins가 맞음. 대신 컨트롤러, 에이전트, 플러그인 업그레이드와 보안 설정을 직접 맡아야 함
  • 테스트 결과를 CI 화면에서 바로 보고 싶으면 결과 표시 방식을 비교함. Jenkins는 JUnit 플러그인으로 결과 추이를, GitLab은 머지 리퀘스트에서 소스와 대상 브랜치의 결과 차이를 보여 줌. GitHub Actions는 리포트를 아티팩트로 올리거나 작업 요약에 기록함
  • 하드웨어 장비, 사내 인증서, 특정 OS가 필요한 테스트는 세 도구 모두 자체 에이전트(러너)로 실행할 수 있음. 장비 관리 주체와 보안 경계를 기준으로 정함

주의할 점

섹션 제목: “주의할 점”
  • 기본 설정은 빌트인 노드에서 빌드를 실행함. 빌트인 노드의 빌드는 Jenkins 프로세스와 같은 파일 시스템 권한을 가지므로, 빌트인 노드의 익스큐터를 0으로 두고 에이전트에서 실행함
  • 에이전트에서 컨트롤러로의 접근 제어(Agent → Controller Access Control)는 2.326부터 항상 켜져 있음. 이전 버전에서 끈 설정이 남아 있으면 다시 켬
  • sh '... || true'는 종료코드를 숨김. 결과 파일 누락과 빈 결과는 junit 스텝이 실패로 처리하지만, 필터 설정 오류로 일부 테스트만 실행된 경우는 빌드 상태에 드러나지 않으므로 테스트 수 추이를 확인함
  • 스테이지 agent와 options { timeout }을 함께 쓰면 에이전트 할당 시간이 제한 시간에 포함됨. 에이전트 대기가 길면 테스트 전에 시간 초과로 실패함
  • 파이프라인 이름에 공백이 있으면 경로에 공백이 들어가 스크립트가 실패할 수 있음
  • 워크스페이스는 정리 정책이 없으면 다음 빌드에 남음. 이전 빌드의 리포트 파일이 같은 패턴으로 함께 수집될 수 있으므로 결과 폴더를 빌드마다 비움

자동화테스트 자동화 기본테스트 자동화는 도구로 테스트를 실행하고 결과를 판정하는 활동이다. 이점과 한계, 테스트 피라미드, 테스트 용이성, 자동화 아키텍처(gTAA)와 프레임워크 계층, 케이스 자동화 방식 7가지, 도입 절차와 파이프라인 배치, 작성 원칙을 ISTQB CTAL-TAE 기준으로 설명한다.자동화Flaky 테스트 관리코드와 환경이 같은데도 실행마다 결과가 달라지는 테스트(Flaky 테스트)의 원인을 분류하고 탐지, 격리, 수정하는 절차다.자동화작업 트리와 커밋 상태 구분로컬 테스트는 작업 트리의 파일로 실행되고 원격 저장소와 CI는 커밋된 파일을 받는다. 스테이징하지 않은 수정은 로컬 테스트를 통과해도 커밋에 포함되지 않는다.도구Git 기본분산 버전 관리 시스템 Git의 핵심 개념(스냅샷, 세 가지 상태, 커밋, 브랜치, 태그, 원격, 병합과 리베이스), 자주 사용하는 명령, 브랜치 전략(Git Flow, GitHub Flow, 트렁크 기반)의 선택 기준.
