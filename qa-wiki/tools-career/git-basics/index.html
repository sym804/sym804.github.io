Git 기본

분산 버전 관리 시스템 Git의 핵심 개념(스냅샷, 세 가지 상태, 커밋, 브랜치, 태그, 원격, 병합과 리베이스), 자주 사용하는 명령, 브랜치 전략(Git Flow, GitHub Flow, 트렁크 기반)의 선택 기준.

기본기난이도 기초최종 업데이트 2026-11-24

Git은 분산 버전 관리 시스템(DVCS)이다. 저장소를 복제하면 최신 파일뿐 아니라 전체 이력이 함께 복제되어, 대부분의 작업을 네트워크 없이 로컬에서 수행한다. 형상관리에서 Git은 소스 코드, 설정 파일, 문서, 테스트 코드 같은 형상 항목의 버전을 관리하는 도구를 맡는다(형상관리 기본).

핵심 개념

섹션 제목: “핵심 개념”
  • 스냅샷: Git은 파일별 변경분이 아니라 커밋 시점의 프로젝트 전체 스냅샷을 저장함. 바뀌지 않은 파일은 이전에 저장한 파일을 가리킴
  • 무결성: 저장하는 모든 내용을 체크섬(해시)으로 계산해 그 값으로 참조함. Git이 모르게 파일 내용을 변경할 수 없음
  • 세 가지 상태: 파일은 수정됨(modified), 스테이징됨(staged), 커밋됨(committed) 중 하나의 상태에 있음
  • 세 영역: 작업 트리(파일을 실제로 편집하는 곳), 스테이징 영역(다음 커밋에 들어갈 내용), Git 디렉터리(.git, 커밋 이력이 저장되는 곳)
개념 뜻
커밋 스테이징 영역의 스냅샷을 이력에 기록한 단위. 해시(예: 236829d)로 식별함
브랜치 특정 커밋을 가리키는 가벼운 이동형 포인터. 새 커밋을 만들면 앞으로 이동함
HEAD 지금 작업 중인 브랜치(또는 커밋)를 가리키는 포인터
태그 특정 커밋에 붙이는 고정 이름. 릴리즈 버전 표시에 사용함. 포인터만 있는 경량 태그와, 작성자·날짜·메시지를 담아 체크섬까지 계산하는 주석 태그가 있음
원격 다른 곳에 있는 같은 저장소. fetch로 받아오고 push로 올림
병합(merge) 두 브랜치의 이력을 합침. 기존 커밋은 그대로 둠. 이력이 갈라졌으면 병합 커밋을 만들고, 갈라지지 않았으면 브랜치 포인터만 앞으로 옮김(fast-forward)
리베이스(rebase) 한 브랜치의 커밋을 다른 기준 위로 다시 적용해 이력을 일직선으로 만듦. 기존 커밋은 새 커밋으로 바뀜

리베이스는 커밋을 새로 만들기 때문에, 이미 원격에 올라가 다른 사람이 그 위에서 작업했을 수 있는 커밋에는 사용하지 않는다(Pro Git 3.6).

자주 사용하는 명령

섹션 제목: “자주 사용하는 명령”

기본 작업

명령 용도
git clone 원격 저장소를 새 디렉터리에 복제함
git status 작업 트리의 상태(수정된 파일, 스테이징된 파일, 추적하지 않는 파일)를 확인함
git add 변경 내용을 스테이징 영역에 추가함
git commit 스테이징 영역의 내용을 이력에 기록함
git restore git restore <파일>은 작업 트리의 수정을 되돌리고, git restore --staged <파일>은 수정은 유지한 채 스테이징을 해제함
git switch 다른 브랜치로 전환함. git switch -c <브랜치>는 새 브랜치를 만들고 전환함
git fetch, git pull 원격의 커밋을 받아옴. pull은 받아온 뒤 현재 브랜치에 통합까지 함
git push 로컬 커밋을 원격에 올림
git merge 다른 브랜치의 이력을 현재 브랜치에 합침

이력 확인과 원인 조사

명령 용도
git log, git show 커밋 이력과 특정 커밋의 내용을 확인함
git diff 인자 없이 실행하면 스테이징하지 않은 변경을, --staged(--cached와 같음)는 다음 커밋에 들어갈 변경을, git diff <A> <B>는 두 커밋·태그·브랜치 사이의 변경을 보여 줌
git blame <파일> 파일의 각 줄을 마지막으로 변경한 커밋과 작성자를 확인함
git bisect 이진 탐색으로 결함이 처음 들어온 커밋을 찾음. 정상 커밋과 결함 커밋을 지정하면 그 사이 커밋을 차례로 검사함
git tag 특정 커밋에 릴리즈 이름을 붙이거나 태그 목록을 확인함
git worktree 하나의 저장소에서 여러 작업 트리를 만들어, 현재 작업을 건드리지 않고 다른 버전을 체크아웃함

git bisect run <스크립트>는 스크립트의 종료코드로 각 커밋의 정상과 결함을 판정해 원인 커밋까지 자동으로 좁힌다.

브랜치 전략

섹션 제목: “브랜치 전략”
전략 구성 맞는 경우
Git Flow 장기 브랜치 master(배포), develop(개발 통합)과 기능, 릴리즈, 핫픽스 브랜치 명시적인 버전으로 배포하거나, 여러 버전을 동시에 지원해야 하는 제품
GitHub Flow 기본 브랜치 하나와 짧은 작업 브랜치, 풀 리퀘스트로 검토 후 병합 지속적으로 배포하는 웹 서비스
트렁크 기반 개발 트렁크(기본 브랜치)에 직접 커밋하거나, 이틀 안팎으로 끝나는 짧은 기능 브랜치를 검토 후 통합함. 장기 개발 브랜치는 두지 않고, 미완성 기능은 기능 플래그로 숨김 작은 단위로 자주 통합하고 자동화 테스트가 갖춰진 팀

선택 기준

  • Git Flow 제안자도 2020년에 덧붙인 글에서, 지속 배포하는 팀에는 GitHub Flow 같은 단순한 방식을 권하고, 명시적 버전 관리나 여러 버전 지원이 필요할 때 git-flow가 맞다고 정리함
  • 장기 브랜치가 많을수록 병합 충돌과 브랜치별 테스트 대상이 늘어남. QA는 어느 브랜치의 어느 커밋을 테스트했는지 회차마다 기록해야 함
  • 트렁크 기반은 통합 빈도가 높은 대신, 기본 브랜치가 항상 배포 가능한 상태를 유지하도록 자동화 테스트와 빌드 검증이 필요함

QA 관점

섹션 제목: “QA 관점”
  • 이전 릴리즈 태그와 현재 커밋 사이의 변경 목록(git log, git diff)을 회귀 범위 선정의 입력으로 사용함(회귀 테스트 범위 선정)
  • 테스트 대상을 브랜치 이름이 아니라 커밋 해시나 태그로 기록함. 브랜치는 이동하는 포인터라 나중에 같은 이름이 다른 커밋을 가리킴
  • 회귀 결함을 찾으면 마지막 정상 릴리즈 태그와 현재 커밋 사이를 git bisect로 좁혀 원인 커밋을 결함 보고서에 기록함. 재현 절차를 자동화 테스트로 만들어 두면 git bisect run으로 탐색을 자동화할 수 있음
  • 로컬에서 통과한 테스트는 작업 트리 기준이고, CI는 커밋된 내용 기준으로 실행함. 커밋 직후 git status로 커밋하지 않은 변경이 남아 있지 않은지 확인함(작업 트리와 커밋 상태 구분)
  • .gitignore는 아직 추적하지 않는 파일에만 적용됨. 이미 추적 중인 파일은 git rm --cached로 추적을 해제해야 함
  • 줄바꿈 규칙(.gitattributes의 eol)이 저장소 전체에 적용되면 Windows 배치 파일처럼 CRLF가 필요한 파일이 깨질 수 있음. 파일 유형별로 규칙을 지정함

현장 노트

  • 저장소 전체에 eol=lf를 지정했더니 로컬 파일은 정상인데 새로 clone한 저장소에서만 Windows 배치 파일(.cmd)이 LF로 체크아웃되어 실행되지 않음. 로컬에서는 보이지 않는 결함이라 .cmd, .bat만 CRLF로 지정하는 규칙을 추가함
  • 릴리즈마다 git 태그를 달고, 테스트가 릴리즈 노트의 현재 버전과 태그를 대조하도록 구성함. 태그를 빠뜨린 릴리즈가 대조 테스트에서 실패로 드러나 소급해 태그를 추가함

관련 문서

기초와 용어형상관리 기본테스트 산출물과 테스트 대상을 형상 항목으로 식별, 통제, 추적하는 형상관리(Configuration Management)의 개념(형상 항목, 베이스라인, 변경 통제, 상태 기록, 감사)과 QA 업무에 적용하는 방법.자동화작업 트리와 커밋 상태 구분로컬 테스트는 작업 트리의 파일로 실행되고 원격 저장소와 CI는 커밋된 파일을 받는다. 스테이징하지 않은 수정은 로컬 테스트를 통과해도 커밋에 포함되지 않는다.프로세스릴리즈 노트와 버전 번호버전 번호(SemVer, CalVer, 4자리 번호, 빌드 번호)와 릴리즈 노트(Keep a Changelog, Conventional Commits 자동 생성, 이슈 중심 형식)의 대표 방식과 선택 기준. 운영 예로 변경 크기 기준 A.B.C.D 규칙을 함께 둔다.
