GitHub Issues

GitHub 저장소의 이슈 추적 기능(이슈, 라벨, 마일스톤, 담당자, 이슈 유형, 하위 이슈, 이슈 템플릿과 이슈 폼)과 Projects, 검색 문법, 닫기 키워드, gh CLI를 정리하고 결함 관리에 적용하는 방법을 다룬다.

기본기난이도 기초최종 업데이트 2026-11-24

깃허브 이슈

GitHub Issues는 GitHub 저장소에 포함된 이슈 추적 기능이다. 코드, 풀 리퀘스트(PR), 커밋과 같은 저장소에서 이슈를 관리하므로 이슈와 수정 PR을 바로 연결할 수 있다. 여러 저장소의 이슈와 PR을 모아 계획하는 기능은 Projects가 맡는다. 명령줄 도구 gh CLI는 GitHub가 관리하는 오픈소스(MIT 라이선스) 프로젝트로, 이슈 등록과 조회를 스크립트로 처리할 때 사용한다.

핵심 개념

섹션 제목: “핵심 개념”
개념 뜻
이슈 저장소 안에서 #123처럼 번호로 식별함. 상태는 열림과 닫힘 두 가지이고, 닫을 때 사유를 completed, not planned, duplicate 중에서 지정함
라벨 이슈와 PR을 분류하는 이름표. 저장소에 쓰기 권한이 있으면 생성할 수 있음
마일스톤 이슈와 PR 묶음의 진행 상황. 설명, 마감일, 완료율, 열린·닫힌 건수를 표시함
담당자 이슈와 PR마다 최대 10명
이슈 유형 조직이나 사용자 계정 수준에서 정하는 유형. 기본값은 task, bug, feature이고 최대 25개
하위 이슈 부모 이슈당 100개, 최대 8단계까지 중첩함. 다른 저장소의 이슈도 하위 이슈로 추가할 수 있음
이슈 의존성 이슈 사이에 blocked by, blocking 관계를 지정함. 막는 관계 없이 연결만 하는 Relates to 관계는 2026-09에 정식 출시됨
이슈 필드 조직이나 개인 계정 수준에서 정의하는 구조화된 필드. 텍스트, 숫자, 날짜, 단일 선택, 다중 선택 유형이 있음. 조직은 2026-07에 정식 출시되었고, 개인 계정 소유 저장소는 2026-11부터 지원함

저장소의 기본 라벨은 bug, documentation, duplicate, enhancement, good first issue, help wanted, invalid, question, wontfix, accessibility이고 수정하거나 삭제할 수 있다. 조직 소유자는 조직 저장소의 기본 라벨을 변경할 수 있다. 이슈 필드를 켜면 Priority(Urgent, High, Medium, Low), Effort, Start date, Target date 필드가 자동으로 생성된다.

주요 기능

섹션 제목: “주요 기능”

이슈 템플릿과 이슈 폼

섹션 제목: “이슈 템플릿과 이슈 폼”

템플릿은 저장소의 .github/ISSUE_TEMPLATE 폴더에 둔다. 마크다운 템플릿은 본문 초안을 채워 주고, 이슈 폼은 YAML로 정의한 입력 칸을 화면에 표시한다. 이슈 폼은 2026-11 기준 공개 미리보기(public preview) 기능이다.

  • 폼 파일은 name, description, body로 시작해야 함. title, labels, assignees, projects, type은 선택 항목임
  • body 요소 유형: markdown(안내문, 제출되지 않음), input(한 줄), textarea(여러 줄), dropdown, checkboxes, upload
  • validations.required는 입력하지 않으면 제출을 막음. 공식 문서 기준으로 공개 저장소에서만 동작함
  • textarea에 render를 지정하면 입력이 코드 블록으로 제출되고 첨부와 마크다운 편집을 사용할 수 없음
  • 같은 폴더의 config.yml에서 blank_issues_enabled: false로 빈 이슈 작성을 막고, contact_links로 다른 접수 경로를 안내함

결함 등록 폼의 최소 예:

폼 최상위의 labels는 그 폼으로 만든 모든 이슈에 같은 라벨을 붙인다. 드롭다운 선택값은 본문에 기록되므로, 선택값에 따라 라벨을 붙이는 자동화(예: GitHub Actions 워크플로)를 두는 경우 옵션을 라벨 값과 글자까지 같게 둔다(심각도 기준).

Projects

섹션 제목: “Projects”

Projects는 사용자나 조직 수준의 계획 도구다. 여러 저장소의 이슈와 PR을 항목으로 추가하고, 항목의 변경은 원본 이슈와 양방향으로 반영된다.

  • 보기 레이아웃: 표(table), 보드(board), 로드맵(roadmap)
  • 사용자 정의 필드: 텍스트, 숫자, 날짜, 단일 선택, 다중 선택, 반복(iteration). 프로젝트당 필드는 이슈 필드와 시스템 필드를 포함해 50개까지
  • 기본 워크플로: 이슈나 PR이 닫히면 Status를 Done으로, PR이 병합되면 Status를 Done으로 설정하는 두 규칙이 처음부터 켜져 있음
  • 그 밖의 기본 워크플로로 조건에 맞는 항목 자동 보관, 저장소에서 필터에 맞는 항목 자동 추가를 켤 수 있음. 더 복잡한 자동화는 GraphQL API나 GitHub Actions로 구성함
  • 항목으로 차트를 생성해 프로젝트를 볼 수 있는 사람과 공유함
  • 이슈 필드는 조직(또는 개인 계정)에서 한 번 정의해 여러 프로젝트에서 열로 사용하고, 프로젝트 사용자 정의 필드는 그 프로젝트 안에서만 사용함

검색 문법

섹션 제목: “검색 문법”
용도 검색어
담당자 없는 열린 결함 is:issue state:open label:bug no:assignee
특정 마일스톤의 열린 이슈 is:issue is:open milestone:"2.3.0"
수정 PR이 연결된 열린 이슈 is:issue is:open linked:pr
not planned로 닫힌 이슈 is:issue is:closed reason:"not planned"
특정 날짜 뒤에 닫힌 결함 is:issue label:bug closed:>2026-11-01
심각도가 blocker 또는 critical인 결함 is:issue state:open label:blocker,critical
유형과 담당자 조합 (type:"Bug" AND assignee:octocat) OR (type:"Feature" AND no:assignee)
  • 라벨을 쉼표로 이으면 OR, label: 한정자를 따로 지정하면 AND
  • 앞에 -를 붙이면 제외함(-label:wontfix)
  • 웹 화면의 고급 검색은 AND, OR와 괄호를 지원하고 괄호는 5단계까지 중첩함. 공백은 AND로 해석함
  • sort:created-asc처럼 정렬을 검색어에 추가함

닫기 키워드

섹션 제목: “닫기 키워드”

PR 설명이나 커밋 메시지에 키워드와 이슈 번호를 작성하면 병합 시 이슈가 닫힌다. 키워드는 close, closes, closed, fix, fixes, fixed, resolve, resolves, resolved다.

  • PR이 기본 브랜치를 대상으로 할 때만 동작함. 다른 브랜치를 대상으로 하는 PR에서는 키워드를 무시하고 연결도 만들지 않음
  • 커밋 메시지의 키워드는 그 커밋이 기본 브랜치에 병합될 때 이슈를 닫음
  • 이슈 여러 개를 닫으려면 이슈마다 키워드를 작성함
  • 쓰기 권한이 있으면 PR 사이드바의 Development에서 같은 저장소의 이슈를 최대 10개까지 직접 연결할 수 있음
  • 키워드 없이 다른 이슈나 PR에서 #123을 언급하면 참조만 생기고 이슈는 닫히지 않음

gh CLI

섹션 제목: “gh CLI”
  • --search는 위의 검색 문법을 그대로 받음(gh issue list --search "no:assignee label:bug")
  • 현재 매뉴얼 기준 --json 필드에 stateReason, labels, milestone, parent, subIssues가 있어 이슈 로그 대조에 사용함
  • 옵션은 버전마다 다름. gh issue create의 --parent(하위 이슈 지정), --type은 현재 매뉴얼(v2.105.0)에 있지만 v2.88.1에는 없음. 설치된 버전의 --help로 확인함

QA에서 사용하는 방법

섹션 제목: “QA에서 사용하는 방법”

결함 생명주기

  • 이슈 상태는 열림과 닫힘뿐이라 결함 생명주기의 할당, 수정 중, 수정 완료는 Projects의 단일 선택 Status 필드나 라벨로 기록함
  • 닫기 사유를 종결 사유에 대응시킴. 확인 테스트를 통과한 종결은 completed, 중복은 duplicate, 결함 아님과 재현 불가는 not planned로 닫고 근거를 코멘트로 남김
  • PR의 닫기 키워드는 병합 시점에 이슈를 닫아 확인 테스트 전에 종결됨. 수정 PR에서는 #123 참조만 하고 QA가 확인 뒤 닫거나, Projects Status를 수정 완료로 두고 확인 테스트 완료를 라벨로 표시함
  • Projects의 기본 워크플로는 닫힌 이슈를 Done으로 옮김. 수정 완료와 종결을 구분하려면 Status 옵션과 워크플로를 함께 조정함

심각도와 우선순위

  • 기본 필드에 심각도와 우선순위가 없어 라벨로 기록함. 조직에서 이슈 필드를 사용하면 Priority 필드를 수정 순서로, 단일 선택 필드나 라벨을 심각도로 나눠 기록함(심각도 기준)

이슈 양식과 이슈 로그

  • 이슈 양식의 발견 블록을 이슈 폼으로 작성하고, 비공개 저장소에서는 required가 동작하지 않으므로 필수 칸을 리뷰나 자동화로 확인함
  • 이슈 로그를 따로 운영하면 이슈 번호(정수)를 로그의 트래커 칸에 기록함. gh issue list --state all --json으로 받은 번호 집합과 로그의 집합을 비교해 누락을 찾음(이슈 로그와 트래커의 조인 키)
  • 다른 트래커로 이관한 원본 이슈는 not planned로 닫고 새 이슈 링크를 코멘트로 남김

비슷한 도구와 선택 기준

섹션 제목: “비슷한 도구와 선택 기준”
항목 GitHub Issues Jira Linear
범위 저장소 단위. Projects로 여러 저장소를 묶음 스페이스 단위, 여러 스페이스를 필터와 보드로 묶음 팀 단위, 프로젝트와 이니셔티브로 묶음
상태 흐름 열림과 닫힘, 닫기 사유. 세부 상태는 Projects 필드 상태, 전이, 조건, 검증, 사후 함수를 설계 팀별 상태, 카테고리 순서 고정
입력 양식 마크다운 템플릿, YAML 이슈 폼 생성 화면과 전이 화면의 필드 표준 템플릿, 폼 템플릿
검색 검색 한정자, 고급 검색의 AND/OR JQL(이력 연산자 포함) 필터 UI, GraphQL 필터
코드 연결 같은 저장소의 PR, 닫기 키워드 스마트 커밋, 개발 도구 연동 매직 워드, 브랜치별 상태 규칙

선택 기준

  • 이슈 대부분이 한 저장소의 코드 변경과 짝을 이루고 외부 기여자도 등록하는 공개 저장소면 GitHub Issues가 단순함
  • 결함 상태를 세분화하고 전이마다 입력을 강제해야 하면 Jira, 정해진 상태 카테고리 안에서 사이클과 트리아지를 사용하려면 Linear가 맞음
  • 이슈 로그나 보고서를 스크립트로 만드는 팀은 gh CLI와 API로 내보내기가 쉬운지도 비교함

주의할 점

섹션 제목: “주의할 점”
  • 이슈 폼은 공개 미리보기라 문법이 변경될 수 있음. 폼 정의 오류는 폼을 생성하거나 저장하거나 볼 때 검증 오류로 표시됨
  • required는 공개 저장소에서만 동작함. 비공개 저장소에서는 필수 칸이 빈 이슈도 등록됨
  • 기본 브랜치가 아닌 브랜치(예: develop)로 병합하는 흐름에서는 닫기 키워드가 동작하지 않아 이슈가 열린 채 남음
  • 마일스톤의 열린 이슈가 500개를 넘으면 마일스톤 안에서 순서를 변경할 수 없음
  • 개인 계정은 이슈 유형과 이슈 필드를 각각 25개까지 생성함. 새로 추가된 기능이라 한도와 동작은 GitHub 변경 공지(changelog)로 확인함
  • 라벨 이름이 저장소마다 다르면 조직 단위 검색과 집계가 어긋남. 조직 기본 라벨로 맞춤

현장 노트

  • gh issue create로 만든 이슈는 저장소의 이슈 폼(YAML)을 거치지 않고 --body 내용이 그대로 본문이 됨. CLI로 등록할 때는 폼과 같은 항목을 본문에 직접 채움
  • 이슈 폼 YAML은 저장 전에 검증하는 공식 API가 없어 SchemaStore의 이슈 폼 스키마로 검증함. textarea에 render를 주면 입력이 코드 블록으로 표시되어 스크린샷을 붙일 수 없었음
  • 이슈 로그와 트래커를 함께 운영하면서 트래커 이슈 제목 앞에 로그 이슈번호를 붙이는 관행이 끊긴 구간에서 조인 실패가 7.5%에서 82.5%로 늘었음. 자세한 내용은 이슈 로그와 트래커의 조인 키에 있음

관련 문서

프로세스이슈 양식버그 이슈의 대표 양식(ISTQB 결함 보고서 항목, Bugzilla 요약·설명, GitHub 이슈 폼)과 선택 기준. 운영 예로 발견 블록과 종결 블록을 나눈 버그 양식과 작업(개선) 양식을 둔다.프로세스결함 생명주기결함이 등록된 시점부터 종결될 때까지 거치는 상태와, 상태 사이에 허용되는 전이를 정한 규칙이다(Defect Lifecycle).프로세스이슈 로그와 트래커의 조인 키이슈를 어디에 기록할지(트래커만, 로그만, 두 곳)의 선택 기준과, 두 곳에 기록할 때 로그의 행과 트래커의 이슈를 연결하는 식별자(조인 키). 조인 키가 없으면 두 기록이 1:1로 대응하는지 확인할 수 없다.도구Git 기본분산 버전 관리 시스템 Git의 핵심 개념(스냅샷, 세 가지 상태, 커밋, 브랜치, 태그, 원격, 병합과 리베이스), 자주 사용하는 명령, 브랜치 전략(Git Flow, GitHub Flow, 트렁크 기반)의 선택 기준.
