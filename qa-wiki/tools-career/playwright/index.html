Playwright

Microsoft가 유지하는 웹 브라우저 자동화 도구 Playwright와 테스트 러너 Playwright Test의 핵심 개념(브라우저 엔진, 컨텍스트 격리, 로케이터, 자동 대기, 웹 우선 단언, 픽스처, 프로젝트)과 설정, 인증 재사용, 네트워크 가로채기, 트레이스, 리포터, 시각 비교, API 테스트를 다룬다.

기본기난이도 중급웹 프론트엔드최종 업데이트 2026-11-24

Playwright는 Microsoft가 유지하는 오픈소스(Apache-2.0) 웹 브라우저 자동화 도구다. 하나의 API로 Chromium, Firefox, WebKit을 Windows, Linux, macOS에서 조작한다. 언어는 JavaScript·TypeScript(Node.js), Python, Java, .NET을 지원하고, Node.js에는 전용 테스트 러너 Playwright Test가 함께 제공된다. Python은 pytest 플러그인, Java는 JUnit·TestNG 같은 일반 테스트 프레임워크, .NET은 MSTest·NUnit·xUnit 기반 클래스를 사용한다. 이 문서는 Playwright Test(Node.js) 기준이며 2026-11 기준 최신 버전은 1.65다.

핵심 개념

섹션 제목: “핵심 개념”
개념 뜻
브라우저 엔진 Chromium, Firefox, WebKit 세 엔진을 지원함. Google Chrome, Microsoft Edge 같은 브랜드 브라우저는 channel 옵션으로 지정하고, Android Chrome과 모바일 Safari는 기기 에뮬레이션으로 실행함
브라우저 컨텍스트 시크릿 모드 프로필과 비슷한 격리 환경. 컨텍스트마다 쿠키, localStorage, sessionStorage가 따로 있음. 생성 비용이 작아 한 브라우저에서 여러 개를 동시에 사용함
테스트 격리 Playwright Test는 테스트마다 새 컨텍스트와 그 안의 기본 페이지를 생성함. 앞 테스트의 로그인 상태나 저장소가 다음 테스트로 넘어가지 않음
로케이터(Locator) 요소를 찾는 방법을 담은 객체. 조작하는 시점에 요소를 다시 찾음
엄격 모드(strict mode) 단일 요소를 조작하는 로케이터가 요소 여러 개와 일치하면 예외가 발생함. count()처럼 여러 요소를 다루는 연산은 예외가 아님
자동 대기(actionability) 조작 전에 요소가 조작 가능한 상태가 될 때까지 기다림
웹 우선 단언 expect(locator) 단언이 조건을 만족할 때까지 재시도함
픽스처(Fixture) 테스트에 필요한 객체와 환경을 준비하고 정리하는 단위
프로젝트(Project) 같은 설정으로 실행하는 테스트 묶음. 브라우저, 기기, 환경별로 나눔
워커(Worker) 테스트를 실행하는 독립 OS 프로세스. 워커마다 브라우저를 따로 실행하고 워커끼리 통신하지 않음

한 테스트 안에서 컨텍스트를 여러 개 생성할 수도 있다. 관리자와 일반 사용자가 같은 채팅방에 있는 상황처럼 여러 사용자가 상호작용하는 시나리오에 사용한다.

로케이터와 권장 우선순위

섹션 제목: “로케이터와 권장 우선순위”

공식 문서는 사용자에게 보이는 속성과 명시적 계약(테스트 ID)을 우선하라고 권한다. 내장 로케이터는 다음과 같다.

로케이터 찾는 기준
getByRole() 명시적·암묵적 접근성 속성(역할과 접근성 이름)
getByText() 텍스트 내용
getByLabel() 연결된 label 텍스트(폼 컨트롤)
getByPlaceholder() 입력란의 placeholder
getByAltText() 이미지 등의 대체 텍스트
getByTitle() title 속성
getByTestId() data-testid 속성. 설정의 testIdAttribute로 다른 속성을 지정함
  • CSS와 XPath는 page.locator()로 사용할 수 있지만 DOM 변경에 약해 권장하지 않음
  • 여러 요소와 일치하면 범위를 좁힘. locator.filter()(hasText, hasNotText, has, hasNot), 로케이터 체이닝, locator.within()(예: 특정 대화상자 안의 저장 버튼)을 사용함
  • first(), last(), nth()도 엄격 모드를 피하지만, 화면이 바뀌면 의도하지 않은 요소를 클릭할 수 있어 공식 문서가 권장하지 않음

자동 대기와 웹 우선 단언

섹션 제목: “자동 대기와 웹 우선 단언”

조작 메서드는 실행 전에 다음 검사를 통과할 때까지 기다리고, 지정한 timeout 안에 통과하지 못하면 실패한다.

검사 기준
Visible 크기가 0이 아닌 경계 상자가 있고 visibility:hidden이 아님. display:none은 보이지 않음, opacity:0은 보임으로 판정함
Stable 연속 두 애니메이션 프레임 동안 경계 상자가 같음
Receives Events 조작 지점에서 포인터 이벤트를 받는 요소가 대상 요소임. 위를 덮은 오버레이가 있으면 실패함
Enabled disabled 속성, 비활성 <fieldset>, aria-disabled=true 하위가 아님
Editable Enabled이면서 readonly, aria-readonly=true가 아님
Not Inert inert 속성이 있는 하위 트리에 속하지 않음
  • click, check는 Visible, Stable, Receives Events, Enabled, Not Inert를 검사함. fill은 Visible, Enabled, Editable, Not Inert를 검사함. focus, press, dispatchEvent는 검사하지 않음
  • force: true는 필수가 아닌 검사를 끔. 실제 사용자가 클릭할 수 없는 요소도 클릭되므로 결함을 놓칠 수 있음

단언은 재시도 여부로 나뉜다.

  • 자동 재시도 단언: toBeVisible(), toHaveText(), toContainText(), toHaveCount(), toHaveURL(), toBeDisabled() 등. 조건을 만족하거나 단언 timeout(기본 5초)이 지날 때까지 다시 확인하며 await가 필요함
  • 재시도하지 않는 단언: toBe(), toEqual(), toBeTruthy() 같은 일반 매처. 비동기로 표시되는 값에 사용하면 Flaky 테스트가 됨
  • expect.soft(): 실패해도 테스트를 멈추지 않고 실패로 기록함
  • expect.poll(): 함수를 반복 호출해 반환값을 단언함. expect().toPass()는 코드 블록 전체를 재시도하고, 기본 timeout이 0이라 값을 직접 지정해야 함

픽스처와 프로젝트

섹션 제목: “픽스처와 프로젝트”

내장 픽스처는 page(테스트 전용 페이지), context(테스트 전용 컨텍스트), browser(워커 안에서 공유), browserName, request(테스트 전용 API 요청 컨텍스트)다. test.extend()로 사용자 픽스처를 정의하고, await use(값) 앞은 준비, 뒤는 정리 단계가 된다.

  • 테스트 범위(기본): 테스트마다 준비와 정리를 수행함
  • 워커 범위({ scope: 'worker' }): 워커 프로세스마다 한 번 준비하고 공유함. 워커별 테스트 계정에 사용함
  • 자동 픽스처({ auto: true }): 테스트가 인자로 지정하지 않아도 항상 실행됨. 실패 시 로그 수집에 사용함
  • 사용하지 않는 픽스처는 준비하지 않음(지연 실행)

프로젝트는 브라우저·기기별 실행, 환경별 baseURL과 retries, testMatch로 나눈 스모크 묶음에 사용한다. dependencies에 지정한 프로젝트가 먼저 실행되고, 그 프로젝트의 테스트가 실패하면 의존하는 프로젝트는 실행되지 않는다. 정리 작업은 준비 프로젝트의 teardown에 지정한다.

설정 파일

섹션 제목: “설정 파일”
  • webServer: 테스트 전에 서버를 실행하고 url이 2xx, 3xx, 400~403을 반환할 때까지 기다림. 대기 기본값은 60초(timeout). 배열로 프론트엔드와 백엔드를 함께 실행할 수 있음
  • reuseExistingServer: !process.env.CI: 로컬에서는 이미 실행 중인 서버를 재사용함. 재사용된 서버가 테스트 대상과 다른 버전일 수 있음(E2E 테스트 전 빌드)
  • retries: 기본값 0. 재시도에서 통과한 테스트는 flaky로 분류됨(Flaky 테스트 관리)
  • workers: 병렬 워커 수. 같은 파일의 테스트는 기본적으로 한 워커에서 순서대로 실행되고, fullyParallel: true면 파일 안의 테스트도 병렬로 실행함. 테스트가 실패하면 해당 워커를 종료하고 새 워커를 시작함
  • use: 모든 테스트에 적용하는 옵션. baseURL, trace, screenshot(off, on, only-on-failure, on-first-failure), video, storageState, 기기 에뮬레이션
  • --shard=2/3처럼 스위트를 샤드로 나눠 여러 머신에서 실행함

주요 기능

섹션 제목: “주요 기능”

인증 상태 재사용

섹션 제목: “인증 상태 재사용”

로그인을 준비 프로젝트에서 한 번 수행하고 storageState를 파일로 저장해 다른 테스트가 재사용한다. 저장 대상은 쿠키와 localStorage이고, storageState({ path, indexedDB: true })처럼 지정하면 IndexedDB도 저장한다. sessionStorage는 저장 API가 없어 공식 문서의 초기화 스크립트 방식을 따로 사용한다.

  • 저장 파일에는 인증 쿠키가 들어 있음. 공식 문서는 playwright/.auth를 .gitignore에 추가하고 저장소에 커밋하지 않도록 권고함
  • 테스트가 서버 상태를 변경하면 워커마다 다른 계정을 사용함(testInfo.parallelIndex 기준 워커 범위 픽스처)
  • 역할이 여럿이면 역할별로 상태 파일을 저장하고, 한 테스트에서 두 역할이 상호작용하면 역할별 컨텍스트를 생성함

네트워크 가로채기

섹션 제목: “네트워크 가로채기”

page.route()는 한 페이지, context.route()는 팝업을 포함한 컨텍스트 전체의 요청을 가로챈다. route.fulfill()로 응답을 대체하고, route.continue()로 요청을 변경해 전달하고, route.abort()로 요청을 실패시킨다. route.fetch()로 실제 응답을 받아 일부만 변경할 수도 있다. glob 패턴은 URL 전체와 일치해야 한다.

서버 오류(500), 지연, 빈 목록처럼 실제 환경에서 만들기 어려운 응답을 재현해 오류 처리 화면을 확인하는 데 사용한다. Mock Service Worker처럼 서비스 워커가 요청을 처리하면 route에 요청이 보이지 않는다. 이때는 serviceWorkers: 'block'을 설정한다.

  • API 테스트 설계는 API 테스트를 따름

섹션 제목: “트레이스 뷰어, 리포터, 코드젠”

시각 비교

섹션 제목: “시각 비교”

await expect(page).toHaveScreenshot()은 첫 실행에서 베이스라인을 생성하고, 이후 실행에서 pixelmatch로 비교한다. 파일 이름에 브라우저와 플랫폼이 포함되며(-chromium-darwin.png), 의도한 변경은 --update-snapshots로 갱신한다. 공식 문서는 OS, 하드웨어, 헤드리스 여부에 따라 렌더링이 달라지므로 베이스라인을 생성한 환경과 같은 환경에서 비교하라고 안내한다. 허용 오차와 베이스라인 관리는 시각 회귀 테스트에 있다.

QA에서 사용하는 방법

섹션 제목: “QA에서 사용하는 방법”
  • 회귀 스위트: 프로젝트로 브라우저별 실행을 나누고, 스모크 프로젝트(재시도 없음)와 전체 회귀 프로젝트를 분리함
  • CI 연동: forbidOnly, CI 전용 retries, JSON·JUnit 리포터를 설정하고, 실패 트레이스와 HTML 리포트를 산출물로 보관함. 파이프라인 구성은 GitHub Actions, Jenkins 문서를 따름
  • 실패 분류: JSON 리포터 결과, 스크린샷, 트레이스를 근거로 원인을 분류한 뒤 결함으로 등록함(E2E 실패 분류)
  • 결함 보고: 트레이스 파일과 실패 스크린샷을 재현 증거로 첨부하고, 대상 브라우저와 Playwright 버전을 발생 환경에 기록함(이슈 양식)
  • 접근성: getByRole('button', { name: '저장' })처럼 접근성 이름으로 찾는 로케이터는 이름이 없는 아이콘 버튼과 일치하지 않음. 이름 없이 getByRole('button')으로는 찾을 수 있으므로, 이름으로 찾지 못한 요소는 접근성 이름 누락을 점검 항목으로 기록함(접근성 테스트)
  • 페이지 객체와 계층 구조는 테스트 자동화 기본의 프레임워크 계층을 따름

선택 기준

  • 팀의 주 언어가 Java, C#, Ruby이거나 기존 WebDriver 자산과 Grid 인프라가 있으면 Selenium의 전환 비용이 작음
  • Safari 엔진(WebKit)까지 하나의 러너로 확인해야 하면 Playwright의 WebKit 지원을 검토함. Cypress의 WebKit은 실험 기능이고 cy.origin()을 지원하지 않음
  • 프론트엔드 개발자가 컴포넌트 테스트와 E2E를 같은 도구로 작성하려면 Cypress의 컴포넌트 테스트를 검토함. Playwright의 컴포넌트 테스트는 실험 패키지임
  • 웹과 모바일 앱을 하나의 API로 다루려면 WebdriverIO를 검토하고, 모바일 앱 자동화는 Appium 문서를 함께 확인함
  • 파일럿으로 같은 시나리오를 후보 도구별로 작성해 실행 시간, 실패 원인 분석 시간, 유지 비용을 비교함(테스트 자동화 기본의 도구 선택 절차)

주의할 점

섹션 제목: “주의할 점”
  • 재시도로 통과한 테스트를 PASS로 집계하면 간헐 결함이 기록되지 않음. retries는 flaky 분류 기록용으로 사용함(Flaky 테스트 관리)
  • force: true, waitForTimeout() 고정 대기, 재시도하지 않는 단언(expect(await locator.textContent()).toBe(...))은 대기 문제를 감춤. 기다릴 조건(URL, 응답, 요소 상태)을 웹 우선 단언으로 작성함
  • test.describe.configure({ mode: 'serial' })은 앞 테스트가 실패하면 뒤 테스트를 건너뜀. 공식 문서는 직렬 모드 대신 격리된 테스트를 권장함
  • 시각 비교 결과는 OS, 브라우저 버전, Playwright 버전에 따라 달라짐. 테스트 도구 버전 범위(^)를 두면 새 버전 설치 시 브라우저가 바뀜
  • 1.65부터 Node.js 20에서 테스트하지 않으며 지원 Node.js는 22.x, 24.x, 26.x임. 1.61에서 videosPath, videoSize 컨텍스트 옵션 등이 제거됨. 업그레이드 전에 릴리즈 노트의 제거 항목을 확인함
  • 1.63 릴리즈 노트는 실험 패키지 @playwright/experimental-ct-react, -react17, -vue를 더 이상 업데이트하지 않는다고 공지함
  • storageState 파일과 코드젠 --save-storage 파일은 인증 정보를 포함함. 저장소와 CI 산출물에 남기지 않음

현장 노트

  • 설정의 webServer가 vite preview처럼 빌드 산출물을 실행하는 구성에서 소스만 수정하고 빌드하지 않아 이전 번들로 테스트가 실행됨. 같은 원인으로 하루에 두 번 오판함(E2E 테스트 전 빌드)
  • 시각 비교 베이스라인은 운영체제와 Playwright 버전에 따라 렌더링 결과가 달라, Playwright 버전을 고정(예: 1.59.1)하고 베이스라인은 CI와 같은 플랫폼에서 생성함. 버전을 올리면 베이스라인을 다시 생성함
  • 화면에서 시각적으로 숨긴 라디오 버튼은 input을 클릭하면 not visible 오류로 실패함. 사용자와 같은 경로인 label을 클릭함
  • 같은 이름의 링크나 버튼이 여러 개면 getByRole이 엄격 모드 위반으로 실패하거나 의도하지 않은 요소를 선택함. 영역으로 범위를 좁혀 로케이터를 작성함

관련 문서

자동화테스트 자동화 기본테스트 자동화는 도구로 테스트를 실행하고 결과를 판정하는 활동이다. 이점과 한계, 테스트 피라미드, 테스트 용이성, 자동화 아키텍처(gTAA)와 프레임워크 계층, 케이스 자동화 방식 7가지, 도입 절차와 파이프라인 배치, 작성 원칙을 ISTQB CTAL-TAE 기준으로 설명한다.자동화Flaky 테스트 관리코드와 환경이 같은데도 실행마다 결과가 달라지는 테스트(Flaky 테스트)의 원인을 분류하고 탐지, 격리, 수정하는 절차다.자동화E2E 실패 분류Playwright 실패를 산출물 근거로 원인별로 분류하는 방법. 원인 분류 체계를 고르는 기준, 결과 상태 확인, 산출물 확인, 재현 순서, 결과 기록 기준을 다룬다. 분류는 수정보다 먼저 수행한다.자동화시각 회귀 테스트화면 캡처를 베이스라인과 비교해 의도하지 않은 화면 변화를 검출하는 테스트다. 캡처 환경, 허용 오차, 베이스라인 갱신 절차를 고정해야 결과를 판정 근거로 사용할 수 있다.
