브라우저 개발자 도구

브라우저에 내장된 개발자 도구를 Chrome DevTools 기준으로 정리한다. 네트워크 패널(필터, 요청 상세, 타이밍, 캐시 비활성화, 쓰로틀링, 요청 차단, 응답 재정의, HAR), 콘솔, Application 패널, 기기 모드와 Firefox·Safari의 차이, QA에서 결함 증거를 남기는 방법을 다룬다.

기본기난이도 기초웹 프론트엔드최종 업데이트 2026-11-24

브라우저 개발자 도구는 브라우저에 내장되어 페이지의 네트워크 요청, 콘솔 메시지, 저장소, 렌더링 성능을 확인하는 도구다. 이 문서는 Chrome DevTools를 기준으로 한다. Chrome DevTools는 Chrome에 포함되어 배포되고, 프런트엔드 코드는 Chromium 프로젝트에서 BSD-3-Clause 라이선스로 공개되어 있다(GitHub ChromeDevTools/devtools-frontend). Firefox는 Firefox DevTools, Safari는 Web Inspector를 내장한다. QA에서는 화면 결함의 원인이 클라이언트인지 서버인지 구분하고, 요청·응답·콘솔 오류를 결함 증거로 남기는 데 사용한다.

핵심 개념

섹션 제목: “핵심 개념”
패널 용도
Network 페이지가 보낸 요청과 받은 응답을 기록함. 상태 코드, 헤더, 본문, 소요 시간을 확인함
Console 페이지와 브라우저가 남긴 메시지를 확인하고 JavaScript를 실행함
Application 쿠키, 로컬 스토리지, 서비스 워커 같은 저장소와 백그라운드 동작을 확인하고 변경함
Elements DOM과 CSS를 확인하고 임시로 수정함
Sources 스크립트를 확인하고 중단점을 설정함. 응답 재정의(Local overrides) 파일도 여기서 관리함
Performance 런타임 성능을 녹화해 병목을 분석함
Lighthouse 페이지를 자동 점검해 성능, 접근성, SEO 등의 보고서를 생성함
  • DevTools는 열려 있는 동안의 네트워크 활동만 기록함. 페이지 로드 과정을 확인하려면 DevTools를 연 뒤 페이지를 새로 고침함
  • 기기 모드, 쓰로틀링, 요청 차단은 데스크톱 브라우저 안에서 조건을 흉내 내는 기능임. 실제 기기와 실제 네트워크를 대신하지 않음

네트워크 패널

섹션 제목: “네트워크 패널”

요청 목록과 필터

섹션 제목: “요청 목록과 필터”

요청 목록은 요청마다 이름, 상태 코드, 유형, 시작 주체(Initiator), 크기, 시간, 워터폴을 한 행으로 보여 준다. Initiator 열에 마우스를 올리면 그 요청을 만든 스크립트의 스택 트레이스가 표시된다.

필터 입력란은 텍스트와 속성 필터를 받는다. 속성 필터를 여러 개 쓰면 AND로 적용되고 OR는 지원하지 않는다. Invert를 체크하면 조건을 반대로 적용한다.

  • 유형 버튼: All, Fetch/XHR, JS, CSS, Img, Media, Font, Doc, WS, Wasm, Manifest, Other. Ctrl(macOS는 Command)을 누른 채 여러 개 선택
  • More filters: 데이터 URL 숨기기, 확장 프로그램 URL 숨기기, 차단된 응답 쿠키, 차단된 요청, 서드파티 요청

요청 상세

섹션 제목: “요청 상세”
탭 내용
Headers 요청 헤더와 응답 헤더. view source로 원래 순서를 확인함
Payload 쿼리 문자열과 폼 데이터
Preview 응답을 렌더링한 미리보기. 주로 이미지 확인에 사용함
Response 응답 본문 원문. 바이너리는 Base64, Hex, UTF-8로 디코딩해 확인함
Cookies 요청에 보낸 쿠키와 응답이 설정한 쿠키
Timing 요청 하나의 단계별 소요 시간
Messages, EventStream WebSocket 메시지와 서버 전송 이벤트(SSE)

워터폴과 타이밍 단계

섹션 제목: “워터폴과 타이밍 단계”

Timing 탭은 요청 하나를 다음 단계로 나눈다.

  • Queueing: 요청이 대기열에서 기다린 시간
  • Stalled: 연결을 열기 전 대기한 시간
  • DNS Lookup: 도메인 이름 확인
  • Initial connection: TCP 연결 수립. TLS 협상(SSL) 포함
  • Proxy negotiation: 프록시 서버와의 협상
  • Request sent: 요청 전송
  • ServiceWorker Preparation, Request to ServiceWorker: 서비스 워커를 거치는 요청의 준비와 전달
  • Waiting (TTFB): 요청을 보낸 뒤 응답 첫 바이트를 받을 때까지의 시간. 서버 처리 시간과 왕복 지연 포함
  • Content Download: 응답 본문을 받는 시간

워터폴 열은 요청마다 막대로 시점과 길이를 보여 준다. 막대의 밝은 부분은 대기 시간, 어두운 부분은 다운로드 시간이다. 목록 헤더를 우클릭해 워터폴 정렬 기준(Start Time, Response Time, End Time, Total Duration, Latency)을 바꿀 수 있다.

재현 조건 설정

섹션 제목: “재현 조건 설정”
기능 위치 용도
Preserve log Network 패널 상단 페이지 이동과 새로 고침 뒤에도 요청 기록을 유지함. 리다이렉트, 로그인 후 이동, 결제 완료 페이지 전환을 기록할 때 사용함
Disable cache Network 패널 상단 DevTools가 열려 있는 동안 브라우저 캐시를 사용하지 않음. 첫 방문 상태를 재현함
쓰로틀링 Throttling 드롭다운 느린 네트워크와 Offline을 흉내 냄. 프리셋(Network 참조 문서 기준 Fast 4G, Slow 4G, 3G)과 사용자 정의 프로필(Custom > Add…)을 사용함. 켜져 있으면 Network 탭에 경고 아이콘이 표시됨
요청 차단 Request conditions 드로어 URL 패턴에 맞는 요청을 차단하거나 개별 요청만 느리게 함
User agent 변경 Network conditions 드로어 Select automatically를 해제하고 다른 user agent를 지정함

요청 차단은 요청을 우클릭해 Block request를 선택하거나, Request conditions 드로어에서 Add condition으로 패턴을 추가한다. 패턴은 * 와일드카드를 받는다(*://cdn.example.com/*). 차단된 요청은 Status 열에 빨간색 (blocked:devtools)로 표시된다. DevTools를 닫으면 차단과 쓰로틀링은 해제되지만 패턴 목록은 저장되어 남는다. 예전 문서의 Network request blocking 탭은 현재 Request conditions 드로어로 합쳐졌다.

응답 재정의(Local overrides)

섹션 제목: “응답 재정의(Local overrides)”

응답 재정의는 서버를 고치지 않고 응답 본문이나 응답 헤더를 로컬 파일로 바꿔 페이지에 제공하는 기능이다. 백엔드 수정 전에 프런트엔드 동작을 확인하거나, 특정 응답(빈 목록, 오류 본문, CORS 헤더 누락)에서 화면이 어떻게 동작하는지 확인할 때 사용한다.

  1. Network 패널에서 요청을 우클릭하고 Override content 또는 Override headers를 선택
  2. 처음 사용하면 재정의 파일을 저장할 폴더를 선택하고 Allow를 클릭
  3. Sources 패널에서 파일을 수정해 저장하거나, Headers 탭의 Response Headers에서 헤더를 수정
  4. 페이지를 새로 고침
  • 재정의가 켜져 있는 동안 캐시는 비활성화됨
  • 재정의된 요청은 Response·Headers 탭 옆에 보라색 점이 표시되고, Has overrides 필터로 모아 볼 수 있음
  • 소스 맵으로 연결된 파일은 재정의할 수 없음. Elements 패널의 DOM 수정은 저장되지 않음
  • 일시 해제는 Sources > Overrides의 Enable Local Overrides 체크를 해제하고, 전체 삭제는 Clear를 클릭함

HAR 내보내기와 가져오기

섹션 제목: “HAR 내보내기와 가져오기”

HAR(HTTP Archive)은 요청과 응답 기록을 JSON으로 저장하는 형식이다. 결함을 재현한 네트워크 기록 전체를 개발자에게 전달할 때 사용한다.

  • 기본 내보내기는 Export HAR (sanitized)이고, Cookie, Set-Cookie, Authorization 헤더를 제외함
  • 이 헤더까지 포함하려면 Settings > Preferences > Network의 Allow to generate HAR with sensitive data를 켠 뒤 Export 드롭다운에서 Export HAR (with sensitive data)를 선택함
  • 가져오기는 HAR 파일을 요청 목록에 끌어 놓거나 Import HAR를 클릭함. 받은 HAR를 같은 화면에서 확인할 수 있음
  • 요청을 우클릭하면 Copy as cURL, Copy as fetch, Copy as PowerShell, Copy response를 사용할 수 있음. Edit and resend as fetch는 요청을 콘솔에서 수정해 다시 보냄

콘솔

섹션 제목: “콘솔”

페이지의 JavaScript와 브라우저가 남긴 메시지를 확인하고, 확인 중인 페이지에서 JavaScript를 실행하는 패널이다. 콘솔에서 실행한 코드는 페이지의 window에 접근하므로 페이지 상태를 실제로 변경한다.

  • 로그 수준: Verbose, Info, Warning, Error. Log Levels 드롭다운으로 Error만 남겨 오류를 확인함
  • 필터: 텍스트와 정규식(공백은 \s), url:과 -url:로 출처 스크립트를 지정하거나 제외함
  • Preserve Log: 콘솔 설정에서 켜면 페이지 이동 뒤에도 메시지를 유지함. 네트워크 패널의 Preserve log와 별도 설정임
  • Hide network: 404 같은 브라우저 네트워크 메시지를 숨김. Log XMLHttpRequests는 XHR·Fetch 요청을 콘솔에 기록함
  • Group similar messages in console: 기본으로 켜져 있어 같은 메시지를 묶어 표시함. 반복 횟수를 확인하려면 해제함
  • 저장: 우클릭 메뉴의 Save as…로 현재 메시지를 .log 텍스트 파일로 저장함

Application 패널

섹션 제목: “Application 패널”
  • 쿠키: Application > Storage > Cookies에서 출처를 선택함. Name, Value, Domain, Path, Expires/Max-Age, Size, HttpOnly, Secure, SameSite, Partition Key, Priority 열을 확인하고 Size 외 모든 칸을 수정할 수 있음. Delete selected, Clear all로 삭제함
  • 로컬 스토리지: Application > Storage > Local Storage에서 키와 값을 추가, 수정, 삭제함. 수정한 값은 페이지를 새로 고침해야 반영됨
  • 서비스 워커: Offline, Update on reload, Bypass for network로 오프라인 동작과 캐시된 응답을 확인함. Update, Unregister, Push, Sync로 갱신과 이벤트를 흉내 냄
  • 저장소 초기화: Clear storage 탭에서 서비스 워커 등록 해제와 캐시·저장소 삭제를 한 번에 수행함

쿠키 속성(HttpOnly, Secure, SameSite)은 보안 점검 항목과 연결된다(보안 테스트). 세션 쿠키를 지우거나 만료 시각을 바꿔 세션 만료 후 동작을 확인할 수도 있다.

기기 모드, Lighthouse, Performance

섹션 제목: “기기 모드, Lighthouse, Performance”

기기 모드는 데스크톱에서 모바일 화면을 근사하는 기능이다. 반응형 모드에서 뷰포트 크기를 직접 지정하거나 기기 프리셋을 선택하고, 기기 픽셀 비율(DPR), 기기 유형(Mobile, Mobile (no touch), Desktop, Desktop (touch)), CPU 쓰로틀링, 네트워크 쓰로틀링을 설정한다. 위치와 방향은 Sensors 패널에서 바꾼다.

공식 문서는 기기 모드를 모바일 기기에서의 모습을 1차로 근사하는 기능으로 설명하고, 코드가 실제 모바일 기기에서 실행되지 않으며 모바일 CPU 구조 같은 차이는 재현할 수 없다고 밝힌다. 실제 기기 확인은 원격 디버깅을 사용한다. Android 기기는 개발자 옵션의 USB 디버깅을 켜고 USB로 연결한 뒤 chrome://inspect#devices에서 Chrome 탭과 WebView를 검사한다.

  • Lighthouse: 성능, 접근성, SEO 등을 자동 점검하는 오픈소스 도구. DevTools 패널, CLI(lighthouse <url>), Node 모듈, PageSpeed Insights로 실행함. 로그인이 필요한 페이지는 DevTools 패널에서 점검함(접근성 테스트)
  • Performance: 런타임 성능을 녹화해 병목을 분석함. 패널을 열면 LCP, CLS를 바로 측정하고 상호작용하면 INP를 추가로 측정함. 녹화는 파일로 저장해 개발자에게 전달할 수 있음

QA에서 사용하는 방법

섹션 제목: “QA에서 사용하는 방법”

결함 증거 남기기

  • 재현 전에 Preserve log를 켜고 Disable cache 여부를 정해 기록함. 캐시 상태가 다르면 같은 절차로도 결과가 달라짐
  • 화면 오류가 나면 Network에서 해당 요청의 상태 코드, 응답 본문, Timing을 먼저 확인함. 4xx·5xx나 응답 본문의 오류 메시지가 있으면 서버 쪽, 응답은 정상인데 화면이 틀리면 클라이언트 쪽 결함 후보로 분류함
  • 이슈의 증거 칸에 실패한 요청의 메서드·URL·상태 코드, 응답 본문 일부, 콘솔 Error 메시지 원문, 스크린샷을 첨부함. 간헐 결함은 재현한 세션의 HAR와 콘솔 .log 파일을 함께 첨부함(이슈 양식)
  • 개발자가 같은 요청을 재현할 수 있도록 Copy as cURL 결과를 첨부함. 인증 헤더와 쿠키 값은 마스킹함
  • 응답 지연은 Timing의 Waiting (TTFB)와 Content Download를 나눠 기록함. TTFB가 길면 서버 처리나 네트워크 왕복, Content Download가 길면 응답 크기나 대역폭 쪽을 먼저 확인함

탐색과 회귀

  • 요청 차단과 응답 재정의로 서드파티 스크립트 실패, API 오류 응답, 빈 데이터 화면을 만들어 오류 처리와 빈 상태 화면을 확인함(탐색적 테스트)
  • 쓰로틀링과 Offline으로 로딩 표시, 타임아웃 메시지, 중복 제출 방지를 확인함
  • 화면에서 보이지 않는 API 응답 필드(권한 없는 데이터, 내부 식별자)가 내려오는지 Response 탭에서 확인함(API 테스트 기본)
  • E2E 실패를 분류할 때 Playwright 트레이스의 네트워크·콘솔 기록과 같은 관점(상태 코드, 콘솔 오류)으로 원인을 나눔(E2E 실패 분류, Playwright)

브라우저 도구와 다른 계층의 도구

기준 브라우저 도구 프록시 패킷 캡처
대표 도구 Chrome DevTools, Firefox DevTools, Safari Web Inspector Fiddler, Charles Wireshark, tcpdump
볼 수 있는 계층 그 브라우저(또는 검사 가능한 WebView)가 보낸 HTTP 요청과 페이지 상태(DOM, 콘솔, 저장소) 프록시를 거치는 HTTP(S) 트래픽. 브라우저 밖의 앱, 다른 기기 포함 네트워크 인터페이스의 패킷 전체. TCP·UDP와 비HTTP 프로토콜 포함
HTTPS 처리 브라우저 안에서 복호화된 내용을 그대로 표시함. 추가 설정 없음 프록시의 루트 인증서를 클라이언트가 신뢰해야 복호화됨 기본은 암호문만 보임. 키 로그 파일 등을 제공해야 복호화됨
설치·권한 설치 불필요 설치와 프록시 설정 필요. Charles 문서 기준 Android 앱은 사용자 인증서를 신뢰하도록 앱 설정이 필요함 설치와 캡처 권한(관리자, 캡처 드라이버) 필요
모바일·기기 트래픽 원격 디버깅으로 모바일 브라우저와 검사 가능한 WebView만 확인함 기기의 프록시를 PC로 지정해 앱 트래픽까지 확인함 같은 네트워크 구간에서 캡처하거나 미러링 포트가 필요함

선택 기준

  • 웹 화면 결함의 1차 확인은 브라우저 도구로 충분함. 설치가 필요 없고 콘솔, DOM, 저장소를 요청과 함께 확인할 수 있음
  • 모바일 네이티브 앱, 데스크톱 앱처럼 브라우저 밖의 HTTP 트래픽을 확인하거나 요청을 가로채 수정하려면 프록시 도구가 맞음
  • HTTP가 아닌 통신(MQTT, 자체 TCP 프로토콜), 연결 수립 실패, 재전송·끊김 같은 전송 계층 문제는 패킷 캡처가 맞음
  • 결함이 특정 브라우저에서만 재현되면 그 브라우저의 도구로 확인함. 브라우저마다 HAR 내보내기의 민감정보 처리가 다르므로 공유 전 처리 방법도 다름

주의할 점

섹션 제목: “주의할 점”
  • HAR에는 요청·응답 헤더와 본문이 들어감. Chrome의 sanitized 내보내기가 제외하는 것은 Cookie, Set-Cookie, Authorization 헤더이고, URL 쿼리 문자열, 요청 본문, 응답 본문에 있는 토큰과 개인정보는 남을 수 있음. Firefox와 Safari 문서에는 제외 옵션이 없으므로 공유 전에 파일을 열어 마스킹함
  • Allow to generate HAR with sensitive data는 필요한 작업이 끝나면 다시 끔. 켠 상태에서 민감정보 포함 HAR를 실수로 첨부할 수 있음
  • Copy as cURL, 콘솔 .log, 스크린샷에도 토큰, 이메일, 주문 정보가 남을 수 있음. 외부 트래커나 공개 저장소에 올리기 전에 마스킹함
  • 운영 계정이나 고객 데이터가 있는 세션의 HAR는 회사의 데이터 취급 기준에 따라 공유 범위를 정함
  • 쓰로틀링, 기기 모드는 근사치임. 성능 수치나 모바일 렌더링 결함은 실제 기기와 실제 네트워크에서 재확인함
  • 쓰로틀링과 요청 차단, 응답 재정의를 켠 채 다른 테스트를 계속하면 결과가 오염됨. 차단 패턴과 재정의 파일은 DevTools를 닫아도 삭제되지 않으므로 테스트 뒤 켜짐 상태를 확인함
  • 콘솔에서 실행한 코드는 실제 페이지 상태와 서버 데이터를 변경할 수 있음. 운영 환경에서는 조회 목적 외의 코드를 실행하지 않음
  • DevTools를 연 뒤에 발생한 요청만 기록됨. 첫 로드에서 발생한 결함은 DevTools를 연 상태에서 다시 로드해 기록함
