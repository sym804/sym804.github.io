회귀 테스트 범위 선정

변경 뒤 기존 기능이 의도하지 않게 실패하는지 확인하기 위해, 회귀 스위트에서 이번 회차에 수행할 TC를 선택하는 절차다(Regression Test Selection).

기본기난이도 중급최종 업데이트 2026-11-24

테스트 시간이 제한된 회차에서 회귀 스위트 중 수행할 TC와 제외할 TC를 정하고, 그 근거를 기록하는 절차다.

확인 테스트와 회귀 테스트

섹션 제목: “확인 테스트와 회귀 테스트”
  • 확인 테스트(Confirmation Testing): 수정한 결함이 해결되었는지 원래 실패한 TC나 재현 절차를 다시 수행함
  • 회귀 테스트(Regression Testing): 변경한 영역을 포함해 기존 동작에 의도하지 않은 영향이 없는지 확인함. 같은 컴포넌트, 다른 컴포넌트, 연결된 시스템이 모두 대상
  • 결함을 수정한 뒤에는 둘 다 수행함. 확인 테스트 통과는 회귀가 없다는 근거가 되지 않음
  • 회귀 테스트가 필요한 변경: 결함 수정, 기능 추가와 변경, 환경 변경(라이브러리, OS, DB, 설정)

선정 순서

섹션 제목: “선정 순서”
  1. 고정 포함: 리스크 기반 테스트의 매우 높음 TC(권한 게이트, 세션, 데이터 격리, 되돌릴 수 없는 삭제, 돈과 데이터 정합성)와 배포 직후 스모크 테스트. 변경 위치와 무관하게 매 회차에 포함함
  2. 변경 영향 분석으로 도출한 영역의 TC
  3. 결함 밀집 영역의 TC: 이슈 로그를 영역별로 집계해 과거 결함, 특히 회귀 결함이 많았던 영역
  4. 남은 시간에 우선순위 높음, 보통 순으로 추가함. 낮음은 마지막

변경 영향 분석

섹션 제목: “변경 영향 분석”
  • 변경 목록은 diff, 릴리즈 노트, 이번 회차에 종결할 이슈에서 수집함
  • 직접 의존: 변경한 함수, API, 화면을 호출하거나 사용하는 기능
  • 간접 의존: 공통 유틸, 공통 컴포넌트, 변경한 DB 테이블과 컬럼을 사용하는 모든 화면, 배치, 보고서. 사용처는 코드 검색으로 확인함
  • 계산식이나 데이터 형식이 변경되면 그 값을 표시하거나 집계하는 기능 모두
  • 라이브러리나 설정 변경처럼 사용처를 특정하기 어려운 변경은 전체 스모크 테스트와 해당 라이브러리를 사용하는 기능
  • 화면 구성 변경(표를 카드로, 목록을 그리드로)은 표시 값과 함께 그 화면이 제공하던 조작(정렬, 필터, 선택, 펼치기, 마우스를 올렸을 때만 표시되는 기능)의 목록을 변경 전후로 대조함
  • 문구와 용어의 일괄 변경은 화면 문구를 찾는 테스트 코드(셀렉터, 기대 문구)도 영향 범위에 포함함

규칙

  • 고정 포함 TC는 일정이 부족해도 제외하지 않음
  • 제외한 TC는 결과를 N/A로 기록하고 비고에 제외 사유를 기록함
  • 영향 분석 근거(변경 목록과 선택한 영역)를 회차 기록에 남김. 회귀 결함이 발견되면 이 기록으로 누락 원인을 확인함

현장 노트

  • 같은 배당 수익률을 화면마다 따로 계산하는 SQL 사본이 세 벌 있었음. 한 곳의 계산 기준을 수정해도 다른 화면은 이전 기준으로 남아, 점검에서 화면 간 수치 불일치 결함이 여러 건 발견됨. 계산을 한 함수로 통합하고, 같은 종목의 값을 화면 사이에서 비교하는 테스트를 추가해 지표 계산을 변경할 때마다 수행함
  • 모바일에서 종목 검색 결과 표를 카드로 변경하면서, 표 헤더가 정렬의 유일한 진입점이었다는 점을 영향 분석에서 놓침. 기간별 수익률 정렬은 드롭다운으로 옮겼으나 세 열(연기금, 현재가, 종목명)의 정렬이 빠져 모바일에서는 주소를 직접 수정해야만 사용할 수 있었고, QA 검토에서 발견됨. 표시 값은 대조했지만 조작 기능은 대조하지 않았음. 소스에서 표 헤더의 정렬 필드와 드롭다운 값을 추출해 차집합이 비었는지 확인하는 테스트를 추가함
  • 문구 용어를 일괄 치환하면서 E2E 테스트의 셀렉터 문자열(“바꾸기”)까지 변경되어, 그 릴리즈부터 CI의 E2E가 실패 상태로 남았고 이틀 뒤에 확인됨. 화면 문구는 맞았고 테스트 코드가 잘못 변경된 경우였음

적용 예: 무료 배송 기준 변경

섹션 제목: “적용 예: 무료 배송 기준 변경”

변경 내용이 “무료 배송 기준을 50,000원 이상에서 30,000원 이상으로 변경한다.“이고 회귀 스위트가 400건(예시)인 경우 선정 결과는 다음과 같다.

  1. 고정 포함: 권한 게이트, 세션, 데이터 격리, 되돌릴 수 없는 삭제, 돈과 데이터 정합성 TC와 스모크 테스트. 예: 60건
  2. 변경 영향 분석: diff에서 배송비 계산 함수와 설정 값의 변경을 확인함
    • 직접 의존: 장바구니, 주문서, 결제 API의 배송비
    • 간접 의존: 부분 환불의 배송비 재계산, 주문 상세와 영수증, 관리자 매출 보고서의 배송비 합계, 배송비 무료 쿠폰, 정산 배치
    • 데이터: 변경 전에 생성된 주문의 배송비가 새 기준으로 다시 계산되지 않는지
    • 선정 TC 예: 85건
  3. 결함 밀집 영역: 이슈 로그에서 부분 환불 영역의 과거 회귀 결함을 확인해 해당 TC를 추가함. 예: 20건
  4. 남은 시간에 우선순위 높음, 보통 TC를 추가함. 예: 35건

선정한 200건(예시) 외의 TC는 N/A로 기록하고 비고에 “무료 배송 기준 변경과 무관(영향 분석 근거: 회차 기록)“처럼 제외 사유를 적는다. 새 기준의 경계값 TC(29,999원, 30,000원, 30,001원)는 이번 회차에 새로 작성해 회귀 스위트에 편입한다.

TC 예시

섹션 제목: “TC 예시”
항목 TC 예시
변경 직접 대상(경계값) 장바구니 상품 금액이 29,999원, 30,000원, 30,001원일 때 주문서의 배송비가 각각 기본 배송비(예: 3,000원), 0원, 0원으로 표시되고 결제 금액에 같은 값이 반영되는지 확인함
간접 의존: 부분 환불 30,000원 주문(무료 배송)에서 10,000원 상품을 부분 환불해 남은 금액이 기준 미만이 될 때, 명세의 환불 규칙(예: 기본 배송비 차감)대로 환불 금액이 7,000원으로 계산되고 환불 내역 화면에 같은 금액이 표시되는지 확인함
간접 의존: 과거 데이터 기준 변경 전에 40,000원으로 결제해 배송비 3,000원이 부과된 주문의 주문 상세와 영수증에서 배송비가 3,000원으로 유지되는지 확인함
간접 의존: 집계 관리자 매출 보고서의 기간별 배송비 합계가 같은 기간 주문 데이터의 배송비 합계와 일치하는지 확인함
고정 포함: 데이터 격리 사용자 A로 로그인한 상태에서 사용자 B의 주문 id로 주문 상세를 요청해 403 또는 404가 반환되고 B의 주문 정보가 응답에 없는지 확인함
확인 테스트(결함 수정 시) 이슈에 기록된 재현 절차를 수정본이 배포된 환경에서 그대로 수행해 기대 결과대로 동작하는지 확인하고, 같은 함수를 사용하는 기능의 회귀 TC를 함께 수행함

전체 회귀 수행 시점

섹션 제목: “전체 회귀 수행 시점”
  • 전체 회귀 시점은 릴리즈 기준과 실행 비용으로 정함. 예: 1인 개발 저장소에서는 작업 중에 변경과 관련된 테스트만 수행하고, 전체 회귀는 그날의 작업 묶음을 마친 뒤 커밋 직전에 한 번 수행함
  • 중간에 수행한 전체 회귀는 그 뒤의 변경을 포함하지 않음. 공통 모듈이나 환경을 변경했거나 전체 회귀 뒤에 추가 수정이 있으면 다시 수행함
  • 전체 회귀 도중에는 코드를 수정하지 않음. 소스 문자열이나 파일 수정 시각을 검사하는 테스트가 실행 도중의 수정 때문에 실패할 수 있음
  • 병렬 워커 수는 테스트 환경이 감당할 수 있는 수로 제한함. 워커가 너무 많으면 자원 부족으로 실패가 발생해 회귀 결함과 구분하기 어려움

현장 노트

  • 전체 회귀를 몇 번 수행하는지 확인하려고 작업 세션 기록 253개를 집계함. 전체 회귀를 수행한 25개 세션 모두 2회 이상 수행했고, 총 292회(세션당 평균 11.7회)였음. 그 저장소의 전체 회귀는 7,000건이 넘고 12~15분이 걸림. 이후 작업 중에는 변경과 관련된 테스트 파일만 수행하고 전체 회귀는 커밋 직전에 한 번 수행함
  • 24코어 PC에서 워커 수를 자동(-n auto, 24개)으로 지정한 전체 회귀에서 9건이 disk I/O error, MemoryError로 실패했으나 순차로 다시 수행하자 140건 모두 통과함. 워커 수를 8개로 제한함
  • 전체 회귀 시작 5분 뒤 파일 하나를 수정하자 소스 문자열을 검사하는 테스트(inspect.getsource 사용) 1건이 실패함(6,843건 통과). 테스트 러너는 시작 시점의 모듈을 사용하는데 파일이 변경되면서 줄 번호가 밀린 것이 원인이었고, 단독으로 수행하면 통과함. 이후 회귀 도중 수정이 있었으면 수정하지 않은 상태로 전체를 다시 수행한 결과를 커밋 근거로 사용함

테스트 계획, 결함 분류, 보고에 적용

섹션 제목: “테스트 계획, 결함 분류, 보고에 적용”

테스트 계획

  • 회차 계획에 변경 목록, 영향 영역, 선정 단계별 TC 수, 제외 TC 수와 사유를 기록함
  • 고정 포함 TC 목록은 회차와 무관하게 유지하고, 리스크 기반 테스트의 평가가 변경되면 함께 갱신함
  • 전체 회귀를 수행하는 시점(커밋 직전, 릴리즈 후보 빌드)을 계획에 명시함

결함 분류

  • 회귀 결함은 이슈에 회귀 여부와 마지막으로 통과한 버전을 기록함. 발생 버전과 비교해 원인 변경을 좁힐 수 있음
  • 회귀 결함마다 그 영역이 이번 회차 영향 분석에 포함되었는지 기록함. 포함되지 않았다면 누락된 의존 경로(공통 함수, 테이블, 설정)를 다음 영향 분석의 확인 항목에 추가함
  • 확인 테스트가 실패하면 재개하고, 수정 때문에 다른 곳에서 새로 발생한 증상은 새 이슈로 등록함(결함 생명주기)

보고

  • 선정 단계별 TC 수와 결과, N/A로 제외한 TC 수와 사유를 함께 보고함. 예: “회귀 400건 중 200건 수행(고정 60, 영향 85, 결함 밀집 20, 추가 35), 199건 PASS, 1건 FAIL, 200건 N/A(영향 분석상 무관)”
  • 발견한 회귀 결함 수와 그중 영향 분석에서 누락된 영역의 결함 수를 구분해 보고함

스위트 유지보수

섹션 제목: “스위트 유지보수”
  • 폐기: 기능이 삭제되거나 변경되어 기대 결과가 더 이상 유효하지 않은 TC는 삭제하거나 수정함
  • 통합: 같은 분기를 같은 레벨에서 확인하는 TC는 하나로 통합함. 레벨 구분은 테스트 레벨과 테스트 유형 참고
  • 편입: 확인 테스트에 사용한 재현 절차와 탐색적 테스트와 세션 기반 테스트 관리에서 발견한 경로를 회귀 TC로 편입함
  • 자동화한 회귀 TC는 Flaky 테스트 관리 기준으로 관리함. 결과를 신뢰할 수 없는 TC는 회귀 판정 근거로 사용하지 않음

흔한 실수

섹션 제목: “흔한 실수”
  • 확인 테스트만 수행하고, 같은 API나 데이터를 공유하는 다른 기능의 회귀 테스트를 생략함
  • 새 TC만 추가하고 폐기와 통합을 하지 않아 수행 시간이 늘어남. 일정에 쫓겨 리스크 기준 없이 스위트 뒷부분을 생략하게 됨
  • 변경 위치 근처만 선정하고 고정 포함 TC를 생략함
  • 무엇을 제외했는지 기록하지 않아 회귀 결함이 발견된 뒤 누락 지점을 찾지 못함

출처

섹션 제목: “출처”
  • ISTQB Certified Tester Foundation Level(CTFL) 실라버스 v4.0.1, 2024-09-15, 2.2.3 Confirmation Testing and Regression Testing

관련 문서

테스트 설계리스크 기반 테스트실패했을 때의 피해와 실패할 가능성을 기준으로 무엇을 먼저, 얼마나 깊게 테스트할지 정하는 방식이다(Risk-Based Testing).프로세스결함 생명주기결함이 등록된 시점부터 종결될 때까지 거치는 상태와, 상태 사이에 허용되는 전이를 정한 규칙이다(Defect Lifecycle).테스트 설계탐색적 테스트와 세션 기반 테스트 관리테스트 대상을 학습하면서 테스트 설계, 실행, 결과 평가를 동시에 진행하는 경험 기반 기법이다(Exploratory Testing). ISTQB, Kaner, Bach·Bolton의 정의 차이, 테스트 아이디어(HTSM)와 판정 기준(FEW HICCUPPS) 휴리스틱, 세션 기반 테스트 관리의 차터, 세션 기록, TBS 지표를 다룬다.
