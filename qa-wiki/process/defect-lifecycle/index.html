결함 생명주기

결함이 등록된 시점부터 종결될 때까지 거치는 상태와, 상태 사이에 허용되는 전이를 정한 규칙이다(Defect Lifecycle).

기본기난이도 기초최종 업데이트 2026-11-24

이슈 양식은 기록 항목을, 심각도 기준은 결함의 영향 정도를 정한다. 생명주기는 결함의 상태를 언제, 어떤 근거로 변경하는지를 정한다. 트래커마다 상태 이름은 다르므로 이름보다 전이 규칙을 맞춘다.

기본 흐름

섹션 제목: “기본 흐름”
  1. 등록(New): 이슈 양식의 발견 블록 작성
  2. 할당(Assigned): 담당자 지정, 심각도 기준과 우선순위 확정
  3. 수정 중(In Progress): 원인 분석과 수정
  4. 수정 완료(Fixed): 수정이 병합되어 확인 테스트를 기다리는 상태
  5. 종결(Closed): 확인 테스트 통과 뒤 종결 블록 작성

확인 테스트에서 원래 증상이 재현되면 재개(Reopened)로 되돌리고 다시 할당한다. 수정 때문에 새로 발생한 다른 증상은 재개하지 않고 새 이슈로 등록한 뒤 원 이슈에 링크한다.

허용 전이

섹션 제목: “허용 전이”
현재 상태 다음 상태 전이 조건
등록 할당 발견 블록 작성 완료, 심각도와 우선순위 확정
등록, 할당, 수정 중 중복, 결함 아님, 재현 불가 아래 「예외 상태」의 근거를 먼저 기록
할당 수정 중 담당자가 착수
할당 보류 수정하지 않기로 합의, 대상 버전 또는 재검토 조건 기록
수정 중 수정 완료 수정이 병합됨, 수정 버전 기록
수정 완료 종결 배포 환경에서 원래 재현 절차로 확인 테스트 통과, 회귀 테스트 수행
수정 완료 재개 확인 테스트에서 원래 증상이 재현됨
재개 할당 재현 결과(환경, 빌드, 증거)를 기록하고 다시 할당
종결 재개 같은 원인의 증상이 다시 발생함
보류 할당 재검토 조건이 충족됨
  • 표에 없는 전이(예: 등록에서 바로 종결, 수정 중에서 종결)는 허용하지 않음. 트래커가 워크플로 제한을 지원하면 설정으로 막음
  • 트래커의 상태 이름이 다르면 이 표의 상태에 대응시킨 표를 팀 문서에 둠. 이슈 로그와 트래커의 상태를 대조할 때 필요한 구분은 동등 분할의 상태 값 예시 참조

예외 상태

섹션 제목: “예외 상태”

수정하지 않고 닫거나 보류하는 상태는 모두 근거를 남긴다. 근거 없이 닫힌 이슈는 같은 내용으로 다시 등록된다.

  • 중복(Duplicate): 같은 원인의 기존 이슈를 링크함. 새 이슈에만 있는 정보(재현 환경, 증거)는 원 이슈에 추가함
  • 결함 아님(Not a Defect): 명세와 일치함을 확인한 경우. 근거가 된 명세 문장이나 결정 기록을 링크함. 명세 자체가 잘못되었다면 결함 아님으로 닫지 않고 명세 수정 이슈로 전환함
  • 재현 불가(Cannot Reproduce): 확인한 환경, 버전, 데이터, 시도한 절차와 횟수를 기록함. 재현 빈도가 간헐이면 등록 시 남긴 증거부터 다시 검토함
  • 보류(Deferred): 이번 릴리즈에서 수정하지 않기로 합의한 경우. 합의한 사람, 대상 버전 또는 재검토 조건을 기록함

규칙

  • 보류는 수정 시점을 미루는 결정이며 심각도를 변경하지 않음
  • 예외 상태로 변경하기 전에 위 근거를 먼저 기록함

개발 완료와 QA 종결의 분리

섹션 제목: “개발 완료와 QA 종결의 분리”
  • 코드 병합으로 도달하는 상태는 수정 완료(Fixed)까지임
  • 커밋 메시지나 PR 본문의 이슈 닫기 키워드로 병합 시 이슈가 자동 종결되는 설정이면 확인 테스트가 누락되기 쉬움. 자동 종결을 사용하지 않거나, 닫힌 뒤에도 확인 테스트 완료 표시(라벨 등)가 있어야 종결로 인정함
  • 종결은 수정본이 배포된 환경에서 원래 재현 절차를 다시 수행해 통과한 뒤에만 진행함
  • 확인 테스트와 함께 변경 영향을 받는 영역의 회귀 테스트를 수행함. 범위는 회귀 테스트 범위 선정 기준을 따름

종결 시 기록

섹션 제목: “종결 시 기록”
  • 확인한 환경과 빌드(버전 또는 커밋 식별자)
  • 확인 테스트 결과: 원래 재현 절차를 그대로 수행한 결과
  • 함께 수행한 회귀 테스트 범위
  • 종결 블록(원인, 수정 내용, 수정 버전, 재발 방지, 영향 범위)

적용 예: 쿠폰 할인 미반영 결제

섹션 제목: “적용 예: 쿠폰 할인 미반영 결제”

가상의 결함 “정률 쿠폰을 적용했는데 할인 전 금액으로 결제됨”이 종결되기까지의 기록은 다음과 같다.

  1. 등록: 발견 블록 작성. 재현 절차(50,000원 상품, 10% 쿠폰 적용, 카드 결제), 기대 결과(45,000원 결제), 실제 결과(50,000원 결제), 재현 빈도 “항상”, 증거(결제 승인 내역 캡처), 환경(PC, 모바일 웹 모두)
  2. 할당: 심각도 기준에 따라 심각도(예: Critical)와 우선순위를 정하고 결제 담당자에게 할당
  3. 수정 완료: 수정이 병합되어 수정 완료로 변경. 커밋 메시지의 자동 종결 키워드는 사용하지 않음
  4. 재개: 스테이징 빌드의 확인 테스트에서 PC는 45,000원으로 결제되었으나 모바일 웹에서 원래 재현 절차대로 50,000원이 결제됨. 원래 증상이라 재개로 변경하고, 모바일 웹 결제 요청 캡처를 첨부해 다시 할당
  5. 수정 완료: 모바일 웹 결제 경로의 할인 금액 전달을 수정해 병합
  6. 확인 테스트와 회귀 테스트: PC와 모바일 웹 모두 45,000원으로 결제됨. 회귀 테스트에서 쿠폰과 적립금을 함께 사용하면 적립금이 두 번 차감되는 증상을 발견함. 원래 증상이 아니므로 새 이슈로 등록하고 원 이슈에 링크
  7. 종결: 확인한 빌드, 확인 테스트 결과, 수행한 회귀 범위, 종결 블록을 기록하고 종결

TC 예시

섹션 제목: “TC 예시”
항목 TC 예시
확인 테스트 이슈에 기록된 재현 절차(50,000원 상품, 10% 쿠폰, 카드 결제)를 수정본이 배포된 환경에서 이슈에 기록된 모든 환경(PC, 모바일 웹)으로 수행해 결제 금액과 승인 금액이 45,000원인지 확인함
재개 판정 확인 테스트에서 이슈의 기대 결과와 다른 동작이 원래 재현 절차로 다시 나타나면 재개로 변경하고, 확인한 빌드와 증거를 이슈에 추가함
새 이슈 판정 확인 테스트는 통과했으나 같은 화면의 다른 조건(예: 쿠폰과 적립금 동시 사용)에서 다른 증상이 발생하면 원 이슈는 종결하고 새 이슈를 등록해 원 이슈에 링크함
재현 불가 판정 전 확인 재현 시도의 절차가 신고된 절차와 단계마다 일치하는지(같은 화면, 같은 조작, 같은 데이터) 확인한 뒤, 일치하는 절차로 정한 횟수(예: 5회)를 수행해 한 번도 재현되지 않을 때만 재현 불가로 변경함
워크플로 설정 이슈 번호를 참조한 PR을 병합해 이슈가 수정 완료로 변경되고 종결로 변경되지 않는지 확인함

테스트 계획, 결함 분류, 보고에 적용

섹션 제목: “테스트 계획, 결함 분류, 보고에 적용”

테스트 계획

  • 회차 일정에 확인 테스트와 회귀 테스트 시간을 따로 배정함. 수정 완료 건이 많은 회차 후반에 시간이 부족해지기 쉬움
  • 종결 기준(배포 환경에서 원래 재현 절차로 확인)과 출시 기준(예: Critical 이상 미해결 결함 0건, 보류 결함은 승인 목록에 있음)을 계획서에 기록함

결함 분류

  • 종결 사유(수정, 중복, 결함 아님, 재현 불가)를 별도로 집계함. 보류는 종결이 아니라 미해결 건수로 집계함. 결함 아님이 많으면 명세가 모호하다는 신호이고, 재현 불가가 많으면 등록 시 증거가 부족하다는 신호임(이슈 양식의 재현 빈도와 증거)
  • 재개된 이슈 수를 영역별로 집계해 확인 테스트 전 개발 단계의 검증이 부족한 영역을 찾음
  • 문서와 구현이 다를 때는 어느 쪽이 틀렸는지 항목마다 판정해, 구현이 틀렸으면 결함으로, 문서가 틀렸으면 문서 수정 이슈로 분류함

보고

  • 상태별 건수에 더해 기간 내 등록·종결 건수를 기록해 미해결 결함의 증감을 함께 보고함
  • 수정 완료 상태로 확인 테스트를 기다리는 건은 종결과 구분해 보고함
  • 보류 결함은 목록, 심각도, 합의한 사람, 재검토 조건을 함께 보고함

현장 노트

  • 사용자가 “수익률 기간 버튼을 클릭해도 열이 표시되지 않는다”고 신고함. 첫 재현 시도는 검색과 다른 컨트롤을 조작한 것이라 결함이 나타나지 않았고, 신고한 기간 버튼을 실제로 클릭하자 표의 값과 헤더는 갱신되지만 어느 기간이 선택되었는지 버튼에 표시되지 않는 결함이 확인됨. 이후 “재현되지 않음”으로 보고하기 전에 재현 절차가 신고의 절차와 일치하는지 확인함
  • QA 검토에서 “이번 변경으로 표의 Ctrl+C/V 복사·붙여넣기가 동작하지 않는다”는 지적이 Major로 보고됨. 확인해 보니 사용하는 그리드 라이브러리의 에디션에서 제공하지 않아 구현된 적이 없는 기능이었고, 사용자 매뉴얼에만 적혀 있었음. 회귀 결함이 아니라 문서 결함으로 처리함. 같은 화면에서 “셀을 더블 클릭하면 편집”이라는 매뉴얼 문장은 맞고 구현(한 번 클릭으로 편집)이 틀린 경우도 함께 발견됨
  • 같은 증상(입력은 전달되지만 제출되지 않음)을 수정한 커밋이 여섯 번 넘게 반복된 도구가 있음. 단위 테스트는 전송 지연이 적용되었는지까지만 확인하고, 실제로 제출되는지는 도구를 실행해야 확인할 수 있었음. 이 경우 단위 테스트 통과는 증상이 해결되었다는 근거가 되지 않아, 원래 재현 절차를 실제 도구에서 수행한 결과로 종결 여부를 판단함
  • 하루에 5건을 종결했으나 모두 그날 등록한 이슈였고, 새 이슈 2건이 추가되어 열린 이슈가 26건에서 28건으로 늘어남. 이후 보고에는 그날 등록하고 그날 종결한 건을 종결 실적과 구분하고, 기존 미해결 결함이 몇 건에서 몇 건으로 변했는지 함께 기록함
  • 이슈를 다른 트래커로 이관할 때 원본은 “not planned”로 닫고 새 이슈 링크를 코멘트로 남김. 양쪽을 모두 열어 두지 않음

흔한 실수

섹션 제목: “흔한 실수”
  • 코드 병합과 동시에 이슈가 자동 종결되어 배포 환경에서 확인하지 않음
  • 재현 불가나 결함 아님으로 닫으면서 확인한 환경과 근거를 남기지 않음
  • 같은 증상이 재발했는데 재개하지 않고 새 이슈를 등록해 이력이 두 곳으로 나뉨
  • 보류하면서 심각도를 함께 낮춤. 보류 기간 동안 영향의 크기를 판단할 근거가 사라짐
