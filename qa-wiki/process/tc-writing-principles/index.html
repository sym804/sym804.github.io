TC 작성 원칙

처음 보는 사람이 따라 할 수 있고 수행 직후 통과와 실패를 판정할 수 있는 테스트 케이스의 작성 기준. TC 형식(단계형, BDD 시나리오, 체크리스트, 탐색적 테스트 차터)의 선택 기준, 구성 요소별 작성법, 리뷰 점검 항목을 다룬다.

노하우난이도 기초최종 업데이트 2026-11-24

테스트 케이스의 구성

섹션 제목: “테스트 케이스의 구성”

ISTQB 용어집은 테스트 케이스를 사전조건, 입력, 동작, 기대 결과, 사후조건의 묶음으로 정의한다. TC 관리 도구의 열 이름은 도구마다 다르지만 대부분 이 구성에 대응한다.

  • 식별자와 제목: 다른 TC와 겹치지 않는 ID, 무엇을 확인하는지 드러나는 제목
  • 사전조건: 수행 전에 갖춰져 있어야 하는 상태(계정, 권한, 데이터, 설정)
  • 절차: 수행자가 하는 조작과 입력값
  • 기대 결과: 조작 뒤 확인할 결과
  • 우선순위: 수행 순서와 회귀 범위를 정하는 기준
  • 추적 정보: 근거가 된 요구사항, 사용자 스토리, 결함 번호

TC 형식

섹션 제목: “TC 형식”
형식 구성 맞는 경우
단계형 TC 사전조건, 절차, 기대 결과 회귀 테스트처럼 여러 사람이 같은 결과를 반복해서 얻어야 하는 경우
BDD 시나리오(Gherkin) Given(초기 맥락), When(행동), Then(기대 결과) 기획, 개발, QA가 같은 문장으로 요구사항을 정하고 자동화 단계와 연결하는 경우
체크리스트 확인할 조건의 목록. 절차는 적지 않음 수행자가 제품에 익숙하고 화면이 자주 바뀌는 경우
탐색적 테스트 차터 테스트 목표를 담은 차터. 세션 기반으로 수행하면 타임박스도 정함 명세가 부족하거나 일정 압박이 큰 경우

선택 기준

  • 수행 절차의 재현성과 인수인계가 중요하면 단계형이 맞음. 절차를 상세히 적을수록 작성과 유지 비용이 늘어남
  • 요구사항 문장을 그대로 자동화와 연결하려면 BDD 시나리오가 맞음. 단, 화면 문구와 입력값 수준의 세부를 Given/When/Then에 모두 넣으면 시나리오가 길어져 읽기 어려워짐
  • 체크리스트와 차터는 작성 비용이 작은 대신 결과가 수행자의 경험에 따라 달라짐. 수행 기록(무엇을 확인했는지)을 남겨야 커버리지를 설명할 수 있음
  • 한 프로젝트에서 섞어 사용할 수 있음. 회귀 핵심 흐름은 단계형, 새 기능은 차터, 반복 점검 항목은 체크리스트처럼 나눔

체크리스트 기반 테스트와 탐색적 테스트의 정의와 진행 방법은 테스트 기법 분류와 탐색적 테스트와 세션 기반 테스트 관리에 있다. 아래 작성 기준은 단계형 TC를 기준으로 하고, 체크리스트와 차터에는 「판정 가능한 기대 결과」만 적용한다.

재현 가능한 절차

섹션 제목: “재현 가능한 절차”
  • 제품을 처음 보는 수행자가 TC만 읽고 같은 조작을 할 수 있어야 함. 메뉴 경로, 입력값, 사용할 파일 이름과 형식을 절차에 적음
  • 절차에는 조작만 적고, 확인할 내용은 기대 결과에 적음. “서버로 전송되는 값을 확인한다”처럼 화면에서 따라 할 수 없는 관측은 절차에 넣지 않고, 필요하면 API TC나 자동화 검증으로 분리함
  • 화면 요소 이름과 문구는 화면에 실제로 표시되는 값 그대로 적음. 표시 언어가 여럿이면 기준 언어를 정함
  • 버튼, 입력란, 표시 문구를 구분하는 표기 규칙(예: 버튼은 대괄호, 표시 문구는 따옴표)을 팀에서 정해 두면 TC 사이의 표기가 맞춰짐

판정 가능한 기대 결과

섹션 제목: “판정 가능한 기대 결과”
  • 수행 직후 통과와 실패를 판정할 수 있게 구체적으로 적음. “정상 동작한다”는 판정 기준이 아님
  • 기능이 동작하지 않았을 때 성립하지 않는 결과를 적음. 예를 들어 저장 기능의 기대 결과가 “오류가 표시되지 않음”뿐이면 저장이 아예 실행되지 않아도 통과함. 저장 후 다시 열었을 때 입력값이 표시되는지까지 적음
  • 확인하는 주체에 맞춰 적음
    • UI TC: 사용자가 화면에서 확인하는 동작(표시 문구, 화면 이동, 목록 변화)을 적음. 화면 요소의 속성 값(DOM 속성)은 기대 결과로 적지 않음
    • 접근성 TC: 스크린 리더가 읽는 이름과 역할, 키보드 초점 이동처럼 보조 기술 사용자가 확인하는 결과를 적음
    • API TC: 응답 상태 코드와 본문을 적음
    • DB 값, 로그처럼 화면과 응답에 나타나지 않는 결과는 API TC나 자동화 검증에서 확인함
  • 명세에 없거나 확정되지 않은 동작은 기대 결과로 적지 않고 확인 질문으로 따로 관리함

규칙

  • 절차 일부만 수행했거나 실제 사용 경로와 다른 경로(주소 직접 입력 등)로 얻은 결과로는 통과를 판정하지 않음

독립성과 반복 수행

섹션 제목: “독립성과 반복 수행”
  • 다른 TC의 수행 결과에 의존하지 않음. 앞 TC가 실패하면 뒤 TC까지 판정할 수 없게 됨. 공통 준비 상태는 사전조건으로 적고, 여러 TC가 같은 사전조건을 사용하면 한 곳에 적고 참조함
  • 생성 기능 TC는 같은 TC를 다시 수행할 때의 상태(같은 이름의 자원이 이미 있음)를 고려해 사전조건과 입력값을 정함
  • 설정, 권한, 공유 자원을 바꾸는 TC는 변경 전 값을 기록하는 절차와 원래 값으로 되돌리는 절차를 포함함. 다른 수행자의 테스트에 영향을 주지 않기 위해서임
  • TC에는 회차와 무관한 기준만 적음. 수행 날짜, 관측값, 캡처 경로, 제품 버전은 회차 결과에 기록함

범위

섹션 제목: “범위”

정상 흐름만 적으면 결함이 많이 나오는 경계와 예외가 빠진다. 설계 기법별 도출 방법은 동등 분할, 경계값 분석, 상태 전이 테스트, 결정 테이블 테스트에 있다. 설계를 마친 뒤 아래 항목이 빠지지 않았는지 확인한다.

  • 입력: 필수 누락, 경계값, 빈값과 공백, 중복, 형식 오류, 최대 길이
  • 역할과 권한: 역할별 차이, 권한 없는 사용자의 진입
  • 데이터 격리: 다른 사용자, 조직, 프로젝트의 ID로 직접 진입
  • 상태 전이: 생성, 수정, 비활성, 삭제와 되돌리기, 삭제한 대상의 참조
  • 동시성: 두 탭이나 두 사용자의 동시 수정, 화면에 남은 이전 상태
  • 세션과 시간: 만료, 재로그인, 시간대, 날짜 경계
  • 표시 환경: 화면 폭, 다크와 라이트 테마, 키보드 조작, 표시 언어
  • 오류와 복구: 서버 오류와 네트워크 실패 뒤의 화면 상태

운영 환경에서는 응답을 가로채 오류를 주입하지 않는다. 오류와 복구 항목은 개발 환경에서 수행하고, 운영 환경에서만 확인할 수 있으면 그 제약을 비고에 적는다.

우선순위

섹션 제목: “우선순위”

ISTQB CTFL은 TC 실행 우선순위를 정하는 방식으로 리스크 기반, 커버리지 기반, 요구사항 기반을 제시한다(ISTQB CTFL 실라버스 핵심 정리). 리스크 기반으로 정할 때는 TC가 확인하는 대상이 실패했을 때의 영향으로 등급을 매기는 방식이 많이 쓰인다. 등급 예와 적용 예는 리스크 기반 테스트에 있다.

  • 우선순위를 모두 매긴 뒤 분포를 확인함. 상위 두 등급이 대부분이면 등급이 수행 순서를 정하는 역할을 하지 못함
  • 결함의 심각도와 TC의 우선순위는 다른 축임(심각도 기준)

리뷰 점검 항목

섹션 제목: “리뷰 점검 항목”

TC 리뷰는 ISTQB CTFL의 정적 테스트에 해당한다. 작성자가 아닌 사람이 아래 항목을 확인한다.

  • 처음 보는 사람이 절차대로 따라 할 수 있는가
  • 기대 결과가 기능이 동작하지 않았을 때 성립하지 않는가
  • 다른 TC의 결과에 의존하지 않는가
  • 경계값과 예외 흐름이 포함되었는가
  • 근거 요구사항과 연결되었는가
  • 참조한 사전조건의 TC ID가 실제로 존재하는가

현장 노트

  • 일부 TC 관리 도구는 한 줄에 물결(~)이 두 개 있으면 그 사이를 취소선으로 표시함. 범위는 물결을 한 줄에 한 번만 쓰거나 “1부터 4까지”처럼 풀어 씀
