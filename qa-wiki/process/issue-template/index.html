이슈 양식

버그 이슈의 대표 양식(ISTQB 결함 보고서 항목, Bugzilla 요약·설명, GitHub 이슈 폼)과 선택 기준. 운영 예로 발견 블록과 종결 블록을 나눈 버그 양식과 작업(개선) 양식을 둔다.

노하우난이도 중급최종 업데이트 2026-11-24

대표 양식

섹션 제목: “대표 양식”
양식 구성 특징
ISTQB CTFL 결함 보고서 식별자, 제목, 관찰 날짜와 작성자, 테스트 대상과 환경, 맥락, 재현 설명, 기대 결과와 실제 결과, 심각도와 우선순위, 상태, 참조 항목 목록을 제시하고, 양식은 ISO/IEC/IEEE 29119-3을 가리킴
ISO/IEC/IEEE 29119-3 인시던트 보고서 테스트 문서 표준이 정한 결함 보고서 양식 유료 표준. 칸 구성을 표준에 맞춰야 하는 조직(인증, 감사 대응)에 맞음
Bugzilla 버그 등록 요약(Summary), 설명(Description)과 분류 필드 설명 칸에 재현 단계를 상세히 적되, 재현에 필요한 최소 단계로 줄이도록 안내함
GitHub 이슈 폼 YAML로 정의한 입력 칸, 드롭다운, 체크박스, 필수 여부 입력값이 마크다운 본문으로 합쳐짐

선택 기준

  • 보고자가 개발 외부(사용자, 고객 지원)이면 입력 부담을 줄임. 재현 단계, 기대 결과, 실제 결과와 제품별 조사에 꼭 필요한 항목(버전, 환경 등)만 필수로 지정함
  • 환경, 심각도, 상태별로 결함을 집계해야 하면 CTFL 항목처럼 해당 항목을 별도 필드로 둠. 본문에만 적으면 필터와 집계에 사용하기 어려움
  • 수정을 마친 뒤 이슈를 몰아서 등록하는 과정에서 발견 당시 정보(재현 조건, 증거)가 빠진다면, 아래 운영 예처럼 발견 시점과 종결 시점의 칸을 나눔
  • 폼을 거치지 않는 등록 경로가 있으면(아래 도구 함정) 본문 템플릿을 함께 둠

운영 예

섹션 제목: “운영 예”

아래는 이 위키 작성자가 개인 프로젝트에 적용하는 양식이다. 버그 양식은 발견 블록과 종결 블록으로 나눈다. 발견 블록은 원인을 몰라도 버그를 확인한 시점에 채울 수 있는 칸이고, 종결 블록은 이슈를 닫을 때 채우는 칸이다. 원인이나 수정 버전처럼 등록 시점에 알 수 없는 칸을 처음부터 필수로 두면, 수정을 마친 뒤에야 이슈를 등록하게 되어 발견 당시의 정보(재현 조건, 증거)가 남지 않는다.

버그 양식

섹션 제목: “버그 양식”

발견 블록

  • 심각도, 영역, 발생 버전
  • 증상: 무엇이 잘못되었는지
  • 기대 결과: 어떻게 동작해야 하는지
  • 실제 결과: 실제로 발생한 동작. 기대 결과와 이 칸의 차이가 버그의 정의
  • 사전 조건: 재현 전에 갖춰져 있어야 하는 상태. 해당 없으면 빈칸으로 두고 “없음”이라고 기재하지 않음
  • 재현 절차: 수행 순서대로 번호를 붙인 단계. 산문으로 작성하지 않음
  • 재현 빈도: 항상 / 간헐 / 1회만 관측 / 미확인
  • 증거: 로그, 스택 트레이스(오류 발생 지점까지의 호출 경로 기록), 쿼리 결과, 스크린샷. 빈도가 “항상”이 아니면 필수
  • 발견 경로: 배치 로그 / 모니터링 / QA / 사용자 / 코드 리뷰

종결 블록

  • 원인: 증상이 아니라 원인. 어디의 무엇이 왜 그렇게 되었는지
  • 수정 내용, 수정 버전(커밋 식별자 포함)
  • 재발 방지: 테스트, 가드(잘못된 입력이나 상태를 차단하는 방어 코드), 모니터링 중 추가한 것. 추가하지 않았으면 그 이유
  • 영향 범위

함께 작성하는 칸

섹션 제목: “함께 작성하는 칸”
  • 재현 빈도와 증거: 항상 재현되지 않는 버그는 그때 남긴 로그가 유일한 기록. 빈도가 “간헐”인데 증거가 비어 있으면 그 이슈는 나중에 “재현 안 됨”으로 닫히기 쉬움
  • 발견 경로: 사용자가 먼저 발견했다면 그 앞단의 배치 로그나 모니터링에 탐지 공백이 있다는 신호. 그 탐지 공백을 별도 이슈로 등록함
  • 재발 방지: 비워 두면 같은 원인의 재발을 막을 장치가 없음. “없음”으로 종결할 때도 이유를 기재함

작업(개선) 양식

섹션 제목: “작업(개선) 양식”

규모, 영역, 착수 버전 같은 분류 칸을 제외하면 버그 양식과 칸이 겹치지 않게 구성한다.

  • 규모, 영역, 착수 버전
  • 현재 상태: 지금 어떻게 동작하는지 사실만
  • 바꾼 뒤 상태: 수단이 아니라 결과
  • 왜 지금인가: 지금 하지 않으면 발생하는 문제. 이 칸을 채우지 못하면 착수하지 않고 백로그(착수하지 않은 작업의 대기 목록)에 둠
  • 완료 조건: 다른 사람이 확인할 수 있는 문장의 체크박스. “개선했다”처럼 확인 기준이 없는 문구는 완료 조건으로 인정하지 않음
  • 하지 않을 것: 이번 범위에서 제외하는 항목을 기재해 범위 확대를 방지. 비워 두면 범위가 계속 늘어나기 쉬움
  • 종결: 결과, 반영 버전

규칙

  • 사후 일괄 작성은 허용함. 다만 발견 블록에는 발견 시점에 알 수 있었던 내용만 기재함
  • 원인을 아는 상태에서 역산해 작성한 재현 절차는 원인 설명에 가까움. 다음 사람이 그대로 따라 해도 재현되지 않을 수 있음

도구 함정

섹션 제목: “도구 함정”
  • GitHub 이슈 폼(.github/ISSUE_TEMPLATE/*.yml)의 유효성을 확인하는 API는 없음. 폼 정의에 오류가 있으면 이슈 생성 화면에 폼이 표시되지 않음. GitHub 웹에서 폼 파일을 저장하거나 볼 때는 검증 오류가 표시되지만, git으로 바로 올린 파일은 따로 확인해야 함. SchemaStore가 제공하는 JSON 스키마(json.schemastore.org/github-issue-forms.json, GitHub 공식 스키마는 아님)로 폼 구조를 검증함
  • 여러 줄 입력 칸(textarea)에 render:를 지정하면 입력 내용이 코드 블록으로 고정되어 스크린샷을 첨부할 수 없음. 증거 칸에는 사용하지 않음
  • gh issue create는 폼을 거치지 않음. --body가 그대로 본문이 되므로 CLI로 등록할 때는 본문에 마크다운 양식을 직접 작성함

현장 노트

  • 발견·종결 블록으로 나누기 전의 버그 이슈 642건을 집계하니 등록에서 종료까지 중앙값 0.0시간, 24시간 안에 종료 94%였음. 수정을 마친 뒤 한꺼번에 작성한 것으로 판단함. 그 결과 기대 결과를 적은 이슈 0%, 재현 빈도 0%, 스크린샷 0.2%였고, 재현 절차의 17%는 번호를 붙인 단계가 하나도 없었음. 사전 조건은 28%가 “없음”, 수정 버전은 80건이 “미정”이었음
  • 양식을 변경하면 이슈 로그의 칸도 함께 변경함. 트래커에만 있고 이슈 로그에 해당 칸이 없는 정보는 나중에 로그에서 검색할 수 없음
  • 목록은 순서가 있을 때만 번호를 사용함. 이 양식에서 번호를 사용하는 칸은 재현 절차 하나뿐

관련 문서

프로세스심각도 기준결함의 영향 크기(심각도)와 수정 순서(우선순위)를 기록하는 대표 방식(ISTQB, Bugzilla, Jira, GitHub 라벨)과 선택 기준. 운영 예로 버그 5단계와 하한 규칙을 둔다.프로세스이슈 로그와 트래커의 조인 키이슈를 어디에 기록할지(트래커만, 로그만, 두 곳)의 선택 기준과, 두 곳에 기록할 때 로그의 행과 트래커의 이슈를 연결하는 식별자(조인 키). 조인 키가 없으면 두 기록이 1:1로 대응하는지 확인할 수 없다.
