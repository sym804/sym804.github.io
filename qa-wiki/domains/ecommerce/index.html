이커머스 테스트 관점

주문, 할인·쿠폰 계산, 결제 연동, 재고 차감, 취소·환불에서 금액 정합성과 상태 전이를 확인하는 테스트 관점이다.

기본기난이도 중급이커머스최종 업데이트 2026-11-24

이커머스의 주요 결함은 금액과 재고에 영향을 준다. 잘못 계산된 금액, 중복 결제, 초과 판매는 고객 응대와 정산 수정 작업으로 이어진다. 정상 결제 한 건보다 계산 경계, 중복 요청, 동시 요청, 부분 취소를 먼저 설계한다.

금액·할인·쿠폰 계산 경계

섹션 제목: “금액·할인·쿠폰 계산 경계”
  • 상품 할인, 쿠폰, 포인트·적립금, 배송비의 적용 순서는 명세 기준. 명세 순서대로 계산한 값과 화면·저장 값을 대조함
  • 정률 할인의 절사·반올림 단위와 시점. 상품별로 계산한 뒤 합산하는지, 합산한 뒤 계산하는지 명세를 확인함. 차이는 최소 화폐 단위에서 발생함(경계값 분석)
  • 쿠폰 조건: 최소 주문 금액의 직전·정확히 같은 값·직후, 최대 할인 한도 직전·직후, 유효기간 시작·만료 시각
  • 무료 배송 기준 금액의 직전·직후
  • 할인 합계가 상품 금액 이상일 때 결제 금액이 0원 또는 음수가 되는지 확인함
  • 중복 적용이 불가능한 쿠폰 두 장, 같은 쿠폰의 중복 적용

클라이언트 금액 위변조

섹션 제목: “클라이언트 금액 위변조”
  • 요청 본문의 단가, 수량, 할인 금액, 최종 금액을 변조해 전송함. 서버가 상품의 현재 가격과 쿠폰 보유 상태로 금액을 다시 계산하는지 확인함
  • 수량 0, 음수, 소수, 재고 초과 값
  • 판매 중지 상품, 다른 사용자의 쿠폰 id, 이미 사용한 쿠폰 id
  • PG(결제 대행사) 승인 금액과 서버가 계산한 주문 금액의 대조 여부
  • 화면을 거치지 않은 요청 전송 방법은 API 테스트 기본, 권한 관련 점검은 보안 테스트의 기본 관점 참조

결제 멱등성과 PG 웹훅 지연

섹션 제목: “결제 멱등성과 PG 웹훅 지연”
  • 결제 요청 중복 전송: 연속 클릭, 네트워크 재시도, 뒤로 가기 후 재전송. 승인은 한 번만 발생해야 함
  • 결제 앱으로 전환한 뒤 이탈, 브라우저 종료
  • 클라이언트 연결은 끊겼지만 PG 웹훅(결제 결과 통지)은 승인으로 도착하는 경우. 주문이 결제 완료로 반영되는지 확인함
  • 웹훅의 지연, 중복 도착, 순서 역전(취소 통지가 승인 통지보다 먼저 도착)
  • 승인은 성공했지만 주문 저장이 실패한 경우의 자동 취소 또는 대사(승인 내역과 주문 내역의 대조) 처리
  • 서명이 없거나 틀린 웹훅 거부

재고·쿠폰 동시성

섹션 제목: “재고·쿠폰 동시성”
  • 재고 1개 상품에 주문 2건 이상을 동시에 전송해 초과 판매(음수 재고)가 차단되는지 확인함
  • 1회용·선착순 쿠폰을 여러 주문에 동시 적용함
  • 같은 사용자가 두 탭에서 동시에 결제
  • 재고 차감 시점(주문 생성 시, 결제 완료 시)과 미결제 주문의 재고 복원 시점
  • 동시성은 순차 요청으로 확인할 수 없음. 같은 시점에 요청을 보내는 도구나 스크립트로 수행함

주문·환불 상태 전이

섹션 제목: “주문·환불 상태 전이”
  • 주문 생성, 결제 완료, 출고 준비, 배송 중, 배송 완료, 구매 확정과 상태별 취소·교환·반품 허용 여부를 상태 전이 표로 작성함(상태 전이 테스트)
  • 취소·환불 완료 시 재고, 쿠폰, 적립금 복원
  • 부분 취소: 남은 상품이 쿠폰 최소 금액이나 무료 배송 기준에 미달할 때 환불 금액 재계산(쿠폰 할인 회수, 배송비 부과) 규칙을 확인함
  • 여러 번의 부분 취소 환불 합계가 결제 금액을 넘지 않는지 확인함
  • 구매 확정 뒤 지급한 적립금의 환불 시 회수

규칙

  • 결제 실패는 Critical, 잘못 계산된 금액은 Major 이상으로 분류함(심각도 기준)
  • 결제 테스트는 PG 테스트 모드와 테스트 결제 수단으로 수행함. 운영 결제 수단으로 테스트하지 않음

TC 예시

섹션 제목: “TC 예시”
점검 항목 TC 예시
쿠폰 최소 주문 금액 최소 주문 금액 30,000원(예시 값) 쿠폰을 주문 금액 29,999원, 30,000원, 30,001원에 적용해 29,999원은 적용이 거부되고 안내 문구가 표시되며, 나머지 둘은 할인이 적용되는지 확인함
정률 할인 절사 1,005원 상품 3개에 10% 쿠폰, 원 단위 미만 절사 조건(예시)을 적용함. 상품별로 계산하면 할인액 300원(100원 x 3), 합산 뒤 계산하면 301원(3,015원의 10%)이므로 명세의 방식과 같은 값이 화면과 저장 값에 나오는지 확인함
쿠폰 유효기간 만료 시각이 23:59:59(예시 값)인 쿠폰을 23:59:58, 23:59:59, 다음 날 00:00:00에 적용해 마지막만 거부되는지 확인함. 장바구니에서 적용한 뒤 결제 직전에 만료되면 결제 단계에서 다시 검증되는지 확인함
0원 결제 5,000원 상품에 5,000원 정액 쿠폰을 적용해 0원 주문의 처리 방식(결제 수단 선택 생략 등)이 명세와 같은지, 할인액이 상품 금액을 넘어도 결제 금액이 음수로 저장되거나 PG에 전달되지 않는지 확인함
금액 위변조 주문 생성 요청의 단가와 최종 금액을 1원으로 변조해 전송하고, PG 승인 요청 금액과 주문 저장 금액이 서버가 계산한 금액인지 또는 주문이 거부되는지 확인함
결제 중복 같은 주문으로 결제 승인 요청을 2회 전송해 PG 테스트 모드 관리 화면의 승인 내역이 1건이고, 주문의 결제 내역도 1건인지 확인함
웹훅 순서 역전 같은 결제의 취소 통지를 승인 통지보다 먼저 전송해 최종 주문 상태가 취소이고, 재고와 쿠폰 복원이 한 번만 수행되는지 확인함
웹훅 서명 서명 헤더를 변조한 승인 통지를 전송해 명세의 오류 응답이 반환되고 주문 상태가 변경되지 않는지 확인함
재고 동시성 재고 1개인 상품에 주문 10건을 동시에 전송해 1건만 성공하고 나머지는 품절 응답을 받으며, 재고가 음수가 아닌 0인지 확인함
누적 환불 상품 3개로 구성된 주문을 1개씩 세 번 부분 취소해 환불 합계가 결제 금액과 같은지 확인함

적용 예: 부분 취소 기능

섹션 제목: “적용 예: 부분 취소 기능”

기획서에 “배송 전 주문은 상품 일부를 취소할 수 있다.“만 있는 경우를 가정한다. 금액을 직접 계산해 보면 명세에 없는 결정 사항이 나온다.

  • 주문 예시: 상품 A 20,000원, 상품 B 15,000원, 합계 35,000원. “30,000원 이상 주문 시 3,000원 할인” 쿠폰 적용, 무료 배송 기준 30,000원(미달 시 배송비 3,000원). 결제 금액은 32,000원임
  • B만 취소하면 남은 주문 20,000원은 쿠폰 조건과 무료 배송 기준에 모두 미달함
  • 혜택을 회수하는 정책이면 남은 주문의 금액은 20,000원 + 배송비 3,000원 = 23,000원이고 환불액은 32,000원 - 23,000원 = 9,000원임
  • 혜택을 유지하고 할인을 상품 금액 비율로 나누는 정책이면 B 몫의 할인은 3,000원 x 15,000/35,000 = 1,285.71…원이라 반올림 규칙이 필요함. 반올림하면 환불액은 15,000원 - 1,286원 = 13,714원임
  • 이어서 A도 취소하면 두 정책 모두 누적 환불이 32,000원이어야 함(9,000원 + 23,000원, 또는 13,714원 + 18,286원)

이 예에서 기획과 확인할 항목은 다음과 같다.

  • 혜택 회수와 유지 중 어느 정책인지, 할인 안분의 반올림 단위와 남는 차액을 어느 상품에 배정하는지
  • 취소를 허용하는 주문 상태 목록(결제 완료, 출고 준비)과 배송 중 요청의 처리(상태 전이 테스트)
  • 카드와 포인트를 함께 사용한 결제에서 어느 수단부터 환불하는지
  • 쿠폰 반환 여부와 반환된 쿠폰의 유효기간이 지났을 때의 처리
  • PG 부분 취소 요청 금액이 화면 표시 환불액, 저장된 환불액과 같은지
  • 같은 주문에 부분 취소 요청 2건이 동시에 들어올 때 누적 환불이 결제 금액을 넘지 않는지

쿠폰 조건과 무료 배송 기준의 조합은 결정 테이블 테스트의 예와 같은 방식으로 표로 정리하고, 정책별 기대 금액을 각 열에 적는다.

테스트 계획, 결함 분류, 보고에 적용

섹션 제목: “테스트 계획, 결함 분류, 보고에 적용”

테스트 계획

  • 금액 규칙(적용 순서, 절사·반올림 단위, 할인 안분 방식)이 명세에 정해진 것을 테스트 시작 조건으로 둠. 정해지지 않은 규칙은 확인 항목으로 계획서에 기록함
  • PG 테스트 모드 계정, 웹훅을 수신할 수 있는 테스트 환경, 동시 요청을 전송하는 도구를 준비 항목으로 계획함
  • 결제, 환불, 재고 차감 TC는 매 릴리즈 회귀 범위에 포함함(회귀 테스트 범위 선정)

결함 기록

  • 주문 번호, 결제 수단, 적용한 쿠폰·포인트, 화면 금액, 저장 금액, PG 승인·취소 금액을 함께 기록함
  • 기대 금액은 계산식과 함께 기록함. 예: “35,000 - 3,000 = 32,000, B 취소 뒤 남은 금액 20,000 + 배송비 3,000”
  • 웹훅 관련 결함은 통지 원문, 수신 시각, 처리 순서를 첨부함

결함 분류와 보고

  • 원인 영역을 금액 계산, 재고, 주문 상태, PG 연동으로 분류하고, 금액 결함은 Major 이상으로 둠(심각도 기준)
  • 보고서에 결제 수단과 시나리오(정상, 중복, 웹훅 지연, 부분 취소)의 조합별 결과를 기록함
  • PG 테스트 모드에서 확인할 수 없는 범위(실제 카드사 응답, 정산 파일)를 미검증 범위로 기록함

현장 노트

  • 결제 결과를 DB에 저장하지 못해도 성공 응답을 반환하던 결함이 검수에서 발견되어, 저장 실패 시 500 오류를 반환하도록 수정함. 승인 내역과 주문 내역이 어긋나는 경우의 처리(위 「결제 멱등성과 PG 웹훅 지연」의 대사)를 확인 범위에 포함하게 된 사례임
  • 만료된 미결제 주문의 정리를 주문 생성 함수 안에서만 호출해, 결제 기능을 기본 비활성화하자 정리도 함께 실행되지 않음. 정리를 배치의 점검·교정 단계로 옮겼지만 그 단계에 도달하는 조건이 “DB 점검에서 실패 항목이 하나 이상 있음”이었음. 점검 결과가 정상이면 정리 단계에 도달하지 않았고(배치 실행 로그 9회 중 2회), 조건 없이 실행되는 위치로 다시 옮김
  • 테스트의 운영 DB 쓰기를 차단하는 가드를 추가할 때 결제 모의(mock) 테스트만 예외로 남음. 이 테스트는 실행할 때마다 운영 DB에 실제 주문·결제 행을 생성하며, 테스트 격리는 보류 항목으로 기록됨

흔한 실수

섹션 제목: “흔한 실수”
  • 단일 상품의 정상 결제와 전액 취소만 확인함. 부분 취소의 환불 금액 재계산 결함이 남음
  • 재고와 쿠폰을 순차 요청으로만 확인함
  • 화면에 표시된 금액만 확인하고 주문 저장 값과 PG 승인 금액을 대조하지 않음

출처

섹션 제목: “출처”
  • OWASP Web Security Testing Guide 4.2, Business Logic Testing: WSTG-BUSL-01 Test Business Logic Data Validation(클라이언트 금액 위변조), WSTG-BUSL-05 Test Number of Times a Function Can Be Used Limits(쿠폰 1회 사용)
  • 결제 멱등성, PG 웹훅 지연, 부분 취소의 확인 기준은 대응하는 공개 표준 절이 없어 위키의 실무 기준임

관련 문서

테스트 설계경계값 분석처리 결과가 달라지는 경계와 그 바로 안팎의 값을 선택해 테스트하는 기법이다(Boundary Value Analysis).테스트 설계상태 전이 테스트대상이 가질 수 있는 상태와 상태를 변경하는 사건을 정리한 뒤, 허용된 전이와 차단되어야 하는 전이를 모두 테스트하는 기법이다(State Transition Testing).기초와 용어API 테스트 기본화면을 거치지 않고 API에 직접 요청을 보내 응답 계약, 상태 코드, 서버 측 검증, 인가를 확인하는 테스트다. 화면 제약만으로는 확인할 수 없는 서버 동작이 대상이다.도메인별보안 테스트의 기본 관점접근 제어, 인증과 세션, 입력 처리, 비밀값 노출, 보안 설정에서 권한 없는 동작과 정보 노출이 발생하지 않는지 확인하는 테스트다. OWASP Top 10, ASVS, WSTG를 점검 기준으로 사용한다.프로세스심각도 기준결함의 영향 크기(심각도)와 수정 순서(우선순위)를 기록하는 대표 방식(ISTQB, Bugzilla, Jira, GitHub 라벨)과 선택 기준. 운영 예로 버그 5단계와 하한 규칙을 둔다.
