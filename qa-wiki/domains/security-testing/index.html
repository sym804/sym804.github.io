보안 테스트의 기본 관점

접근 제어, 인증과 세션, 입력 처리, 비밀값 노출, 보안 설정에서 권한 없는 동작과 정보 노출이 발생하지 않는지 확인하는 테스트다. OWASP Top 10, ASVS, WSTG를 점검 기준으로 사용한다.

기본기난이도 중급백엔드 API보안최종 업데이트 2026-11-24

기능 테스트는 허용된 사용자가 허용된 일을 할 수 있는지 확인한다. 보안 테스트는 허용되지 않은 사용자와 요청이 차단되는지, 차단되는 과정에서 정보가 새어 나가지 않는지 확인한다. 화면에서 보이지 않는 경로가 대상이라 대부분의 확인을 API 요청으로 수행한다.

OWASP 기준 문서

섹션 제목: “OWASP 기준 문서”
  • OWASP Top 10:2025: 웹 애플리케이션의 위험 범주 10개. 점검 범위의 누락을 확인하는 목록으로 사용함
    • A01 접근 제어 실패, A02 보안 설정 오류, A03 소프트웨어 공급망 실패, A04 암호화 실패, A05 인젝션
    • A06 안전하지 않은 설계, A07 인증 실패, A08 소프트웨어·데이터 무결성 실패, A09 보안 로깅·알림 실패, A10 예외 상황 처리 미흡
  • OWASP ASVS(애플리케이션 보안 검증 표준): 보안 요구 사항을 검증 항목 단위로 정리한 표준. TC의 기대 결과를 정할 때 항목 단위로 참조함
  • OWASP WSTG(웹 보안 테스트 가이드): 항목별 점검 방법을 정리한 가이드. 절차를 작성할 때 참조함
  • OWASP API Security Top 10 2023: API 대상 위험 범주. API 점검 항목은 API 테스트 기본 참조

점검 항목

섹션 제목: “점검 항목”

접근 제어와 데이터 격리(A01)

  • 수직 권한 상승: 낮은 역할의 토큰으로 관리 기능 API를 직접 호출해 차단되는지 확인함. 화면의 메뉴 숨김은 차단으로 보지 않음
  • 수평 권한 상승: 다른 사용자·조직·프로젝트의 id로 조회, 수정, 삭제, 첨부 파일 다운로드를 요청해 차단되는지 확인함
  • 목록, 검색, 내보내기, 통계가 요청한 사용자의 소속 기준으로 필터링되는지 확인함
  • URL을 받아 서버가 대신 요청하는 기능이 내부 주소로 요청하지 않는지 확인함. 서버 측 요청 위조(SSRF)는 2025판에서 A01에 통합됨

인증과 세션 무효화(A07)

  • 로그인 실패 횟수 제한을 IP 단위와 계정 단위로 각각 확인함. IP를 변경해 가며 같은 계정으로 로그인을 시도하는 경우를 포함함
  • 비밀번호 변경·초기화, 계정 비활성화, 로그아웃마다 무효화할 대상(현재 세션, 다른 기기 세션, 액세스 토큰, 리프레시 토큰, API 키)과 반영 시점을 명세로 정하고, 그대로 동작하는지 확인함
  • 비밀번호 재설정 링크의 만료와 1회 사용 제한
  • 세션 쿠키의 HttpOnly, Secure, SameSite 속성

입력 검증과 파일 업로드(A05)

  • 입력이 화면 렌더링, 쿼리, 명령, 파일 경로에 사용되는 지점마다 XSS, SQL 인젝션, 경로 순회(../) 여부를 확인함
  • 확장자와 실제 형식이 다른 파일, 선언 크기와 실제 크기가 다른 파일 업로드
  • 압축 형식 파일(zip, xlsx)은 해제 후 크기 상한 적용 여부를 확인함

비밀값 노출과 타이밍 차이

  • 시스템이 발급하는 API 키, 초기 비밀번호, 토큰 원문은 발급 직후 1회만 표시하고 이후 마스킹함. 사용자가 설정한 비밀번호는 저장 뒤 어떤 경로로도 원문을 반환하지 않음. 응답, 로그, URL, 오류 메시지에 원문이 포함되지 않는지 확인함
  • 존재하는 계정과 없는 계정에 대한 응답 문구와 상태 코드가 같은지 확인함. 응답 시간은 같은 조건에서 반복 측정해 계정 존재 여부를 구분할 만한 일관된 차이가 있는지 확인함

보안 설정과 오류 처리(A02, A10)

  • 운영 환경에서 기본 비밀키와 기본 계정이 사용되지 않고 디버그 모드가 비활성화되었는지 확인함
  • CORS 허용 출처가 제한되고 보안 헤더(Content-Security-Policy, Strict-Transport-Security, X-Content-Type-Options)가 적용되었는지 확인함
  • 오류 응답에 스택 트레이스, 내부 경로, 쿼리 문이 포함되지 않음
  • 예외가 발생했을 때 접근이 허용되는 쪽으로 처리되지 않는지 확인함. 인가 확인 중 오류가 나면 거부되어야 함

TC 예시

섹션 제목: “TC 예시”
점검 항목 TC 예시
수평 권한 상승(A01) 사용자 A로 로그인한 상태에서 사용자 B의 주문 id로 GET /orders/{id}를 요청해 403 또는 404가 반환되고 B의 데이터가 응답에 없는지 확인함
수직 권한 상승(A01) 일반 사용자 토큰으로 관리자 API(사용자 비활성화)를 직접 호출해 403이 반환되고 대상 계정 상태가 변경되지 않는지 확인함
세션 무효화(A07) 비밀번호를 변경한 뒤 변경 전 세션 쿠키와 액세스 토큰으로 보호 API를 호출해 401이 반환되는지 확인함. 변경 전 리프레시 토큰으로 토큰 갱신을 요청해 거부되는지(OAuth 2.0이면 400 invalid_grant) 확인함. 서명만 검증하는 JWT 액세스 토큰은 만료 전까지 통과할 수 있어 폐기 정책을 함께 확인함
요청 횟수 제한(A07) X-Forwarded-For 헤더 값을 변경해 가며 로그인을 반복 시도해 제한이 우회되지 않는지 확인함
입력 검증(A05) 검색어에 <img src=x onerror=alert(1)>를 입력해 결과 화면에서 스크립트가 실행되지 않고, 출력 정책에 따라 문자열로 표시되거나 위험한 태그·속성이 제거되는지 DOM까지 확인함
비밀값 노출 API 키를 발급한 직후 화면을 새로 고쳤을 때 키 원문이 다시 표시되지 않고 마스킹되는지 확인함
타이밍 차이 존재하는 계정과 없는 계정으로 비밀번호 찾기를 각각 반복 요청해 응답 문구·상태 코드가 같고, 응답 시간 분포에 계정 유무를 구분할 만한 차이가 없는지 확인함
오류 처리(A02, A10) 형식이 깨진 요청과 권한 오류를 유발해 응답에 스택 트레이스·쿼리 문·내부 경로가 없고, 인가 확인 중 오류가 접근 허용으로 처리되지 않는지 확인함

적용 예: 비밀번호 재설정 기능

섹션 제목: “적용 예: 비밀번호 재설정 기능”

기획서에 “이메일로 재설정 링크를 보내 비밀번호를 바꾼다”만 있는 경우 보안 관점에서 기획과 확인할 항목은 다음과 같다.

  • 링크 토큰의 만료 시간, 1회 사용 제한, 새 링크 발급 시 이전 링크 무효화 여부
  • 없는 이메일을 입력했을 때의 응답 문구와 응답 시간(계정 존재 노출 여부)
  • 같은 이메일로 재설정 요청을 반복할 때의 횟수 제한 기준(IP 단위와 계정 단위)
  • 비밀번호 변경 뒤 기존 세션과 발급된 API 키의 무효화 여부
  • 재설정 링크의 리퍼러 헤더·외부 로그 노출 여부
  • 변경 사실의 계정 소유자 알림과 감사 기록 여부

심각도, 계획, 결함 분류, 보고

섹션 제목: “심각도, 계획, 결함 분류, 보고”

규칙

  • 보안 결함은 Minor 미만으로 지정하지 않음(심각도 기준)
  • 공개된 트래커나 저장소에 수정 전 취약점의 재현 절차를 그대로 기록하지 않음
  • 확인된 영향이 작아도 악용 경로가 있으면 피해가 커질 수 있어 하한을 둠
  • 재현 절차에는 사용한 계정의 역할, 요청 원문, 기대한 차단 응답과 실제 응답을 기록함
  • 권한 게이트, 세션, 데이터 격리를 확인하는 TC는 우선순위 매우 높음으로 분류함(리스크 기반 테스트의 우선순위 매핑)
  • 계획: 비로그인, 일반 사용자 A, 일반 사용자 B, 관리자처럼 권한 맥락이 다른 테스트 계정을 준비하고, 권한 게이트(A01)와 세션 무효화(A07) TC는 매 릴리즈 회귀 범위에 항상 포함함
  • 결함마다 OWASP Top 10 범주(A01 등)나 ASVS 항목 번호를 라벨로 남김. 결함 집계와 별도로 범주별 계획 TC, 수행 TC, 결과를 관리해야 결함 0건이 미점검인지 점검 후 0건인지 구분됨
  • 보안 점검 보고는 범주별로 확인한 범위와 확인하지 않은 범위를 함께 적음. “취약점 0건”만 적지 않음

현장 노트

  • 요청 횟수 제한과 방문자 집계가 클라이언트가 보낸 X-Forwarded-For 헤더를 그대로 신뢰하는지 확인함. 헤더 값을 바꿔 보내 제한이 풀리거나 집계가 늘어나면 우회 가능함. 요청이 신뢰하는 프록시 주소에서 왔을 때만 그 프록시가 설정한 헤더(예: CF-Connecting-IP)를 읽고, 계정 단위 제한을 함께 두는 것이 일반적인 방식임
  • 테스트 계정 비밀번호가 공개 저장소의 테스트 코드, 문서 예시 값과 같지 않은지 확인함. 테스트 서버도 외부에서 접근할 수 있으면 운영 계정과 같은 기준을 적용함
  • 토큰, 서명 비교가 상수 시간 비교(hmac.compare_digest 등)를 사용하는지 코드 리뷰에서 확인함. 응답 시간 차이는 네트워크 측정으로 판별하기 어려워 블랙박스 테스트로는 찾기 어려움
  • 공개 저장소의 이슈, 로그에는 수정 전 취약점의 재현 방법을 남기지 않음. 수정이 배포된 뒤 공개함

흔한 실수

섹션 제목: “흔한 실수”
  • 숨긴 버튼과 메뉴만 확인하고 권한 검증을 완료로 판정함
  • 쿠키 세션만 확인하고 API 키, 임시 비밀번호 상태 같은 다른 인증 경로를 확인하지 않음
  • 로그인 화면 차단만 확인하고 이미 발급된 토큰의 폐기를 확인하지 않음
  • 테스트 계정 하나로 데이터 격리를 확인함

관련 문서

기초와 용어API 테스트 기본화면을 거치지 않고 API에 직접 요청을 보내 응답 계약, 상태 코드, 서버 측 검증, 인가를 확인하는 테스트다. 화면 제약만으로는 확인할 수 없는 서버 동작이 대상이다.프로세스심각도 기준결함의 영향 크기(심각도)와 수정 순서(우선순위)를 기록하는 대표 방식(ISTQB, Bugzilla, Jira, GitHub 라벨)과 선택 기준. 운영 예로 버그 5단계와 하한 규칙을 둔다.프로세스TC 작성 원칙처음 보는 사람이 따라 할 수 있고 수행 직후 통과와 실패를 판정할 수 있는 테스트 케이스의 작성 기준. TC 형식(단계형, BDD 시나리오, 체크리스트, 탐색적 테스트 차터)의 선택 기준, 구성 요소별 작성법, 리뷰 점검 항목을 다룬다.테스트 설계리스크 기반 테스트실패했을 때의 피해와 실패할 가능성을 기준으로 무엇을 먼저, 얼마나 깊게 테스트할지 정하는 방식이다(Risk-Based Testing).
