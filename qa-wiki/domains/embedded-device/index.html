임베디드·디바이스 테스트 관점

펌웨어나 단말 에이전트가 업데이트 중단, 전원·통신 단절, 하드웨어·OS 조합 차이, 장기 가동 같은 조건에서도 복구되고 데이터를 잃지 않는지 확인하는 테스트 관점이다.

기본기난이도 중급임베디드최종 업데이트 2026-11-24

안정된 전원과 네트워크를 갖춘 시험실에서는 대부분의 기능이 정상 동작한다. 현장 장비의 결함은 주로 업데이트 중 전원 차단, 장시간 끊긴 통신의 복구, 수 주 이상의 연속 가동 같은 조건에서 발생한다. 그래서 중단과 복구 시나리오를 정상 기능과 같은 비중으로 설계한다.

업데이트 중단과 롤백

섹션 제목: “업데이트 중단과 롤백”

NIST SP 800-193(Platform Firmware Resiliency Guidelines)은 플랫폼 펌웨어의 복원력을 보호(Protection), 감지(Detection), 복구(Recovery) 세 원칙으로 정리한다. 업데이트 TC도 이 세 가지를 기준으로 작성한다.

  • 시점별 전원 차단: 다운로드 중, 이미지 검증 중, 플래시 기록 중, 기록 직후 첫 부팅 중
  • 다운로드 중 통신 단절과 재개. 이어받은 이미지의 무결성을 확인함
  • 인가되지 않은 경로(서명 없는 이미지, 디버그 포트 등)로 펌웨어를 기록할 수 없는지 확인함(보호)
  • 체크섬이나 서명이 맞지 않는 이미지는 기록하지 않고 거부함(감지)
  • 기록에 실패하면 이전 정상 이미지로 부팅하는지, 부팅 불능 상태가 되지 않는지 확인함(복구)
  • 이전 버전으로 되돌리는 업데이트의 허용 여부는 명세와 대조함
  • 업데이트 뒤 설정과 사용자 데이터 보존

통신 단절과 재동기화

섹션 제목: “통신 단절과 재동기화”

로컬 버퍼링과 재전송

  • 단절 중 수집한 데이터를 로컬에 보관하는지 확인함. 버퍼 상한에 도달했을 때 어떤 데이터를 버리는지 명세와 대조함
  • 복구 후 재전송에서 유실과 중복이 모두 없어야 함. 서버가 같은 레코드를 두 번 받아도 한 번만 저장하는지(레코드 id, 순번 기준) 확인함
  • 수집 시각과 전송 시각을 구분해 기록하는지 확인함
  • 짧은 끊김의 반복, 지연과 패킷 손실, 서버 장애 상태
  • 단절 중 단말 재부팅: 보관하던 데이터가 전원 차단 뒤에도 남는지 확인함
  • 시계 초기화(RTC), 시간 동기화(NTP)로 시각이 뒤로 이동할 때의 스케줄과 타임스탬프

원시 프로토콜과 체크섬 대조

  • 화면이나 서버에 표시된 값만 확인하지 않음. 통신 구간의 원시 프레임을 캡처해 명세의 필드 배치, 바이트 순서, 단위와 대조함
  • 체크섬·CRC를 독립적으로 계산해 프레임의 값과 대조함. 체크섬이 틀린 프레임을 주입해 거부되는지 확인함
  • 필드 최대값, 길이 필드와 실제 길이의 불일치, 잘린 프레임(경계값 분석)

하드웨어·OS 조합

섹션 제목: “하드웨어·OS 조합”
  • 조합 요소: 장비 모델, 보드 리비전, 펌웨어 버전, OS 버전과 패치, 드라이버, 주변기기, 통신 모듈, 함께 설치된 보안 프로그램
  • 모든 조합의 실행은 불가능함. 요소 두 개의 조합을 모두 포함하는 최소 조합을 페어와이즈로 선택함(조합 테스트(페어와이즈))
  • 현장 장애 이력이 있는 조합과 보급 대수가 많은 조합은 페어와이즈 결과와 별도로 추가함(리스크 기반 테스트)

장기 가동

섹션 제목: “장기 가동”
  • 장시간 연속 가동과 반복 이벤트 동안 메모리 사용량, 핸들·파일 디스크립터·소켓 수의 추이를 기록함. 증가가 멈추지 않으면 누수 의심으로 기록함
  • 로그와 캐시 누적: 로그 로테이션, 오래된 데이터 정리, 저장 공간이 가득 찬 상태의 동작
  • 워치독: 프로세스가 멈추거나 응답하지 않을 때 재시작되는지, 재시작 뒤 상태가 복원되는지 확인함
  • 가동 시간 카운터와 타이머: 자료형 상한에 도달하는 시점을 계산해 그 시점 전후의 동작을 확인함

TC 예시

섹션 제목: “TC 예시”
점검 항목 TC 예시
기록 중 전원 차단 이전 이미지로 되돌리는 설계(A/B 파티션 등)에서, 플래시 기록 진행률 50%(예시 값) 시점에 전원을 차단하고 다시 투입해 이전 정상 이미지로 부팅하고 버전 정보가 이전 버전으로 표시되며 업데이트 실패 이벤트가 기록되는지 확인함. 이어서 업데이트를 재시도해 성공하는지 확인함
서명 불일치 서명 영역 1바이트를 변조한 이미지를 배포해 기록이 거부되고, 현재 이미지가 유지되며, 거부 사유가 단말 로그와 서버 상태에 남는지 확인함
다운로드 재개 다운로드 60%(예시 값)에서 네트워크를 5분 차단한 뒤 복구해 명세대로 이어받는지, 최종 이미지의 해시가 배포 이미지의 해시와 같은지 확인함
버퍼 상한 로컬 버퍼 상한이 N건(예: 10,000건)인 단말을 단절 상태로 두고 N-1, N, N+1건을 수집한 뒤 통신을 복구해, 서버 수신 건수와 폐기된 레코드가 명세의 폐기 규칙(예: 가장 오래된 것부터)과 같은지 확인함
재전송 중복 서버가 레코드를 저장한 직후, 단말이 응답(ACK)을 받기 전에 통신을 차단하고 복구해, 단말이 재전송한 같은 레코드가 서버에 1건만 저장되는지 확인함
단절 중 재부팅 단절 상태에서 레코드 100건(예시 값)을 보관한 뒤 전원을 차단하고 재투입해, 통신 복구 후 서버에 100건이 모두 도착하는지 확인함
시각 역행 NTP 동기화로 단말 시각을 10분 뒤로 이동시켜, 그 10분 안에 예약된 작업이 두 번 실행되지 않는지와 레코드의 수집 시각이 명세대로 기록되는지 확인함
체크섬 오류 CRC가 틀린 프레임을 통신 구간에 주입해 해당 값이 반영되지 않고 오류 카운터가 1 증가하는지 확인함
카운터 상한 부호 없는 32비트 밀리초 카운터는 약 49.7일에 상한(2^32 - 1)에 도달함. 카운터를 상한 직전 값으로 설정할 수 있으면 상한 직전, 도달, 직후의 타이머와 스케줄 동작을 확인함
장기 가동 72시간(예시 값) 연속 가동하며 1시간 간격으로 메모리 사용량과 핸들 수를 기록해, 초기 안정화 구간 이후 증가가 멈추는지 확인함. 판정 기준(예: 마지막 24시간 증가량 1% 이하)은 착수 전에 계획서에 정함

적용 예: 단말 에이전트 자동 업데이트

섹션 제목: “적용 예: 단말 에이전트 자동 업데이트”

기획서에 “에이전트는 서버에 새 버전이 있으면 자동으로 내려받아 설치한다.“만 있는 경우 확인할 항목은 다음과 같다.

  • 다운로드: 중단과 재개, 디스크 공간 부족, 프록시 환경, 동시에 업데이트하는 단말 수에 따른 서버 부하와 단계적 배포 여부
  • 검증: 서명과 해시 확인, 이전 버전이 배포되었을 때의 다운그레이드 허용 여부
  • 설치: 설치 중 전원 차단과 OS 재부팅, 실행 중인 에이전트 파일의 교체 방식, 설치 권한, 함께 설치된 보안 프로그램의 차단
  • 복구: 설치 실패 시 이전 버전 복원 여부(복구 이미지 진입이나 재시도 방식이면 명세의 복구 경로), 실패한 버전의 재시도 횟수와 간격
  • 보존: 설정 값, 로컬 버퍼에 남은 미전송 데이터, 로그
  • 시점: 사용자가 작업 중일 때의 재시작 허용 여부, 업데이트 시간대 제한
  • 서버 측 확인: 단말별 현재 버전과 실패 사유의 서버 관리 화면 반영 여부
  • 조합: OS 버전과 패치, 아키텍처(x86, ARM), 보안 프로그램 종류를 요소로 둔 페어와이즈 조합

재부팅이 포함된 시나리오는 종료 방식(완전 종료, 빠른 시작, 재시작)을 사전 조건으로 명시한다. 윈도우의 빠른 시작이 켜진 단말은 시스템을 종료했다 켜도 서비스 프로세스가 다시 시작되지 않을 수 있다(아래 현장 노트).

테스트 계획, 결함 분류, 보고에 적용

섹션 제목: “테스트 계획, 결함 분류, 보고에 적용”

테스트 계획

  • 보유 장비 목록과 조합표를 작성하고, 장비가 없어 시험하지 못하는 조합을 계획서에 기록함(조합 테스트(페어와이즈))
  • 전원 차단은 원격 제어 전원 장치나 릴레이로 시점을 반복 재현하도록 계획함. 손으로 전원을 차단하면 차단 시점이 매번 달라짐
  • 장기 가동 테스트의 기간, 측정 항목, 측정 주기, 판정 기준을 착수 전에 정함
  • 시험실 조건(안정 전원, 유선 네트워크)과 현장 조건(불안정 전원, 무선, 장시간 단절)의 차이를 기록하고 현장 조건을 재현할 항목을 선정함

결함 기록

  • 장비 모델, 보드 리비전, 펌웨어 버전, OS 빌드, 주변기기를 기록함
  • 전원 차단이나 통신 단절 시점(진행률, 경과 시간), 단말 로그, 서버 저장 결과를 함께 첨부함
  • 간헐 결함은 “전원 차단 50회 중 3회 부팅 불능”(예시)처럼 시도 횟수와 발생 횟수로 기록하고, 원시 프레임 캡처나 시리얼 콘솔 로그를 증거로 첨부함(이슈 양식)

결함 분류와 보고

  • 원인 영역을 업데이트, 통신·동기화, 하드웨어·OS 조합, 장기 가동으로 분류함
  • 데이터 유실과 부팅 불능은 현장 회수 필요 여부를 함께 기록하고 심각도 기준에 따라 분류함
  • 보고서에 조합별 결과와 미시험 조합, 장기 가동 측정값(시작·종료 시점의 메모리 사용량과 핸들 수), 간헐 결함의 시도 대비 발생 횟수를 기록함

현장 노트

장비 제품이 아니라 PC와 USB 장치를 조사한 기록이지만, 단말 에이전트와 장치 테스트에 같은 원칙이 적용된다.

  • 윈도우 빠른 시작이 켜진 PC에서는 시스템 종료와 부팅을 여러 번 거쳐도 세션 0의 백그라운드 프로세스가 재시작되지 않고 91.6시간 동안 계속 동작함. “재부팅하면 에이전트가 새로 시작된다”는 가정을 테스트 전에 확인함. 실제 부팅 여부는 Microsoft-Windows-Kernel-Boot 이벤트 27의 boot type(0x0 완전 부팅, 0x1 최대 절전 복귀)으로 판별함
  • 무선 수신기가 끊긴 동안에도 장치의 Status 값은 OK로 남았음. 상태 값 대신 연결 해제·연결 시각(LastRemovalDate, LastArrivalDate)의 변화로 재연결을 확인함
  • 포트를 옮긴 뒤 67분 동안 끊김 0회를 관측해 원인을 찾았다고 판단했으나 같은 증상이 재발함. 그 67분 동안 재현 조건(유휴 뒤 입력)이 만들어지지 않았던 것으로 판단함. 재현 조건이 성립한 시간만 관측 시간으로 셈
  • 간헐 장애 분석에서 이벤트 로그가 크기 기준으로 순환해 일부 로그는 9일치만 남아 있었음. 기록이 없는 기간을 장애 없음으로 판단하지 않도록 분석 전에 보존 범위를 확인함
  • 발생률 약 17%(60회 중 10회)인 장애가 특정 조건의 10회 시험에서 0건이었음. 이 발생률에서 10회 연속 0건은 약 16% 확률((50/60)^10)로 나오므로, 그 조건을 원인에서 제외하는 근거로 사용하지 않음

흔한 실수

섹션 제목: “흔한 실수”
  • 안정된 전원과 네트워크에서 단발성 기능만 확인함. 업데이트 중 전원 차단과 통신 복구 시나리오가 빠짐
  • 짧게 수행하고 종료해 장기 가동에서만 드러나는 누수와 저장 공간 고갈을 놓침
  • 단말 쪽 로그만 확인하고 서버에 저장된 결과(중복, 유실)를 대조하지 않음

관련 문서

테스트 설계조합 테스트(페어와이즈)파라미터가 여러 개일 때 모든 조합을 수행하지 않고, 임의의 두 파라미터 값 쌍이 모두 한 번 이상 포함되도록 테스트 집합을 구성하는 기법이다(Pairwise Testing). 두 파라미터를 넘는 상호작용까지 보장하는 기법은 t-way 조합 테스트라고 한다.테스트 설계상태 전이 테스트대상이 가질 수 있는 상태와 상태를 변경하는 사건을 정리한 뒤, 허용된 전이와 차단되어야 하는 전이를 모두 테스트하는 기법이다(State Transition Testing).테스트 설계리스크 기반 테스트실패했을 때의 피해와 실패할 가능성을 기준으로 무엇을 먼저, 얼마나 깊게 테스트할지 정하는 방식이다(Risk-Based Testing).테스트 설계경계값 분석처리 결과가 달라지는 경계와 그 바로 안팎의 값을 선택해 테스트하는 기법이다(Boundary Value Analysis).
